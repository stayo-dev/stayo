## 1. What the module is

Two jobs that share a tab and almost nothing else:

| | **Operating** | **Planning** |
|---|---|---|
| Question | *What are we serving right now?* | *What will we serve this month?* |
| Frequency | daily, seconds | monthly, minutes |
| Surfaces | Today card, owner Home line, Kitchen sheet, tenant Food tab | Library, voting, weekly grid, publish |

Before Phase 1 the tab served only the second job — it opened on the Food Library accordion, and there was no today view anywhere in the owner app at all. Phase 1 put Operating first without moving Planning off the same screen; a fully separate "Plan `<Month>`" flow is Phase 2 and is **not built**.

**There is a second weekly menu in this system, and it is not this one.** A hostel's public Discovery listing carries its own reviewed copy of a weekly mess menu, inside `hostel_marketing_revisions.content.mess` ([[Decisions#ADR-077|ADR-077]]) — written on the owner's Marketing page and approved by an admin before a tenant sees it. **Discovery does not read `food_schedules`, and should not be wired to**: this module's schedules are regenerated monthly and can be driven by resident polls, so a listing pointed at them would change what a prospective tenant was promised with no review at all. The two are allowed to disagree — this one is what is being cooked, that one is what was advertised. See [[Business-Rules]].

## 2. The grain — one week, repeated. This is the ceiling.

`food_schedule_meals` is keyed:

```prisma
@@unique([schedule_id, day_of_week, meal_type])   // FoodDayOfWeek = MONDAY..SUNDAY
```

7 days × 4 `FoodMealType` = **28 rows per schedule**, and **there is no date column anywhere in the food schema**. `food_schedules` is one mutable row per `(hostel_id, month)`. So a "month" is a container for exactly one Mon–Sun pattern.

Consequences, all structural:

- Every Monday in a month is identical by construction, and so is every other weekday. Editing one cell changes **that weekday for the whole month** — the meals-PATCH route now says so in its own doc comment, where it previously did not.
- **A festival menu, an exam-week menu, a one-off guest meal, or "kitchen closed on the 15th" are unrepresentable.**
- Month History shows a *pattern*, not what was served. *"What did we serve on 14 August?"* was never recorded and cannot be answered.
- Cost-per-day, ingredient forecasting and dated analytics are all blocked on the same missing column.

Per-date menus need `food_schedule_meals.serve_date`, which **does not exist**. Adding it is Phase 3 of the redesign; [[Decisions#ADR-029|ADR-029]] already recorded this consequence when the model was chosen.

**What a cell holds is a separate question from the grain above, and changed 2026-08-24 (§17): a cell now holds an *ordered collection* of dishes, not exactly one.** The 28-row-per-schedule, one-cell-per-weekday grain itself is untouched — this only affects what lives *inside* a cell.

The six models are inventoried in [[Database]] (`food_menu_items`, `food_voting_periods`, `food_votes`, `food_schedules`, `food_schedule_meals`, `food_schedule_meal_items`) — that page is current and is not restated here.

## 3. API surface

**13 route files under `app/api/food/`, exposing 17 method handlers** (was 15/18 before 2026-08-25's removal of `generate`/`meals/swap` and addition of `POST /api/food/schedules` alongside the existing `GET`, [[Decisions#ADR-114|ADR-114]]), plus one cron. Every one has a live frontend caller through `features/food/api/index.ts` — the audit found **no orphaned food endpoint**, which is the opposite of the Expenses finding. The full per-endpoint table lives in [[APIs]].

Changed 2026-08-24 ([[Decisions#ADR-113|ADR-113]], §17):

- `PATCH /api/food/schedules/[id]/meals/[mealId]`'s body changed from `{ menuItemId }` to **`{ menuItemIds: string[] }`** — full-replace, not single-overwrite.
- `POST /api/food/schedules/[id]/meals/swap`'s optimistic-concurrency guard moved from a `menu_item_id` equality check to `updated_at` equality, to generalize past exactly one item.
- `GET /api/food/schedules` and `GET /api/food/tenant/schedule` now nest each cell's `food_schedule_meal_items`, ordered by `display_order`.

Changed on `feat/food-phase-0-1` (2026-08-05):

- `POST /api/food/schedules/generate` gained **`mode: "BUILD" | "FILL_GAPS" | "START_OVER"`** (defaults to `BUILD` when absent or unrecognised) and can now answer **`409 SCHEDULE_PUBLISHED`**. See §5.

Changed on `feat/food-ux-pass` (2026-08-06):

- **`POST /api/food/schedules/[id]/meals/swap` is new** — the module's 15th route and its first addition since 2026-07-26. Body `{ aMealId, bMealId }`; exchanges two cells' items in one `$transaction`. See §7.1.
- `POST /api/food/voting-periods` now **notifies tenants** when a round genuinely opens, and returns `notified`. See §10.
- `GET /api/food/voting-periods/[id]/results` gained **`voterCount`** (distinct tenants) and **`eligibleCount`**, alongside the unchanged `totalVotes`. See §10.

Changed 2026-08-08:

- `POST /api/food/schedules/generate` **no longer auto-looks-up an existing voting period** for the hostel+month when `votingPeriodId` is omitted. Voting-ranked generation is now reachable only by a caller explicitly passing `votingPeriodId` — no current caller does. See §10.

Owner routes all follow `getSession` → `resolveOwnerScope` → `requireHostelBelongsToOwner`; `app/api/food` is one of `scripts/architectural-invariants-check.ts`'s scanned roots, so `hostelId` can never become optional and no route may fall back to `hostels[0]` ([[Decisions#ADR-003|ADR-003]]).

## 4. Publish semantics — correct, and deliberately not rebuilt

`POST /api/food/schedules/[id]/publish`:

1. **Atomic in the sense that matters.** The state change is a single-row update. The notification fan-out is deliberately *outside* it, under `Promise.allSettled`, so a failed notification cannot roll back a publish.
2. **Idempotent.** `wasAlreadyPublished` preserves the original `published_at` and suppresses a second notification storm. Publishing twice is safe.
3. **Guarded.** Rejects with `VALIDATION_ERROR` if the schedule has zero meal rows.
4. **Fan-out** is one in-app notification (`food_schedule_published`) per `ACTIVE` tenant of that hostel with a non-null `profile_id`. In-app only — no WhatsApp, no email.

**There is no draft/live pair.** `@@unique([hostel_id, month])` means one row per hostel per month, so once published *that row is the live menu* and every subsequent edit is live the moment it saves. This is per the original product spec, not an oversight. Phase 1's answer to it is an **undo affordance rather than a staging step** (§7), which is why no draft-copy workflow was built.

## 5. Rebuild modes — `decideRebuild` *(removed 2026-08-25, [[Decisions#ADR-114|ADR-114]] — kept as historical record, see §18)*

**This entire section describes code that no longer exists.** `POST /api/food/schedules/generate`, `assignWeekForMealType`, and `decideRebuild` were deleted along with their tests when scheduling became manual-only. A month's schedule row is now created empty, on demand, by `POST /api/food/schedules` — see §18.

`apps/backend/lib/services/food/schedule-rebuild-policy.ts` is a pure function that decides what a rebuild request may touch. It exists because the old Regenerate button set `status: "DRAFT"` and `deleteMany`'d all 28 cells unconditionally — see [[Bugs]].

| `mode` | Against a DRAFT / absent month | Against a **PUBLISHED** month |
|---|---|---|
| `BUILD` | replaces all 28 cells, status → `DRAFT` | **refused** — `409 SCHEDULE_PUBLISHED` |
| `START_OVER` | replaces all 28 cells, status → `DRAFT` | **refused** — `409 SCHEDULE_PUBLISHED` |
| `FILL_GAPS` | writes only cells with `menu_item_id: null`, status untouched | **allowed** — the only mode that is |

The decision also carries **`rewritesProvenance`** — true only when `replace === "ALL"`. `source` and `generated_from_voting_period_id` belong to whoever authored the week, so a `FILL_GAPS` run adds cells and claims nothing: a month carried forward from last month keeps saying `CARRIED_FORWARD` after its snacks are filled in, instead of flipping to `GENERATED` and pointing at whatever voting period happened to exist. That matters twice over, because `source` is the sole basis for *"carried forward from July"* vs *"built from student votes"*, and `generated_from_voting_period_id` is the honest input to the votes publish check (§8).

The invariant, stated once: **a `PUBLISHED` schedule is never demoted to `DRAFT` and never has its cells wholesale deleted.** A test enumerates every `(mode × currentStatus)` pair and asserts no combination can ever write `status: "PUBLISHED"`, and another asserts `rewritesProvenance` tracks `replace === "ALL"` exactly.

The status check runs **twice**: once early, for a cheap rejection, and once **inside the `$transaction`** that acts on it. The early read is separated from the write by 5–9 generator round-trips, so a second device publishing in that window could otherwise have its month deleted by the first device's already-made decision. The in-transaction re-assert aborts with the same `409 SCHEDULE_PUBLISHED` shape.

The owner-side control reflects this: the button reads **Rebuild** on a draft (sends `BUILD`) and **Fill gaps** on a published month (sends `FILL_GAPS`). `START_OVER` is accepted by the route and plumbed through `foodService.generateSchedule` and `useFoodSchedule.generate`, but **no UI control currently sends it** — see §12.

## 6. The `WeekGrid` contract — the seam for templates

`apps/frontend/src/features/owner-food/weekGrid.ts`. Design doc §8.1, binding.

> **Rule:** every producer and consumer of a week operates on a `WeekGrid` — `Array<{ id, day_of_week, meal_type, items: {id, menu_item_id, item_name, display_order}[] }>` — never on raw `food_schedules` rows.
>
> **Shape changed 2026-08-24 ([[Decisions#ADR-113|ADR-113]], §17):** `menu_item_id`/`item_name` were the cell's only content until this date — a cell now carries an ordered `items` array instead, with `menu_item_id`/`item_name` kept on `WeekGridCell` only as a `@deprecated` derived passthrough (first item's id; all names comma-joined) for anything not yet migrated to read `items`. No current owner/tenant surface reads the deprecated fields any more; `formatCellItems(cell)` is the one shared "Rice • Dal • Curry • Chutney" renderer every surface now calls.

Why: a *template* (Exam Week / Festival / Holiday) **is** a week — same 28 cells, same shape, just not bound to a month. So the forward-compatibility seam is not a template system; it is refusing to let anything read schedule rows directly. There are three producers today (generate, carry-forward, manual edit) and `food_schedules.source` is already the enum that names them (`GENERATED | CARRIED_FORWARD | MANUAL`); a template is a fourth producer and one more enum value. The future `food_menu_templates` / `food_template_meals` tables are byte-identical in shape to `food_schedule_meals` and are **not built**.

The module supplies alongside the type:

- `toWeekGrid(meals)` — the one adapter from API rows, silently dropping any row whose day or slot is unrecognised.
- `dayKeyFor(date)` — JS `getDay()` is Sunday-first, the grid is Monday-first.
- `cellAt`, `isFilled`, `dayCompleteness` — `isFilled` is the single definition of "this cell holds at least one real dish" (**redefined 2026-08-24 as `items.length > 0`**, was `menu_item_id && item_name !== 'Not set'`).
- `formatCellItems(cell, separator = ' • ')` and `itemSetKey`/`sameItemSet` — **new 2026-08-24.** `formatCellItems` is the one shared multi-item display string; `sameItemSet` is an order-independent "same dishes" comparison (used by `publishChecks.ts`'s dominance/repeat warnings, so a reorder alone can't dodge them).
- `MEAL_TIMES`/`mealSlotAt(now)` — **removed 2026-08-19 ([[Decisions#ADR-083|ADR-083]])**, resolving §15's open item below. Real, owner-configurable, per-hostel serving windows now live in `hostels.preferences_config.meal_timings` (`{start, end, enabled}` per meal type, `"HH:mm"` strings) — see `apps/frontend/src/features/food/mealTimings.ts` for the replacement pure functions (`currentAndNextMeal` for the Today card's exact "current/next" contract, `nextServingAt`/`mealStatusAt` for the tenant Next Serving card and Today's Meals status). `weekGrid.ts` itself no longer knows about time of day at all — that split (`WeekGrid` = what, `meal_timings` = when) is now the module's actual shape, not just this file's framing of it.

- `EMPTY_CELL_LABEL` (`"Not set"`) — the one word every surface renders for an empty cell, and the literal `isFilled` recognises. Three spellings of the same state ("Empty", "Not set", "not set") were in use across the surfaces until they were collapsed onto this.

**Every** week reader now consumes `WeekGrid`: the Today card, the Kitchen sheet, the publish checks, the owner Home line, and — since 2026-08-25 ([[Decisions#ADR-114|ADR-114]], §18) — the Timetable page (`TimetablePage.tsx`, replacing the deleted `WeeklyScheduleGrid`). The editor originally rendered from a second, raw-row `grid` map built beside `weekGrid` in the same hook and open-coded its own filled-ness test; that projection is deleted, so the seam's operative claim — a fourth producer (templates) arrives without any consumer changing — now actually holds. The tenant hook (`useTenantFoodSchedule`) keeps its own separate `grid` and is out of scope for this contract.

`WeekGridCell` gained `updated_at: string | null` (2026-08-25, ADR-114) — the cell row's own `updated_at`, threaded through `toWeekGrid` from a field the API was already returning but the frontend type previously ignored. It's what the Timetable page sends back as `expectedUpdatedAt` on every PATCH, so a stale write from another tab is rejected (`409 STALE_WRITE`) instead of silently overwriting a newer edit — see §18.

`is_manual` (the cell lock — "automation never overwrites a human") is part of the design's `WeekGrid` shape but **the column does not exist yet**, so it is not on the type. That is Phase 2.

### 7.1 The compact week, and drag-to-swap (2026-08-06) *(cross-day swap and this layout removed 2026-08-25, [[Decisions#ADR-114|ADR-114]] — see §18)*

**Everything below about swapping a meal onto another day describes code that no longer exists** — `POST /api/food/schedules/[id]/meals/swap`, `canSwap`, `isValidDrop`, `dragSwap.ts`, `DayRow.tsx`, and `WeeklyScheduleGrid.tsx` were all deleted. The 7-days-at-once grid was replaced by a day-tabbed single-day view; dragging now moves an item **from the Food Library into a meal section**, not between two days. Kept below as historical record of a real, tested feature — not current behavior. See §18.

**The layout first, because it is what makes the gesture possible.** `WeeklyScheduleGrid` rendered a 2×2 card block per day — 28 cards over roughly seven screens of scrolling. It is now seven rows of four chips (`components/schedule/DayRow.tsx`, new), the same day-label-plus-inline-slots shape `MonthHistoryList` already uses for a published month, so this reuses a pattern the module owns rather than inventing one. Today's row is tinted. The whole week fits in about one screen, which is the difference between a short drag and a drag that fights the page scroll.

One deliberate divergence: an **empty chip renders its own meal-type name** ("Snacks"), not the shared `EMPTY_CELL_LABEL` ("Not set") from §6. A chip that names the slot it is missing invites a fill; "Not set" four times in a row does not. `EMPTY_CELL_LABEL` is unchanged and still the single spelling used by `TodayCard`, `KitchenSheetPage` and `kitchenSheet.ts` — this is an editor-only exception, not a third spelling loose in the codebase.

**The swap is one write, not two.** `POST /api/food/schedules/[id]/meals/swap` exchanges both cells' `menu_item_id` + `item_name` inside a single `$transaction` and flips `food_schedules.source` to `MANUAL`, exactly as a single-cell PATCH does. Two sequential PATCHes are not equivalent: a failure between them leaves one meal duplicated and the other lost, on a row tenants may already be reading. Ownership is checked on `food_schedules.owner_id` before the transaction opens.

> **The rule: a swap is same-meal-type only, and it is enforced in three places.**
> An item belongs to exactly one meal type, so a breakfast item can never legally occupy a dinner slot. That is not a new rule — it is the rule **every** cell write already applied:
> 1. `PATCH /api/food/schedules/[id]/meals/[mealId]` — validates the item against the cell's meal type. The original enforcement point.
> 2. `canSwap` (`apps/backend/lib/services/food/meal-swap.ts`) — pure, 7 tests (the file holds 11 since `swapWritesLanded` joined it). Also refuses a missing cell, a cell swapped with itself, and a cell belonging to another schedule. The route throws `SWAP_REFUSED: <reason>`, matched by prefix in the catch and returned as **`400 VALIDATION_ERROR`** before the generic 500.
> 3. `isValidDrop` (`apps/frontend/src/features/owner-food/dragSwap.ts`) — mirrors `canSwap` client-side so an invalid drag dies silently at the drop, instead of surfacing as a 400 mid-gesture.
>
> Three enforcement points is duplication with a reason: (1) is the true guard, (2) exists so the *transaction* cannot be talked into an illegal write, (3) exists so the owner never sees an error for a gesture the UI could have declined. They are not independently derived — (2) and (3) both restate (1), and both say so in their own doc comments.

**The gesture.** Drag starts from the grip handle only — `dragListener={false}` + `useDragControls` from `motion/react`, the combination `PropertyList.tsx` established and [[Decisions#ADR-042|ADR-042]] records. This reuses that rule rather than setting a new one: the page keeps its vertical scroll and the chip keeps its tap-to-open-the-picker everywhere except the handle. `dragSnapToOrigin` returns the chip home and the true position arrives from the refetch, since the grid is authoritative. A second drag is blocked while a swap is in flight (`dragDisabled={schedule.isSwapping}`) — it would hit-test against the pre-swap grid and write the wrong pair. The hint line appears only once some meal type is filled on two or more days, since there is nothing to swap with before that.

`dragSwap.ts` is pure and holds the two decisions worth testing (8 tests):

- **`findDropTarget` hit-tests measured rects, not `elementFromPoint`.** The dragged chip sits above the pointer for the whole gesture, so `elementFromPoint` would return the chip being dragged, every time.
- **Rects are stored in page coordinates.** `getBoundingClientRect()` is viewport-relative, but motion's `PanInfo.point` is `pageX`/`pageY` — verified in `node_modules/framer-motion/dist/es/events/event-info.mjs`, since the documentation only says "relative to the device or page". `measure()` in `WeeklyScheduleGrid` adds `window.scrollX`/`scrollY` to put both in one space. Getting this wrong makes every drop on a scrolled page land on the wrong cell, and it fails silently. Page coordinates also survive a scroll mid-drag, which rects measured at drag start in viewport space would not. Chips are registered as *elements* and measured at drag start, not at mount, for the same reason.

`useFoodSchedule` exposes `swapMeals`/`isSwapping`; the mutation's `onError` **re-invalidates**, so a rejected swap cannot linger on screen looking applied, while *what to say* is decided per call — a failed undo is a different sentence from a failed swap.

**Blast radius is unchanged, and it is large.** A swap is a cell edit, so it moves both meals for **every** such weekday in the month, not one date (§2).

### 7.2 What the final review sent back (2026-08-06) *(the gesture this describes no longer exists — see §18)*

The whole-branch review (`.superpowers/sdd/2026-08-05-food-ux-pass/final-review.md`) confirmed the coordinate maths and the three-way meal-type enforcement, and found the gesture's *edges* unfinished. Fixed in one wave:

- **A swap on a PUBLISHED week now has an undo.** It had none, while the tap-to-edit path — half the blast radius, one weekday rather than two — already fired `stayoToast.undo` with a blast-radius line. A successful swap on a published schedule now announces *"Swapped every {dayA} and {dayB} this month · students see it now"*, and undo re-issues the same call, because **a swap is its own inverse**. A failed undo says so in its own words rather than looking like a successful one. Draft schedules stay silent — nothing is live.
- **A drop that lands on nothing now says so.** `handleChipDragEnd` used to `return` in silence when `findDropTarget` yielded `null`, which is the *common* miss: by the review's CSS arithmetic the grid is ~766px against ~590px of usable height on a 390×844 phone, motion does not auto-scroll the page mid-drag, so any two days that are not co-visible cannot be joined by a drag at all. Silence there is indistinguishable from a broken feature. The meal-type refusal now speaks too; a chip dropped back on itself does not, since that is a change of mind.
- **"Move to another day" in the picker sheet** — the same swap, by tapping. It makes Monday↔Sunday reachable without a drag, and it is the **non-pointer equivalent [[Decisions#ADR-042|ADR-042]] point 6 requires**, which this module previously declined (see §13, where it is no longer listed as not built). `useFoodSchedule.moveTargets` lists the other six days holding that meal type, sorted in week order and empty when the cell has nothing to move; `moveMeal` runs the swap and closes the sheet. The hint line now leads with tapping and offers the drag for a nearby day, rather than advertising the pointer-only path first.
- **The grip keeps its box while a swap is in flight.** It was gated on `draggable`, so all 28 grips unmounted and every chip's icon and text jumped ~30px sideways and back, right after a gesture whose whole point was precise placement. It is disabled now, not removed.
- **The grip is `aria-hidden`.** Its `aria-label` sat on a role-less `<span>`, where conforming AT drops it — coverage that was not there. Rather than dress a pointer-only affordance up as an operable control (a grip cannot be dragged from a keyboard), the label is gone and the capability AT *can* reach is the picker sheet's Move list, opened and announced by the chip's own button.
- **A cancelled mouse drag no longer opens the picker.** When `mousedown` lands on the grip and `mouseup` on the chip's text, the browser dispatches `click` at their **common ancestor** — the chip button — which `stopPropagation` on the grip can never intercept. The chip now swallows the click that follows a real drag. Touch never had this: the browser suppresses the click past its slop threshold.
- **The dragged chip is `zIndex: 50`.** At `30` it disappeared behind the shell's `z-40` fixed bottom nav exactly when dragged low.

**One gap remains, recorded rather than papered over.** The gesture wiring still has no automated test: the frontend suite is node-only with no jsdom, so `findDropTarget` and `isValidDrop` are covered as arithmetic and predicates while the wiring between them, motion, and the mutation is not. The interaction has never been exercised in a browser.

## 8. Publish pre-flight checks

`apps/frontend/src/features/owner-food/publishChecks.ts` — three checks, all arithmetic over the `WeekGrid` already in hand. No endpoint, no service, no model.

1. **Complete** — all 28 cells filled; names any meal type that is empty *all week*.
2. **Variety** — WARN when one item occupies more than 3 of a slot's 7 days. Reports **every** dominated meal type, not just the worst one: the motivating live menu was Dosa ×7 breakfast *and* Sambar Rice ×7 lunch, and naming only the worst silently endorsed the other.
3. **Runs** — WARN when any item repeats on back-to-back days, **including across the Sunday→Monday wrap**. One row per `(day, meal)` means the week repeats all month, so Sunday's lunch really is followed by Monday's, four times over.

**Removed 2026-08-08:** a fourth **Votes** check (PASS when the schedule was built from a voting period, via the pure `hasVotesApplied(schedule)`) existed here — deleted along with `hasVotesApplied` now that generation is decoupled from voting (§10) and no schedule is ever built from votes in the current flow.

> **They inform, they never block.** `PublishCheck.status` is `'PASS' | 'WARN'` and there is no third value — a test asserts it, so no future check can acquire the power to disable the Publish button. The owner is the one who knows whether Dosa every day is fine.

This exists because a live menu of Dosa ×7, Sambar Rice ×7 and empty snacks was published to real tenants with nothing anywhere pointing it out.

## 10. Voting

**Decoupled from schedule generation and hidden from both Food tabs, 2026-08-08 — a deliberate product decision, not a bugfix.** The owner wanted Generate to always build straight from the Food Library, with voting/polling coming back later as a separate (likely different) feature rather than a gate on generation. Concretely:

- `VotingPanel` no longer renders on the owner `/owner/food` page, and Generate is no longer gated on voting status (`canGenerate` is gone).
- The tenant Food tab's "Vote on this month's menu" section is likewise removed — it would otherwise have shown a permanent "Voting hasn't started" dead-end once the owner stopped opening rounds.
- `POST /api/food/schedules/generate` no longer auto-attaches an existing voting period; the tally branch below only runs when a caller explicitly passes `votingPeriodId`, which nothing does today.
- **Nothing described below this point was deleted.** `food_voting_periods`/`food_votes` (schema), every `/api/food/voting-periods/*` and `/api/food/tenant/vote*` route, `VotingPanel.tsx`, `useFoodVoting.ts`, and `useTenantFoodVoting.ts` are all left in place, simply unimported from the main flow — reversible groundwork rather than a rebuild-from-scratch requirement for whatever the future polling feature turns out to be. `useTenantHome`'s poll-preview banner (`TenantHomePage.tsx`) still calls `useTenantFoodVoting` too, but is gated on `pollAvailable = Boolean(voting.period && voting.isOpen)`, so with no period ever open it degrades to simply not rendering — no dead-end UI there, unlike the tenant Food tab section that was removed.
- The rest of this section (below) documents that dormant infrastructure as it existed before this change, for whenever it's picked back up.

- One `food_voting_periods` row per `(hostel_id, month)`, `DRAFT | OPEN | CLOSED`, with a start/end window. `POST /api/food/voting-periods` is an **upsert** on that key, which is also how the owner edits an existing window.
- **Opening voting notifies tenants** (2026-08-06). It previously notified *nobody* — there was no notification call in the route at all, while publishing a schedule fanned out to every active tenant. Live data showed **1 voting period and 2 votes in the product's lifetime** (§14); this is the most likely cause, though not proven. The fan-out mirrors publish's exactly: one in-app notification (`food_voting_opened`) per `ACTIVE` tenant of that hostel with a non-null `profile_id`, under `Promise.allSettled` so a failed notification cannot fail the write. The response gains **`notified`** — the count, or `0` when suppressed.
  - **Guarded by `isNewRound`**, mirroring publish's `wasAlreadyPublished`. Because the route is an upsert and *is* the edit-the-window path, an unguarded fan-out would notify on every date tweak, which trains tenants to ignore it.
  - ✅ **Hardened 2026-08-06 (final review, Minor 2).** `isNewRound` was a `findUnique` taken *before* the upsert — a read-then-write race in which two genuinely concurrent first-opens both see no `OPEN` row and both fan out, notifying every tenant twice. The round is **claimed** instead: a conditional `updateMany` on `status: { not: "OPEN" }`, which only one concurrent request can win because row locking makes the loser re-evaluate the predicate after the winner commits; the create race is caught on the `(hostel_id, month)` unique key (`P2002`) and demoted to an edit. Note a transaction alone would **not** have fixed this — under READ COMMITTED both readers still see no row. `notified` also now counts **fulfilled** `Promise.allSettled` results; it was assigned `tenants.length` before the fan-out ran, so a wholly failed fan-out still reported full delivery.
  - ✅ **Fixed before merge (`9f7cb8c`).** The notification title first shipped as *"Vote on next month's menu"* — the copy this module deliberately corrected on the previous branch, reintroduced in a second place, since `FoodPage` opens voting for `new Date().toISOString().slice(0,7)`, **the current month**. It now reads *"Vote on this month's menu"*, matching the tenant Food tab. Worth keeping in the record because it was **found by documenting**: the copy was checked against which month the route actually operates on, rather than against the plan that specified the string.
- **Turnout is a distinct-tenant count** (2026-08-06). `GET .../results` gained **`voterCount`** — `food_votes` with `distinct: ["tenant_id"]` — and **`eligibleCount`**, the `ACTIVE`, profiled tenants of the period's hostel. `VotingPanel` reads *"N of M students voted."* `totalVotes` is **retained and unchanged**: it counts vote *rows*, and a tenant may pick several items per meal type, so the two numbers legitimately differ and mean different things. This is the same distinction the previous branch's `voterCount` → `voteCount` rename was making — the honest turnout number simply did not exist until now.
- **The owner can edit an open voting window** (2026-08-06). Once voting opened, the only action on the panel was *Close Voting*; the dates could not be changed. The backend upsert already supported it — only the UI was missing — another built-but-unreachable capability, of which this module has had several. The Edit-window control pre-fills from the current window and re-posts through the same `openVoting` mutation. **No new endpoint.** Reopening a *closed* round, or running a second round in one month, is still not possible and was deliberately not built.
  - ✅ **Fixed before merge (final review, Important 1).** The prefill first shipped as `toISOString().slice(0,16)` — a **UTC** wall clock — while `<input type="datetime-local">` has no offset and is therefore read back as **local** time. An open-and-save that changed nothing subtracted the owner's UTC offset, and it *compounded*: −5h30m per save in IST, −11h after two. A window ending within 5h30m landed in the past, so `POST /api/food/tenant/vote` answered `409 VOTING_CLOSED` to every tenant while the panel still showed the green OPEN badge and `status` was still `"OPEN"`. The same screen contradicted itself — "11:00 pm" in the header, "17:30" in the field. Both directions now go through the pure `features/owner-food/votingWindow.ts` (`toLocalInputValue` / `fromLocalInputValue`, 9 tests); `defaultStart`/`defaultEnd` carried the same bug latently — benign only because nothing round-tripped them — and use it too. The tests pin **no** timezone: `process.env.TZ` is untyped in this app's tsconfig and mutating it would leak across vitest workers, so the size of the old drift is asserted as `getTimezoneOffset()` and holds in every zone.
- **Turnout waits for its own load** (2026-08-06, final review Minor 8). The panel rendered a confident *"0 of 0 students voted"* for the duration of every results request, on hostels with plenty of both. `isLoadingResults` was already exposed by `useFoodVoting` and simply not consulted; it now shows a skeleton, the pattern `TodayCard` already set in this module.
- `POST /api/food/tenant/vote` **toggles** a `(meal_type, menu_item_id)` pair. Voting is **multi-select per meal type** — the `food_votes` unique constraint includes `menu_item_id` precisely so a second pick is a second row, not an overwrite. The schema doc-comment claimed single-choice until `feat/food-phase-0-1` corrected it; the constraint and the route had been multi-select since [[Decisions#ADR-029|ADR-029]]'s same-day revision.
- When explicitly asked to (§ above — no current caller does this): `generate` tallies votes per meal type via `groupBy`, ranks by count (ties by name), and falls back to *all active library items, alphabetically* when a meal type has zero votes, so no slot is left empty.
- **Voting is for the month already running.** `tenant/vote` uses `firstOfMonth(new Date())` and the owner page opens voting for the current month. The tenant copy used to say *"Vote for next month"*, which was simply false; it now reads *"Vote on this month's menu"*. **Moving voting to the month being planned is Phase 2 and is not built** — the copy was made true rather than the behaviour changed.
- `assignWeekForMealType` (`lib/services/food-schedule-generator.ts`) is the only real algorithm: largest-remainder proportional allocation of the 7 slots by vote share, then a round-robin deal pass so repeats spread across the week instead of clustering. It labels itself *"v1 heuristic, not claimed-optimal"* and was **explicitly kept, not rewritten** — `feat/food-phase-0-1`'s contribution was its first tests.

## 16. Food Polls (real feature, added 2026-08-08) — deliberately a third, separate system

Three things now share the word "poll/vote" in this module and must not be confused:

1. **§10's monthly voting window** (`food_voting_periods`/`food_votes`) — real, dormant since §10's "Decoupled" note; was tied to schedule generation.
2. **The mock "Food Polls"** ([[Decisions#ADR-048|ADR-048]]) — deleted `ee51a83`, pure `useState`, no backend, never votable by a real tenant.
3. **This section** — a new, real, independent feature: ad-hoc, owner-created, single-instance polls (`food_polls`/`food_poll_options`/`food_poll_votes`), unrelated to (1) and not a revival of (2)'s code (rebuilt from scratch against real data, reusing only (2)'s visual design as a reference — confirmed via `git show ee51a83^:...` — plus a few concrete field names it never actually got to use for real).

This intentionally revisits territory [[Decisions#ADR-048|ADR-048]] warned about ("two voting systems under two names was itself a top-three audit finding") — now a third. See [[Decisions#ADR-057|ADR-057]] for why: it's deliberate, made with (1)'s continued existence known, and driven by the product wanting ad-hoc single-meal polls as a genuinely different shape than a monthly recurring window.

**Schema** (`prisma/schema.prisma`, "Food Polls (V1)" section): `FoodPollType` (`SINGLE_CHOICE | MULTIPLE_CHOICE | RATING | YES_NO`), `FoodPollStatus` (`OPEN | CLOSED`). `food_polls` (one row per poll — title, poll_type, meal_type, poll_date, closes_at, is_anonymous, allow_multiple, status, closed_at). `food_poll_options` (owner-authored labels for `SINGLE_CHOICE`/`MULTIPLE_CHOICE`; **`RATING`/`YES_NO` polls also use this table** — the frontend resolves their fixed labels, "Yes"/"No" or "5 stars".."1 star", at creation time, so one options+votes model covers all four poll types with no nullable rating-value column). `food_poll_votes` (`@@unique([poll_id, tenant_id, option_id])`, same shape as `food_votes`).

Applied via a hand-written migration (`prisma/migrations/20260808130000_add_food_polls/migration.sql`), executed directly rather than through `prisma migrate deploy`/`db push` — both were blocked in this dev environment at the time by **pre-existing, unrelated** issues: a failed migration already recorded against `20260501000000_add_late_fee` (blocks `migrate deploy` entirely until resolved — still unaddressed, `migrate deploy` remains unusable here), and `schema.prisma` no longer declaring two `tenants` columns (`reservation_policy`, `minimum_reservation_deposit`, removed from the schema in `9597421` without a matching migration) that still held real rows in the live dev DB (`db push` would silently drop them).

**This migration was never applied to production**, which went unnoticed until 2026-08-15 when every `/api/food/polls/*` request started 500ing on `yourstayo.com` (`the table public.food_polls does not exist`). Fixed by applying the same SQL directly to production by hand — see [[Bugs]] for the full incident, including a first attempt that mis-split the SQL on comments and left a stray `FoodPollStatus` enum type behind before the corrected pass created everything cleanly. This is the same class of gap as the `tenants`-column production outage the day before ([[Bugs]]): dev and production drift because nothing in the build applies migrations automatically.

**Resolved 2026-08-10** ([[Decisions#ADR-062|ADR-062]]): the next schema change (`rooms.sort_order`, Rooms tab reorder) did hit this exact wall — `npm run prisma:push` dropped both `tenants` columns (729 rows each at the time) as a side effect of syncing `schema.prisma`. This was not new data loss: migration `062_tenancy_per_row.sql` already contained `DROP COLUMN IF EXISTS` for both, per the deliberate removal in [[Decisions#ADR-052|ADR-052]]/[[Decisions#ADR-053|ADR-053]] — the columns were dead (no code referenced them; `tests/activation-enforcement-coverage.test.ts` asserts the opposite), just never actually applied to this particular dev database until `db push` finally caught it up. **Tenant UI**: a "Food polls" section on `/tenant/food` (`useTenantFoodPolls.ts`), visually following the pattern the removed §10 tenant section used (button-per-option, `Check` icon when selected) — renders nothing when there are no open polls, rather than a permanent empty-state card, since polls are ad-hoc and often nonexistent.

**Anonymity — an honest scope note.** `is_anonymous` is stored and toggleable (screenshot fidelity, per explicit instruction to keep it), but neither the deleted mock's results sheet nor this one ever shows a per-voter breakdown — only aggregate counts/percentages/bars. So the toggle currently has **no visible behavioral effect**; `tenant_id` is always stored server-side regardless, since it's required to prevent duplicate votes and compute participation. **Tests:** none yet — this environment has no `DATABASE_URL_TEST` (§12), and the vote toggle/replace logic and `shouldAutoClosePoll` are the kind of pure logic this codebase's `test:pure` convention would cover, not yet extracted/written.

## 17. Multiple items per meal (2026-08-24)

**The problem this closes:** a scheduled cell ("Monday Lunch") could hold exactly one dish. Real hostel meals are combinations — Rice, Dal, Curry, Chutney — and picking a second item in the old picker silently overwrote the first. See [[Decisions#ADR-113|ADR-113]] for the full design record; this section is the implementation write-up.

**What did not change.** The weekly grain (§2): `@@unique([schedule_id, day_of_week, meal_type])` is untouched, still exactly one `food_schedule_meals` row per day+meal-type. The dormant monthly voting window (§10, `food_votes`/`food_voting_periods`) — already multi-select, for a different purpose (voting on what to serve next month, not what's actually served) — is untouched. Food Polls (§16) is untouched. The Discovery-listing mess-menu importer (`src/services/marketing/mess-import.ts`, [[Decisions#ADR-077|ADR-077]]) needed **zero code changes**, because of the schema decision below.

**Schema.** A new child table, `food_schedule_meal_items` (`schedule_meal_id` FK `onDelete: Cascade`, `menu_item_id` nullable FK `onDelete: SetNull`, `item_name` snapshot, `display_order`, `@@unique([schedule_meal_id, display_order])`). "Monday Lunch" is now one `food_schedule_meals` row with N ordered children. `food_schedule_meals.menu_item_id`/`.item_name` are **kept**, not dropped — auto-maintained as a denormalized cache (first item's id; names comma-joined in order) on every write, purely so the marketing importer above — which `select`s `item_name` directly, no service in between — keeps working unmodified. See [[Database]].

Applied via a hand-written idempotent migration, `prisma/migrations/20260824090000_add_food_schedule_meal_items/migration.sql` (same `CREATE TABLE IF NOT EXISTS` / `DO $$...EXCEPTION WHEN duplicate_object` pattern as `food_polls`'s migration, §16), plus a backfill `INSERT` copying every existing cell's single item into a `display_order=0` child row — excluding the generator's true-empty sentinel (`item_name='Not set' AND menu_item_id IS NULL`) so no fake dish gets created. Same convention as always in this environment: `db push` handles the DDL, the backfill `INSERT` is a separate manual step against the same database (`db push` diffs schema only, it does not execute a migration file's DML).

**API.** `PATCH /api/food/schedules/[id]/meals/[mealId]`'s body changed from `{menuItemId}` to `{menuItemIds: string[]}` — ordered, full-replace-the-cell (same "PATCH replaces the whole cell" convention, pluralized; the one caller in the repo changed in the same commit, so no back-compat shim). Every id is validated against the hostel's active library for that meal type by a new pure module, `lib/services/food/meal-items.ts` (`validateMenuItemIds` — dedupes first-occurrence-wins, rejects any id that doesn't belong; `deriveLegacyFields` — the comma-join derivation, reused by every write path). The swap endpoint's optimistic-concurrency guard moved from `menu_item_id` equality (a complete state check only while there was exactly one scalar) to `updated_at` equality, which stays a full-state fingerprint at any item count. `GET /api/food/schedules` and `GET /api/food/tenant/schedule` nest `food_schedule_meal_items` (`orderBy: display_order`); the two `*/history` GETs were checked and confirmed to never include meal rows at all, so neither needed a change. See [[APIs]].

`POST /api/food/schedules/generate` and the daily carry-forward cron both switched their meal-row writes from bulk `createMany` to a nested `create` per row (`food_schedule_meals.create({ data: { ..., food_schedule_meal_items: { create: [...] } } })`) — a bulk insert doesn't hand back generated row ids, and recovering them with a follow-up lookup just to attach one child each is more moving parts than ≤28 sequential creates cost at this action's frequency. `assignWeekForMealType` itself (`lib/services/food-schedule-generator.ts`) is **unchanged** — the generator still assigns one item per day; multi-item authorship stays a manual, owner-driven action in the picker.

**`WeekGrid` contract (§6).** `WeekGridCell` gained `items: {id, menu_item_id, item_name, display_order}[]`; `isFilled` is redefined as `items.length > 0`; `menu_item_id`/`item_name` stay on the type only as a `@deprecated` derived passthrough. New shared helpers: `formatCellItems(cell, separator=' • ')` (the one "Rice • Dal • Curry • Chutney" renderer every surface now calls) and `itemSetKey`/`sameItemSet` (order-independent dish-set comparison). **Every** week reader was migrated to the new shape in the same change — Today card, owner Home line, Kitchen sheet (+ its WhatsApp message builder), Month History, publish checks, both tenant surfaces (Food tab, Home tab) — none were left reading the deprecated fields.

**The owner picker (`ScheduleMealPickerSheet.tsx`) is now a checklist, not pick-and-close.** Opening a cell seeds a local, staged selection from its current items; tapping a library item toggles it (doesn't commit); "add new item" appends the new id to the staged selection instead of immediately placing it; **Save** commits the whole ordered selection in one PATCH, **Cancel** discards every staged change. The toggle/seed logic is a pure, tested module (`pickerSelection.ts`) rather than component state, matching this app's node-only-vitest convention (no `.test.tsx`, no component rendering). **A genuine new footgun this design introduced, and its fix:** "Move to another day" fires an immediate swap and force-closes the sheet — against a *staged, unsaved* checklist selection, that would have silently discarded it with no warning. The move buttons are now disabled whenever the staged selection differs from what was seeded, with an inline hint to Save or Cancel first.

**The weekly grid (`DayRow.tsx`) shows a compact preview, not the full list, per the instruction not to make a chip unnecessarily huge:** the first dish's name plus a `+N` badge when there are more, full enumeration only in the `aria-label` and in the picker (which is one tap away). Drag-to-swap (§7.1) is unaffected — a chip is still draggable exactly when its cell is non-empty, now keyed on `items.length > 0` rather than a single name.

**`publishChecks.ts`'s two warnings needed a real semantic decision, not silent inheritance.** "Dominant item" (one dish on too many days of a meal type) and "runs" (the same dish on consecutive days) both used to compare `item_name` strings. Naively comparing the new joined string would make two cells with the *same dishes in a different order* — e.g. after a picker reorder — stop registering as "the same meal," silently weakening both warnings for a reason that has nothing to do with variety. Both checks now compare cells via `sameItemSet` (order-independent, by sorted item id/name), while `formatCellItems` (order-preserving) is still what's actually displayed to the owner. Two empty cells are never counted as "the same meal repeating."

**Tests.** New: `lib/services/food/meal-items.test.ts` (backend pure — add/remove/reorder/duplicate-id/empty/cross-hostel-id-rejected, the last one being the explicit tenant/hostel-isolation coverage this change needed) and `pickerSelection.test.ts` (frontend). Updated fixtures + new cases in `weekGrid.test.ts`, `kitchenSheet.test.ts`, `publishChecks.test.ts`. Confirmed unchanged: `dragSwap.test.ts` (pure geometry, no item-shape coupling) and `food-schedule-generator.test.ts` (the generator's own logic is untouched). See §12 for the verified counts.

**Not verified against a live database in this environment** (no `DATABASE_URL_TEST` provisioned here, same standing gap §12 already documents) — the new PATCH/swap/generate/carry-forward code paths are verified by direct code review, Prisma schema validation (`prisma validate` — passing), and the pure-logic test coverage above, not by an end-to-end request against real Postgres. The migration's DDL was written and validated but **not applied to any database as part of this change** — `schema.prisma` already carried unrelated, pre-existing uncommitted changes (a `hostels.latitude`/`.longitude` addition) at the time this work started, and applying `db push` would have pushed both together; left for whoever owns that decision.

## 18. Manual-only scheduling — the Timetable, and everything that replaced (2026-08-25)

**The problem this closes:** the module had three separate pieces of automation sitting on top of the owner's actual menu — a vote-share/alphabetical generator, a cross-day swap-drag, and a nightly carry-forward clone. Product direction changed: the owner builds the week entirely by hand. See [[Decisions#ADR-114|ADR-114]] for the full decision record; this section is the implementation write-up, in the same style §17 used for the previous major change.

**What did not change, and why this was a removal-and-reshape rather than a rewrite.** `food_menu_items` (the library) and `food_schedule_meals`/`food_schedule_meal_items` (§17) already modeled exactly the target shape — a reusable item, referenced (not copied) by an ordered per-cell list. `PATCH /api/food/schedules/[id]/meals/[mealId]` (full-replace-the-ordered-item-list) was already the one write primitive a manual UI needed. The weekly grain (§2) is untouched. Food Polls (§16), the dormant voting window (§10), and Meal Timings (§7 table) are all untouched — none of them did automatic *meal-schedule* generation, so none of them conflicted with this change.

**Removed outright** (code, not just UI): `lib/services/food-schedule-generator.ts` (`assignWeekForMealType`), `lib/services/food/schedule-rebuild-policy.ts` (`decideRebuild`), `POST /api/food/schedules/generate`; `lib/services/food/meal-swap.ts` (`canSwap`, `swapWritesLanded`), `POST /api/food/schedules/[id]/meals/swap`; the frontend's `WeeklyScheduleGrid.tsx`, `DayRow.tsx`, `ScheduleMealPickerSheet.tsx`, `dragSwap.ts`, `pickerSelection.ts`. See §5, §7.1, §7.2 above for what each used to do (kept as historical record, now marked superseded).

**New endpoint — `POST /api/food/schedules`, same file as the existing `GET`.** Body `{ hostelId, month }`. Creates an empty `DRAFT` schedule (`source: "MANUAL"`) plus all 28 empty `food_schedule_meals` cells (`menu_item_id: null, item_name: "Not set"`, no child items) if none exists yet for that hostel+month; returns the **existing** row unchanged (`200`) if one already does. No dish is ever chosen, ranked, or copied by this call — it is scaffolding, not generation, which is the whole reason it's safe to call automatically (see month navigation below). Replaces the generator as the only remaining creator of a `food_schedules` row; the carry-forward cron no longer creates rows either (§11) — `food_schedules.source` will only ever be written as `MANUAL` going forward.

**`PATCH .../meals/[mealId]` gained an `expectedUpdatedAt` guard (stale-write protection).** Body is now `{ menuItemIds: string[], expectedUpdatedAt: string }`. Inside the transaction, a conditional `updateMany` on `id`+`updated_at` runs before anything else; a `count !== 1` throws `STALE_WRITE`, mapped to **`409`**, and nothing is written. This is the exact technique the now-deleted swap endpoint used for its own optimistic-concurrency guard (§7.1), reused here now that swap itself is gone. No realtime/WebSocket layer was introduced — a second tab's stale edit is rejected, not merged; the frontend rolls its own optimistic UI back and refetches (below).

**The new owner surface — one Timetable page, not a picker sheet.** `TimetablePage.tsx`, route `/owner/food/timetable`, hostel on `?hostelId=` (same convention as Kitchen Sheet/Meal Timings/Food Polls). Linked from `FoodPage.tsx` as a card, same position `WeeklyScheduleGrid` used to occupy. Structure, all on one page (no per-day routing):

- **Month navigation.** Previous/current/Next controls, no bound in either direction. Switching months re-keys `useFoodSchedule(hostelId, month)` (already parameterized by month) and, if the month has no schedule row yet, fires the new create-if-missing call once. **A newly created month is always empty — never copies the previous month, never auto-selects a dish.** Reloading the same month is a no-op against the server (the `200` idempotent path), so this can safely fire on every navigation with no duplicate-row risk.
- **Day tabs**, Monday–Sunday, each showing a small completeness dot (`dayCompleteness` — reused from §6 unchanged).
- **The active day's 4 meal sections**, all visible at once, each showing its placed dishes. Tapping a section's header makes it the "active" one — the single live drop zone, and what the library/search panel below is scoped to.
- **The Food Library panel**, filtered to the active section's meal type only, with a search box (`No food items found` when nothing matches). **Search never crosses meal types** — switching the active section re-scopes both the visible library and whatever was typed into the search box.
- **Publish**, reusing `PublishChecklist`/`buildPublishChecks` — see the gating change below.

**Drag-and-tap, not drag-only.** Desktop's primary path is dragging a library chip onto the active section (handle-only drag — `dragListener={false}` + `useDragControls`, the same convention §7.1 established, chosen specifically so a swipe anywhere except the small grip is an ordinary scroll, never an accidental add). Tapping a library chip is the mobile-primary fallback and adds immediately. Reordering a placed chip is drag-with-handle only (no tap-to-reorder — nothing ambiguous to resolve there). Removing a placed chip is a plain × button, never drag — deletion stays unambiguous and discoverable. All of this lives in the new pure module `apps/frontend/src/features/owner-food/timetableDnd.ts` (`isOverDropZone`, `addItem`, `removeItem`, `reorderIndexAt`, `moveItem`, `filterByName`, `resolveDisplayName` — 26 tests) plus the drag wiring in `TimetablePage.tsx` itself (untested end-to-end, same standing limitation §7.1/§12 already documented for the old gesture).

**No duplicate food within one meal slot.** Enforced once, in the pure `addItem(currentIds, itemId)` — a duplicate is a no-op, reporting `added: false` so the UI can show "Already added" rather than silently doing nothing. Both drag-add and tap-add call the same function, so the rule can't drift between the two gestures. The same item is unaffected on a *different* day or a different meal type — each cell's id list is independent, so this was never something to special-case.

**No cap on items per meal.** Deliberately not implemented — a section's chip list wraps/scrolls, nothing warns about or blocks count.

**Publish gating — the one deliberate reversal of `publishChecks.ts`'s stated philosophy (§8).** §8's checks were, and for `variety`/`runs` still are, informational-only ("checks inform, they never block" — whether Dosa every day is fine is the owner's call). That reasoning does not extend to an outright empty cell: it isn't a stylistic choice, it's the literal "Not set" placeholder tenants would see live. `buildPublishChecks` now returns `{ checks, incompleteCells }` — `incompleteCells` names **every individual empty day+meal cell** (not just "which meal types are empty all week," §8's old granularity), computed for the gate itself; a new `canPublish(result)` reads `incompleteCells.length === 0`, and the Timetable's Publish button is disabled while it's false. **`PublishChecklist.tsx` deliberately does not enumerate `incompleteCells` on screen** — a brand-new month is 28 identical "Not set" lines, which is noise, not information; the `complete` check's own one-line summary ("0 of 28 meals filled — fill every meal to publish") is what's shown, and the button simply won't respond until every cell is filled. `variety`/`runs` are unchanged — still `PASS`/`WARN` only, never gate anything.

**Immediate persistence, no Save button — with optimistic UI and rollback.** Every add/remove/reorder calls `useFoodSchedule.setCellItems(mealId, menuItemIds)` directly against the PATCH endpoint; there is no staged/local-only state anywhere on the Timetable page (contrast the deleted picker sheet's stage-then-Save model). `setCellItems`'s mutation is optimistic (`onMutate` snapshots the query cache and writes the new state in immediately, so a drag/tap looks instant) with rollback on failure (`onError` restores the snapshot and shows `stayoToast.error` — a specific message for a `409 STALE_WRITE`, generic otherwise) and always settles with a real refetch (`onSettled: invalidate()`), which is also how the next edit picks up a fresh `updated_at` for its own concurrency check.

**Library rename/delete propagation.** A cell's stored `item_name` is a snapshot taken at the PATCH that last touched it — renaming a library item does **not** retroactively update every cell that already references it (self-heals only on that cell's next edit, since the PATCH route always re-derives `item_name` from the current library). To make renames show up immediately anyway, the Timetable resolves each placed chip's display name live: `resolveDisplayName(item, liveNameById)` prefers the Food Library's *current* name for that `menu_item_id`, falling back to the stored snapshot only when the id is null or not found (soft-deleted). **Scope note:** this fix is specific to the Timetable's own rendering — `MonthHistoryList`, `KitchenSheetPage`, and the tenant-facing schedule view still read the stored snapshot as before; making them live-resolve too was out of scope for this change. Deletion needed no new work at all: `DELETE /api/food/menu-items/[id]` was already, and remains, soft-delete-only (`is_active: false`) — confirmed via its own doc comment, which already explained why (a hard delete could orphan a historical/published schedule's reference). A deleted item's placements keep showing their last known name via the same fallback.

**Editing a `PUBLISHED` schedule is unchanged.** Same row, same live-immediately semantics, same `stayoToast.undo` affordance (§7 table) — this refactor changed how an edit is *composed* (drag/tap vs. tap-checklist), never what happens once it's sent. Worth stating explicitly since it would have been an easy thing to silently regress while replacing the call sites.

**Tests.** New: `timetableDnd.test.ts` (26, frontend pure). Updated: `publishChecks.test.ts` (16→20 — the `incompleteCells`/`canPublish` gate), `weekGrid.test.ts` (28, unchanged count — only the new `updated_at` field threaded through). Removed along with the code they covered: `food-schedule-generator.test.ts` (9), `food-schedule-rebuild-policy.test.ts` (11), `food-meal-swap.test.ts` (11) on the backend; `dragSwap.test.ts`, `pickerSelection.test.ts` on the frontend. Full current counts in §12.

**Verified:** backend `npx tsc --noEmit` — zero new errors from this change (the food routes' `$transaction(async (tx) => …)` implicit-`any` warnings are pre-existing across every food route using a transaction, including ones untouched by this change, not something newly introduced here); `prisma validate` passing (schema itself unmodified); backend pure suite 727/729 (56 files); frontend `vite build` (production) succeeds with `TimetablePage` code-splitting cleanly into its own chunk; frontend architecture check passing; frontend suite 997/997 (66 files). **Not verified against a live database in this environment**, same standing gap §12/§17 already documented — the new `POST /api/food/schedules` and the PATCH endpoint's `expectedUpdatedAt` guard are verified by code review, `tsc`, and the pure-logic suite above, not by an end-to-end request against real Postgres, and not exercised in a running browser (no reachable dev server or headless browser in this environment).

## 19. Food Library / Meal Plan split, and every cell is a live drop zone (2026-08-26)

**The problem this closes:** planning had two separate routes for one job — a Meal Timings page and a Timetable page (§18) — that belonged together. Product direction: collapse those two into one **Meal Plan** page, plus a richer editor where every one of the 28 cells is simultaneously a live drop target. See [[Decisions#ADR-121|ADR-121]] for the full decision record; this section is the implementation write-up, in the same style §17/§18 used for the previous two major changes.

**Corrected same-day, kept here rather than silently rewritten:** an earlier pass under this same ADR also moved the Food Library accordion off `/owner/food` onto its own `/owner/food/library` route, on the reasoning that "Food Library" and "Meal Plan" made a cleaner two-destination landing page. That was **reverted the same day** — the Food Library stays exactly where it always was, inline on `/owner/food`'s landing page (`FoodLibraryCard.tsx`/`useFoodMenuItems.ts`, genuinely unchanged), and `/owner/food/library` and `FoodLibraryPage.tsx` no longer exist. The paragraphs below describe only what's actually current: the Meal Timings + Timetable merge, and the Meal Plan editor's drawer as an *on-demand* window onto the same inline library, not a second copy of it.

**What did not change.** The weekly grain (§2, 28 cells) is untouched. The backend is untouched — `POST/GET /api/food/schedules`, `PATCH .../meals/[mealId]`, `POST .../publish` are exactly as §18 left them; this is a frontend IA/interaction change only. `food_menu_items` CRUD, the inline Food Library accordion on `/owner/food`, Food Polls (§16), and the dormant voting window (§10) are all untouched.

**Routing.** `/owner/food/meal-plan` (new, `MealPlanPage.tsx`) replaces `MealTimingsPage.tsx` and `TimetablePage.tsx`, both deleted. `/owner/food/meal-timings` and `/owner/food/timetable` now redirect to `/owner/food/meal-plan` via `RetiredFoodRoutes.tsx`'s `RetiredToMealPlan`, forwarding the full querystring — a bare `<Navigate>` (this app's usual retired-route pattern) would drop `?hostelId=` and the Today card's `?day=&slot=` "Fix" deep link, both of which this flow depends on. `/owner/food`'s own two link-cards ("Meal Timings", "Weekly Timetable") collapsed into one ("Meal Plan"); the Food Library section above them on that same page is untouched markup.

**Meal Plan page** (`MealPlanPage.tsx`) composes the same hooks as before (`useFoodSchedule`, `useFoodMenuItems`, `useMealTimings`, `buildPublishChecks`/`canPublish`) into one page: a header (month nav, Draft/Published badge, "X / 28 meals planned"), a compact Meal Timings strip ("Edit timings" opens a `BottomSheet` containing `MealTimingsForm.tsx` — the old standalone page's form body, extracted verbatim, same draft/dirty-check logic, still backed by the one `useMealTimings` source of truth), then either `MealPlanGrid.tsx` (desktop, `useIsMobile() === false`) or `MealPlanMobile.tsx` (mobile) — the page renders exactly one of the two, not both CSS-hidden, since both would otherwise race to register the same drop resolver (see below).

**Every cell is a drop zone now, not one active cell.** New pure module `gridDnd.ts`: `findDropTarget(point, cells: GridCellRect[])` resolves which of many simultaneously-registered cells a drop point landed on, reusing `timetableDnd.ts`'s `isOverDropZone` unchanged — that function was always a plain point-in-rect test; "one active zone" was an assumption at its old call site, not in its own logic. `MealPlanGrid` registers all 28 cells (a real 7-day×4-meal matrix, sticky meal-name column); `MealPlanMobile` registers only the visible day's 4, since a drop can't land on a day that isn't rendered. Each cell is `MealPlanCell.tsx` — chips, a persistent "+ Add food" (no "tap header to activate first" gate any more), and a ⋯ menu.

**Meal Plan reaches the same Food Library through an on-demand drawer** (`FoodLibraryDrawer.tsx`), not a copy of it — one `Sheet` component, `side="bottom"` on mobile / `side="right"` on desktop via `useIsMobile()`, the same pattern `features/change-management/components/ChangeRequestDrawer.tsx` already established elsewhere in this app (not a second overlay primitive). It reads from the exact same `useFoodMenuItems(hostelId)` hook the landing page's inline accordion does — one data source, two ways to look at it: browse-and-edit inline on `/owner/food`, or a scoped picker inside Meal Plan for placing dishes into cells. Every chip in the drawer is drag-or-tap-able: a **drag** resolves its landing cell purely by geometry (via the grid/mobile view's registered resolver) and can land on any cell regardless of which one opened the drawer; a **tap** adds to whichever specific cell's "+ Add food" opened the drawer (`drawerTarget`) — tapping with no such target (a page-level generic open, if one exists) shows a toast asking to open Add Food from a specific meal instead. The two affordances are deliberately not the same mechanism. A food placed into a cell stays in the Food Library afterward — nothing here ever removes or copies a library row, the cell just references it.

**Duplicate prevention needed no new logic.** `addItem` (`timetableDnd.ts`) already only ever sees the *target* cell's own ids — same-food-twice-in-one-cell was already a no-op reporting `added: false`, and same-food-on-a-different-cell was already allowed. Resolving "which cell" is `gridDnd.ts`'s new job, layered on top; `addItem` itself is unchanged.

**Cross-cell chip drag (physically dragging an already-placed dish from one cell straight into another) was deliberately not built.** Reordering stays within a cell, exactly as before; moving content across cells/days is served by Copy-to-days instead.

**Copy to days / Clear meal**, composed from the existing single-cell PATCH — no new backend endpoint, and no new hook method either. `planCopyToDays(sourceItems, targetDays)` (pure, `gridDnd.ts`) computes the per-day id lists; `MealPlanPage.tsx`'s `handleCopyToDays` calls it and loops the existing `useFoodSchedule.setCellItems` once per target day, so each PATCH gets its own optimistic update/rollback/toast, and a `STALE_WRITE` on one target day surfaces independently rather than failing the whole batch. "Copy meal" was not built as a separate action — a single day selected in the same "Copy to days" picker (`CopyToDaysSheet.tsx`) is exactly what it would have meant. "Clear meal" is `setCellItems(mealId, [])`, already how the PATCH route's own doc comment describes clearing a cell.

**`publishChecks.ts`'s `PublishCheckResult` gained `filledCount`/`totalCells`** — the Meal Plan header's progress line reads this instead of a second computation that could drift from the publish gate's own count. The line reads "X / 28 meals planned" plus, from the same `canPublish`/`incompleteCells` values, either "· N meals remaining" (incomplete) or "· Ready to publish" (complete) — no new arithmetic, just a second rendering of numbers already computed for the gate.

**Drag hover feedback and client-side meal-type rejection**, added same day as a follow-up. `DropResolution` (the shape `MealPlanGrid`/`MealPlanMobile`'s resolver hands back on drop) gained `day`/`slot` alongside the existing `cellId`/`currentIds`, since the page needs to know *which* cell is currently under the pointer, not just resolve one at drop time. `LibraryChip` gained an `onDrag` (fires continuously, not just at drop) alongside its existing `onDragEnd`; the page tracks `dragHover: {day, slot, valid} | null` by comparing the hovered cell's `slot` against the dragged chip's own meal type (the drawer's active tab — every chip visible in it shares that type). `MealPlanCell` renders this as a green "Drop here" border+label when `valid`, a red "Wrong meal type" border+label when not, keyed off a new `dropState` prop — the multi-zone resolver itself (`gridDnd.findDropTarget`) is unchanged, this is purely a read of its result on every drag frame instead of only once at drop. On an actual drop, `handleDrawerDragEnd` now checks `resolved.slot !== mealType` *before* calling `addItem`/`setCellItems` — a mismatched drop is refused client-side with an error toast, never reaching the backend's own `validateMenuItemIds` rejection (still there as the real guard; this is UX, not the security boundary).

**Publish confirmation**, added same day. Clicking Publish no longer calls `schedule.publish()` directly — it opens a `BottomSheet` ("Publish `<Month>`?") with Cancel/Publish buttons. Cancel just closes the sheet (no request fires). Publish calls the exact same `schedule.publish()` mutation the button always called, then closes the sheet — no new publish logic, no change to `canPublish`'s gate (the confirmation sheet only opens when the button was already enabled).

**Published-snapshot immutability, verified rather than newly built.** `food_schedule_meal_items.item_name` is written only at PATCH-time (`lib/services/food/meal-items.ts`) and never rewritten by a later Food Library rename — confirmed by reading the PATCH route directly, no other write path touches that column. `resolveDisplayName`'s live-name override (§18/§6) only ever affects the one schedule currently open in the Meal Plan editor; `MonthHistoryList`, `KitchenSheetPage`, and the tenant-facing view all still call `formatCellItems`, reading the stored snapshot. A renamed library item therefore shows its new name only in whichever month is currently being edited — every other, already-published month keeps showing what was actually served, unaffected.

**Tests.** New: `gridDnd.test.ts` (8: `findDropTarget` disambiguation/no-match/empty-cells, `planCopyToDays` including the orphaned-`menu_item_id` and empty-source/empty-targets cases). `timetableDnd.ts`'s header comment updated (its "one drop zone" framing is stale now that `gridDnd.ts` exists). `publishChecks.test.ts` unaffected (existing assertions on `.checks`/`.incompleteCells` don't touch the two new fields). All new component-level wiring (drag registration, drawer open/close, the grid/mobile responsive split) is per this app's standing node-only-tests convention — covered by direct verification against the running dev app, not `.test.tsx`.

**Verified live** (Playwright, real dev backend, `owner@teststayo.dev`), with a correction worth recording honestly: an initial pass checked only the optimistic UI (a drag landing visually, a filled-count ticking up) and read that as proof the PATCH persisted — it hadn't been. Checking the database directly surfaced a real bug ([[Bugs]] — every never-before-edited cell's first write 400'd on `expectedUpdatedAt`, invisible behind the optimistic update) that predates this section and affected §18's Timetable equally. Fixed, then re-verified the correct way: a tap-to-add confirmed via a direct query against the schedule row, `updated_at` moving from `null` to a real timestamp and `food_schedule_meal_items` populated. The full grid/drawer/copy-to-days flow's live verification (desktop mouse drag with multi-cell disambiguation, mobile touch drag via real CDP touch events, tap-to-add, copy-to-days, and the retired-route redirect) is recorded in [[Changelog]].

The drag-hover highlight, client-side meal-type rejection, publish confirmation, progress-text variants, and the Food-Library-stays-inline revert were all verified the same way in a follow-up pass: mid-drag `data-drop-state` checked directly on the DOM (`valid` over a matching cell, `invalid` over a mismatched one, confirmed the mismatched drop left the target cell untouched with no PATCH sent), the confirm sheet's Cancel path confirmed to fire no network request, Confirm confirmed against a fully-filled test month going from Draft to Published, an in-cell drag-reorder confirmed by reading the PATCH's own request body (`menuItemIds` in the new order), a meal-timing edit confirmed reflected in the grid's timing label, and `/owner/food` confirmed rendering the Food Library inline again with `/owner/food/library` now 404ing.
