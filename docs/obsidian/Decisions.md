## ADR-034: Signup phone verification degrades to "accepted unverified" when WhatsApp can't deliver — skip and record, not block

- **Date:** 2026-07-31
- **Status:** accepted
- **Context:** StayO's WhatsApp Business setup is still incomplete (no Meta credentials, no approved OTP template), but every owner-acquisition entry point routed through a phone-OTP gate: the landing-page lead modal and the onboarding wizard's account step both call `POST /api/auth/send-phone-otp` → `MetaWhatsAppProvider.sendOtp()`, which throws without credentials. In production that is a `502` and signup is simply impossible. In development it was papered over by two workarounds inside `AuthOtpService.sendPhoneOtp` — a plaintext dump of every generated code to `apps/backend/latest-otp.txt`, and a `NODE_ENV !== "production"` bypass that returned `success: true` with nothing actually sent. Either way the user still faced a six-digit OTP screen for a code that could only be obtained by reading a file off disk. Both downstream gates (`/api/leads/self-serve`, `/api/auth/owner-signup`) additionally required a `VERIFIED` `phone_verification_otps` row within 30 minutes.
- **Decision:** verification becomes conditional on the provider actually being able to deliver, and its absence is **recorded rather than enforced away**.
  - A pure env-derived resolver (`resolvePhoneVerificationMode()`) returns `on` only when `OTP_PROVIDER=whatsapp` + access token + phone-number ID + `WHATSAPP_OTP_TEMPLATE` are all present, with `PHONE_VERIFICATION_MODE` as an explicit override in either direction.
  - A circuit breaker (3 failures / 10 min → open 15 min → single half-open trial) stops burning a 10-second Meta timeout per signup when the provider is configured but broken.
  - For purposes `PHONE_VERIFICATION` and `LEAD_CAPTURE` **only**, an undeliverable OTP writes a `SKIPPED` row (`provider_status: UNAVAILABLE`, `verified_at` set) and returns `verification_required: false`; the frontend then never renders its OTP step. All other purposes keep the hard `502`.
  - Both signup gates move to one shared `resolveSignupPhoneVerification()` helper accepting `VERIFIED` **or** `SKIPPED` within the same 30-minute window, returning which — written to `profiles.phone_verified`/`mobile_verified` (previously hardcoded `true` in `selfSignUpOwner`) and to the new `platform_leads.phone_verified`.
  - The two dev workarounds are deleted.
  - **The two import-time `validateWhatsAppConfiguration()` calls** (`notification-service.ts`, and one at the bottom of `meta-provider.ts`) now log instead of throwing. Found during live verification: they run at *module import*, so a half-configured environment 500'd the route before any fallback logic could execute — the exact state this ADR exists to survive. The function still throws for callers that assert on it. See [[Bugs]].
- **Alternatives considered:**
  - **Email OTP as a fallback channel** (send the code via Resend instead, keeping real verification) — rejected: this environment's `RESEND_API_KEY` is separately known-invalid (see ADR-032's notes), so it would have swapped one unavailable channel for another, and a second delivery channel is more surface than the problem warrants. Revisit if email delivery becomes reliable and unverified numbers prove to be a real cost.
  - **Blocking signup until WhatsApp is approved** — rejected: makes the entire owner-acquisition funnel unusable for an external dependency with no committed date.
  - **Dropping the gate on the two signup endpoints entirely while degraded** — rejected: writing a `SKIPPED` row instead keeps both endpoints reachable only by a caller that just went through `/send-phone-otp` for that exact number, preserving the anti-spam property, and leaves an audit trail of *why* each number is unverified.
  - **Degrading only requests *after* the breaker opens**, letting the failing request itself 502 — rejected: that hands one unlucky user per cooldown a dead end for a condition the system already knows about.
  - **A login-time or step-up catch-up prompt for unverified users** — explicitly out of scope per the requester; this change is about the signup page, and a catch-up regime is a separate decision.
- **Consequences:** signup works today, and turning verification back on is configuration-only (set the four variables, or `PHONE_VERIFICATION_MODE=on`) with no code change and no migration. Honestly named cost: **a real phone number that nobody confirmed can now back a lead or an owner account** — mitigated by human lead review before approval plus an "Unverified" marker in the admin leads list, and bounded by the fact that nothing retroactively verifies the backlog once WhatsApp is live. Second cost: with the breaker, a credentials expiry downgrades verification *silently*; the `otp.request.skipped` metric line makes the rate observable, but no alert is wired to it yet.
- **Related:** [[Business-Rules#Signup phone verification|Business-Rules]], [[APIs]], [[Database]], [[Features]], [[Changelog]], [[Decisions#ADR-028|ADR-028]] (the signup path this modifies), [[Decisions#ADR-032|ADR-032]] (the same WhatsApp/email gap on the activation leg)

## ADR-032: Owner-acquisition funnel phase 2 — real lead activation via a `tenant_invitations`-style token, not a shared table

- **Date:** 2026-07-29
- **Status:** accepted
- **Context:** Phase 1 wired the landing page's "Manage My Hostel" CTA to real Google sign-in + phone-OTP-verified lead capture, creating real `platform_leads` rows. The Admin Console's "Approve"/"Reject"/status-dropdown were pure status-label writers — `PATCH /api/platform-admin/leads/[id]` did nothing beyond `prisma.platform_leads.update({ status })`, for any of the 6 old status values. This phase makes "Approve" do something real: generate a single-use activation link, send it (WhatsApp, email fallback), and land the owner on the real onboarding wizard, prefilled, with the lead's status then auto-advancing as real signup/hostel-creation events happen.
- **Decision:**
  - **New `platform_lead_invitations` table**, deliberately a new table rather than reusing `tenant_invitations` directly — a lead has no `tenant_id`/`hostel_id`/`room_id` yet, and `tenant_invitations` is FK'd to all three. Copies its proven shape instead: an opaque `token` (`crypto.randomBytes(32).toString("hex")`) stored separately from the row's own `id` — the URL never carries a database primary key — with `status` (`PENDING → OPENED → ACTIVATED`, or `EXPIRED`) and `expires_at` (+7 days) enforcing single-use and expiry, mirroring `tenant-invitation-lifecycle-service.ts`'s pattern without sharing its code.
  - **`PlatformLeadStatus` enum replaced outright**, not extended: `NEW, UNDER_REVIEW, APPROVED, INVITE_SENT, OWNER_ACTIVATED, HOSTEL_CREATED, LIVE, LOST` (was `NEW, CONTACTED, DEMO_SCHEDULED, ONBOARDING, ACTIVE, LOST`). A real `ALTER TYPE`/recreate migration, not `ADD VALUE`, since old values are retired. Existing rows mapped: `CONTACTED→APPROVED`, `DEMO_SCHEDULED→UNDER_REVIEW`, `ONBOARDING→INVITE_SENT`, `ACTIVE→LIVE`, `NEW→NEW`, `LOST→LOST`. Judged low-risk since the table held only this session's own test/demo rows at migration time.
  - **`APPROVED` onward is system-managed, enforced server-side, not just a UI convention**: `PATCH /api/platform-admin/leads/[id]` now rejects any attempt to set `status` to anything except `NEW`/`UNDER_REVIEW`/`LOST` (400 `VALIDATION_ERROR`). The only way to `APPROVED`+ is `POST .../approve`, and only the auto-progression choke points below can move a lead past `INVITE_SENT`. This is what actually guarantees "no manual status updates required after invite sent" — a convention alone wouldn't have.
  - **Three auto-progression choke points, each a real backend side effect, not polling**: `OWNER_ACTIVATED` inside `POST /api/auth/owner-signup` (when the request carries an optional `lead_token`, threaded from the wizard) — single-use is enforced here via an `updateMany({ where: { status: { in: ["PENDING","OPENED"] } } })` count check, inside the real signup's own success path, not trusted to frontend call ordering. `HOSTEL_CREATED` inside `POST /api/owner/hostels`, looked up via `platform_leads.converted_owner_id` (see below) — no new column needed on `hostels`. `LIVE` is the one exception with no natural server hook (floor/room creation is a frontend-orchestrated loop of several separate calls, confirmed no existing event fires when it finishes) — the wizard's publish step makes one small trailing `POST /api/leads/invitation/[token]/complete` call after that loop succeeds. All three are wrapped so a failure in the lead-tracking side effect can never fail or roll back the owner's real signup/hostel-creation/publish.
  - **`platform_leads.converted_owner_id`** (present in the schema since Phase 1's design but never actually written by any code — confirmed dead, see [[Bugs]]) is populated for the first time here, at the `OWNER_ACTIVATED` step, and is what lets the `HOSTEL_CREATED` step look the lead back up without a new FK anywhere on `hostels`.
  - **`systemEventLog` reused as-is for the audit trail, with a stated tradeoff**: it has `owner_id`/`tenant_id` columns but no `lead_id` — lead-scoped events (`LEAD_CREATED`, `LEAD_APPROVED`, `LEAD_INVITE_SENT`, `LEAD_INVITE_OPENED`, `LEAD_OWNER_ACTIVATED`, `LEAD_HOSTEL_CREATED`, `LEAD_LIVE`) are logged with `owner_id: null` and `lead_id` inside the JSON `metadata` field; the Admin drawer's new Timeline section queries via a Prisma JSON-path filter (`metadata: { path: ["lead_id"], equals: id }`) rather than an indexed FK join. Chosen over adding a `lead_id` column to a shared table used by many unrelated flows — acceptable at current lead volume, revisit only if that ever becomes a real query-performance concern.
  - **WhatsApp needs a new Meta-approved template** (`WHATSAPP_OWNER_ACTIVATION_TEMPLATE`, no default value that will actually send) — this is a real external dependency outside this codebase, not something code alone can complete. Until approved (and always in dev, since no WhatsApp credentials are configured), `MetaWhatsAppProvider.sendOwnerActivation()` throws internally and the flow falls straight through to `EmailService.sendOwnerActivation()`, exactly like Phase 1's lead-capture OTP already does — the feature is fully verifiable end-to-end via the email leg regardless of Meta's approval timeline.
- **Alternatives considered:** Reusing `tenant_invitations` directly with nullable `tenant_id`/`hostel_id`/`room_id` (rejected — would force every consumer of that table to handle a "lead, not tenant" case it was never designed for, and blur a table that's already load-bearing for a completely different domain). Adding the granular lifecycle as new *additional* enum values via `ADD VALUE` (rejected — the old 6 values don't map cleanly onto real business progress, e.g. `ONBOARDING` meant nothing specific; a clean replacement with an explicit data-migration mapping was judged clearer than accumulating both old and new labels side by side). Adding a `lead_id` column to `systemEventLog` (rejected for now — a schema change to a table read by many unrelated flows, for one new feature's benefit; the metadata-filter approach is reused infrastructure at the cost of an unindexed query, acceptable at current scale).
- **Consequences:**
  - A lead that's approved but where both WhatsApp and email fail to send is deliberately left at `APPROVED`, not silently marked `INVITE_SENT` — the admin sees an accurate state and the delivery error, and can retry. Verified live: with WhatsApp unconfigured and (separately, an existing environment issue) an invalid `RESEND_API_KEY`, a real approve attempt correctly stayed at `APPROVED` rather than lying about delivery.
  - The onboarding wizard (`OwnerOnboardingWizard.tsx`) gained its first-ever external-prefill capability (`useOwnerOnboardingState(initialData?)`) and a new `city` field it didn't have before — both small, additive changes; a normal non-lead-originated `/onboarding` visit is unaffected (verified live: a fresh signup with no `lead_token` completes exactly as before).
  - Full lifecycle verified live against the real dev database end-to-end: lead created → approved (WhatsApp+email attempted, correctly failed and logged) → activation context fetched (prefill data returned, `PENDING→OPENED`, event logged) → real owner-signup with the token (`OWNER_ACTIVATED`, `converted_owner_id` set, invitation `ACTIVATED`, single-use re-verified via a second invitation row created earlier by the failed approve attempt, which correctly stayed `PENDING` and unusable) → hostel creation (`HOSTEL_CREATED`) → publish-complete call (`LIVE`) → Admin drawer's timeline query returned all 6 logged events in the correct order.
- **Related:** [[Backend]], [[Frontend]], [[Database]], [[APIs]], [[Bugs]], [[Changelog]], ADR-031 (the Supabase Auth migration this phase's `owner-signup` change builds on top of)

## ADR-031: Migrate authentication from the custom JWT+refresh-token system to Supabase Auth

- **Date:** 2026-07-29
- **Status:** accepted
- **Context:** The existing "Continue with Google" flow (`authService.googleLogin()`) was a hand-rolled raw OAuth2 code exchange against `https://oauth2.googleapis.com/token`, discarding Google's `sub`/`email_verified` claims and never verifying the ID token's signature — and it was non-functional in every environment checked, since `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`/`VITE_GOOGLE_CLIENT_ID` were never configured. Separately, the app already had a *parallel, inconsistent* relationship with Supabase Auth: `registerOwner()`/`selfSignUpOwner()` tried `supabase.auth.admin.createUser()` and silently fell back to a local `crypto.randomUUID()` on any failure (no flag recorded on which case occurred), while tenant and admin profile-creation paths never attempted Supabase at all — meaning **every tenant and admin account, and an unknown subset of owner accounts, had zero real Supabase identity**, and `profiles.id === auth.users.id` was an unenforced intent, not a guarantee. Rather than patch the Google flow in isolation, the decision was made to migrate the whole session layer onto Supabase Auth as the single provider (email/password and Google both), fixing the underlying identity-linking problem in the same pass instead of building Google auth on top of it.
  Also corrects two facts CLAUDE.md/`docs/obsidian/Backend.md` had wrong before this migration started (found during research, unrelated to Supabase): the access token was actually **12h**, not 20 min; the absolute session cap was **30 days** for both OWNER and TENANT, not 12h. The custom refresh-token rotation/reuse-detection logic (`SessionLifecycleService.rotateRefreshToken()`) was fully implemented but **dead code** — `/api/auth/refresh` never called it, running its own non-rotating logic instead — so Supabase's own (real, working) refresh rotation is a strict improvement for that piece, not a regression.
- **Decision:**
  - **`profiles.auth_user_id` (nullable, unique) + `auth_linked_at`** link `profiles` to `auth.users`. Not a business-model change — pure auth linkage, matches the architecture the migration was scoped around.
  - **Just-in-time (lazy) identity linking**, not a forced password reset (a reset would be a workflow change, out of scope by the migration's own constraints): on every successful password login (`login()`, `loginWithPhone()`, `selfSignUpOwner()`, tenant-activation auto-login), `ensureSupabaseIdentity()` (`lib/auth/supabase-identity.ts`) silently creates-or-links a real `auth.users` row using the plaintext password available for that one request, then calls `signInWithSupabasePassword()` to mint a real Supabase session. The plaintext is never persisted anywhere new. **No more silent local-UUID fallback** on Supabase failure — that was the root cause of the pre-migration unreliable-linkage state, and this migration removes it rather than extending it; if Supabase is unreachable, the login/signup now fails loudly instead.
  - **Login stays backend-mediated** — the SPA does not call `supabase.auth.signInWithPassword()` directly. `/api/auth/login` is the only place rate-limiting, tenant-status checks, `PASSWORD_RESET_REQUIRED`, and the JIT linking itself can run; moving it client-side would mean losing those gates or reimplementing them against Supabase.
  - **Role/`owner_id`/`tenant_id` resolution happens Node-side** (`lib/auth/supabase-session.ts`'s `resolveSupabaseSession()`), not via a Supabase Custom Access Token Hook baking these into every minted JWT. Seriously considered and rejected: `tenant_id` doesn't exist until activation, `is_active` must revoke access immediately when an owner disables a tenant, and `owner_id` is already known to go stale (the pre-existing self-heal in `createSessionAndTokens()` exists for exactly this reason) — baking these into a JWT that only refreshes hourly would reintroduce staleness bugs the current design already works around. The cost is one indexed DB lookup per authenticated request; `/api/auth/me` already did two on every heartbeat, so this isn't a new category of cost.
  - **`middleware.ts` stays on the Edge runtime and stays cheap**: `getSession()`'s well-known chokepoint shape (241+ route files call it, reading only headers `middleware.ts` injects, doing zero DB/crypto themselves) meant swapping the verification method there — not touching any of those 243+ call sites — was the cheapest possible migration seam. Verification is via `jose`'s `createRemoteJWKSet` against Supabase's live JWKS endpoint (the project uses asymmetric ES256 signing, confirmed live during planning), so no shared secret to manage and no network round-trip per request.
  - **Dual-accept during the transition**: `middleware.ts` tries Supabase verification first, falls back to legacy HS256 verification, tagging the request `x-auth-mode: supabase|legacy`. `getSession()` (now Node-only, moved out of the Edge-only `lib/auth-edge.ts` since it needs Prisma) branches on that tag. This means the migration didn't force-invalidate any session that was valid at deploy time — legacy sessions simply age out over their normal 12h lifetime once `/api/auth/login` stops issuing new ones.
  - **`password_hash` on `profiles` stays permanently** — required by the 2-minute `identity_tokens` step-up-confirmation flow (6 financially-sensitive OWNER routes: offline payment, obligation cancel/waive, change-rent, change-frequency ×2), which re-verifies via `authService.verifyOrMigrateLegacyPassword()`/bcrypt and is unrelated to the login-session migration. Reimplementing that step-up against Supabase reauthentication (a very different UX — a one-time emailed code instead of re-typing a password in a modal) would itself be a workflow change, which this migration is not authorized to make.
  - **`JWT_SECRET` stays** — SSE short-lived tokens, receipt-verification tokens, `identity_tokens`, and password-reset tokens are app-minted/app-verified and unrelated to the login session; none of this moves to Supabase.
  - **Revocation is preserved, and is actually stronger than before, not weaker**: Supabase access tokens are stateless and valid until `exp` — Supabase itself has no way to instantly kill one. The pre-existing Redis deny-list (`checkSessionRevocationEdge`, checked on every request regardless of auth mode) is kept for exactly this, and `/api/auth/logout`/`logout-all` additionally call `supabase.auth.admin.signOut()` so the refresh token dies server-side too. The 30-minute idle-timeout business rule (also something Supabase has no concept of) is preserved the same way — reimplemented in Redis, checked in `middleware.ts` for Supabase-mode requests specifically (legacy-mode idle-checking is untouched, still Node-side via `sessionLifecycleService.touchSession()`).
  - **Google sign-in keeps its exact pre-migration invariants**, now enforced in `resolveSupabaseSession()` instead of the old `googleLogin()`: never auto-provisions an account (matches by `auth_user_id`, then by email — rejects with `NO_STAYO_ACCOUNT` if no profile exists), tenants may not sign in with Google (`TENANT_GOOGLE_NOT_ALLOWED`), disabled accounts are rejected (`ACCOUNT_DISABLED`). The one behavior change is a *strengthening*: `email_verified` is now actually checked before linking a Google identity to an existing profile, where the old raw-OAuth2 flow discarded that claim entirely.
- **Alternatives considered:** Scoping this migration to Google-only, leaving email/password on the custom system (rejected — the user's explicit direction was Supabase as sole provider; a two-provider split would also mean maintaining both the custom refresh-rotation code and Supabase's, doubling the surface this migration was meant to simplify). A Custom Access Token Hook for claims (rejected, see above — staleness). Client-side-only `signInWithPassword()` calls, bypassing the backend (rejected — loses rate-limiting/status-gate enforcement and the JIT linking hook). Cookie-based session storage via `@supabase/ssr` (rejected — that package is designed for same-origin SSR frameworks; this is a cross-origin Vite SPA talking to a separate Next.js API host, and adopting it would be a materially larger change than this migration's scope).
- **Consequences:**
  - **Real, accepted security-posture tradeoff**: the refresh token moves from an httpOnly `SameSite=Lax` cookie (today's model) to Supabase's client-side session storage (localStorage by default), which is more XSS-exposed. Mitigated by shortening the Supabase access-token TTL and by Supabase's own real (unlike the dead code it replaces) refresh-token rotation with reuse detection. This is an inherent consequence of a cross-origin SPA using the client-side Supabase SDK, not a mistake — see the rejected `@supabase/ssr` alternative above.
  - Accounts that never log in again stay unlinked to Supabase indefinitely — an accepted consequence, not a gap to force-close with a reset campaign. Made measurable via `npm run reconcile:supabase-identities` (dry-run by default; matches `profiles` against `auth.users` by both `id` and `email`, never auto-links an ambiguous match).
  - `googleLogin()`, `getGoogleCodeRedirectUri()`, `app/api/auth/google-callback/`, `app/api/auth/refresh/`, `generateRefreshToken`/`hashToken`, and the dead `ensureSupabaseResetIdentity()` are removed outright. `SessionLifecycleService` is trimmed to the policy constants (`ACCESS_TOKEN_MAX_AGE_SECONDS`, `TENANT_REFRESH_DAYS`, `OWNER_ABSOLUTE_MS`, `INACTIVITY_TIMEOUT_MS`, `getSessionCookieOptions`) plus `touchSession`/`revokeSession` — its session-minting/rotation methods are gone.
  - Two real, previously-undiscovered bugs were found and fixed in the same pass (see [[Bugs]]): `changePassword()` passed the local `profiles.id` straight to `supabase.auth.admin.updateUserById()`, which only ever worked for the subset of profiles born with `id === auth.users.id` — every other profile 500'd the whole password-change request; `completePasswordReset()` used unpaginated `supabase.auth.admin.listUsers()` to find a user by email, silently missing anyone past the first page.
  - Zero runtime test coverage existed for login/refresh/logout/session-lifecycle before this migration, and that gap is not closed by it — `tests/auth-hardening-security.test.ts` (a static source-code scan, retargeted at the new `resolveSupabaseSession`/`ensureSupabaseIdentity` code) plus manual verification are the safety net.

## ADR-028: Real StayO owner self-signup is a separate, ungated service method — not a reuse or relaxation of `registerOwner`'s `ALLOW_OWNER_BOOTSTRAP` gate

- **Date:** 2026-07-25
- **Status:** accepted
- **Context:** StayO's real owner-acquisition journey (landing → onboarding wizard → dashboard) needed a working self-serve signup, but the only existing owner-creation path, `POST /api/auth/register`, is structurally unreachable for this: it requires an already-authenticated OWNER session (a contradiction for signup) *and* a `verification_token` that no route in the codebase actually mints — `verify-phone-otp` only flips flags on an *existing* profile, and `confirm-identity` (the only token-issuing route) doesn't include `PHONE_VERIFICATION`/`registration` in its allowed purposes. `registerOwner()` itself is additionally guarded by `ALLOW_OWNER_BOOTSTRAP`, whose own doc comment states "HMS is a single-owner system... no new owners should be created through any code path" — a safety flag from the legacy single-owner-HMS heritage, not something meant to gate a real multi-tenant SaaS's normal signup traffic.
- **Decision:** Added `authService.selfSignUpOwner()` — a new method duplicating the safe parts of `registerOwner()` (email/phone uniqueness checks, best-effort Supabase-user create with local-UUID fallback, `hashPassword`, single `profiles` row insert with `role: OWNER`) but with no `ALLOW_OWNER_BOOTSTRAP` check, backing a new public route `POST /api/auth/owner-signup`. Instead of the broken `identity_tokens` mechanism, this route re-purposes the already-working `send-phone-otp`/`verify-phone-otp` pair: it looks up a `phone_verification_otps` row with `status: VERIFIED` for that phone, issued within the last 30 minutes, and rejects signup if none exists. On success it calls the same `createSessionAndTokens()` used by `/login`, so the response/cookie shape matches exactly.
- **Alternatives considered:** Reusing `registerOwner()` with `ALLOW_OWNER_BOOTSTRAP` always set in production (rejected — that flag exists specifically to prevent uncontrolled owner creation; setting it permanently on defeats its purpose and conflates two different products' safety models). Fixing `confirm-identity` to add `PHONE_VERIFICATION`/`registration` to its allowed purposes (rejected — that route requires an existing OWNER session by design, still a dead end for brand-new signups; would need its own auth exemption anyway, at which point a dedicated route is cleaner). Skipping phone verification entirely for now (rejected — the OTP send/verify infrastructure already works end-to-end in this environment via the dev debug-file fallback, no reason to leave signup unverified when the pieces exist).
- **Consequences:** `/api/auth/register` remains exactly as restricted as before (no weakening of the legacy gate); StayO owner signup is fully real and independently testable. The 30-minute OTP freshness window is arbitrary and not yet configurable — revisit if real-world signup latency (e.g. slow WhatsApp delivery once configured) makes it too tight.

## ADR-027: Regeneration wipes ALL live UPCOMING rent, not just rows on/after the new effectiveFrom, and revives stale rows instead of colliding with them

- **Date:** 2026-07-22
- **Status:** accepted
- **Context:** Two related bugs surfaced from repeated real-time testing of the ADR-024 regeneration logic (switching the same tenant Quarterly → Monthly → Quarterly in quick succession):
  1. `(agreement_id, rent_month, obligation_type)` is a **hard, unfiltered** unique index (not scoped to `is_superseded: false`) — a stale, already-superseded row from an earlier switch still permanently occupies its `rent_month` slot. A later switch landing on that same month (very likely when switching back to a previously-used cadence) hit `Unique constraint failed` trying to `create()` a fresh row on top of it.
  2. Once (1) was fixed, a second bug appeared: the supersede step only cleared obligations with `due_date >= effectiveFrom`. Since a shorter cadence (Monthly) computes an earlier `effectiveFrom` than a longer one (Quarterly), switching Monthly → Quarterly could leave a few of the Monthly pass's earliest obligations dated *before* the Quarterly pass's `effectiveFrom` — un-superseded, still live, at the old cadence's amount, sitting alongside the newly-created Quarterly rows. The live schedule ended up mixing two cadences' amounts.
- **Decision:** (1) Before creating each schedule item, look up any existing row for that exact `(agreement_id, rent_month, obligation_type)` — regardless of `is_superseded` — and `update()` it in place (reviving it: `is_superseded: false`, fresh amount/dates/labels/plan link) instead of blindly `create()`ing, mirroring `agreement-rent-schedule-service.ts`'s own duplicate-guard pattern, just not filtered to live rows since that's precisely the row that would otherwise collide. (2) The supersede step now clears **every** currently-live `UPCOMING` `RENT` row for the tenant, with no `due_date` filter at all, before creating the new schedule — safe because `UPCOMING` rows are by definition never activated for collection (zero payments possible on any of them), so fully wiping and regenerating them on every switch can't touch real money and keeps the schedule always single-cadence, never mixed.
- **Alternatives considered:** Catching the P2002 unique-constraint error and skipping that period (rejected — matches the codebase's existing convention in `generateForAgreementInTx` for a *different* scenario, but here it would silently create a gap in the tenant's schedule for that one period, which is worse than reviving the row). Scoping the wipe to `due_date >= min(effectiveFrom, existing obligations' earliest due date)` instead of everything (rejected as needless complexity — since only `UPCOMING` rows are touched and none represent real collected/collectible debt yet, there's no downside to a full wipe-and-regenerate every time).
- **Consequences:** Regeneration is now idempotent under repeated switching — the live schedule is always fully and only the most-recently-requested cadence, with no stale remnants regardless of how many times an owner changes their mind. New regression test (`tests/billing-frequency-owner-initiate.test.ts`) exercises exactly the reported 3-switch sequence and asserts every live row matches the final cadence's amount.

## ADR-026: Owner-direct frequency changes search forward for a clean period instead of failing on the first naive candidate

- **Date:** 2026-07-22
- **Status:** accepted
- **Context:** `getNextCleanBillingPeriodDate` picks a single candidate effective date (the next calendar boundary aligned to the requested frequency), entirely calendar-based, with no awareness of the tenant's actual obligations. `ownerInitiateChange` then checked that ONE candidate for overlap and threw `UNCLEAN_BILLING_PERIOD` if it collided — reported live: switching tenant "shiva" from Quarterly back to Monthly failed because the very next month's rent was already activated (`PENDING`), even though a later month would have been perfectly clean.
- **Decision:** Added `findCleanEffectiveFrom()` — walks forward month by month (same iteration cap as `getNextCleanBillingPeriodDate`, 36 months), and at each candidate that's a valid period start for the requested frequency, actually checks it against `findOverlappingObligations` (ADR-023) instead of assuming the first candidate is fine. Returns the first genuinely clean one; still throws `UNCLEAN_BILLING_PERIOD` if none is found in the search horizon. `ownerInitiateChange` now calls this instead of `getNextCleanBillingPeriodDate` + a single overlap check.
- **Alternatives considered:** Leaving it as a single-candidate check and just improving the error message to say "try again later" (rejected — the system already has all the information needed to find a working date itself; making the owner guess-and-retry across months is worse UX for no real safety benefit). Applying the same forward-search to `ownerSetCustomSchedule` (rejected — custom installment dates are explicitly owner-chosen; silently shifting a date the owner typed in would be surprising, not helpful — blocking clearly and letting them pick a different date is the right UX there).
- **Consequences:** Owner-direct frequency changes now succeed in substantially more real scenarios (e.g. switching back and forth between cadences) without the owner needing to understand *why* a given month didn't work.
- **Related:** [[Bugs]], [[Changelog]], ADR-023

## ADR-025: Frequency-change cooldown and minimum-commitment checks disabled for the owner-direct path (temporary)

- **Date:** 2026-07-22
- **Status:** accepted — explicitly temporary, flagged for revisit
- **Context:** `validateCooldown()` (90-day default) and `validateCommitment()` (minimum months on the current frequency before switching) both blocked repeated owner-direct frequency changes on the same tenant during local testing/iteration — surfaced as `FREQUENCY_CHANGE_COOLDOWN_ACTIVE` and then, once that was disabled, `MINIMUM_COMMITMENT_NOT_MET` on the very next attempt. Both times: explicit request to remove it "for now."

- **Alternatives considered:** Deleting the logic entirely (rejected — "for now" signals a testing-convenience request, not a permanent policy change; commenting out keeps restoring it a one-line change). Making either check configurable per-request (rejected — unnecessary API surface for what's meant to be a quick temporary disable).

## ADR-024: Owner-direct recurring frequency changes now regroup an agreement-based tenant's future rent for real

- **Date:** 2026-07-22
- **Status:** accepted
- **Context:** ADR-021 shipped owner-direct MONTHLY/QUARTERLY/HALF_YEARLY changes with a disclosed, deliberate limitation: for a tenant with a signed agreement, the change updated `tenants.payment_frequency`/`tenant_billing_plans` but never touched the individual monthly `rent_obligations` rows `agreement-rent-schedule-service.ts` had already generated up front at signing — so the Charges tab kept showing unchanged monthly rows after a "successful" frequency change. Direct user report with a screenshot confirmed exactly this. ADR-022's Custom Dates work already established *why* this is safe to fix directly: `generateForAgreementInTx` is a one-shot call (signing / renewal activation) that never re-runs for an already-signed agreement, so directly superseding and replacing its future obligations can't be undone or duplicated by a later automatic run.
- **Decision:** `ownerInitiateChange` now checks whether the tenant has an active agreement. If so, it: computes how many of the new frequency's periods are needed to cover the remaining agreement term (`agreement.agreement_end_date`, already a real column — no need to derive it from duration), builds the full schedule via `billingScheduleService.previewSchedule` (not just a 4-period preview), and inside the same transaction supersedes the tenant's not-yet-due (`UPCOMING`, `due_date >= effectiveFrom`) `RENT` rows and creates the new grouped ones (`agreement_id`/`billing_plan_id` stamped, same `is_superseded`/audit fields as the Custom Dates path). Non-agreement tenants are unaffected — `rent-generation-service.ts`'s rolling monthly generator already reads `payment_frequency`/`payment_frequency_effective_from` correctly for any month not yet generated, so updating the setting alone remains sufficient there. `ChangeFrequencyModal.tsx`'s agreement-tenant warning banner (and the now-unused `hasActiveAgreement` prop) removed since the limitation it described no longer exists.
- **Alternatives considered:** Teaching `agreement-rent-schedule-service.ts` itself to understand periodic frequencies as a generation-time concept (rejected, same reasoning as ADR-022 — the one-shot call pattern makes direct supersede-and-replace simpler and equally safe, without touching the shared generator every agreement-based tenant depends on). Only fixing Custom Dates and leaving the Recurring path's limitation in place long-term (rejected once a live user report showed it was actively confusing rather than a theoretical gap).
- **Consequences:** The `agreement-rent-schedule-service.ts` gap noted in ADR-021/ADR-022's Bugs.md entry is now resolved for the *recurring* path too — nothing agreement-related is left broken by this feature area. `ownerInitiateChange`'s return shape gained `obligations_created`/`obligations_superseded` (0/0 for non-agreement tenants) matching `ownerSetCustomSchedule`'s existing shape.
- **Related:** [[Bugs]], [[Changelog]], ADR-021, ADR-022, ADR-023

## ADR-023: Owner-direct frequency changes no longer block on a tenant's older, non-overlapping unpaid rent

- **Date:** 2026-07-22
- **Status:** accepted
- **Context:** Direct user report — an owner tried to change a tenant's billing frequency and got `UNCLEAN_BILLING_PERIOD` simply because the tenant had ordinary overdue rent from before. Tracing `validateCleanPeriod` (the shared guard used by both the tenant-request→approve path and, until now, `ownerInitiateChange` from ADR-021): it flags a still-unpaid `PENDING`/`PARTIAL` obligation as a blocker under *either* of two conditions — `overlapsNewWindow` (its billing period genuinely overlaps the new schedule's window — the real double-billing risk) **or** `beforeEffective` (its period simply ends before the new effective date — i.e., any older unresolved debt at all, whether or not it has anything to do with the new schedule). The second condition meant the guard effectively blocked the single most common real trigger for wanting a frequency change in the first place: a tenant already behind on the old cadence.
- **Decision:** Added `findOverlappingObligations()` — the same query, but only the `overlapsNewWindow` condition. `ownerInitiateChange` now uses this instead of `validateCleanPeriod`, so it only blocks on a genuine period overlap with the new schedule (double-billing risk), not merely because older debt exists. The old debt is left completely untouched — not superseded, not merged into anything — and stays exactly as collectible as it always was, independent of the new frequency setting. `validateCleanPeriod` itself is untouched and still governs the tenant-request→`approve()` path exactly as before — this is a deliberate divergence, not a shared-logic fix, since the two paths have different risk postures (a request submitted possibly weeks ago being approved now vs. an owner acting on the tenant's *current* state immediately).
- **Alternatives considered:** Also relaxing `validateCleanPeriod` for the tenant-request path (rejected — out of scope for what was reported, and changes intentionally-shipped-earlier behavior without a matching report against it). Trying to fold the old due amount into the newly-computed schedule's first installment (rejected — the periodic path doesn't create `rent_obligations` rows synchronously at all; they're generated later by `rent-generation-service.ts`/`agreement-rent-schedule-service.ts` from the frequency setting, so there is no "first new installment" object to merge into at the point this guard runs. Leaving the old debt as its own untouched obligation is simpler and loses nothing).
- **Consequences:** An owner can now change frequency for a tenant who has ordinary overdue/partial rent, as long as that debt's period doesn't genuinely collide with the new schedule's window. `ownerSetCustomSchedule` (ADR-022) already had the narrower, correct check from the start (`due_date >= effectiveFrom` only, never blocking on already-past due dates) so it needed no change.
- **Related:** [[Bugs]], [[Changelog]], ADR-021, ADR-022

## ADR-022: Custom installment schedules bypass the periodic-frequency generator entirely, rather than waiting on it to be fixed

- **Date:** 2026-07-22
- **Status:** accepted
- **Context:** ADR-021 shipped owner-direct MONTHLY/QUARTERLY/HALF_YEARLY changes but explicitly deferred `CUSTOM_INSTALLMENTS` (an owner-defined list of arbitrary due-date + amount charges) because it looked like it needed the same `agreement-rent-schedule-service.ts` fix as the periodic frequencies. On closer inspection that turned out not to be true: `generateForAgreementInTx` (the function that actually creates monthly rent rows for an agreement) is only ever called twice — once at initial tenant activation, once at renewal activation for a *new* successor agreement (confirmed by grepping every call site) — it never re-runs for an already-signed agreement. That means anything created directly as `rent_obligations` rows today, for a currently-signed agreement, will never be silently duplicated or overwritten by that generator later.
- **Decision:** `BillingTransitionService.ownerSetCustomSchedule()` doesn't try to make the periodic generator frequency-aware — it sidesteps it. Given a list of `{due_date, amount, label?}`, it: validates (positive amounts, dates today-or-later, no duplicates, max 24), refuses if any already-activated obligation (PENDING/PARTIAL/OVERDUE) with a real balance falls on/after the first installment date (same "don't silently sweep away real debt" rule as the periodic path's clean-period check, just obligation-level instead of period-level since there's no fixed period shape to check against), then in one transaction: supersedes the tenant's future UPCOMING RENT obligations from the first installment date onward and creates the owner-specified rows directly (status `UPCOMING`, activated normally later by the existing `syncDueStatuses` sweep — no new activation logic needed). Also fixed a related bug caught while building this: `ownerInitiateChange` (ADR-021) and this new method were each opening their own `prisma.$transaction` internally while their routes *also* wrapped them in an outer transaction for identity-token consumption — nested/separately-committing transactions, meaning a token could be marked consumed even if the outer transaction later failed for an unrelated reason. Both now take an optional `identityJti` and consume it as the first write inside their own single transaction; the routes no longer wrap them in anything.
- **Alternatives considered:** Teaching `agreement-rent-schedule-service.ts` to understand `CUSTOM_INSTALLMENTS` as a schedule shape it can generate from (rejected — unnecessary complexity given the generator's one-shot call pattern already makes direct obligation creation safe; would also require solving the exact same problem ADR-021 deferred for periodic frequencies, for no added benefit here). Requiring the custom schedule's total to reconcile with the tenant's remaining contracted rent (rejected — a custom schedule is explicitly for cases where the owner and tenant have agreed to deviate from the standard cadence/amount, e.g. a hardship arrangement; enforcing reconciliation would defeat the point).
- **Consequences:** Custom Dates works correctly today for both agreement and non-agreement tenants — it has none of ADR-021's "doesn't take effect yet" caveat. `ChangeFrequencyModal.tsx` reflects this: the agreement-tenant warning banner only shows for the Recurring tab, not Custom Dates.
- **Related:** [[Bugs]], [[Business-Rules]], [[Changelog]], ADR-021

## ADR-021: Owner can change a tenant's billing frequency directly — same guards as the tenant-request path, minus the wait

- **Date:** 2026-07-22
- **Status:** accepted
- **Context:** `billing-transition-service.ts` only supported a tenant-request → owner-approve flow for changing billing frequency (monthly/quarterly/half-yearly), governed the same way as other Category C contractual fields (`field-classification.ts`). ## ADR-017: Payment links are amount-flexible and tenant-scoped, not obligation-locked

- **Date:** 2026-07-21
- **Status:** accepted
- **Evidence:** `src/services/payments/payment-link-service.ts::getOrCreateToken` previously required resolving a `tenantId` to exactly one `PENDING`/`PARTIAL` obligation, throwing `"No outstanding rent obligations found for this tenant"` otherwise; `payment_link_tokens.obligation_id` was a required FK with no `amount` column, and the online checkout path (`createMultiObligationPaymentIntent`) always charged that one obligation's full remaining balance.
- **Decision:** A payment link now maps to a tenant, not an obligation. `obligation_id` became an optional default-amount hint. The payer enters any amount on the link's page; the backend FIFO-allocates it across the tenant's outstanding obligations via `buildSettlementPlan` — the same engine the offline "Receive Payment" flow already used — with any excess credited as future rent, via a new `createAmountPaymentIntent` function that mirrors `createMultiObligationPaymentIntent` but starts from a raw amount instead of a pre-picked obligation list. Both owners and tenants can generate a link.
- **Alternatives considered:** Synthesizing a placeholder `rent_obligations` row for the entered amount — rejected, since obligations are the audit-first source of truth for money owed and a synthetic row would pollute every dues/report calculation that reads obligations. A separate parallel "flexible link" type that always books as future credit — rejected, since a payer with real current dues would have their payment misfiled as advance credit instead of clearing what they actually owe.
- **Consequences:** The online (Razorpay) and offline (manual "Receive Payment") payment paths now converge on the same FIFO allocation engine for the first time, rather than diverging (online was previously obligation-first-only, offline was amount-first-only). A payment link generated from a specific obligation card is no longer a hard guarantee that payment will apply to only that obligation — it's a default-amount suggestion. Full design: `docs/superpowers/specs/2026-07-21-flexible-payment-links-design.md`.
- **Related:** [[Business-Rules]], [[APIs]], [[Database]]

## ADR-006: The multi-hostel SaaS billing/subscription model was removed in favor of a single-business model

## ADR-009: Expense export is a decoupled service (not route-embedded logic), built on a shared query builder, with format-specific streaming strategies

- **Date:** 2026-07-18
- **Status:** accepted
- **Context:** The Expense Export feature requires CSV/XLSX/PDF output that is guaranteed to match whatever filters the owner has applied in the UI, must not load unbounded record sets into memory, and needs to stay extensible toward future scheduled exports / saved report templates without a later redesign.
- **Decision:**
  1. Extract the expenses list WHERE-clause construction out of `expense-service.ts::getAllExpenses` into a standalone exported function, `buildExpenseLedgerWhere()`, and have both the list endpoint and the new export service call it — one filtering implementation, not two that can drift.
  2. Put all export logic in a new `lib/services/expense-export-service.ts` that takes/returns plain data (no `NextRequest`/`Response`), so the HTTP route (`app/api/expenses/export/route.ts`) is a thin adapter; a future cron or template runner can call the same functions directly.
  3. Pick the streaming strategy per format rather than one-size-fits-all: CSV is hand-rolled (trivial to stream correctly, no library needed), XLSX uses `exceljs`'s `WorkbookWriter` (true incremental zip writing — the existing `xlsx`/SheetJS dependency can't stream writes in its free edition), and PDF (`pdf-lib`, matching the existing receipt-PDF convention) is treated as a capped-row business report rather than an unbounded stream, since PDF isn't a practical format for arbitrary-size tabular dumps.
- **Alternatives considered:** Reusing the `xlsx` package for XLSX export (rejected — would require buffering the full row set in memory before writing, defeating the memory-bounded requirement for large exports). Embedding export logic directly in the route handler (rejected — the explicit "modular, no redesign for future scheduled exports" requirement argues for a decoupled service from the start).
- **Consequences:** One more npm dependency (`exceljs`, moderate-severity transitive `uuid` advisory, no direct vulnerability) in exchange for correct streaming behavior. Any future change to expense filtering must go through `buildExpenseLedgerWhere()` — a filter added only to the list route's inline logic would silently not apply to exports, so this is now a single deliberate touch-point to keep in mind.

## ADR-010: Expense export financials reuse the dashboard's calculation functions, parameterized by period — never a second implementation

- **Date:** 2026-07-18
- **Status:** accepted
- **Context:** The expense export's Financial Summary needed Revenue/Net Profit/Expense Ratio/largest-expense figures. Two options existed: literally reuse the dashboard's current "this month" KPI numbers regardless of what period the export covers, or reimplement the calculation independently, scoped to the export's own filters. Both were rejected — the first would print a report whose stated "Reporting Period" and whose Revenue figure describe two different windows (e.g. exporting "Last Quarter" but showing this month's revenue); the second is exactly the "~6 independent calculators" drift pattern [[Decisions]] ADR-001 already fixed once for tenant financials, now at risk of recurring for business expenses.

Same formulas and query shape everywhere; only the date window and expense total each caller supplies differ — verified by a dashboard-vs-export parity test in `tests/expense-export.test.ts`.
- **Alternatives considered:** (1) Export always shows today's dashboard figures — rejected, described above. (2) Independent revenue query in the export service — rejected as reintroducing the exact drift risk ADR-001 was written to prevent, just in a new domain.

Any future business-expense financial figure shown anywhere (dashboard, export, or a future surface) must be added to these shared functions, not computed locally.

## ADR-012: Every renewal chain mutation uses `SELECT ... FOR UPDATE` + conditional `updateMany` + count check — no third variant

- **Date:** 2026-07-19
- **Status:** accepted
- **Context:** The Agreement Renewal subsystem has three call sites that can mutate the `renewed_from_agreement_id`/`renewed_to_agreement_id` chain and/or transition a draft to `SIGNED`: `AgreementRenewalService.createRenewalDraft` (manual draft creation), `AgreementRenewalSigningService.signRenewalAgreement` (manual signing), and — after this pass — `AgreementLifecycleService.activateScheduledRenewals` (cron activation) and `RenewalOfferService.acceptOffer` (offer acceptance). The first two already used a `SELECT ... FOR UPDATE` row lock followed by a conditional `updateMany` whose `.count` is checked (throwing on mismatch) before proceeding. The latter two didn't: cron activation used unconditional `update()` calls with no lock, and offer acceptance checked `offer.status` before opening its transaction (a stale read) and linked the predecessor via an `updateMany` whose count was never checked — both allowed a concurrent writer to silently corrupt the chain (e.g. an orphaned, unlinked successor `Agreement`) instead of failing loudly.
- **Decision:** All four call sites now use the identical pattern: lock the predecessor (and, where a second row is mutated, the draft) with `SELECT ... FOR UPDATE` at the top of the transaction, re-read anything checked pre-transaction fresh inside the lock (closing the TOCTOU window), and replace every `update()` on a row whose eligibility could have changed concurrently with `updateMany()` gated on that eligibility, checking `.count !== 1` and throwing to roll back the transaction on a mismatch.
- **Alternatives considered:** A Postgres unique constraint on `renewed_from_agreement_id`/`renewed_to_agreement_id` alone (rejected as insufficient on its own — it would catch a duplicate *link* but not an unconditional status-overwrite race, and this repo's stated policy is "review transactions/locking/update conditions/schema constraints where appropriate" rather than a schema-only fix). A dedicated advisory lock per tenant/agreement (rejected — `SELECT ... FOR UPDATE` on the specific row already serializes exactly the contention that matters and matches the pattern already proven out in this subsystem, so introducing a second locking primitive would be pure divergence).
- **Consequences:** Any future renewal-chain-mutating code path must follow this same pattern (lock → fresh re-check → conditional `updateMany` → count check) rather than inventing a fourth variant. A losing concurrent request now gets a clear thrown error (`CONFLICT: ...` / `Renewal chain changed during cron activation (...)`) instead of silently succeeding into a corrupted state.
- **Related:** [[Bugs]], [[Backend]]

## ADR-013: A renewal's expiry-reminder stage is suppressed once a successor agreement exists

- **Date:** 2026-07-19
- **Status:** accepted
- **Context:** `RenewalStatusService.determineRenewalStage` computed 30-day/15-day/expiry-day/overdue WhatsApp reminder stages purely from the predecessor agreement's own days-until-expiry / days-overdue, without checking whether the tenant had already accepted a renewal offer (or an owner had already created a manual renewal draft). `RenewalDecisionService.evaluateAgreement` already computes `has_successor` for exactly this purpose (used elsewhere to compute `renewal_blocked_reason: "SUCCESSOR_EXISTS"`), but `determineRenewalStage` never consulted it — so a tenant who had already renewed kept receiving "please renew" nudges on the agreement they'd already acted on, right up until the predecessor's actual expiry date.
- **Decision:** `determineRenewalStage` now returns `null` immediately whenever `decision.has_successor` is true, before evaluating any day-count band. This is a full suppression, not a softened message — once a successor exists, the predecessor's expiry-reminder concern is fully superseded; the tenant is now waiting on the successor's own activation (cron `activateScheduledRenewals` or manual signing), which is communicated through a different flow.
- **Alternatives considered:** Softening the message copy to acknowledge a pending renewal while still sending (rejected — adds template/payload complexity for a stage that's simply no longer relevant) — Scoping the fix to only `RenewalStatusService`/WhatsApp rather than also touching the plain in-app 30d/15d notifications in `AgreementLifecycleService.processDailyLifecycle`'s main loop, which has the identical gap (deferred — out of scope for the specific bug as reported; flagged as a discovered adjacent issue for a follow-up decision rather than silently expanding scope).
- **Consequences:** Any future renewal-adjacent notification path (in-app, email, SMS) that fires based on days-until-expiry should apply the same `has_successor` guard, or it will reintroduce this exact bug independently.

## ADR-014: Renewal reminder stages use threshold bands, relying on delivery-layer idempotency, instead of exact-day matching

- **Date:** 2026-07-19
- **Status:** accepted
- **Context:** `RenewalStatusService.determineRenewalStage` matched reminder stages with exact equality (`daysUntilExpiry === 30`, `=== 15`; `daysOverdue === 7`, `=== gracePeriodDays`). If the daily lifecycle cron missed a single run — an outage, a deploy window, a transient failure — the day counter moved past the exact trigger value before the next run, and that stage was silently skipped forever; the tenant/owner never got that reminder for that agreement.
- **Decision:** Reminder/overdue-milestone stages now use inclusive threshold bands instead of exact equality: `30_DAY_REMINDER` for `16–30` days remaining, `15_DAY_REMINDER` for `1–15`, `7_DAY_OVERDUE` for `≥7` days overdue, `30_DAY_CRITICAL` for `≥grace_period_days` days overdue (checked first, so it takes priority over `7_DAY_OVERDUE` rather than double-matching). This is safe *because* `whatsAppTemplateDeliveryService.send()` already enforces per-`(stage, agreementId)` idempotency via a DB unique constraint (`whatsapp_logs.idempotency_key`, `ON CONFLICT DO NOTHING`) — a stage matching on several consecutive cron runs (because the tenant's day-count sits inside its band for more than one day) still only ever sends once. `EXPIRY_DAY_ALERT` (`daysUntilExpiry === 0`) and `EXPIRED_RENT_OVERDUE` (a rent-overdue *state* check, not a day-count) were deliberately left unchanged — see the "Alternatives considered" note.
- **Alternatives considered:** Also broadening `EXPIRY_DAY_ALERT` into a multi-day catch-up band, e.g. `1 ≤ daysOverdue < 7` (rejected — verified by hand against the existing test suite that this collides with `EXPIRED_RENT_OVERDUE`'s fallback: an agreement 6 days overdue with actual overdue rent would incorrectly report "Expires Today" instead of "Rent Overdue," breaking `tests/whatsapp-renewal-notification.test.ts`'s pre-existing `"sends EXPIRED_RENT_OVERDUE alert..."` case). Adding a persisted "last reminder stage sent" column to `Agreement` to drive catch-up logic explicitly (rejected as unnecessary — the existing idempotency-key mechanism already provides exactly-once delivery per stage without a schema change).
- **Consequences:** A tenant/owner may now receive a given reminder stage on a later day than the "ideal" one if cron was down on the ideal day, but they will always receive it exactly once rather than potentially never. Verified by hand that all 6 existing exact-day test cases in `whatsapp-renewal-notification.test.ts` still resolve to the same stage under the new bands (each exact value is the boundary of exactly one band).
- **Related:** [[Bugs]], [[Business-Rules]]

## ADR-015: Renewal readiness and activation logic consolidated into two shared engines, replacing three hand-duplicated implementations

- **Date:** 2026-07-20
- **Status:** accepted
- **Context:** Three call sites independently re-implemented overlapping "is this renewal eligible/ready" validation: `AgreementLifecycleService.activateScheduledRenewals` (cron), `AgreementRenewalSigningService.signRenewalAgreement` (manual signing), and `AgreementRenewalService.createRenewalDraft` (manual draft creation) — each with its own copy of the predecessor-renewable, chain-consistency, move-out, lifecycle-complete, and deposit checks, in slightly different orders and with slightly different query freshness. Separately, the two activation paths (cron and manual signing) each hand-rolled the full activation mutation sequence (lock rows, transition predecessor to `RENEWED`, transition successor to `SIGNED`, sync `tenants` contract fields, generate the rent schedule) — this was flagged as a deferred "P2: eliminate duplicated activation logic" item in the immediately-preceding bug-fix pass (`docs/superpowers/plans/2026-07-19-agreement-renewal-bugfixes.md`) and independently re-surfaced as gap-analysis §1.7/§1.8 ("Readiness Engine and Activation Engine are the same refactor, not two") — see `docs/business-logic/renewal-management-workspace-gap-analysis.md`.
- **Decision:** Introduced `renewal-readiness-engine.ts` (individual pure/async check functions — `checkPredecessorRenewable`, `checkChainConsistent`, `checkNoActiveMoveOut`, `checkLifecycleComplete`, `checkNoUnpaidDeposit`, `checkNoExistingSuccessor` — plus two orchestrators, `evaluateActivationReadiness` and `evaluateCreationReadiness`, each running its full check set and returning *all* failures rather than stopping at the first) and `renewal-activation-engine.ts` (`activateRenewal()` — locks both rows, runs `evaluateActivationReadiness`, then performs the predecessor/successor status transitions, `tenants` sync, and rent-schedule generation). All three original call sites now delegate to these; each retains only what's genuinely specific to it: cron builds its "copy predecessor's signature forward" successor payload, manual signing builds its "fresh e-signature + freshly-resolved template/rules" payload, and each call site maps the engines' generic `ReadinessFailure`/`RenewalChainRaceError` back to its own existing typed error codes and messages, preserving each surface's exact prior error contract.
- **Alternatives considered:** Forcing full unification of the signature/rules-resolution logic too (rejected — cron's copy-forward and manual signing's fresh-resolve are deliberately different behaviors per Business-Rules §13, not incidental duplication; unifying them would be a business-rule change, not a refactor). Keeping cron's weaker checks as-is to minimize diff size (rejected — cron was missing the chain-consistency check that manual signing already had, and checked the deposit obligation via a pre-transaction snapshot instead of a lock-fresh read; both were closed as part of this consolidation, using the already-proven-correct pattern from the sibling path, not a new rule).
- **Consequences:** Manual signing now also syncs `tenants.monthly_rent/security_deposit/maintenance_charge` (previously only cron did — closes the gap found during the post-bugfix flow audit). Two internal `RENEWAL_ACTIVATION_BLOCKED` reason strings were unified to one canonical wording each (cosmetic log-message text, not a behavior change; the blocking *condition* was already identical). A future 4th consumer of these checks (e.g. an "explain why this renewal is blocked" UI or AI-assistant endpoint per gap-analysis §1.13) can call `evaluateActivationReadiness`/`evaluateCreationReadiness` directly and get the full failure list, not just the first.

## ADR-016: Renewal Timeline is a new append-only `RenewalTimelineEvent` table, written inside the same transaction as the mutation it describes

- **Date:** 2026-07-20
- **Status:** accepted
- **Context:** Per the gap analysis (`docs/business-logic/renewal-management-workspace-gap-analysis.md` S1.6), owner-side renewal actions (offer created, sent, revised) had zero persisted, queryable audit trail — only `logger.info()` lines, gone once log retention rotates. Tenant-side actions were only partially captured in `RenewalDecision` (no actor-role field, no `VIEWED` event, and `discussOffer()` overloaded the `RenewalOfferStatus.SENT` enum value to mean "tenant requested discussion," unrelated to its literal meaning). Separately, the gap analysis's cross-cutting finding #1 — independently rediscovered from the same finding in `docs/business-logic/operation-recovery-undo-system-proposal.md` S0 — is that this codebase's existing generic audit log (`eventLog.log()` / `systemEventLog`) always writes via the top-level `prisma` client, never a passed-in `tx`, so it is not transactionally coupled to the mutation it describes even when called from inside one.
- **Decision:** Added `RenewalTimelineEvent` (new table, migration `20260720000000_renewal_timeline_events`) — `hostel_id`/`tenant_id`/`agreement_id`/`offer_id` foreign keys, `RenewalTimelineEventType` (10 values covering the full offer + activation lifecycle), `RenewalTimelineActorType` (OWNER/TENANT/SYSTEM), free-text `reason`, JSON `metadata`. New `renewal-timeline-service.ts` (`registerEvent(tx, params)`) is called from inside the same transaction as the mutation it describes at every write site: `generateOffer`, `generateBulkOffers`, `sendOffer`, `acceptOffer`, `declineOffer`, `discussOffer`, `reviseOffer`, `expireStaleOffers` (all in `renewal-offer-service.ts`), `createRenewalDraft` (`agreement-renewal-service.ts`), and `activateRenewal` (`renewal-activation-engine.ts`, so both cron and manual signing get the `RENEWAL_ACTIVATED` event for free). `registerEvent()` deliberately does not swallow its own errors — a failed timeline write rolls back together with the mutation it describes, rather than silently drifting from it, directly closing the "audit writes must be transactionally coupled" finding.
- **Alternatives considered:** Generalizing `recovery_events`/`change_request_events` (from the not-yet-approved Undo proposal) into a shared "domain event log" both subsystems use (this was gap-analysis open question #2) — rejected for now: coupling this shipped work to another proposal's not-yet-approved, not-yet-implemented schema would block this feature on an unrelated decision. A bespoke, purpose-built table is the lower-risk choice today; nothing prevents a future migration onto a shared event-log table if the Undo proposal is approved. Extending `RenewalDecision` to also carry owner-side events (rejected — it's fundamentally shaped around tenant decisions, `decision: RenewalOfferStatus`; bending it to fit owner actions would repeat the exact enum-overloading problem already flagged in `discussOffer()`).
- **Consequences:** Three previously-non-transactional write paths (`generateOffer`, `sendOffer`, `discussOffer`) are now wrapped in `$transaction` for the first time, so their single write plus the new timeline write commit or roll back together — a minor, low-risk structural change (single-statement transactions), not a business-rule change. `expireStaleOffers()` changed from one bulk `updateMany` to a `findMany` (to capture per-offer IDs) followed by a scoped `updateMany` inside a transaction — same net effect, same idempotent WHERE clause, now with a per-offer `OFFER_EXPIRED` event. `createRenewalDraft`'s `DRAFT_CREATED` event and `RENEWAL_ACTIVATION_BLOCKED` events are recorded with actor `SYSTEM` since neither call site currently receives caller-identity information through its API — a future pass threading real actor identity through those routes would only need to change the `timelineActor`/event call, not the storage model.
- **Related:** [[Bugs]], [[Database]], [[Business-Rules]], ADR-015 (the engine consolidation this timeline instrumentation builds on top of)

## ADR-029: Food schedules are modeled as a repeating weekly pattern per month, not calendar-dated rows; voting is single-choice per meal type; the existing generic Food Polls feature stays as a separate, untouched feature

- **Date:** 2026-07-26
- **Status:** accepted
- **Context:** The Food tab's Monthly Schedule sub-tab was 100% mock (a client-side Week1-4 rotation, `buildSchedule.ts`, ignoring any tenant input) with no backend at all. The user specified a full replacement: owner maintains a food-item library per meal type → opens monthly voting → tenants vote → owner generates a weekly Mon-Sun timetable from the vote results → owner reviews/edits → publishes → tenant dashboard updates immediately, including on any later edit, with no separate "republish" step → next month auto-carries-forward the previous published schedule as a draft. Three design questions had to be resolved before building: (1) how a schedule's 7 days relate to a calendar month (which has 4-5 real weeks, not one), (2) whether a tenant's vote is single- or multi-select per meal type, (3) whether this new system replaces or coexists with the pre-existing generic "Food Polls" feature (arbitrary single/multi/rating/yes-no owner-created polls, `CreatePollModal`/`PollResultsSheet`/`useFoodPolls`, unrelated in shape to menu voting).
- **Decision:** (1) `food_schedules` is one mutable row per `(hostel_id, month)` representing a **repeating weekly pattern** — 7 `FoodDayOfWeek` × 4 `FoodMealType` = 28 `food_schedule_meals` rows, not calendar-dated. This directly matches the spec's own wording ("a weekly timetable," singular) and makes every other requirement fall out for free: "publish" is a status flip (`DRAFT`→`PUBLISHED`) on the same row; an edit made after publishing is immediately live with no republish step, because there is only ever one row per month, not a version chain; and carry-forward is a straight 28-row clone into a new month's row. (2) Voting is **multi-select per meal type** — one `food_votes` row per `(voting_period_id, tenant_id, meal_type, menu_item_id)`, toggled on/off per item — see the 2026-07-26 revision note below; this superseded an initial single-choice design from the same day. (3) The new voting-driven system and the existing generic Food Polls feature **coexist, unmodified relative to each other** — per explicit user choice ("keep both," not "replace it"). `FoodPage.tsx`'s existing Monthly Schedule / Food Polls toggle is preserved as-is; only the Monthly Schedule side was rebuilt.
- **Revision (2026-07-26, same day):** Vote granularity was reversed from single-choice to multi-select per meal type, per explicit user direction ("tenants can vote for multiple food items per meal type, allowing the generator to build a balanced weekly schedule from collective preferences"). Schema change: `food_votes`'s unique constraint widened from `(voting_period_id, tenant_id, meal_type)` to `(voting_period_id, tenant_id, meal_type, menu_item_id)`, so a tenant can hold multiple vote rows within one meal type instead of exactly one. `POST /api/food/tenant/vote` changed from upsert-overwrite (change your one pick) to toggle (add/remove one item's vote), since there is no longer a single "current pick" to overwrite. The vote-tally step in both `voting-periods/[id]/results` and `schedules/generate` (`groupBy` on `menu_item_id`) needed **no change** — it already counted votes per item regardless of how many items one tenant could vote for, so the generation algorithm and its balanced-schedule behavior are unaffected by this reversal. Tenant UI changed from radio-style single-selection to checkbox-style multi-selection (`useTenantFoodVoting`'s `myVoteBySlot: Record<slot, itemId>` became `myVotesBySlot: Record<slot, Set<itemId>>`; `castVote` became `toggleVote`).
- **Alternatives considered:** Calendar-dated schedule rows (one row per actual date, `food_schedules` keyed by date not month) — rejected: the spec's "weekly timetable" language and the publish/edit-propagates/carry-forward requirements are all far simpler against a single repeating-pattern row than against 4-5 dated rows per month that would need to individually track publish state and repeat/vary content. Merging/replacing Food Polls with the new system — rejected by explicit user pick; the two remain product-distinct (structured monthly menu-item voting vs. ad hoc owner-created polls of any shape).
- **Consequences:** A schedule cell has no notion of "this specific Tuesday the 14th" — only "Tuesday, this month's pattern" — so any future requirement for date-specific one-off overrides (e.g. "special dinner on the 25th") would need a new, separate mechanism, not an extension of `food_schedule_meals`. The carry-forward cron's "clone from previous month" branch was not exercised against a real prior published month at build time (only its idempotent no-op branch was live-verified) — see [[Features]], [[Changelog]] for the testing-gap note. Food Polls remains entirely mock/unwired; a future decision to build it for real is untouched by this ADR either way.
- **Related:** [[Database]] (`food_menu_items`/`food_voting_periods`/`food_votes`/`food_schedules`/`food_schedule_meals`), [[APIs]] (`/api/food/*`), [[Features]], [[Changelog]]

## ADR-030: The Platform Admin Console deliberately reverses ADR-006 — multi-hostel SaaS billing/subscription is back, per explicit user direction

- **Date:** 2026-07-26
- **Status:** accepted
- **Context:** A new design source, `Stayo Admin Dashboard/Stayo Admin.dc.html`, specifies a full "platform admin" persona: approving hostel-owner signups and hostel *listings* across many different owner businesses, tracking MRR/ARR/churn/ARPU, billing owners a recurring subscription fee to use Stayo, generating GST reports on that platform revenue, and managing platform staff accounts. This is unambiguously a multi-tenant SaaS marketplace model. ADR-006 documents that this exact model — subscription/plan/add-on/usage-quota concepts for multiple owner-businesses — was deliberately removed from this codebase (`20260517000000_decommission_saas_tables`, 37 tombstoned `410 Gone` routes) in favor of treating each deployment as a single owner's business. Before starting any implementation, the user was directly told, in these terms, that building the Admin Dashboard as designed would reverse that documented decision, and was offered three explicit options: (1) build the full SaaS platform-admin model as designed, (2) build a scoped-down internal ops console for the current single-business model instead (no cross-owner billing/leads), or (3) defer Admin entirely and ship only the tenant-app work in this pass. **The user chose option (1) — full reversal — explicitly and with the tradeoff stated up front.**
- **Decision:** Built the Platform Admin Console as designed. `Role` gained a real `ADMIN` value (previously present only in abandoned migration history, never actually assignable — `schema.prisma` had only `OWNER`/`TENANT` immediately before this). New schema: `platform_admins` (staff sub-roles), `platform_leads` (prospective hostel *owners*, distinct from the pre-existing tenant-admissions `leads` table), `subscription_plans` + `hostel_subscriptions` + `platform_invoices` (the reintroduced marketplace billing model — deliberately reshaped around "marketplace tier" rather than the old metered-usage shape ADR-006 removed, not a literal restoration of the dropped tables), `notification_templates`, `platform_settings`, plus `hostels.verification_status`/`listing_status`. No public self-serve admin signup (`scripts/bootstrap-platform-admin.ts` creates the first one) — matches the security posture already established for owner bootstrap (ADR-028's `ALLOW_OWNER_BOOTSTRAP` gate). All `/api/platform-admin/*` routes are deliberately **cross-owner** and excluded from `architectural-invariants-check.ts`'s owner-scoping checks, since those checks exist to catch OWNER-scoped code silently leaking cross-owner data — a concept that doesn't apply to a persona whose entire purpose is seeing everything.
- **Alternatives considered:** The two declined options are recorded above rather than omitted, since the user's choice among them is the load-bearing fact of this ADR — a future reader needs to know this wasn't a default or an oversight. Reusing the exact table shapes ADR-006 dropped (`plans`, `owner_subscriptions`, `owner_invoices`, etc.) instead of new tables — rejected: those tables were designed around a different (metered/usage) billing philosophy, and this feature's design source specifies flat marketplace tiers instead; resurrecting the old shape verbatim would have been a worse fit, not a savings.
- **Consequences:** This codebase now simultaneously supports two different business-model framings that don't fully reconcile: the core tenant/rent/payment domain remains single-business-oriented (per ADR-003's `hostelId`-required invariant, e.g.), while the new platform-admin layer assumes multiple independent owner-businesses coexist on one Stayo deployment. No attempt was made to unify these — the new tables are additive and the old single-business invariants are untouched. A future reader should not assume the presence of `hostel_subscriptions` means the rest of the system is multi-tenant-aware; it isn't. `/api/admin/finance-ops/*` (an older, separate ADMIN-gated subsystem, see [[APIs]]) is incidentally no longer unreachable now that `ADMIN` is a real role, though it remains functionally unrelated to `/api/platform-admin/*` and still has no confirmed frontend consumer. A real, previously-latent bug was found and fixed while building the Broadcast Notice feature: `notifications.id` had no schema default, so `NotificationService.createNotification()` had always failed silently everywhere in the codebase it was called (not just this new feature) — see [[Bugs]].
- **Related:** [[Database]], [[APIs]] (Platform Admin Console), [[Features]], [[Bugs]], ADR-006 (the decision this reverses), ADR-028 (the bootstrap-gate precedent this follows)

## ADR-033: Trishul Solutions is the operating company; Stayo is its product — a company-identity layer, not a rebrand

- **Context:** Ahead of production launch and Meta Business Verification / WhatsApp display-name approval, the public site presented three conflicting identities: the live premium "Stayo" marketplace, leftover "Sri Adithya Boys Hostel" single-hostel branding (SEO, JSON-LD, legacy navy sub-pages), and three different domains (`stayo.app`, `sriadithyahostels.in`, `yourstayo.com`). Legal pages also carried an individual's personal name/Gmail/mobile as the grievance & data officer. Conflicting identity and non-domain-matched contact are common Meta/WhatsApp rejection causes.
- **Decision:** Establish a single hierarchy — **Trishul Solutions (company / AI software company) → Stayo (flagship product)** — as an additive identity layer, *without* redesigning the product or changing its visual language. Canonical domain standardized to **`yourstayo.com`**; all `stayo.app` and `sriadithyahostels.in`/"Sri Adithya" references removed. Public email scheme: `contact@` / `support@` / `privacy@` / `legal@ yourstayo.com`; personal PII removed from legal pages and replaced with the entity + role labels. New `/company` page + `src/content/company.ts` (single source of truth, products-array-driven for future multi-product scaling), a shared `MarketingFooter`, an inlined `TrishulMark`, a hero trust line, footer attribution ("Stayo is developed and operated by Trishul Solutions"), and `index.html` structured data reworked to an `Organization` (Trishul Solutions) that `publisher`-links a `SoftwareApplication` (Stayo). Two values are intentional placeholders (`{{REGISTERED_BUSINESS_ADDRESS}}`, `{{BUSINESS_PHONE}}`) — never invented.
- **Guardrail reversal:** `scripts/check-production-branding.mjs` previously *forbade* the strings `Trishul`/`Trishul Solutions` (to keep the internal codename out of the customer site). Those bans were removed; the retired identities (`Sri Adithya`, `sriadithyahostels`, `stayo.app`, the personal Gmail) were **added** as forbidden instead — so the build now hard-fails if any conflicting identity leaks back into `dist`.
- **Alternatives considered:** Rebranding Stayo under Trishul (rejected — Stayo must stay the primary customer-facing brand); text-only company wordmark (rejected in favor of a subtle inlined mark for trust, kept secondary to Stayo); leaving legacy navy sub-pages untouched (rejected — they asserted a physical-hostel identity conflicting with the SaaS company).
- **Consequences:** One accepted exception remains in source — `AuthContext.tsx` still calls `localStorage.removeItem('sri_adithya_onboarding_complete')`; the old key name is required to actually purge legacy state from returning browsers, it is internal-only, and it does not match the build guard's `/Sri\s*Adithya/` pattern (underscore), so `dist` stays clean. Real social `sameAs` profiles are still to be supplied. See [[Changelog]], [[Features]], [[Business-Rules]].
- **Update (2026-07-30, same day):** the two placeholders were filled with the real registered values (phone `+91 76750 80090`; the office address was supplied but see below), and `public/og-cover.png` (1200×630) was added. Per explicit follow-up direction, exposed business detail was then **minimised** in three steps: (1) JSON-LD reduced to an `Organization` carrying only name/url/logo/email/telephone + `brand: Stayo` (removed `SoftwareApplication`, `PostalAddress`, `contactPoint`, description, legalName); (2) the Udyam registration number kept out of all public surfaces (JSON-LD, footer, legal, `company.ts`); (3) **the office address removed from every public surface** — Contact, footer, PublicLayout top-bar/footer, legal Terms/contact block, and `company.ts` — with the `/location` "Location & Directions" page repurposed to an online-first "Reach Us" note (no address/map) and dropped from the nav. Public contact is now phone + email/WhatsApp only. Rationale: the user wants a minimal public footprint; the registered address/registration exist on the Udyam certificate for any provider that privately requires them, and can be re-added to legal pages if a payment/Meta reviewer explicitly demands it.
