## ADR-040: A hostel is provisioned in one transaction, and an owner's publish choice is an intent — not a listing status

- **Date:** 2026-08-01
- **Status:** accepted
- **Context:** the onboarding wizard's Publish step created a hostel with `1 + F + (F × R)` sequential HTTP calls — 45 for the default 4-floor/10-room property — against `/api/owner/hostels`, `/api/floors` and `/api/rooms`, with no transaction and no rollback. A failure at floor 3 of 4 committed a partially built hostel; pressing Publish again then hit the owner-scoped duplicate-name guard on `POST /api/owner/hostels` and returned `400 A hostel with this name already exists` forever. The owner was permanently stuck on step 11 of 12, with no path forward inside the wizard. Separately, four fields the wizard collected were never sent anywhere: hostel type, "food available?", the security deposit, and the publish-vs-draft choice; rooms were created with no `base_rent`. Surfaced by the 2026-08-01 owner product integration audit (P0-3).
- **Decision:** two decisions, taken together.
  1. **One endpoint, one transaction.** `POST /api/owner/hostels/provision` → `hostelProvisioningService.provision()`, which does the owner-scoped duplicate check *before* opening a transaction (a conflict is a user-facing 409, not a database failure, and shouldn't hold a connection), then creates the hostel, its floors and one batched `createMany` of rooms per floor inside a single `prisma.$transaction` with a 20s timeout. Either every row lands or none does. The 409 carries the existing `hostel_id` so a client can offer to open it rather than dead-ending — which also unsticks owners left holding a shell hostel by the old flow.
  2. **`publish: "now"` sets `hostels.publish_requested`, not `hostels.listing_status`.** `listing_status = LIVE` is written only by the Platform Admin console, always paired with `verification_status = VERIFIED` (`approve-listing`). Letting onboarding write it would let any owner self-approve their own public listing past platform verification — a real authorization hole, not a modelling preference. The owner's *intent* is recorded separately; the gate stays where it is.
- **Alternatives considered:**
  - *Keep the loop, add client-side retry/resume.* Rejected: it makes the client responsible for database consistency, and cannot clean up rows a failed run already committed.
  - *Make the loop idempotent by upserting on `(hostel_id, room_no)`.* Rejected: it fixes rooms but not the hostel row, so the duplicate-name deadlock survives; and it still leaves a half-built hostel visible between attempts.
  - *Let onboarding set `listing_status = LIVE` and have the admin console demote.* Rejected — fail-open on a verification gate.
  - *`base_rent` optional.* Rejected on explicit product direction: room rent is required business information. A room with no rent shows ₹0 on the room grid and prefills nothing in the invite wizard, so the wizard now asks for a **Starting monthly rent** on the Details step and the schema rejects null. (`z.coerce.number()` is deliberately *not* used for it — that silently turns `null` into `0`, i.e. a free room.)
- **Consequences:**
  - Publish is 1 request instead of ~45, and a failed publish is always safely retryable because it leaves nothing behind.
  - Three new columns on `hostels` (`hostel_type`, `food_included`, `publish_requested`) — see [[Database]].
  - Onboarding gains one required field. Owners who published before this change keep `base_rent: null` on their rooms; nothing backfills them, and per-room rent editing is still unbuilt (audit P2).
  - `publish_requested` has **no consumer yet** — the Platform Admin console does not surface or act on it. It is recorded now so the signal isn't lost a second time; wiring it into the admin approval queue is follow-up work.
  - `POST /api/owner/hostels` is unchanged and still used for non-onboarding creation paths.
  - Provisioning reproduces `POST /api/owner/hostels`'s lead side effect (`leadInvitationService.markHostelCreated`) as a **post-commit** step. Caught by test rather than review: `markLive` — the wizard's trailing `/leads/invitation/:token/complete` — only promotes a lead already at `HOSTEL_CREATED`, so omitting it would have silently stalled every lead-originated owner at `OWNER_ACTIVATED`.
- **Related:** [[APIs]], [[Database]], [[Features]], [[Changelog]], [[Decisions#ADR-032|ADR-032]] (the `OWNER_ACTIVATED → HOSTEL_CREATED → LIVE` lead lifecycle this endpoint must keep driving)

## ADR-039: WhatsApp inbound routing is identity → intent → permission, not owner-assistant-first

- **Date:** 2026-08-01
- **Status:** accepted
- **Context:** every inbound message was handed to `ownerWhatsAppAssistantService.processInboundMessage()` first, whatever it said and whoever sent it. The assistant parsed it as an owner command, found the sender's phone absent from `owner_whatsapp_identities`, logged `unauthorized_owner` and returned `null` — an authorization decision taken *before* anyone had established what was being asked. It happened to be harmless (the message continued to the tenant handlers), but it put the most privileged surface at the front of the pipeline, made the logs read as though ordinary tenant traffic was being rejected, and left no seam where a new role or a model-based classifier could be introduced without editing the routing code itself.
- **Decision:** the pipeline is now **identity → intent(s) → permission → handler → fallback**, in `lib/services/notifications/routing/`.
  - **Identity resolver** (`identity-resolver.ts`) classifies the sender once per message into `OWNER | TENANT | STAFF | ADMIN | UNKNOWN`, returning *all* roles the phone holds (an owner who also rents resolves to both) plus `ownerId`/`tenantIds`. UNKNOWN is a first-class identity, not an error — LINK has to work from a number nobody has seen yet.
  - **Intent resolvers** (`intent-resolvers.ts`) implement one interface and return *ranked candidates*: tapped buttons, then a pending prompt, then LINK, then the owner assistant (for verified owners), then keywords. Order is data, not control flow.
  - **Permission** is checked per intent, from the `allowedRoles` on its registry entry, and only *after* the intent is known.
  - **Handlers may decline.** Returning `null`/`{handled: false}` sends the router to the next candidate, which is how an owner's message that the assistant doesn't recognise still reaches the tenant commands.
  - **Every path replies**: handler result, denial message, error notice, or fallback.
- **Alternatives considered:**
  - **Keep the assistant first and just move the `unauthorized_owner` check inward** (rejected — it fixes the log line, not the shape: authorization still precedes understanding, and there is still no place to add a role or a classifier).
  - **One resolver returning a single intent** (rejected — an owner-tenant sending `DUES` needs two candidates tried in order; single-intent resolution forces a precedence guess at classification time, before any handler has looked at the message).
  - **Permissions inside each handler** (rejected — that is the status quo dispersed across 7000+ lines, and it is why "who may do this" was previously unanswerable without reading every handler).
  - **Bring in an LLM classifier now** (rejected as premature — the seam is what matters. `IntentResolver` is async and returns ranked intents with a `slots` bag, and each registry entry carries a `description` that doubles as a tool description, so a model-backed resolver is appended to the chain without touching the router).
- **Consequences:** `unauthorized_owner` effectively disappears — the assistant is now only consulted for verified owners or an explicit LINK, so it is no longer *asked* about traffic it was always going to refuse. Adding a role is a union member plus `allowedRoles` entries; adding an intent is a registry row. Costs, stated plainly: identity resolution adds up to three queries per inbound message (owner identity, tenants, admin profile) that the old path did not run, and an unrecognised number sending `DUES` now gets an explicit "this number isn't linked" reply where it previously got the balance handler's "no active tenant found" — better copy, but a different message. **STAFF is declared in the union and permission tables but is never produced**: this schema's `Role` enum is `OWNER | TENANT | ADMIN` and there is no staff table to resolve against, so the role is ready but inert.
- **Enrichment (same decision, extended 2026-08-01):** `SenderIdentity` now carries the entity context handlers would otherwise re-query — `ownerId`, `tenantIds`/`hostelIds`, and a `residents[]` of `{tenantId, hostelId, name, status, matchedVia}` — plus derived `permissions` and a `confidence` score. Two deliberate constraints:
  - **`tenantId` and `hostelId` are set only when unambiguous.** A guardian paying for two siblings gets `tenantId: null` and two entries in `residents`. Collapsing that to the first match would be the "first hostel" bug in another costume, which `architectural-invariants-check.ts` exists to prevent.
  - **`confidence` reflects the evidence**: a verified owner link is `1`, a tenant matched on their own handset `0.95`, one matched only through a *guardian's* phone `0.6` — the person holding that phone is probably not the resident. UNKNOWN is `0`.
  Permissions (`billing.read`, `payment.initiate`, `resident.switch`, `owner.console`, `self.service`) are derived from roles and enforced by the router alongside roles, so a capability distinction like "STAFF may read a balance but not start a payment" needs no new branch. `Intent` gained `metadata` (resolver provenance, model, latency, alternatives) and intents may declare `minConfidence` — a model that is 40% sure someone wants to pay now falls through to the fallback instead of sending a payment link. Handlers see none of this unless they ask for it, which is what keeps a resolver swap from touching them.

## ADR-038: Owner KYC is a real upload with an admin-only verified state, in its own table

- **Date:** 2026-08-01
- **Status:** accepted
- **Context:** The onboarding KYC step was three toggles wired to local React state. Tapping one turned it green and the copy read "Required · auto-verified" and "Documents check automatically" — but nothing was uploaded, nothing was stored, and the state vanished on reload. There was no owner KYC endpoint in the codebase at all. An owner could reasonably finish onboarding believing they were identity-verified when no file had ever left their device, which is a trust problem and, for a platform handling rent, a compliance one.
- **Decision:** build the real thing, in a new table.
  - **`owner_documents`**, not `identification_documents`: the existing table is `tenant_id NOT NULL` and FK'd to `tenants`, so it structurally cannot hold an owner's document. Widening it would have meant a nullable tenant link on a table every tenant-document query already trusts.
  - `GET`/`POST /api/owner/kyc-documents`, uploading to ImageKit through the same path `hostels/[id]/logo` already uses — no second upload mechanism.
  - **`status` is always `PENDING` on upload**, and nothing in the request can set it. Only an admin review may move it to `VERIFIED`; the uploader can never assert their own verification, which was precisely the old UI's failure.
  - **Re-uploading supersedes rather than overwrites**: the previous row is flipped `is_active = false` and kept. A unique index on `(profile_id, doc_type, is_active)` enforces exactly one active document per type while preserving what was submitted before.
- **Alternatives considered:** widening `identification_documents` with a nullable `tenant_id` (rejected — it weakens a constraint that every existing tenant-document query depends on, to serve a different actor). Storing files as base64 in Postgres (rejected — ImageKit is already the document store, and identity documents do not belong in the primary database). Leaving the toggles and only correcting the copy (rejected as a stopgap: the step would still collect nothing, so "required before you go live" would remain unenforceable).
- **Consequences:** owners can now actually submit Aadhaar/PAN/photo, and Stayo holds verifiable evidence rather than a checkbox. Two things this deliberately does **not** yet do: there is no admin review surface, so documents sit `PENDING` until one is built; and nothing blocks publishing on missing KYC — the copy says "required before you go live" but no gate enforces it. Both are follow-ups, and until the review UI exists no document can ever leave `PENDING`. Files land in a `/owner_kyc` ImageKit folder; locally, with no `IMAGEKIT_PRIVATE_KEY`, the shared mock uploader returns a data URL so the flow is testable end to end.

## ADR-037: The Meta WhatsApp webhook is acknowledged first and processed after the response, at one canonical URL with two mounts

- **Date:** 2026-08-01
- **Status:** accepted
- **Context:** Meta Business/WhatsApp verification requires a fixed callback URL, and the one being registered is `https://yourstayo.com/api/webhooks/whatsapp`. The implementation already existed but was mounted at `/api/webhooks/notifications/whatsapp`, so the URL Meta would call did not resolve. Two further mismatches with the Cloud API's delivery contract: the route ran the *entire* inbound-command pipeline (DB reads, dues computation, outbound Graph API sends) **before** returning 200, and its duplicate guard only short-circuited events already marked `PROCESSED`. Meta retries a delivery it considers unacknowledged, so a slow send made a retry likely, and a retry landing while the first was still `PROCESSING` re-ran the handlers — sending a tenant the same reply twice.
- **Decision:**
  - **One implementation, two mounts.** The handler moved to `lib/services/notifications/whatsapp-webhook-handler.ts`; `app/api/webhooks/whatsapp/route.ts` (canonical) and `app/api/webhooks/notifications/whatsapp/route.ts` (legacy) are both four-line delegations. No logic is duplicated, and an app subscription still pointing at the old path keeps working.
  - **Acknowledge, then process.** Once the signature verifies and the event is durably recorded, the route answers `200` and runs the business logic afterwards (registered with the host's `waitUntil` when one is present, so it survives on Vercel as well as on the long-lived Render process). A handler failure marks the row `FAILED` instead of turning into a 500.
  - **Idempotency is a claim, not a status read.** `claimForProcessing()` is a conditional `UPDATE … RETURNING` that only one delivery can win. A row stuck `PROCESSING` by a crashed process becomes claimable again after 10 minutes; `FAILED` rows are immediately claimable, which is what makes a Meta retry a recovery mechanism rather than a duplicate.
  - **Env names follow Meta's vocabulary, old ones still read.** `WHATSAPP_WEBHOOK_VERIFY_TOKEN` and `META_APP_SECRET` are preferred, falling back to the deployed `WHATSAPP_VERIFY_TOKEN` / `WHATSAPP_APP_SECRET`.
- **Alternatives considered:**
  - **Move the route and let the old path 404** (rejected — whatever is configured in the Meta app today would start failing on deploy, with no signal until messages went missing).
  - **A Next.js rewrite from the canonical path to the old one** (rejected — a rewrite is invisible in the route tree; a reader looking for the webhook Meta calls should find a file at that path).
  - **Keep processing synchronous and rely on Meta's retries** (rejected — retries are the thing that caused double sends; the fix is to stop provoking them).
  - **A durable queue for the deferred work** (rejected as premature — the event row *is* the queue: it persists before the 200, and its status records the outcome).
- **Consequences:** a webhook response no longer depends on how slow the Graph API is. The cost is that a 200 now means "accepted", not "processed" — the outcome lives in `whatsapp_webhook_events.processing_status`, which is where failures must be looked for. Signature failures still answer 401 (and 429 once per-IP abuse limiting trips) and are recorded for audit; a body that cannot even be persisted still answers 500, because Meta's retry is then the only recovery.

## ADR-036: Remove future rent credit — every payment settles a real installment

- **Date:** 2026-07-31
- **Status:** accepted
- **Context:** Paying more than was currently due parked the excess as a balance: the planner returned `future_credit`, and the engine credited it to `tenant_financial_ledger` (`FUTURE_RENT_CREDIT_TOPUP`), with a matching `EXISTING_CREDIT` funding source for spending it back down. That meant money could sit in an abstract balance that no installment accounted for, and owners had two different mental models for "what has this tenant paid". Requested directly by the product owner: payments should be marked against installments, full stop.
- **Decision:** the credit balance is removed from the payment path entirely.
  - The planner's `future_credit` becomes **`unallocated`** — money it could not place on any obligation, which is an *error condition*, never a balance.
  - The engine's two ledger branches (the topup credit and the `EXISTING_CREDIT` debit) are deleted along with `fundingSource`, and a plan with `unallocated > 0` is refused (`BAD_REQUEST`).
  - Before planning, an amount exceeding what is due generates the tenant's next installment(s) from their ACTIVE agreement via a new **tenant-scoped** `rentGenerationService.ensureInstallmentsForTenant`, then re-reads so the planner allocates across them.
  - If the agreement cannot yield further installments (ended, or absent), the payment is **rejected** rather than parked.
  - The settlement invariant becomes `Paid = ΣAllocations` exactly, with no credit term.
- **Alternatives considered:**
  - **Cap the amount at what is currently due** (rejected by the product owner — it refuses money the tenant is genuinely handing over).
  - **Keep a small "unapplied" balance until an installment exists** (rejected — that is future credit under another name, the exact thing being removed).
  - **Call the existing `generateMonthlyRent()` from the payment path** (rejected on evidence: it is hostel-wide and month-locked, so collecting one tenant's advance would have created next month's rent for *every* tenant in that hostel, inflating their dashboards and potentially triggering reminders).
  - **Reuse `rent_generation_ledgers` for idempotency** (rejected on evidence: its key is `(owner, hostel, month)`, so marking it from a single-tenant path would make the monthly cron skip the whole hostel. The real guard is the pre-existing `@@unique([agreement_id, rent_month, obligation_type])` constraint, and the cron already tolerates pre-existing rows via `existingSet` + `createMany({ skipDuplicates: true })`).
- **Consequences:** every rupee is now traceable to an installment, and the owner's "outstanding" is the whole story. Costs, stated plainly: **recording a payment can now create obligations**, which is new coupling between the payment path and rent generation (scoped to the paying tenant, and idempotent); and **the system will now refuse money** when a tenant tries to pay past the end of their agreement. Period maths reuses `billingScheduleService.buildInstallment`, the same computation the cron uses, so labels/sequences/due dates stay identical. Retained-but-dead for now, to avoid a migration on an empty table: `payment_groups.future_credit_amount` (always `0`), three `FinancialLedgerReason` enum values, and `/api/verify/receipt`'s ledger read (always `0`). Safe because `tenant_financial_ledger` was verified **empty (0 rows)** before the change — this was a code change with no balances to migrate.
- **Open question — one credit writer deliberately left in place:** `renewal-offer-service.ts` still writes `FUTURE_RENT_CREDIT_TOPUP` when a renewal offer's `deposit_refund_policy` is `KEEP_AS_CREDIT` — carrying an excess *security deposit* forward. That is not a rent overpayment and it is driven by an explicit owner choice in the renewal UI, so removing it would silently break that option. **Needs a product decision:** should `KEEP_AS_CREDIT` now settle the excess deposit against the tenant's next installment(s) instead, be forced to `REFUND`, or remain the one legitimate credit? Until decided, this is the only path that can put a balance in `tenant_financial_ledger`.
- **Related:** [[Business-Rules#Payment allocation|Business-Rules]], [[Database]], [[APIs]], [[Features]], [[Changelog]], [[TODO]], plan at `docs/superpowers/plans/2026-07-31-remove-future-rent-credit.md`

## ADR-035: One login surface (the Stayo popup), and tenant self-signup creates a *marketplace account*, not a tenant

- **Date:** 2026-07-31
- **Status:** accepted
- **Context:** Two login UIs existed side by side. `app/pages/LoginPage.tsx` (395 lines, `/login`) did the real work — `AuthContext.login()`, Google sign-in, role routing to `/admin` / `/owner/home` / `/tenant/home` — but was still in the retired navy identity (`#1B2D5B`, orange circle logo), so it looked like a different product from the landing page that links to it. `shared/ui-patterns/LoginModal.tsx`, the on-brand popup the landing page opens, was a **mock**: a 650ms `setTimeout` where the network call belonged, per its own doc comment. It had never authenticated anyone. Its "Sign Up" tab was equally decorative — there is no tenant self-signup endpoint, because tenants are invited by an owner into a specific room and then activate.
- **Decision:** the popup becomes the single, real login surface.
  - `LoginModal` gains real `login()`, `loginWithGoogle()`, server error surfacing, a Forgot password link, and the role routing the page owned.
  - **`/login` is kept as a route** but renders `LandingPage` with the popup already open. A modal has no URL, and 12 call sites redirect to `/login` — session expiry (`AuthContext`), `RequireAdminSession`, password reset, tenant activation. Deleting the route would have broken all of them. It moves under `PublicShell` because the popup needs `AuthProvider`.
  - `LoginPage.tsx` is deleted.
  - **Tenant self-signup is real** (`POST /api/auth/tenant-signup`), and deliberately creates a `profiles` row with `role: TENANT`, `owner_id` null and **no `tenants` row** — a *marketplace account* (browse, save, enquire). A `tenants` record binds a person to a hostel, room and agreement, none of which exist at signup. Someone becomes a tenant *of a hostel* only through the existing invite → activate flow.
- **Alternatives considered:**
  - **Restyling `/login` as a full page and keeping both surfaces** (rejected — two login UIs to keep in sync is what produced this drift in the first place; one real surface is the point).
  - **Deleting `/login` outright and only opening the modal from buttons** (rejected — redirects need a URL; session expiry would have had nowhere to land).
  - **Redirecting `/login` → `/?login=1`** (rejected — a bookmarked `/login` would silently become the homepage in the address bar).
  - **Creating a `tenants` row at signup with null hostel/room** (rejected — it would put a row into the table that every downstream financial and allocation query assumes is bound to a hostel; the nullable-everything tenant is exactly the kind of half-object that causes silent wrong-hostel bugs this codebase already has invariant checks against).
  - **Leaving the Sign Up tab decorative or pointing it at hostel search** (offered and rejected by the requester, who chose to build real signup).
- **Consequences:** one place to change login, and it's on-brand. The new account type is genuinely new to the product: a TENANT profile that is not anyone's tenant. Verified compatible with the invite flow before building — `tenant-invitation-lifecycle-service` only rejects an existing profile that already has an *active* `tenants` row, and otherwise updates the profile in place, so an owner inviting a self-registered user links to their account instead of colliding. Two smaller consequences handled deliberately: `is_profile_completed` is set true at signup (that flag gates the *invited* tenant's guardian/document wizard, which a marketplace account has no hostel to complete), and post-login routing sends a tenant **with** a `tenant_id` to `/tenant/home` but one **without** to the hostel search, since the portal renders dues and agreements that don't exist. Not yet designed: what the marketplace account can actually *do* beyond browsing — saved hostels and enquiry history are implied by the signup copy but not built.
- **Related:** [[APIs]], [[Features]], [[Frontend]], [[Business-Rules]], [[Decisions#ADR-034|ADR-034]] (the phone-verification gate this reuses), [[Decisions#ADR-031|ADR-031]] (Supabase session plumbing), [[Changelog]]

## ADR-034: Signup phone verification degrades to "accepted unverified" when WhatsApp can't deliver — skip and record, not block

- **Date:** 2026-07-31
- **Status:** accepted
- **Context:** StayO's WhatsApp Business setup is still incomplete (no Meta credentials, no approved OTP template), but every owner-acquisition entry point routed through a phone-OTP gate: the landing-page lead modal and the onboarding wizard's account step both call `POST /api/auth/send-phone-otp` → `MetaWhatsAppProvider.sendOtp()`, which throws without credentials. In production that is a `502` and signup is simply impossible. In development it was papered over by two workarounds inside `AuthOtpService.sendPhoneOtp` — a plaintext dump of every generated code to `apps/backend/latest-otp.txt`, and a `NODE_ENV !== "production"` bypass that returned `success: true` with nothing actually sent. Either way the user still faced a six-digit OTP screen for a code that could only be obtained by reading a file off disk. Both downstream gates (`/api/leads/self-serve`, `/api/auth/owner-signup`) additionally required a `VERIFIED` `phone_verification_otps` row within 30 minutes.
- **Decision:** verification becomes conditional on the provider actually being able to deliver, and its absence is **recorded rather than enforced away**.
  - A pure env-derived resolver (`resolvePhoneVerificationMode()`) returns `on` only when `OTP_PROVIDER=whatsapp` + access token + phone-number ID + `WHATSAPP_OTP_TEMPLATE` are all present, with `PHONE_VERIFICATION_MODE` as an explicit override in either direction.
  - A circuit breaker (3 failures / 10 min → open 15 min → single half-open trial) stops burning a 10-second Meta timeout per signup when the provider is configured but broken.
  - For purposes `PHONE_VERIFICATION` and `LEAD_CAPTURE` **only**, an undeliverable OTP writes a `SKIPPED` row (`provider_status: UNAVAILABLE`, `verified_at` set) and returns `verification_required: false`; the frontend then never renders its OTP step. All other purposes keep the hard `502`.
  - Both signup gates move to one shared `resolveSignupPhoneVerification()` helper accepting `VERIFIED` **or** `SKIPPED` within the same 30-minute window, returning which — written to `profiles.phone_verified`/`mobile_verified` (previously hardcoded `true` in `selfSignUpOwner`) and to the new `platform_leads.phone_verified`.
  - The two dev workarounds are deleted.
  - **The two import-time `validateWhatsAppConfiguration()` calls** (`notification-service.ts`, and one at the bottom of `meta-provider.ts`) now log instead of throwing. Found during live verification: they run at *module import*, so a half-configured environment 500'd the route before any fallback logic could execute — the exact state this ADR exists to survive. The function still throws for callers that assert on it. See [[Bugs]].
- **Alternatives considered:**
  - **Email OTP as a fallback channel** (send the code via Resend instead, keeping real verification) — rejected: this environment's `RESEND_API_KEY` is separately known-invalid (see ADR-032's notes), so it would have swapped one unavailable channel for another, and a second delivery channel is more surface than the problem warrants. Revisit if email delivery becomes reliable and unverified numbers prove to be a real cost.
  - **Blocking signup until WhatsApp is approved** — rejected: makes the entire owner-acquisition funnel unusable for an external dependency with no committed date.
  - **Dropping the gate on the two signup endpoints entirely while degraded** — rejected: writing a `SKIPPED` row instead keeps both endpoints reachable only by a caller that just went through `/send-phone-otp` for that exact number, preserving the anti-spam property, and leaves an audit trail of *why* each number is unverified.
  - **Degrading only requests *after* the breaker opens**, letting the failing request itself 502 — rejected: that hands one unlucky user per cooldown a dead end for a condition the system already knows about.
  - **A login-time or step-up catch-up prompt for unverified users** — explicitly out of scope per the requester; this change is about the signup page, and a catch-up regime is a separate decision.
- **Consequences:** signup works today, and turning verification back on is configuration-only (set the four variables, or `PHONE_VERIFICATION_MODE=on`) with no code change and no migration. Honestly named cost: **a real phone number that nobody confirmed can now back a lead or an owner account** — mitigated by human lead review before approval plus an "Unverified" marker in the admin leads list, and bounded by the fact that nothing retroactively verifies the backlog once WhatsApp is live. Second cost: with the breaker, a credentials expiry downgrades verification *silently*; the `otp.request.skipped` metric line makes the rate observable, but no alert is wired to it yet.

## ADR-032: Owner-acquisition funnel phase 2 — real lead activation via a `tenant_invitations`-style token, not a shared table

- **Date:** 2026-07-29
- **Status:** accepted
- **Context:** Phase 1 wired the landing page's "Manage My Hostel" CTA to real Google sign-in + phone-OTP-verified lead capture, creating real `platform_leads` rows. The Admin Console's "Approve"/"Reject"/status-dropdown were pure status-label writers — `PATCH /api/platform-admin/leads/[id]` did nothing beyond `prisma.platform_leads.update({ status })`, for any of the 6 old status values. This phase makes "Approve" do something real: generate a single-use activation link, send it (WhatsApp, email fallback), and land the owner on the real onboarding wizard, prefilled, with the lead's status then auto-advancing as real signup/hostel-creation events happen.
- **Decision:**
  - **New `platform_lead_invitations` table**, deliberately a new table rather than reusing `tenant_invitations` directly — a lead has no `tenant_id`/`hostel_id`/`room_id` yet, and `tenant_invitations` is FK'd to all three. Copies its proven shape instead: an opaque `token` (`crypto.randomBytes(32).toString("hex")`) stored separately from the row's own `id` — the URL never carries a database primary key — with `status` (`PENDING → OPENED → ACTIVATED`, or `EXPIRED`) and `expires_at` (+7 days) enforcing single-use and expiry, mirroring `tenant-invitation-lifecycle-service.ts`'s pattern without sharing its code.
  - **`PlatformLeadStatus` enum replaced outright**, not extended: `NEW, UNDER_REVIEW, APPROVED, INVITE_SENT, OWNER_ACTIVATED, HOSTEL_CREATED, LIVE, LOST` (was `NEW, CONTACTED, DEMO_SCHEDULED, ONBOARDING, ACTIVE, LOST`). A real `ALTER TYPE`/recreate migration, not `ADD VALUE`, since old values are retired. Existing rows mapped: `CONTACTED→APPROVED`, `DEMO_SCHEDULED→UNDER_REVIEW`, `ONBOARDING→INVITE_SENT`, `ACTIVE→LIVE`, `NEW→NEW`, `LOST→LOST`. Judged low-risk since the table held only this session's own test/demo rows at migration time.
  - **`APPROVED` onward is system-managed, enforced server-side, not just a UI convention**: `PATCH /api/platform-admin/leads/[id]` now rejects any attempt to set `status` to anything except `NEW`/`UNDER_REVIEW`/`LOST` (400 `VALIDATION_ERROR`). The only way to `APPROVED`+ is `POST .../approve`, and only the auto-progression choke points below can move a lead past `INVITE_SENT`. This is what actually guarantees "no manual status updates required after invite sent" — a convention alone wouldn't have.
  - **Three auto-progression choke points, each a real backend side effect, not polling**: `OWNER_ACTIVATED` inside `POST /api/auth/owner-signup` (when the request carries an optional `lead_token`, threaded from the wizard) — single-use is enforced here via an `updateMany({ where: { status: { in: ["PENDING","OPENED"] } } })` count check, inside the real signup's own success path, not trusted to frontend call ordering. `HOSTEL_CREATED` inside `POST /api/owner/hostels`, looked up via `platform_leads.converted_owner_id` (see below) — no new column needed on `hostels`. `LIVE` is the one exception with no natural server hook (floor/room creation is a frontend-orchestrated loop of several separate calls, confirmed no existing event fires when it finishes) — the wizard's publish step makes one small trailing `POST /api/leads/invitation/[token]/complete` call after that loop succeeds. All three are wrapped so a failure in the lead-tracking side effect can never fail or roll back the owner's real signup/hostel-creation/publish.
  - **`platform_leads.converted_owner_id`** (present in the schema since Phase 1's design but never actually written by any code — confirmed dead, see [[Bugs]]) is populated for the first time here, at the `OWNER_ACTIVATED` step, and is what lets the `HOSTEL_CREATED` step look the lead back up without a new FK anywhere on `hostels`.
  - **`systemEventLog` reused as-is for the audit trail, with a stated tradeoff**: it has `owner_id`/`tenant_id` columns but no `lead_id` — lead-scoped events (`LEAD_CREATED`, `LEAD_APPROVED`, `LEAD_INVITE_SENT`, `LEAD_INVITE_OPENED`, `LEAD_OWNER_ACTIVATED`, `LEAD_HOSTEL_CREATED`, `LEAD_LIVE`) are logged with `owner_id: null` and `lead_id` inside the JSON `metadata` field; the Admin drawer's new Timeline section queries via a Prisma JSON-path filter (`metadata: { path: ["lead_id"], equals: id }`) rather than an indexed FK join. Chosen over adding a `lead_id` column to a shared table used by many unrelated flows — acceptable at current lead volume, revisit only if that ever becomes a real query-performance concern.
  - **WhatsApp needs a new Meta-approved template** (`WHATSAPP_OWNER_ACTIVATION_TEMPLATE`, no default value that will actually send) — this is a real external dependency outside this codebase, not something code alone can complete. Until approved (and always in dev, since no WhatsApp credentials are configured), `MetaWhatsAppProvider.sendOwnerActivation()` throws internally and the flow falls straight through to `EmailService.sendOwnerActivation()`, exactly like Phase 1's lead-capture OTP already does — the feature is fully verifiable end-to-end via the email leg regardless of Meta's approval timeline.
- **Alternatives considered:** Reusing `tenant_invitations` directly with nullable `tenant_id`/`hostel_id`/`room_id` (rejected — would force every consumer of that table to handle a "lead, not tenant" case it was never designed for, and blur a table that's already load-bearing for a completely different domain). Adding the granular lifecycle as new *additional* enum values via `ADD VALUE` (rejected — the old 6 values don't map cleanly onto real business progress, e.g. `ONBOARDING` meant nothing specific; a clean replacement with an explicit data-migration mapping was judged clearer than accumulating both old and new labels side by side). Adding a `lead_id` column to `systemEventLog` (rejected for now — a schema change to a table read by many unrelated flows, for one new feature's benefit; the metadata-filter approach is reused infrastructure at the cost of an unindexed query, acceptable at current scale).
- **Consequences:**
  - A lead that's approved but where both WhatsApp and email fail to send is deliberately left at `APPROVED`, not silently marked `INVITE_SENT` — the admin sees an accurate state and the delivery error, and can retry. Verified live: with WhatsApp unconfigured and (separately, an existing environment issue) an invalid `RESEND_API_KEY`, a real approve attempt correctly stayed at `APPROVED` rather than lying about delivery.
  - The onboarding wizard (`OwnerOnboardingWizard.tsx`) gained its first-ever external-prefill capability (`useOwnerOnboardingState(initialData?)`) and a new `city` field it didn't have before — both small, additive changes; a normal non-lead-originated `/onboarding` visit is unaffected (verified live: a fresh signup with no `lead_token` completes exactly as before).
  - Full lifecycle verified live against the real dev database end-to-end: lead created → approved (WhatsApp+email attempted, correctly failed and logged) → activation context fetched (prefill data returned, `PENDING→OPENED`, event logged) → real owner-signup with the token (`OWNER_ACTIVATED`, `converted_owner_id` set, invitation `ACTIVATED`, single-use re-verified via a second invitation row created earlier by the failed approve attempt, which correctly stayed `PENDING` and unusable) → hostel creation (`HOSTEL_CREATED`) → publish-complete call (`LIVE`) → Admin drawer's timeline query returned all 6 logged events in the correct order.
- **Related:** [[Backend]], [[Frontend]], [[Database]], [[APIs]], [[Bugs]], [[Changelog]], ADR-031 (the Supabase Auth migration this phase's `owner-signup` change builds on top of)

## ADR-031: Migrate authentication from the custom JWT+refresh-token system to Supabase Auth

- **Date:** 2026-07-29
- **Status:** accepted
- **Context:** The existing "Continue with Google" flow (`authService.googleLogin()`) was a hand-rolled raw OAuth2 code exchange against `https://oauth2.googleapis.com/token`, discarding Google's `sub`/`email_verified` claims and never verifying the ID token's signature — and it was non-functional in every environment checked, since `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`/`VITE_GOOGLE_CLIENT_ID` were never configured. Separately, the app already had a *parallel, inconsistent* relationship with Supabase Auth: `registerOwner()`/`selfSignUpOwner()` tried `supabase.auth.admin.createUser()` and silently fell back to a local `crypto.randomUUID()` on any failure (no flag recorded on which case occurred), while tenant and admin profile-creation paths never attempted Supabase at all — meaning **every tenant and admin account, and an unknown subset of owner accounts, had zero real Supabase identity**, and `profiles.id === auth.users.id` was an unenforced intent, not a guarantee. Rather than patch the Google flow in isolation, the decision was made to migrate the whole session layer onto Supabase Auth as the single provider (email/password and Google both), fixing the underlying identity-linking problem in the same pass instead of building Google auth on top of it.
  Also corrects two facts CLAUDE.md/`docs/obsidian/Backend.md` had wrong before this migration started (found during research, unrelated to Supabase): the access token was actually **12h**, not 20 min; the absolute session cap was **30 days** for both OWNER and TENANT, not 12h. The custom refresh-token rotation/reuse-detection logic (`SessionLifecycleService.rotateRefreshToken()`) was fully implemented but **dead code** — `/api/auth/refresh` never called it, running its own non-rotating logic instead — so Supabase's own (real, working) refresh rotation is a strict improvement for that piece, not a regression.
- **Decision:**
  - **`profiles.auth_user_id` (nullable, unique) + `auth_linked_at`** link `profiles` to `auth.users`. Not a business-model change — pure auth linkage, matches the architecture the migration was scoped around.
  - **Just-in-time (lazy) identity linking**, not a forced password reset (a reset would be a workflow change, out of scope by the migration's own constraints): on every successful password login (`login()`, `loginWithPhone()`, `selfSignUpOwner()`, tenant-activation auto-login), `ensureSupabaseIdentity()` (`lib/auth/supabase-identity.ts`) silently creates-or-links a real `auth.users` row using the plaintext password available for that one request, then calls `signInWithSupabasePassword()` to mint a real Supabase session. The plaintext is never persisted anywhere new. **No more silent local-UUID fallback** on Supabase failure — that was the root cause of the pre-migration unreliable-linkage state, and this migration removes it rather than extending it; if Supabase is unreachable, the login/signup now fails loudly instead.
  - **Login stays backend-mediated** — the SPA does not call `supabase.auth.signInWithPassword()` directly. `/api/auth/login` is the only place rate-limiting, tenant-status checks, `PASSWORD_RESET_REQUIRED`, and the JIT linking itself can run; moving it client-side would mean losing those gates or reimplementing them against Supabase.
  - **Role/`owner_id`/`tenant_id` resolution happens Node-side** (`lib/auth/supabase-session.ts`'s `resolveSupabaseSession()`), not via a Supabase Custom Access Token Hook baking these into every minted JWT. Seriously considered and rejected: `tenant_id` doesn't exist until activation, `is_active` must revoke access immediately when an owner disables a tenant, and `owner_id` is already known to go stale (the pre-existing self-heal in `createSessionAndTokens()` exists for exactly this reason) — baking these into a JWT that only refreshes hourly would reintroduce staleness bugs the current design already works around. The cost is one indexed DB lookup per authenticated request; `/api/auth/me` already did two on every heartbeat, so this isn't a new category of cost.
  - **`middleware.ts` stays on the Edge runtime and stays cheap**: `getSession()`'s well-known chokepoint shape (241+ route files call it, reading only headers `middleware.ts` injects, doing zero DB/crypto themselves) meant swapping the verification method there — not touching any of those 243+ call sites — was the cheapest possible migration seam. Verification is via `jose`'s `createRemoteJWKSet` against Supabase's live JWKS endpoint (the project uses asymmetric ES256 signing, confirmed live during planning), so no shared secret to manage and no network round-trip per request.
  - **Dual-accept during the transition**: `middleware.ts` tries Supabase verification first, falls back to legacy HS256 verification, tagging the request `x-auth-mode: supabase|legacy`. `getSession()` (now Node-only, moved out of the Edge-only `lib/auth-edge.ts` since it needs Prisma) branches on that tag. This means the migration didn't force-invalidate any session that was valid at deploy time — legacy sessions simply age out over their normal 12h lifetime once `/api/auth/login` stops issuing new ones.
  - **`password_hash` on `profiles` stays permanently** — required by the 2-minute `identity_tokens` step-up-confirmation flow (6 financially-sensitive OWNER routes: offline payment, obligation cancel/waive, change-rent, change-frequency ×2), which re-verifies via `authService.verifyOrMigrateLegacyPassword()`/bcrypt and is unrelated to the login-session migration. Reimplementing that step-up against Supabase reauthentication (a very different UX — a one-time emailed code instead of re-typing a password in a modal) would itself be a workflow change, which this migration is not authorized to make.
  - **`JWT_SECRET` stays** — SSE short-lived tokens, receipt-verification tokens, `identity_tokens`, and password-reset tokens are app-minted/app-verified and unrelated to the login session; none of this moves to Supabase.
  - **Revocation is preserved, and is actually stronger than before, not weaker**: Supabase access tokens are stateless and valid until `exp` — Supabase itself has no way to instantly kill one. The pre-existing Redis deny-list (`checkSessionRevocationEdge`, checked on every request regardless of auth mode) is kept for exactly this, and `/api/auth/logout`/`logout-all` additionally call `supabase.auth.admin.signOut()` so the refresh token dies server-side too. The 30-minute idle-timeout business rule (also something Supabase has no concept of) is preserved the same way — reimplemented in Redis, checked in `middleware.ts` for Supabase-mode requests specifically (legacy-mode idle-checking is untouched, still Node-side via `sessionLifecycleService.touchSession()`).
  - **Google sign-in keeps its exact pre-migration invariants**, now enforced in `resolveSupabaseSession()` instead of the old `googleLogin()`: never auto-provisions an account (matches by `auth_user_id`, then by email — rejects with `NO_STAYO_ACCOUNT` if no profile exists), tenants may not sign in with Google (`TENANT_GOOGLE_NOT_ALLOWED`), disabled accounts are rejected (`ACCOUNT_DISABLED`). The one behavior change is a *strengthening*: `email_verified` is now actually checked before linking a Google identity to an existing profile, where the old raw-OAuth2 flow discarded that claim entirely.
- **Alternatives considered:** Scoping this migration to Google-only, leaving email/password on the custom system (rejected — the user's explicit direction was Supabase as sole provider; a two-provider split would also mean maintaining both the custom refresh-rotation code and Supabase's, doubling the surface this migration was meant to simplify). A Custom Access Token Hook for claims (rejected, see above — staleness). Client-side-only `signInWithPassword()` calls, bypassing the backend (rejected — loses rate-limiting/status-gate enforcement and the JIT linking hook). Cookie-based session storage via `@supabase/ssr` (rejected — that package is designed for same-origin SSR frameworks; this is a cross-origin Vite SPA talking to a separate Next.js API host, and adopting it would be a materially larger change than this migration's scope).
- **Consequences:**
  - **Real, accepted security-posture tradeoff**: the refresh token moves from an httpOnly `SameSite=Lax` cookie (today's model) to Supabase's client-side session storage (localStorage by default), which is more XSS-exposed. Mitigated by shortening the Supabase access-token TTL and by Supabase's own real (unlike the dead code it replaces) refresh-token rotation with reuse detection. This is an inherent consequence of a cross-origin SPA using the client-side Supabase SDK, not a mistake — see the rejected `@supabase/ssr` alternative above.
  - Accounts that never log in again stay unlinked to Supabase indefinitely — an accepted consequence, not a gap to force-close with a reset campaign. Made measurable via `npm run reconcile:supabase-identities` (dry-run by default; matches `profiles` against `auth.users` by both `id` and `email`, never auto-links an ambiguous match).
  - `googleLogin()`, `getGoogleCodeRedirectUri()`, `app/api/auth/google-callback/`, `app/api/auth/refresh/`, `generateRefreshToken`/`hashToken`, and the dead `ensureSupabaseResetIdentity()` are removed outright. `SessionLifecycleService` is trimmed to the policy constants (`ACCESS_TOKEN_MAX_AGE_SECONDS`, `TENANT_REFRESH_DAYS`, `OWNER_ABSOLUTE_MS`, `INACTIVITY_TIMEOUT_MS`, `getSessionCookieOptions`) plus `touchSession`/`revokeSession` — its session-minting/rotation methods are gone.
  - Two real, previously-undiscovered bugs were found and fixed in the same pass (see [[Bugs]]): `changePassword()` passed the local `profiles.id` straight to `supabase.auth.admin.updateUserById()`, which only ever worked for the subset of profiles born with `id === auth.users.id` — every other profile 500'd the whole password-change request; `completePasswordReset()` used unpaginated `supabase.auth.admin.listUsers()` to find a user by email, silently missing anyone past the first page.
  - Zero runtime test coverage existed for login/refresh/logout/session-lifecycle before this migration, and that gap is not closed by it — `tests/auth-hardening-security.test.ts` (a static source-code scan, retargeted at the new `resolveSupabaseSession`/`ensureSupabaseIdentity` code) plus manual verification are the safety net.
- **Related:** [[Backend]], [[Frontend]], [[Database]], [[APIs]], [[Bugs]], [[Changelog]]

## ADR-028: Real StayO owner self-signup is a separate, ungated service method — not a reuse or relaxation of `registerOwner`'s `ALLOW_OWNER_BOOTSTRAP` gate

- **Date:** 2026-07-25
- **Status:** accepted
- **Context:** StayO's real owner-acquisition journey (landing → onboarding wizard → dashboard) needed a working self-serve signup, but the only existing owner-creation path, `POST /api/auth/register`, is structurally unreachable for this: it requires an already-authenticated OWNER session (a contradiction for signup) *and* a `verification_token` that no route in the codebase actually mints — `verify-phone-otp` only flips flags on an *existing* profile, and `confirm-identity` (the only token-issuing route) doesn't include `PHONE_VERIFICATION`/`registration` in its allowed purposes. `registerOwner()` itself is additionally guarded by `ALLOW_OWNER_BOOTSTRAP`, whose own doc comment states "HMS is a single-owner system... no new owners should be created through any code path" — a safety flag from the legacy single-owner-HMS heritage, not something meant to gate a real multi-tenant SaaS's normal signup traffic.
- **Decision:** Added `authService.selfSignUpOwner()` — a new method duplicating the safe parts of `registerOwner()` (email/phone uniqueness checks, best-effort Supabase-user create with local-UUID fallback, `hashPassword`, single `profiles` row insert with `role: OWNER`) but with no `ALLOW_OWNER_BOOTSTRAP` check, backing a new public route `POST /api/auth/owner-signup`. Instead of the broken `identity_tokens` mechanism, this route re-purposes the already-working `send-phone-otp`/`verify-phone-otp` pair: it looks up a `phone_verification_otps` row with `status: VERIFIED` for that phone, issued within the last 30 minutes, and rejects signup if none exists. On success it calls the same `createSessionAndTokens()` used by `/login`, so the response/cookie shape matches exactly.
- **Alternatives considered:** Reusing `registerOwner()` with `ALLOW_OWNER_BOOTSTRAP` always set in production (rejected — that flag exists specifically to prevent uncontrolled owner creation; setting it permanently on defeats its purpose and conflates two different products' safety models). Fixing `confirm-identity` to add `PHONE_VERIFICATION`/`registration` to its allowed purposes (rejected — that route requires an existing OWNER session by design, still a dead end for brand-new signups; would need its own auth exemption anyway, at which point a dedicated route is cleaner). Skipping phone verification entirely for now (rejected — the OTP send/verify infrastructure already works end-to-end in this environment via the dev debug-file fallback, no reason to leave signup unverified when the pieces exist).
- **Consequences:** `/api/auth/register` remains exactly as restricted as before (no weakening of the legacy gate); StayO owner signup is fully real and independently testable. The 30-minute OTP freshness window is arbitrary and not yet configurable — revisit if real-world signup latency (e.g. slow WhatsApp delivery once configured) makes it too tight.

## ADR-027: Regeneration wipes ALL live UPCOMING rent, not just rows on/after the new effectiveFrom, and revives stale rows instead of colliding with them

- **Date:** 2026-07-22
- **Status:** accepted
- **Context:** Two related bugs surfaced from repeated real-time testing of the ADR-024 regeneration logic (switching the same tenant Quarterly → Monthly → Quarterly in quick succession):
  1. `(agreement_id, rent_month, obligation_type)` is a **hard, unfiltered** unique index (not scoped to `is_superseded: false`) — a stale, already-superseded row from an earlier switch still permanently occupies its `rent_month` slot. A later switch landing on that same month (very likely when switching back to a previously-used cadence) hit `Unique constraint failed` trying to `create()` a fresh row on top of it.
  2. Once (1) was fixed, a second bug appeared: the supersede step only cleared obligations with `due_date >= effectiveFrom`. Since a shorter cadence (Monthly) computes an earlier `effectiveFrom` than a longer one (Quarterly), switching Monthly → Quarterly could leave a few of the Monthly pass's earliest obligations dated *before* the Quarterly pass's `effectiveFrom` — un-superseded, still live, at the old cadence's amount, sitting alongside the newly-created Quarterly rows. The live schedule ended up mixing two cadences' amounts.
- **Decision:** (1) Before creating each schedule item, look up any existing row for that exact `(agreement_id, rent_month, obligation_type)` — regardless of `is_superseded` — and `update()` it in place (reviving it: `is_superseded: false`, fresh amount/dates/labels/plan link) instead of blindly `create()`ing, mirroring `agreement-rent-schedule-service.ts`'s own duplicate-guard pattern, just not filtered to live rows since that's precisely the row that would otherwise collide. (2) The supersede step now clears **every** currently-live `UPCOMING` `RENT` row for the tenant, with no `due_date` filter at all, before creating the new schedule — safe because `UPCOMING` rows are by definition never activated for collection (zero payments possible on any of them), so fully wiping and regenerating them on every switch can't touch real money and keeps the schedule always single-cadence, never mixed.
- **Alternatives considered:** Catching the P2002 unique-constraint error and skipping that period (rejected — matches the codebase's existing convention in `generateForAgreementInTx` for a *different* scenario, but here it would silently create a gap in the tenant's schedule for that one period, which is worse than reviving the row). Scoping the wipe to `due_date >= min(effectiveFrom, existing obligations' earliest due date)` instead of everything (rejected as needless complexity — since only `UPCOMING` rows are touched and none represent real collected/collectible debt yet, there's no downside to a full wipe-and-regenerate every time).
- **Consequences:** Regeneration is now idempotent under repeated switching — the live schedule is always fully and only the most-recently-requested cadence, with no stale remnants regardless of how many times an owner changes their mind. New regression test (`tests/billing-frequency-owner-initiate.test.ts`) exercises exactly the reported 3-switch sequence and asserts every live row matches the final cadence's amount.
- **Related:** [[Bugs]], [[Changelog]], ADR-024

## ADR-026: Owner-direct frequency changes search forward for a clean period instead of failing on the first naive candidate

- **Date:** 2026-07-22
- **Status:** accepted
- **Context:** `getNextCleanBillingPeriodDate` picks a single candidate effective date (the next calendar boundary aligned to the requested frequency), entirely calendar-based, with no awareness of the tenant's actual obligations. `ownerInitiateChange` then checked that ONE candidate for overlap and threw `UNCLEAN_BILLING_PERIOD` if it collided — reported live: switching tenant "shiva" from Quarterly back to Monthly failed because the very next month's rent was already activated (`PENDING`), even though a later month would have been perfectly clean.
- **Decision:** Added `findCleanEffectiveFrom()` — walks forward month by month (same iteration cap as `getNextCleanBillingPeriodDate`, 36 months), and at each candidate that's a valid period start for the requested frequency, actually checks it against `findOverlappingObligations` (ADR-023) instead of assuming the first candidate is fine. Returns the first genuinely clean one; still throws `UNCLEAN_BILLING_PERIOD` if none is found in the search horizon. `ownerInitiateChange` now calls this instead of `getNextCleanBillingPeriodDate` + a single overlap check.
- **Alternatives considered:** Leaving it as a single-candidate check and just improving the error message to say "try again later" (rejected — the system already has all the information needed to find a working date itself; making the owner guess-and-retry across months is worse UX for no real safety benefit). Applying the same forward-search to `ownerSetCustomSchedule` (rejected — custom installment dates are explicitly owner-chosen; silently shifting a date the owner typed in would be surprising, not helpful — blocking clearly and letting them pick a different date is the right UX there).
- **Consequences:** Owner-direct frequency changes now succeed in substantially more real scenarios (e.g. switching back and forth between cadences) without the owner needing to understand *why* a given month didn't work.

## ADR-024: Owner-direct recurring frequency changes now regroup an agreement-based tenant's future rent for real

- **Date:** 2026-07-22
- **Status:** accepted
- **Context:** ADR-021 shipped owner-direct MONTHLY/QUARTERLY/HALF_YEARLY changes with a disclosed, deliberate limitation: for a tenant with a signed agreement, the change updated `tenants.payment_frequency`/`tenant_billing_plans` but never touched the individual monthly `rent_obligations` rows `agreement-rent-schedule-service.ts` had already generated up front at signing — so the Charges tab kept showing unchanged monthly rows after a "successful" frequency change. Direct user report with a screenshot confirmed exactly this. ADR-022's Custom Dates work already established *why* this is safe to fix directly: `generateForAgreementInTx` is a one-shot call (signing / renewal activation) that never re-runs for an already-signed agreement, so directly superseding and replacing its future obligations can't be undone or duplicated by a later automatic run.
- **Decision:** `ownerInitiateChange` now checks whether the tenant has an active agreement. If so, it: computes how many of the new frequency's periods are needed to cover the remaining agreement term (`agreement.agreement_end_date`, already a real column — no need to derive it from duration), builds the full schedule via `billingScheduleService.previewSchedule` (not just a 4-period preview), and inside the same transaction supersedes the tenant's not-yet-due (`UPCOMING`, `due_date >= effectiveFrom`) `RENT` rows and creates the new grouped ones (`agreement_id`/`billing_plan_id` stamped, same `is_superseded`/audit fields as the Custom Dates path). Non-agreement tenants are unaffected — `rent-generation-service.ts`'s rolling monthly generator already reads `payment_frequency`/`payment_frequency_effective_from` correctly for any month not yet generated, so updating the setting alone remains sufficient there. `ChangeFrequencyModal.tsx`'s agreement-tenant warning banner (and the now-unused `hasActiveAgreement` prop) removed since the limitation it described no longer exists.
- **Alternatives considered:** Teaching `agreement-rent-schedule-service.ts` itself to understand periodic frequencies as a generation-time concept (rejected, same reasoning as ADR-022 — the one-shot call pattern makes direct supersede-and-replace simpler and equally safe, without touching the shared generator every agreement-based tenant depends on). Only fixing Custom Dates and leaving the Recurring path's limitation in place long-term (rejected once a live user report showed it was actively confusing rather than a theoretical gap).
- **Consequences:** The `agreement-rent-schedule-service.ts` gap noted in ADR-021/ADR-022's Bugs.md entry is now resolved for the *recurring* path too — nothing agreement-related is left broken by this feature area. `ownerInitiateChange`'s return shape gained `obligations_created`/`obligations_superseded` (0/0 for non-agreement tenants) matching `ownerSetCustomSchedule`'s existing shape.
- **Related:** [[Bugs]], [[Changelog]], ADR-021, ADR-022, ADR-023

## ADR-023: Owner-direct frequency changes no longer block on a tenant's older, non-overlapping unpaid rent

- **Date:** 2026-07-22
- **Status:** accepted
- **Context:** Direct user report — an owner tried to change a tenant's billing frequency and got `UNCLEAN_BILLING_PERIOD` simply because the tenant had ordinary overdue rent from before. Tracing `validateCleanPeriod` (the shared guard used by both the tenant-request→approve path and, until now, `ownerInitiateChange` from ADR-021): it flags a still-unpaid `PENDING`/`PARTIAL` obligation as a blocker under *either* of two conditions — `overlapsNewWindow` (its billing period genuinely overlaps the new schedule's window — the real double-billing risk) **or** `beforeEffective` (its period simply ends before the new effective date — i.e., any older unresolved debt at all, whether or not it has anything to do with the new schedule). The second condition meant the guard effectively blocked the single most common real trigger for wanting a frequency change in the first place: a tenant already behind on the old cadence.
- **Decision:** Added `findOverlappingObligations()` — the same query, but only the `overlapsNewWindow` condition. `ownerInitiateChange` now uses this instead of `validateCleanPeriod`, so it only blocks on a genuine period overlap with the new schedule (double-billing risk), not merely because older debt exists. The old debt is left completely untouched — not superseded, not merged into anything — and stays exactly as collectible as it always was, independent of the new frequency setting. `validateCleanPeriod` itself is untouched and still governs the tenant-request→`approve()` path exactly as before — this is a deliberate divergence, not a shared-logic fix, since the two paths have different risk postures (a request submitted possibly weeks ago being approved now vs. an owner acting on the tenant's *current* state immediately).
- **Alternatives considered:** Also relaxing `validateCleanPeriod` for the tenant-request path (rejected — out of scope for what was reported, and changes intentionally-shipped-earlier behavior without a matching report against it). Trying to fold the old due amount into the newly-computed schedule's first installment (rejected — the periodic path doesn't create `rent_obligations` rows synchronously at all; they're generated later by `rent-generation-service.ts`/`agreement-rent-schedule-service.ts` from the frequency setting, so there is no "first new installment" object to merge into at the point this guard runs. Leaving the old debt as its own untouched obligation is simpler and loses nothing).
- **Consequences:** An owner can now change frequency for a tenant who has ordinary overdue/partial rent, as long as that debt's period doesn't genuinely collide with the new schedule's window. `ownerSetCustomSchedule` (ADR-022) already had the narrower, correct check from the start (`due_date >= effectiveFrom` only, never blocking on already-past due dates) so it needed no change.
- **Related:** [[Bugs]], [[Changelog]], ADR-021, ADR-022

## ADR-022: Custom installment schedules bypass the periodic-frequency generator entirely, rather than waiting on it to be fixed

- **Date:** 2026-07-22
- **Status:** accepted
- **Context:** ADR-021 shipped owner-direct MONTHLY/QUARTERLY/HALF_YEARLY changes but explicitly deferred `CUSTOM_INSTALLMENTS` (an owner-defined list of arbitrary due-date + amount charges) because it looked like it needed the same `agreement-rent-schedule-service.ts` fix as the periodic frequencies. On closer inspection that turned out not to be true: `generateForAgreementInTx` (the function that actually creates monthly rent rows for an agreement) is only ever called twice — once at initial tenant activation, once at renewal activation for a *new* successor agreement (confirmed by grepping every call site) — it never re-runs for an already-signed agreement. That means anything created directly as `rent_obligations` rows today, for a currently-signed agreement, will never be silently duplicated or overwritten by that generator later.
- **Decision:** `BillingTransitionService.ownerSetCustomSchedule()` doesn't try to make the periodic generator frequency-aware — it sidesteps it. Given a list of `{due_date, amount, label?}`, it: validates (positive amounts, dates today-or-later, no duplicates, max 24), refuses if any already-activated obligation (PENDING/PARTIAL/OVERDUE) with a real balance falls on/after the first installment date (same "don't silently sweep away real debt" rule as the periodic path's clean-period check, just obligation-level instead of period-level since there's no fixed period shape to check against), then in one transaction: supersedes the tenant's future UPCOMING RENT obligations from the first installment date onward and creates the owner-specified rows directly (status `UPCOMING`, activated normally later by the existing `syncDueStatuses` sweep — no new activation logic needed). Also fixed a related bug caught while building this: `ownerInitiateChange` (ADR-021) and this new method were each opening their own `prisma.$transaction` internally while their routes *also* wrapped them in an outer transaction for identity-token consumption — nested/separately-committing transactions, meaning a token could be marked consumed even if the outer transaction later failed for an unrelated reason. Both now take an optional `identityJti` and consume it as the first write inside their own single transaction; the routes no longer wrap them in anything.
- **Alternatives considered:** Teaching `agreement-rent-schedule-service.ts` to understand `CUSTOM_INSTALLMENTS` as a schedule shape it can generate from (rejected — unnecessary complexity given the generator's one-shot call pattern already makes direct obligation creation safe; would also require solving the exact same problem ADR-021 deferred for periodic frequencies, for no added benefit here). Requiring the custom schedule's total to reconcile with the tenant's remaining contracted rent (rejected — a custom schedule is explicitly for cases where the owner and tenant have agreed to deviate from the standard cadence/amount, e.g. a hardship arrangement; enforcing reconciliation would defeat the point).
- **Consequences:** Custom Dates works correctly today for both agreement and non-agreement tenants — it has none of ADR-021's "doesn't take effect yet" caveat. `ChangeFrequencyModal.tsx` reflects this: the agreement-tenant warning banner only shows for the Recurring tab, not Custom Dates.
- **Related:** [[Bugs]], [[Business-Rules]], [[Changelog]], ADR-021

## ADR-021: Owner can change a tenant's billing frequency directly — same guards as the tenant-request path, minus the wait

- **Date:** 2026-07-22
- **Status:** accepted
- **Context:** `billing-transition-service.ts` only supported a tenant-request → owner-approve flow for changing billing frequency (monthly/quarterly/half-yearly), governed the same way as other Category C contractual fields (`field-classification.ts`). Direct owner feedback: this should work like `change-rent` — owner-initiated, immediate, no waiting on the tenant. Silently making the button a no-op for agreement tenants without disclosure (rejected — worse than not shipping it, since a success toast with no real effect erodes trust in the feature).
- **Consequences:** Non-agreement tenants (if any exist in this system — most appear to be agreement-based per the domain model) get real, working owner-initiated frequency changes today. Agreement-based tenants get the setting recorded and audited, but actual monthly-only generation continues until `agreement-rent-schedule-service.ts` is updated — tracked as an open item, see [[Bugs]].

## ADR-020: `currentAgreementWhere()` is the one canonical "does this tenant have an agreement" check — every surface must use it, not a proxy

- **Status:** accepted

Any future "does this tenant have an agreement" need on this page has an obvious, correct place to read from instead of re-inventing a proxy. Onboarding itself needed no changes — `activation-workflow-service.ts` already wrote the real agreement correctly; this closes a read-side gap only.

## ADR-017: Payment links are amount-flexible and tenant-scoped, not obligation-locked

- **Date:** 2026-07-21
- **Status:** accepted
- **Evidence:** `src/services/payments/payment-link-service.ts::getOrCreateToken` previously required resolving a `tenantId` to exactly one `PENDING`/`PARTIAL` obligation, throwing `"No outstanding rent obligations found for this tenant"` otherwise; `payment_link_tokens.obligation_id` was a required FK with no `amount` column, and the online checkout path (`createMultiObligationPaymentIntent`) always charged that one obligation's full remaining balance.
- **Decision:** A payment link now maps to a tenant, not an obligation. `obligation_id` became an optional default-amount hint. The payer enters any amount on the link's page; the backend FIFO-allocates it across the tenant's outstanding obligations via `buildSettlementPlan` — the same engine the offline "Receive Payment" flow already used — with any excess credited as future rent, via a new `createAmountPaymentIntent` function that mirrors `createMultiObligationPaymentIntent` but starts from a raw amount instead of a pre-picked obligation list. Both owners and tenants can generate a link.
- **Alternatives considered:** Synthesizing a placeholder `rent_obligations` row for the entered amount — rejected, since obligations are the audit-first source of truth for money owed and a synthetic row would pollute every dues/report calculation that reads obligations. A separate parallel "flexible link" type that always books as future credit — rejected, since a payer with real current dues would have their payment misfiled as advance credit instead of clearing what they actually owe.
- **Consequences:** The online (Razorpay) and offline (manual "Receive Payment") payment paths now converge on the same FIFO allocation engine for the first time, rather than diverging (online was previously obligation-first-only, offline was amount-first-only). A payment link generated from a specific obligation card is no longer a hard guarantee that payment will apply to only that obligation — it's a default-amount suggestion. Full design: `docs/superpowers/specs/2026-07-21-flexible-payment-links-design.md`.
- **Related:** [[Business-Rules]], [[APIs]], [[Database]]

  2. Put all export logic in a new `lib/services/expense-export-service.ts` that takes/returns plain data (no `NextRequest`/`Response`), so the HTTP route (`app/api/expenses/export/route.ts`) is a thin adapter; a future cron or template runner can call the same functions directly.
  3. Pick the streaming strategy per format rather than one-size-fits-all: CSV is hand-rolled (trivial to stream correctly, no library needed), XLSX uses `exceljs`'s `WorkbookWriter` (true incremental zip writing — the existing `xlsx`/SheetJS dependency can't stream writes in its free edition), and PDF (`pdf-lib`, matching the existing receipt-PDF convention) is treated as a capped-row business report rather than an unbounded stream, since PDF isn't a practical format for arbitrary-size tabular dumps.
- **Alternatives considered:** Reusing the `xlsx` package for XLSX export (rejected — would require buffering the full row set in memory before writing, defeating the memory-bounded requirement for large exports). Embedding export logic directly in the route handler (rejected — the explicit "modular, no redesign for future scheduled exports" requirement argues for a decoupled service from the start).
- **Consequences:** One more npm dependency (`exceljs`, moderate-severity transitive `uuid` advisory, no direct vulnerability) in exchange for correct streaming behavior. Any future change to expense filtering must go through `buildExpenseLedgerWhere()` — a filter added only to the list route's inline logic would silently not apply to exports, so this is now a single deliberate touch-point to keep in mind.

## ADR-012: Every renewal chain mutation uses `SELECT ... FOR UPDATE` + conditional `updateMany` + count check — no third variant

- **Date:** 2026-07-19
- **Status:** accepted
- **Context:** The Agreement Renewal subsystem has three call sites that can mutate the `renewed_from_agreement_id`/`renewed_to_agreement_id` chain and/or transition a draft to `SIGNED`: `AgreementRenewalService.createRenewalDraft` (manual draft creation), `AgreementRenewalSigningService.signRenewalAgreement` (manual signing), and — after this pass — `AgreementLifecycleService.activateScheduledRenewals` (cron activation) and `RenewalOfferService.acceptOffer` (offer acceptance). The first two already used a `SELECT ... FOR UPDATE` row lock followed by a conditional `updateMany` whose `.count` is checked (throwing on mismatch) before proceeding. The latter two didn't: cron activation used unconditional `update()` calls with no lock, and offer acceptance checked `offer.status` before opening its transaction (a stale read) and linked the predecessor via an `updateMany` whose count was never checked — both allowed a concurrent writer to silently corrupt the chain (e.g. an orphaned, unlinked successor `Agreement`) instead of failing loudly.
- **Decision:** All four call sites now use the identical pattern: lock the predecessor (and, where a second row is mutated, the draft) with `SELECT ... FOR UPDATE` at the top of the transaction, re-read anything checked pre-transaction fresh inside the lock (closing the TOCTOU window), and replace every `update()` on a row whose eligibility could have changed concurrently with `updateMany()` gated on that eligibility, checking `.count !== 1` and throwing to roll back the transaction on a mismatch.
- **Alternatives considered:** A Postgres unique constraint on `renewed_from_agreement_id`/`renewed_to_agreement_id` alone (rejected as insufficient on its own — it would catch a duplicate *link* but not an unconditional status-overwrite race, and this repo's stated policy is "review transactions/locking/update conditions/schema constraints where appropriate" rather than a schema-only fix). A dedicated advisory lock per tenant/agreement (rejected — `SELECT ... FOR UPDATE` on the specific row already serializes exactly the contention that matters and matches the pattern already proven out in this subsystem, so introducing a second locking primitive would be pure divergence).
- **Consequences:** Any future renewal-chain-mutating code path must follow this same pattern (lock → fresh re-check → conditional `updateMany` → count check) rather than inventing a fourth variant. A losing concurrent request now gets a clear thrown error (`CONFLICT: ...` / `Renewal chain changed during cron activation (...)`) instead of silently succeeding into a corrupted state.
- **Related:** [[Bugs]], [[Backend]]

## ADR-013: A renewal's expiry-reminder stage is suppressed once a successor agreement exists

- **Date:** 2026-07-19
- **Status:** accepted
- **Context:** `RenewalStatusService.determineRenewalStage` computed 30-day/15-day/expiry-day/overdue WhatsApp reminder stages purely from the predecessor agreement's own days-until-expiry / days-overdue, without checking whether the tenant had already accepted a renewal offer (or an owner had already created a manual renewal draft). `RenewalDecisionService.evaluateAgreement` already computes `has_successor` for exactly this purpose (used elsewhere to compute `renewal_blocked_reason: "SUCCESSOR_EXISTS"`), but `determineRenewalStage` never consulted it — so a tenant who had already renewed kept receiving "please renew" nudges on the agreement they'd already acted on, right up until the predecessor's actual expiry date.
- **Decision:** `determineRenewalStage` now returns `null` immediately whenever `decision.has_successor` is true, before evaluating any day-count band. This is a full suppression, not a softened message — once a successor exists, the predecessor's expiry-reminder concern is fully superseded; the tenant is now waiting on the successor's own activation (cron `activateScheduledRenewals` or manual signing), which is communicated through a different flow.
- **Alternatives considered:** Softening the message copy to acknowledge a pending renewal while still sending (rejected — adds template/payload complexity for a stage that's simply no longer relevant) — Scoping the fix to only `RenewalStatusService`/WhatsApp rather than also touching the plain in-app 30d/15d notifications in `AgreementLifecycleService.processDailyLifecycle`'s main loop, which has the identical gap (deferred — out of scope for the specific bug as reported; flagged as a discovered adjacent issue for a follow-up decision rather than silently expanding scope).
- **Consequences:** Any future renewal-adjacent notification path (in-app, email, SMS) that fires based on days-until-expiry should apply the same `has_successor` guard, or it will reintroduce this exact bug independently.

## ADR-014: Renewal reminder stages use threshold bands, relying on delivery-layer idempotency, instead of exact-day matching

- **Date:** 2026-07-19
- **Status:** accepted
- **Context:** `RenewalStatusService.determineRenewalStage` matched reminder stages with exact equality (`daysUntilExpiry === 30`, `=== 15`; `daysOverdue === 7`, `=== gracePeriodDays`). If the daily lifecycle cron missed a single run — an outage, a deploy window, a transient failure — the day counter moved past the exact trigger value before the next run, and that stage was silently skipped forever; the tenant/owner never got that reminder for that agreement.
- **Decision:** Reminder/overdue-milestone stages now use inclusive threshold bands instead of exact equality: `30_DAY_REMINDER` for `16–30` days remaining, `15_DAY_REMINDER` for `1–15`, `7_DAY_OVERDUE` for `≥7` days overdue, `30_DAY_CRITICAL` for `≥grace_period_days` days overdue (checked first, so it takes priority over `7_DAY_OVERDUE` rather than double-matching). This is safe *because* `whatsAppTemplateDeliveryService.send()` already enforces per-`(stage, agreementId)` idempotency via a DB unique constraint (`whatsapp_logs.idempotency_key`, `ON CONFLICT DO NOTHING`) — a stage matching on several consecutive cron runs (because the tenant's day-count sits inside its band for more than one day) still only ever sends once. `EXPIRY_DAY_ALERT` (`daysUntilExpiry === 0`) and `EXPIRED_RENT_OVERDUE` (a rent-overdue *state* check, not a day-count) were deliberately left unchanged — see the "Alternatives considered" note.
- **Alternatives considered:** Also broadening `EXPIRY_DAY_ALERT` into a multi-day catch-up band, e.g. `1 ≤ daysOverdue < 7` (rejected — verified by hand against the existing test suite that this collides with `EXPIRED_RENT_OVERDUE`'s fallback: an agreement 6 days overdue with actual overdue rent would incorrectly report "Expires Today" instead of "Rent Overdue," breaking `tests/whatsapp-renewal-notification.test.ts`'s pre-existing `"sends EXPIRED_RENT_OVERDUE alert..."` case). Adding a persisted "last reminder stage sent" column to `Agreement` to drive catch-up logic explicitly (rejected as unnecessary — the existing idempotency-key mechanism already provides exactly-once delivery per stage without a schema change).
- **Consequences:** A tenant/owner may now receive a given reminder stage on a later day than the "ideal" one if cron was down on the ideal day, but they will always receive it exactly once rather than potentially never. Verified by hand that all 6 existing exact-day test cases in `whatsapp-renewal-notification.test.ts` still resolve to the same stage under the new bands (each exact value is the boundary of exactly one band).
- **Related:** [[Bugs]], [[Business-Rules]]

## ADR-015: Renewal readiness and activation logic consolidated into two shared engines, replacing three hand-duplicated implementations

- **Date:** 2026-07-20
- **Status:** accepted
- **Context:** Three call sites independently re-implemented overlapping "is this renewal eligible/ready" validation: `AgreementLifecycleService.activateScheduledRenewals` (cron), `AgreementRenewalSigningService.signRenewalAgreement` (manual signing), and `AgreementRenewalService.createRenewalDraft` (manual draft creation) — each with its own copy of the predecessor-renewable, chain-consistency, move-out, lifecycle-complete, and deposit checks, in slightly different orders and with slightly different query freshness. Separately, the two activation paths (cron and manual signing) each hand-rolled the full activation mutation sequence (lock rows, transition predecessor to `RENEWED`, transition successor to `SIGNED`, sync `tenants` contract fields, generate the rent schedule) — this was flagged as a deferred "P2: eliminate duplicated activation logic" item in the immediately-preceding bug-fix pass (`docs/superpowers/plans/2026-07-19-agreement-renewal-bugfixes.md`) and independently re-surfaced as gap-analysis §1.7/§1.8 ("Readiness Engine and Activation Engine are the same refactor, not two") — see `docs/business-logic/renewal-management-workspace-gap-analysis.md`.
- **Decision:** Introduced `renewal-readiness-engine.ts` (individual pure/async check functions — `checkPredecessorRenewable`, `checkChainConsistent`, `checkNoActiveMoveOut`, `checkLifecycleComplete`, `checkNoUnpaidDeposit`, `checkNoExistingSuccessor` — plus two orchestrators, `evaluateActivationReadiness` and `evaluateCreationReadiness`, each running its full check set and returning *all* failures rather than stopping at the first) and `renewal-activation-engine.ts` (`activateRenewal()` — locks both rows, runs `evaluateActivationReadiness`, then performs the predecessor/successor status transitions, `tenants` sync, and rent-schedule generation). All three original call sites now delegate to these; each retains only what's genuinely specific to it: cron builds its "copy predecessor's signature forward" successor payload, manual signing builds its "fresh e-signature + freshly-resolved template/rules" payload, and each call site maps the engines' generic `ReadinessFailure`/`RenewalChainRaceError` back to its own existing typed error codes and messages, preserving each surface's exact prior error contract.
- **Alternatives considered:** Forcing full unification of the signature/rules-resolution logic too (rejected — cron's copy-forward and manual signing's fresh-resolve are deliberately different behaviors per Business-Rules §13, not incidental duplication; unifying them would be a business-rule change, not a refactor). Keeping cron's weaker checks as-is to minimize diff size (rejected — cron was missing the chain-consistency check that manual signing already had, and checked the deposit obligation via a pre-transaction snapshot instead of a lock-fresh read; both were closed as part of this consolidation, using the already-proven-correct pattern from the sibling path, not a new rule).
- **Consequences:** Manual signing now also syncs `tenants.monthly_rent/security_deposit/maintenance_charge` (previously only cron did — closes the gap found during the post-bugfix flow audit). Two internal `RENEWAL_ACTIVATION_BLOCKED` reason strings were unified to one canonical wording each (cosmetic log-message text, not a behavior change; the blocking *condition* was already identical). A future 4th consumer of these checks (e.g. an "explain why this renewal is blocked" UI or AI-assistant endpoint per gap-analysis §1.13) can call `evaluateActivationReadiness`/`evaluateCreationReadiness` directly and get the full failure list, not just the first.

## ADR-016: Renewal Timeline is a new append-only `RenewalTimelineEvent` table, written inside the same transaction as the mutation it describes

- **Date:** 2026-07-20
- **Status:** accepted
- **Context:** Per the gap analysis (`docs/business-logic/renewal-management-workspace-gap-analysis.md` S1.6), owner-side renewal actions (offer created, sent, revised) had zero persisted, queryable audit trail — only `logger.info()` lines, gone once log retention rotates. Tenant-side actions were only partially captured in `RenewalDecision` (no actor-role field, no `VIEWED` event, and `discussOffer()` overloaded the `RenewalOfferStatus.SENT` enum value to mean "tenant requested discussion," unrelated to its literal meaning). Separately, the gap analysis's cross-cutting finding #1 — independently rediscovered from the same finding in `docs/business-logic/operation-recovery-undo-system-proposal.md` S0 — is that this codebase's existing generic audit log (`eventLog.log()` / `systemEventLog`) always writes via the top-level `prisma` client, never a passed-in `tx`, so it is not transactionally coupled to the mutation it describes even when called from inside one.
- **Decision:** Added `RenewalTimelineEvent` (new table, migration `20260720000000_renewal_timeline_events`) — `hostel_id`/`tenant_id`/`agreement_id`/`offer_id` foreign keys, `RenewalTimelineEventType` (10 values covering the full offer + activation lifecycle), `RenewalTimelineActorType` (OWNER/TENANT/SYSTEM), free-text `reason`, JSON `metadata`. New `renewal-timeline-service.ts` (`registerEvent(tx, params)`) is called from inside the same transaction as the mutation it describes at every write site: `generateOffer`, `generateBulkOffers`, `sendOffer`, `acceptOffer`, `declineOffer`, `discussOffer`, `reviseOffer`, `expireStaleOffers` (all in `renewal-offer-service.ts`), `createRenewalDraft` (`agreement-renewal-service.ts`), and `activateRenewal` (`renewal-activation-engine.ts`, so both cron and manual signing get the `RENEWAL_ACTIVATED` event for free). `registerEvent()` deliberately does not swallow its own errors — a failed timeline write rolls back together with the mutation it describes, rather than silently drifting from it, directly closing the "audit writes must be transactionally coupled" finding.
- **Alternatives considered:** Generalizing `recovery_events`/`change_request_events` (from the not-yet-approved Undo proposal) into a shared "domain event log" both subsystems use (this was gap-analysis open question #2) — rejected for now: coupling this shipped work to another proposal's not-yet-approved, not-yet-implemented schema would block this feature on an unrelated decision. A bespoke, purpose-built table is the lower-risk choice today; nothing prevents a future migration onto a shared event-log table if the Undo proposal is approved. Extending `RenewalDecision` to also carry owner-side events (rejected — it's fundamentally shaped around tenant decisions, `decision: RenewalOfferStatus`; bending it to fit owner actions would repeat the exact enum-overloading problem already flagged in `discussOffer()`).
- **Consequences:** Three previously-non-transactional write paths (`generateOffer`, `sendOffer`, `discussOffer`) are now wrapped in `$transaction` for the first time, so their single write plus the new timeline write commit or roll back together — a minor, low-risk structural change (single-statement transactions), not a business-rule change. `expireStaleOffers()` changed from one bulk `updateMany` to a `findMany` (to capture per-offer IDs) followed by a scoped `updateMany` inside a transaction — same net effect, same idempotent WHERE clause, now with a per-offer `OFFER_EXPIRED` event. `createRenewalDraft`'s `DRAFT_CREATED` event and `RENEWAL_ACTIVATION_BLOCKED` events are recorded with actor `SYSTEM` since neither call site currently receives caller-identity information through its API — a future pass threading real actor identity through those routes would only need to change the `timelineActor`/event call, not the storage model.
- **Related:** [[Bugs]], [[Database]], [[Business-Rules]], ADR-015 (the engine consolidation this timeline instrumentation builds on top of)

## ADR-029: Food schedules are modeled as a repeating weekly pattern per month, not calendar-dated rows; voting is single-choice per meal type; the existing generic Food Polls feature stays as a separate, untouched feature

- **Date:** 2026-07-26
- **Status:** accepted — **except point (3), superseded 2026-08-05 by [[Decisions#ADR-048|ADR-048]]**
- **⚠️ Point (3) is no longer current.** This ADR records that the new voting-driven menu system and the pre-existing generic Food Polls feature would *"coexist, unmodified relative to each other"*, per an explicit user choice of "keep both" over "replace it". **Food Polls was deleted outright on 2026-08-05** — a reversal authorised by the user after the audit (`docs/audits/food-module-audit.md` §0.3) established it was pure `useState(mockFoodPolls)` writing nothing, promoted by a Home Quick Action, while the real voting system sat unnamed on the other tab. Read [[Decisions#ADR-048|ADR-048]] before acting on point (3). Points (1) and (2) — the weekly-pattern grain and multi-select voting — **still stand and are still the model**; see [[Food]].
- **Context:** The Food tab's Monthly Schedule sub-tab was 100% mock (a client-side Week1-4 rotation, `buildSchedule.ts`, ignoring any tenant input) with no backend at all. The user specified a full replacement: owner maintains a food-item library per meal type → opens monthly voting → tenants vote → owner generates a weekly Mon-Sun timetable from the vote results → owner reviews/edits → publishes → tenant dashboard updates immediately, including on any later edit, with no separate "republish" step → next month auto-carries-forward the previous published schedule as a draft. Three design questions had to be resolved before building: (1) how a schedule's 7 days relate to a calendar month (which has 4-5 real weeks, not one), (2) whether a tenant's vote is single- or multi-select per meal type, (3) whether this new system replaces or coexists with the pre-existing generic "Food Polls" feature (arbitrary single/multi/rating/yes-no owner-created polls, `CreatePollModal`/`PollResultsSheet`/`useFoodPolls`, unrelated in shape to menu voting).
- **Decision:** (1) `food_schedules` is one mutable row per `(hostel_id, month)` representing a **repeating weekly pattern** — 7 `FoodDayOfWeek` × 4 `FoodMealType` = 28 `food_schedule_meals` rows, not calendar-dated. This directly matches the spec's own wording ("a weekly timetable," singular) and makes every other requirement fall out for free: "publish" is a status flip (`DRAFT`→`PUBLISHED`) on the same row; an edit made after publishing is immediately live with no republish step, because there is only ever one row per month, not a version chain; and carry-forward is a straight 28-row clone into a new month's row. (2) Voting is **multi-select per meal type** — one `food_votes` row per `(voting_period_id, tenant_id, meal_type, menu_item_id)`, toggled on/off per item — see the 2026-07-26 revision note below; this superseded an initial single-choice design from the same day. (3) The new voting-driven system and the existing generic Food Polls feature **coexist, unmodified relative to each other** — per explicit user choice ("keep both," not "replace it"). `FoodPage.tsx`'s existing Monthly Schedule / Food Polls toggle is preserved as-is; only the Monthly Schedule side was rebuilt.
- **Revision (2026-07-26, same day):** Vote granularity was reversed from single-choice to multi-select per meal type, per explicit user direction ("tenants can vote for multiple food items per meal type, allowing the generator to build a balanced weekly schedule from collective preferences"). Schema change: `food_votes`'s unique constraint widened from `(voting_period_id, tenant_id, meal_type)` to `(voting_period_id, tenant_id, meal_type, menu_item_id)`, so a tenant can hold multiple vote rows within one meal type instead of exactly one. `POST /api/food/tenant/vote` changed from upsert-overwrite (change your one pick) to toggle (add/remove one item's vote), since there is no longer a single "current pick" to overwrite. The vote-tally step in both `voting-periods/[id]/results` and `schedules/generate` (`groupBy` on `menu_item_id`) needed **no change** — it already counted votes per item regardless of how many items one tenant could vote for, so the generation algorithm and its balanced-schedule behavior are unaffected by this reversal. Tenant UI changed from radio-style single-selection to checkbox-style multi-selection (`useTenantFoodVoting`'s `myVoteBySlot: Record<slot, itemId>` became `myVotesBySlot: Record<slot, Set<itemId>>`; `castVote` became `toggleVote`).
- **Alternatives considered:** Calendar-dated schedule rows (one row per actual date, `food_schedules` keyed by date not month) — rejected: the spec's "weekly timetable" language and the publish/edit-propagates/carry-forward requirements are all far simpler against a single repeating-pattern row than against 4-5 dated rows per month that would need to individually track publish state and repeat/vary content. Merging/replacing Food Polls with the new system — rejected by explicit user pick; the two remain product-distinct (structured monthly menu-item voting vs. ad hoc owner-created polls of any shape).
- **Consequences:** A schedule cell has no notion of "this specific Tuesday the 14th" — only "Tuesday, this month's pattern" — so any future requirement for date-specific one-off overrides (e.g. "special dinner on the 25th") would need a new, separate mechanism, not an extension of `food_schedule_meals`. The carry-forward cron's "clone from previous month" branch was not exercised against a real prior published month at build time (only its idempotent no-op branch was live-verified) — see [[Features]], [[Changelog]] for the testing-gap note. Food Polls remains entirely mock/unwired; a future decision to build it for real is untouched by this ADR either way.

## ADR-030: The Platform Admin Console deliberately reverses ADR-006 — multi-hostel SaaS billing/subscription is back, per explicit user direction

- **Date:** 2026-07-26
- **Status:** accepted
- **Context:** A new design source, `Stayo Admin Dashboard/Stayo Admin.dc.html`, specifies a full "platform admin" persona: approving hostel-owner signups and hostel *listings* across many different owner businesses, tracking MRR/ARR/churn/ARPU, billing owners a recurring subscription fee to use Stayo, generating GST reports on that platform revenue, and managing platform staff accounts. This is unambiguously a multi-tenant SaaS marketplace model. ADR-006 documents that this exact model — subscription/plan/add-on/usage-quota concepts for multiple owner-businesses — was deliberately removed from this codebase (`20260517000000_decommission_saas_tables`, 37 tombstoned `410 Gone` routes) in favor of treating each deployment as a single owner's business. Before starting any implementation, the user was directly told, in these terms, that building the Admin Dashboard as designed would reverse that documented decision, and was offered three explicit options: (1) build the full SaaS platform-admin model as designed, (2) build a scoped-down internal ops console for the current single-business model instead (no cross-owner billing/leads), or (3) defer Admin entirely and ship only the tenant-app work in this pass. **The user chose option (1) — full reversal — explicitly and with the tradeoff stated up front.**
- **Decision:** Built the Platform Admin Console as designed. `Role` gained a real `ADMIN` value (previously present only in abandoned migration history, never actually assignable — `schema.prisma` had only `OWNER`/`TENANT` immediately before this). New schema: `platform_admins` (staff sub-roles), `platform_leads` (prospective hostel *owners*, distinct from the pre-existing tenant-admissions `leads` table), `subscription_plans` + `hostel_subscriptions` + `platform_invoices` (the reintroduced marketplace billing model — deliberately reshaped around "marketplace tier" rather than the old metered-usage shape ADR-006 removed, not a literal restoration of the dropped tables), `notification_templates`, `platform_settings`, plus `hostels.verification_status`/`listing_status`. No public self-serve admin signup (`scripts/bootstrap-platform-admin.ts` creates the first one) — matches the security posture already established for owner bootstrap (ADR-028's `ALLOW_OWNER_BOOTSTRAP` gate). All `/api/platform-admin/*` routes are deliberately **cross-owner** and excluded from `architectural-invariants-check.ts`'s owner-scoping checks, since those checks exist to catch OWNER-scoped code silently leaking cross-owner data — a concept that doesn't apply to a persona whose entire purpose is seeing everything.
- **Alternatives considered:** The two declined options are recorded above rather than omitted, since the user's choice among them is the load-bearing fact of this ADR — a future reader needs to know this wasn't a default or an oversight. Reusing the exact table shapes ADR-006 dropped (`plans`, `owner_subscriptions`, `owner_invoices`, etc.) instead of new tables — rejected: those tables were designed around a different (metered/usage) billing philosophy, and this feature's design source specifies flat marketplace tiers instead; resurrecting the old shape verbatim would have been a worse fit, not a savings.
- **Consequences:** This codebase now simultaneously supports two different business-model framings that don't fully reconcile: the core tenant/rent/payment domain remains single-business-oriented (per ADR-003's `hostelId`-required invariant, e.g.), while the new platform-admin layer assumes multiple independent owner-businesses coexist on one Stayo deployment. ## ADR-041: Backend latency is addressed by fixing placement and query strategy first, before any service-code optimisation

**Date:** 2026-08-04 · **Status:** Accepted (phases 1–2 shipped; phase 3 not decided) · See [[Performance]] for all measured values.

**Context.** The owner Tenants screen was taking ~10.9s to load. The obvious reading of the network waterfall was "the queries are too slow", which points straight at `tenantService.getAllTenants` and its 10-relation `include`.

That reading was wrong, and measurement is what showed it. Two production endpoints were compared: `GET /api/tenants` unauthenticated (401 from middleware, no database access) ran in **117ms**, while `GET /api/health` (the same path plus a single `SELECT 1`) ran in **1388ms**. Function invocation was never the problem — **one trivial database query cost ~1271ms**. `x-vercel-id: bom1::iad1::…` explained why: `apps/backend/vercel.json` declared no `regions`, so functions defaulted to `iad1` (Washington DC) while Postgres runs in `ap-south-1` (Mumbai). Every query crossed the planet twice.

**Decision.** Fix causes in order of measured impact, deploying and re-measuring between each, rather than bundling changes:

1. **Pin functions to `bom1`** (`"regions": ["bom1"]`). Config only. Cost of a DB round-trip fell **~1271ms → ~28ms**.
2. **Enable Prisma `relationJoins`** (`previewFeatures = ["relationJoins"]`). Schema flag only — no service code touched, because `join` becomes the default relation load strategy on PostgreSQL once the feature is enabled (verified: an unspecified strategy emits the same query count as an explicit `join`). The `getAllTenants` `findMany` went from **14 SQL queries to 4**.
3. **Service-code optimisation is deliberately deferred** and may not be justified at all. It will be decided from measurements, not assumed.

**Consequences.**
- Region pinning is a single region; multi-region deploys require a Vercel plan above Hobby.
- `relationJoins` is a *preview* feature. Before deploying it, `query` and `join` were verified to return identical rows for the tenants `include` across every hostel — a silent semantic change here would be worse than a slow query. Re-verify if the `include` shape changes materially.
- Ordering the work this way meant the expensive refactor was never needed to get the large win. Had `tenant-service.ts` been optimised first, it would have been credited with an improvement that actually came from a one-line config change, and the real cause would have remained in place.
- The known remaining cost centres (unbounded `PAID` obligation fetch, per-`INVITED`-tenant `getReservationStatus`, the sequential ownership check) are recorded in [[Performance]] as *unmeasured* and were left in place.

## ADR-042: Hostel ordering is server-persisted and manual drag is one mode among sorts, not the only way to order

**Date:** 2026-08-04 · **Status:** Accepted · See [[Features]], [[Database]], [[APIs]].

**Context.** The Home "Property" cards rendered a `⠿` drag handle that did nothing. The feature had never been built, not regressed: `react-dnd` and `react-dnd-html5-backend` were in `package.json` but **imported nowhere**, no `DndProvider` was mounted anywhere in `src/`, and `DragHandle` was a decorative `<span aria-hidden="true">` with no handlers. `hostels` had no ordering column either, so nothing could have been stored. Even fully wired, `react-dnd-html5-backend` would not have worked on the owner's phone — the HTML5 drag-and-drop API doesn't fire on touch.

**Decision.**

1. **Manual order persists server-side** in `hostels.display_order`, not `localStorage`. The owner's stated reason for wanting it — deliberately promoting a hostel they're watching — is a decision about their business, not a per-browser view preference; an order that silently differs between their phone and their desktop would read as broken.
2. **Drag is one mode among five sorts** (My order · Most dues · Most vacant · Top revenue · Name), not the only ordering mechanism. At two or three properties, hand-ordering earns little; sorting by dues answers a question the owner actually has daily. Manual order earns its keep as the portfolio grows.
3. **The handle appears only in "My order" mode.** Hand-ordering a metric-sorted list is incoherent, and hiding the handle explains *why* it can't be dragged rather than leaving a dead affordance — the exact failure this ADR exists to fix.
4. **Drag starts from the handle only** (`dragListener={false}` + `useDragControls`, plus `touch-none` on the handle). This is what makes it work on touch: the card keeps tap-to-drill and the page keeps vertical scroll everywhere except the handle itself.
5. **`motion` rather than a new drag library.** It was already a dependency and already used in `TenantCard.tsx`; `motion/react` exports `Reorder` and `useDragControls`. `react-dnd` and `react-dnd-html5-backend` were removed as dead weight.
6. **Move up / Move down in the ⋮ sheet** is the keyboard and screen-reader path. Dragging is inherently pointer-only, so drag alone would make the feature unreachable without a mouse or touch.

**Consequences.**
- Sort mode is view state and stays in `localStorage`; only the *order* is owner data and goes to the server. Splitting them keeps the server contract to the thing that genuinely needs to follow the owner across devices.
- `MockProperty` gained optional numeric fields (`occupancyPercent`, `revenueValue`, `outstandingValue`, `displayOrder`) because sorting cannot use the formatted display strings — `'₹1,32,600'` doesn't compare numerically.
- `DragHandle` is dual-mode: interactive only when given an `onDragStart`. Its three other call sites (floor groups, room layout, food-poll options) stay decorative **on purpose** — those reorder behaviours also don't exist, and making them look interactive would recreate this same bug elsewhere.
- The occupancy pill now tones by threshold. It had been hardcoded `success`, so 75% and 88% rendered identically green — a status-shaped decoration carrying no status.
- **Second adopter, 2026-08-06:** the Food module's weekly editor uses point 4's handle-only rule verbatim for drag-to-swap on its meal chips (`DayRow.tsx`, see [[Food]] §7.1) — **this ADR was reused, not extended**; no new drag policy was set, and no new ADR was written for it. The adoption does expose the limit of point 6, though: chips have **no** Move up / Move down equivalent, so unlike the Property cards their direct swap is pointer-only. The capability is reachable the long way (edit each cell), so nothing is unreachable without a pointer — but the parity this ADR set for hostels does not yet hold there.
- **Not verified by automated backend tests.** `tests/hostel-order-service.test.ts` was written (8 cases: ordering, NULL default, cross-owner rejection, partial-list rejection, duplicates, idempotency, owner isolation, portfolio read-through) but **never executed** — `DATABASE_URL_TEST` is defined nowhere and `.env.test` does not exist, so the entire backend suite is unrunnable in this environment, a pre-existing gap confirmed by an untouched existing test failing identically. Verified live against the real API instead. Running the suite needs a test database provisioned first.

## ADR-043: One business concept, one screen — billing behaviour is configured in exactly one place, and the collect flow states the policy instead of refusing at the end

**Date:** 2026-08-05 · **Status:** Accepted · Direction set explicitly by the user. See [[Business-Rules]], [[Features]], [[Bugs]].

**Context.** An owner collecting ₹100 against ₹8,000 of rent was told *"Full payment required. Minimum: ₹8,000 (Rent)"* at the confirmation step — and could find nowhere to change it. Investigation found four distinct problems behind that one symptom:

1. `partial_payments.enabled` was fully implemented and **enforced** in `settlement-planner.ts`, defaulted to `false`, and was **exposed in no UI whatsoever**. The enforcement shipped; the control never did.
2. The review sheet rendered the refusal **and** a full success preview at once — "1 installment left part-paid", "₹7,900 still outstanding", "a receipt is generated" — describing an outcome that could not happen, while Confirm sat disabled.
3. **Three screens** each owned a slice of billing: `MoreBillingPage` (Settings → "Rent and billing"), `MoreConfigLateFeesPage` (Configure → Finance) and `MoreConfigTenantDefaultsPage` (Configure → Hostel). The first wrote `type: 'FLAT'` unconditionally and omitted `max_amount`, so opening it after configuring a PERCENTAGE fee with a cap **silently destroyed both**.
4. Three Configure screens pinned their save bar at `bottom-0` with no nav offset or z-index, putting the save button **underneath the bottom nav**.

- **A second floor type, `minimum_percentage`** (0-100 of total outstanding), added alongside `minimum_amount`. Both are floors, so the **larger wins**; the result is clamped to the outstanding balance so a large absolute floor can't strand a small final balance.
- **The collect flow states the policy before the owner types an amount** ("Full payment only" / "Part payments allowed", with the floor spelled out and a Change link), and the review step **either** explains the block with a route to fix it **or** shows the outcome — never both.
- **Owner language everywhere.** No screen or message names `allow_partial_payments`, `minimum_amount` or `payment_policy`. Enforced by tests that assert those strings never appear in generated copy.

**Consequences.**
- Wording changes to `rejection_reason` broke 3 existing assertions that pinned the old sentences. They were updated to assert the new wording — the change was deliberate, not a regression.
- `PaymentPolicy.minimum_percentage` is **optional** so the many callers that hand-build a policy keep compiling and behave as 0.
- Deposit/agreement defaults moved out of Configure → Hostel; that row now points at Billing policy rather than 404ing.
- **A `test:pure` runner was added** (`vitest.pure.config.ts`, no `setupFiles`). The main config loads `tests/setup.ts`, which imports `lib/db` and TRUNCATEs the `test` schema, so with no `DATABASE_URL_TEST` provisioned the *entire* suite is unrunnable — including tests of genuinely pure functions like `buildSettlementPlan`. That meant financially sensitive allocation logic could not be verified locally at all. `test:pure` runs 56 such tests with no database reachable. **This is a stopgap** — provisioning a real test database remains open work, and every DB-touching test is still unrun.
- `npm run check:financial-safety` and `check:payment-production` both still exit 1. **Pre-existing and unrelated**: the first points at `backend-next/prisma/migrations`, a directory that does not exist in this repo layout, and reports payment-ledger triggers that were never applied; the second warns about env keys expecting `sriadithyahostels.in`, the pre-Stayo domain. Neither inspects anything this change touches.

## ADR-044: Universal search is a provider registry, and a search result is a place work gets done

**Date:** 2026-08-05 · **Status:** Accepted (Phase 1 of 4) · Direction set by the user: *"Do not build pages. Build workflows."* See [[Features]], [[APIs]].

**Context.** The owner Home had a search bar that was a `<div>` containing a `<span>` — not an input, no handler. Behind it sat **two overlapping tenant-search implementations**: `/api/owner/search` (documented as "for the global navbar", tenants only, no ranking, bare-array response outside the standard envelope, and **orphaned** — its client wrapper `ownerService.searchTenants` existed but nothing in the app called it) and `/api/payments/quick-collect/search` (genuinely good ranking, but ACTIVE-tenants-only and issuing a per-tenant obligations query *plus* a ledger query for every hit — 40 round-trips for 20 results).

**Decision.**

1. **One universal endpoint, rebuilt on the orphaned path.** `/api/owner/search` becomes the single entry point. It had the right name, was already owner-scoped, and had zero consumers to break.
2. **A provider registry, not a search function.** Sources implement `SearchProvider` and are listed in one array. **The route never names a result type**, and neither does the client: each result carries its own `href` and display fields, so adding payments, complaints, expenses, receipts or staff means writing a provider and registering it — no route change, no response-shape change, no UI change. The moment anything outside a provider branches on a type, that property is gone.
3. **Ranking is a pure, tested module**, shared by all providers so a tenant result and a hostel result stay comparable on one scale. Priority per product direction: exact name → phone → room → hostel → prefix → contains → fuzzy. Scores are spread (100/95/90…) so a future provider can slot between two without renumbering.
4. **Providers are fault-isolated.** `Promise.allSettled` — one failing source degrades its own group and never blanks the search mid-keystroke.
5. **A result is a workspace, not a link.** Tenant rows carry inline Call / WhatsApp / Copy number / Collect / Profile. Collect deep-links into the *existing* QuickCollect flow with the tenant preselected. Actions appear only when they can work — no Call without a number, no Collect for an invited tenant or a zero balance.

**Consequences.**
- **Reuse over reimplementation:** the hostel provider composes `portfolioService.getPortfolioSummary`, so search occupancy/dues are the same numbers the Home cards show rather than a second calculation that could drift. The tenant provider composes `financialService.getTenantPaymentSummary` — sync, pre-fetched rows, one query for all matched tenants — so outstanding is never independently derived (CLAUDE.md).
- `/api/payments/quick-collect/search` is deliberately **left alone**: its per-tenant ledger fetch is appropriate for a considered payment flow and wrong for a typeahead. Two callers, two cost profiles, one shared ranking idea.
- `whatsAppNumber()` returns `null` rather than guessing a country code it can't infer — a WhatsApp button that opens the wrong chat is worse than no button.
- Phone matching compares the **national 10-digit tail**, so `9845013001`, `+91 98765 43210` and `919845013001` are one person. A unit test caught this before it shipped: the first implementation scored a bare-10-digit query against a `+91`-stored number as a weak *contains*.
- `viewState()` makes `loading` beat `empty`, so "No matches" can never flash at an owner who is still typing.
- Room results deep-link `?room=<id>`, consumed and then cleared from the URL so a back navigation doesn't silently reopen the sheet.
- **Phases 2–4 (Collect Rent queue, agreement/activation/vacancy queues, unified daily task list) are not built.** The Action Center still shows counts only.

## ADR-045: The collection queue is a work list with an explainable score, not a filtered tenant list

**Date:** 2026-08-05 · **Status:** Accepted (Phase 2 of 4) · See [[Business-Rules]], [[Features]], [[APIs]].

**Context.** The Action Center's "Collect Rent" card showed a total and a `›` chevron — and had **no `onClick`**. The fifth dead affordance found in this codebase. Owners could see ₹1,08,600 was owed and had nowhere to go with it.

**Audit first, per the standing rule.** `/api/owner/finance/collections` is a 410 tombstone. `paymentService.getDuesReport` is per-*obligation* and hostel-scoped, while a queue is per-*tenant* and portfolio-wide. `financialService.getTenantDues` is per-tenant and async — N+1 for a list. The right primitive already existed: **`financialService.getTenantPaymentSummary`**, which is sync and documented as taking pre-fetched rows specifically for batch/list views, plus **`isOverdue()`** from the settlement planner and the **`reminder_logs`** table.

**Decision.**

1. **Never compute money twice.** `outstanding` and `last payment` come from `getTenantPaymentSummary`; overdue-ness from `isOverdue()`. The queue service assembles existing answers and orders them — it derives no financial figure of its own.
2. **Fixed query budget of 4**, whatever the tenant count: tenants, open obligations (+payments), reminders (grouped), historically-late obligations. A per-tenant fan-out would be 2N.
3. **Every point is attributed.** A score is never a bare number: `factors[]` carries `{id, label, points}` in owner language, the UI shows the top two on the card and all of them in a bottom sheet, and a test asserts `score === sum(factors)`. Ordering can always be explained without reading code.
4. **Buckets order sections; score orders within a section.** One global score would let a large not-yet-due balance outrank a small long-overdue one — the opposite of how an owner works.
5. **A recent reminder defers a tenant, but only up to a point.** Chasing someone the day after you chased them is noise. **Caught against live data:** without a severity cap this rule put 7 of 10 tenants into "waiting" and demoted an 11-day-overdue tenant below a 12-day one, reporting almost no work while ₹59,000 sat uncollected. `reminderCooldownMaxOverdueDays` (7) now stops the deferral once reminders have visibly failed.
6. **`recommendation: null` ships on the contract from day one.** The recommendation engine is explicitly out of scope, but reserving the field means adding it later is a value change, not a redesign of the page.

**Consequences.**
- The service takes `hostelFilter: string | null`, **not** an optional hostel id. The architectural invariant caught the optional form and was right to: explicit `null` makes "whole portfolio" a stated decision rather than a forgotten argument. (Amusing side-note: the check is a plain regex over source, so quoting the banned signature *in a comment explaining the avoidance* also tripped it.)
- Prioritisation is pure and clock-injected (`today` is a parameter), so ordering is reproducible and runs under `npm run test:pure` — which matters, because the backend suite still cannot run without a test database.
- Buckets are returned only when non-empty; an empty section is a decision the owner has to make for no benefit.
- **Verified end-to-end against live data, before and after the fix.** Pre-fix: 3 in "needs attention", 7 in "waiting", with an 11-day-overdue tenant demoted below a 12-day one. Post-fix: **4 in "needs attention"** (12d, 12d, 12d, 11d) and **6 in "waiting"** (all 5d) — the 11-day tenant correctly promoted. Same 10 tenants, same ₹84,500 total, so the fix changed placement without disturbing any figure.

## ADR-047: Expense entry is backed by the owner's own history, and never invents a value

**Date:** 2026-08-05 · **Status:** Accepted (Phase 1 of 4) · Direction set by the user: *"Do not build an expense tracker. Build an expense memory system."* See [[Features]], [[APIs]].

**Context.** The Add Expense wizard opened on an empty form whose helper text read *"Suggestions come from your past entries."* — a promise nothing kept.

**Audit first, and it changed the work entirely.** The `expenses` table already carried `vendor_name`, `payment_method`, `receipt_url`, `is_recurring`, `recurring_frequency`, `notes` and `metadata`. `expenseService.getFrequentExpenses` already grouped expenses by normalised title and returned vendor, category, payment method, occurrence count, last amount and last date. `getExpenseTitleSummary` already produced spend summaries. Both were exposed via `mode=suggestions` / `mode=title_summary`, and **both had frontend wrappers** (`getSuggestions`, `getTitleSummary`). Neither had a single caller anywhere in the app. **The tenth built-but-never-wired feature found in this codebase**, and the most misleading, because the UI explicitly advertised it.

**Decision.**

1. **Extend, don't parallel.** `getExpenseMemory` was added to the existing `expense-service`, and exposed as another `mode` on the existing `/api/expenses` route — no new service, no new endpoint. It adds what the entry form actually needs on top of the existing grouping: average and highest amount, notes, recurrence, receipt-attachment rate, hostel spread, and the day-of-month history that drives prediction. A **vendor-keyed** view sits alongside the title-keyed one, so typing a supplier works as well as typing what was bought.
2. **Nothing is invented.** Where the owner never supplied a value, the field stays `null` and the form stays empty. Reuse prefills the **last** amount rather than the average, because the average is a number that never actually occurred and the owner is about to correct it anyway.
3. **Prediction is historical, not clever.** `typicalDayOfMonth` uses the **median** so one mistimed entry can't drag it, and returns `null` when there are fewer than three occurrences or when they're genuinely scattered — a wrong nudge is worse than none. `dueAroundNow` also requires that nothing has been recorded this calendar month.
4. **Ranking is frequency-first, recency-second, with due-now dominant.** A recency-only order would bury a weekly rice delivery under a one-off repair. Caught by test: the due-now bonus was initially +100, which quietly lost to a frequent recent expense (max 230) — it is now larger than any achievable frequency+recency total, so "due around now" genuinely jumps the queue as the comment claimed.
5. **The wizard is preserved.** Per the "do not redesign everything" rule, the three-step flow is untouched; the empty first step simply became a list of the owner's own history. Reusing an entry advances straight to the amount, making the target **reuse → edit → save**.

**Consequences.**
- All ranking, pattern detection and phrasing live in the pure `lib/services/expenses/expense-memory.ts`, so they run under `npm run test:pure` while the backend suite still has no test database.
- Two aggregate queries regardless of history size; no per-expense fan-out.
- `getFrequentExpenses` is left in place and still serves `mode=suggestions` — it has no callers, but removing it is a separate decision from wiring its successor.
- **Verified live**: with 11 real expenses, browsing returns the two genuinely repeated items, and typing "rice" returns three entries including the vendor *Sri Rice traders* with category, payment method, average and last purchase — the spec's own example. `typicalDayOfMonth` correctly returned `null` for both, refusing to claim a monthly pattern from two occurrences.
- **Phases 2–4 (search summaries, dashboard simplification, branded exports) are not built.** `getExpenseTitleSummary` already exists and is the natural backbone for Phase 2.

## ADR-048: Food Polls is deleted — the real voting system is the only voting system; and a published menu is never destroyed by a rebuild

**Date:** 2026-08-05 · **Status:** Accepted (Phases 0–1 of 3) · **Supersedes [[Decisions#ADR-029|ADR-029]] point (3)** · Direction set by the user in a design session after the audit: *"delete it"* — an explicit reversal of the earlier *"keep both."* See [[Food]], [[Features]], [[APIs]], [[Bugs]].

**Context.** `docs/audits/food-module-audit.md` (2026-08-05) audited the whole Food lifecycle against live code **and live production data**. Three findings drove this ADR, and two of them only became visible once the database was queried:

1. **Regenerate destroyed the live menu.** The generate route's upsert set `status: "DRAFT"` and `deleteMany`'d all 28 meal rows unconditionally. The button sat next to the green PUBLISHED badge with no confirmation and — unlike first-time Generate — no `canGenerate` gate. Since the tenant read filters on `status: "PUBLISHED"`, one tap emptied every tenant's Food tab. The route's own doc comment asserted regeneration was *"always safe."*
2. **A correct cron had never run.** `app/api/cron/food-carry-forward` was 95 lines of transactional, idempotent, `CRON_SECRET`-protected code that `apps/backend/vercel.json` simply never scheduled. Live `CARRIED_FORWARD` count: **0**. Note that [[Changelog]]'s 2026-07-26 entry claims it was registered at `0 4 * * *` — that claim was wrong, and the discrepancy is exactly why the live-data check mattered.
3. **Food Polls was pure `useState(mockFoodPolls)`.** ~600 lines of frontend — 4 hardcoded polls, `totalTenants: 180` hardcoded in two places, date/close-time rendered as `<div>`s rather than inputs, "Edit" as a toast, and `useWinner` showing *"added to menu"* while adding nothing to anything. Four hardcoded strings were presented as "Smart Insights." Everything evaporated on refresh. **And it was the Home screen's Quick Action** — so the most discoverable food feature in the product was the one that did nothing, while the real, working voting system sat unnamed on the other tab.

**Decision.**

1. **Food Polls is deleted outright — ~842 lines net, reversing ADR-029 point (3).** ADR-029 recorded that the new voting-driven menu system and the pre-existing generic Food Polls would *"coexist, unmodified relative to each other — per explicit user choice ('keep both,' not 'replace it')."* That is no longer true and this ADR supersedes it. The reversal was authorised by the user in an explicit design session, with the audit's evidence on the table. It is a small reversal: ADR-029 itself already conceded Food Polls was *"entirely mock/unwired"* and explicitly left the rebuild decision open, so what is being reversed is the coexistence, not a working feature. **No capability was lost — there was none.** The Home Quick Action was repointed at `/owner/food` and relabelled *"Food menu"* rather than left advertising a deleted feature. `FOOD_SLOTS`, `MEAL_CATEGORY_META`, `MealSlotKey` and `mealIcons.ts` were **kept** — they are real design tokens used by ~20 files across owner and tenant, and only happened to live under `shared/mocks/`.
2. **A `PUBLISHED` schedule can never be demoted to `DRAFT` nor wholesale deleted.** Enforced by the pure `decideRebuild` (`lib/services/food/schedule-rebuild-policy.ts`), not by discipline. `POST /api/food/schedules/generate` gained `mode: "BUILD" | "FILL_GAPS" | "START_OVER"` and answers `409 SCHEDULE_PUBLISHED` when refused; **`FILL_GAPS` is the only mode allowed against a published month**, because it is purely additive — it writes unassigned cells and leaves status alone. A test enumerates every `(mode × status)` pair and asserts no combination can write `status: "PUBLISHED"`.
3. **Checks inform, they never block.** `buildPublishChecks` returns only `PASS | WARN`, and a test asserts there is no third value, so no future check can acquire the power to disable Publish. A publish button a check can disable is a product arguing with its owner, and the owner is the one who knows whether Dosa every day is fine.
4. **Every week-reader consumes one shape — `WeekGrid`** (design doc §8.1, binding). Nothing may read `food_schedules` rows directly. The observation that makes this cheap: a *template* (Exam Week / Festival / Holiday) **is** a week — same 28 cells, unbound to a month — so the seam for templates is not a template system, it is a contract. Three producers exist today (generate, carry-forward, manual edit) and `food_schedules.source` already names them; a template is a fourth and one enum value. The Today card, Kitchen sheet, publish checks and Home line — the first new grid readers — all consume `WeekGrid`, which is what keeps the contract alive rather than aspirational.
5. **The undo toast replaces a draft/live workflow.** Editing a published menu is live immediately and always has been (one row per hostel-month, no version chain). Rather than building a staging pair, the edit names its own blast radius — *"Changed for every Thursday this month · students see it now"* — and offers Undo for 6 seconds. The honest sentence plus a reversal is cheaper and truer than a workflow the product model does not support.
6. **The Kitchen sheet gets no backend.** Print + a `wa.me` share link, reusing the pattern `searchActions.ts` already established. Two personas (cook, kitchen staff) that had nothing at all are served with **no new route, no notification service, and no Meta template approval** — which was the point, since a template dependency would have made Phase 1 wait on Meta. A real broadcast template stays Phase 3 and was explicitly not allowed to block this.

**Alternatives considered.** *Keeping Food Polls and rebuilding it for real* — rejected: it duplicates, in a worse mental model, what `food_voting_periods`/`food_votes` already do correctly, and two voting systems under two names was itself a top-three audit finding. *A confirmation dialog on Regenerate instead of a policy function* — rejected: a dialog is a plea, not an invariant; the destructive path had to become unreachable, and a pure function is testable where a dialog is not. *Adding `serve_date` now* to unblock festival menus — deferred to Phase 3 on the design doc's own stated prerequisite: a migration against live published menus should not ship while the backend suite still has no `DATABASE_URL_TEST`.

**Consequences.**
- **`START_OVER` currently has no caller.** The route accepts it and both frontend layers pass it through, but the UI sends `BUILD` on a draft and `FILL_GAPS` on a published month. Whether it is reserved for the Phase 2 "Plan `<Month>`" flow or is dead surface is undecided — flagged in [[Food]] rather than quietly removed.
- **Voting still runs against the month already in progress.** Only the tenant *copy* was corrected (*"Vote for next month"* → *"Vote on this month's menu"*); moving the vote to the month being planned is Phase 2. The label was made true rather than the behaviour changed, deliberately — a false label is a bug, a behaviour change is a product decision.
- **The carry-forward cron is registered but has not been observed running**, since that is deploy-gated. Its clone-from-previous-month branch remains unexercised against a real prior published month — a gap ADR-029 first flagged in July and this branch does not close.
- **The weekly-pattern ceiling is unchanged and is now documented rather than implied.** Festival menus, per-date history and cost-per-meal all still wait on one column.
- All new food logic is pure and runs under `npm run test:pure`, because the backend suite still has no test database. Food went from **0 tests to 63** (22 backend, 41 frontend).
- The vault gained [[Food]], its first **module-level** page. Correcting the audit on its own finding #8: it claimed `docs/obsidian/` had *no* Food coverage, which is not accurate — [[APIs]] carries a full 14-endpoint table and [[Database]] a full five-model section, both current. What genuinely did not exist was a [[Features]] entry, any [[Business-Rules]] coverage, and any single page tying the grain, the publish semantics and the constraints together. That gap is what [[Food]] closes.

**Related:** [[Food]], [[Features]], [[APIs]], [[Database]], [[Bugs]], [[Changelog]], [[Decisions#ADR-029|ADR-029]] (the decision this partly supersedes), [[Decisions#ADR-003|ADR-003]] (the `hostels[0]` invariant the hostel picker closes), [[Decisions#ADR-047|ADR-047]] (the compose-don't-recalculate read-model pattern `food-memory-service` will follow in Phase 2).

## ADR-050: Public enquiry-status tracking uses a bearer token in the URL, not OTP or Google re-auth

- **Date:** 2026-08-06
- **Status:** accepted
- **Context:** the owner-acquisition funnel (see [[Features]]) creates a `platform_leads` row before any account exists — a prospective owner has no session and no credentials to authenticate a "check my status" request with. Design doc §3 (D1) considered two authenticated alternatives before settling on a token: **phone + OTP** (an OTP send on every status check, adding cost and a friction step to something that should be a one-tap link) and **Google re-auth** (`platform_leads.google_email` is nullable — the phone-OTP path is the only field guaranteed present — so some leads would have no way to re-authenticate at all).
- **Decision:** `GET /api/leads/track/[token]` (see [[APIs]]) is public and unauthenticated, gated only by possession of `tracking_token` — a 32-byte hex string (`crypto.randomBytes(32).toString("hex")`) minted at row creation and never expiring, distinct from `platform_lead_invitations.token`'s 7-day-expiring activation token (see [[Database]]). This mirrors the already-proven `/owner-invite/:token` pattern rather than inventing a new access model. The response is an explicit field allowlist (`hostel_name`, `submitted_at`, `stage`, `is_terminal`, `timeline`, `applicant_message`) — `notes` (the admin's private scratchpad), the row `id`, `converted_owner_id`, and the raw status string are never selected, by construction, not by care at the call site.
- **Alternatives considered:** phone+OTP and Google re-auth, both rejected per the reasoning above — see design doc §3 D1 for the full comparison.
- **Consequences:** **the tracking token is a bearer secret.** Anyone who obtains the link (forwarded email, shared screenshot, a browser history sync) can read that enquiry's stage and `applicant_message` — there is no second factor. This is the accepted trade-off of the design, and is exactly why `applicant_message` is a distinct, deliberately-scoped column rather than exposing `notes` directly (see [[Database]]) — the blast radius of a leaked link is bounded to what the applicant was always meant to see. Because the token never expires, a lead that goes stale still has a permanently-valid tracking link; this was accepted rather than adding an expiry, since the alternative (an expired tracking link for someone still waiting on a decision) was judged the worse failure mode.
- **Implementation notes carried by this same change:** the five WhatsApp templates this funnel now sends (see [[Business-Rules]]) are declared in one new registry module, `lib/services/notifications/providers/whatsapp/platform-lead-template-contracts.ts`, rather than five separate `*-template-contract.ts` files following the established one-file-per-template pattern every earlier template used. This is a deliberate departure: the five ship together, share an identical shape (env-var name/language override, declared `bodyParameters`/`buttonParameters`, a pure payload builder), and five near-identical files would have been roughly 500 lines of copy-pasted assert/check machinery for no additional safety. Separately, template ③ `stayo_owner_account_activated` **supersedes** the older `stayo_owner_welcome` template for the owner-signup notification — `stayo_owner_welcome` and its handler (`whatsapp-owner-welcome-handler.ts`'s `sendOwnerWelcomeNotification`, `owner-welcome-template-contract.ts`) are left in place and remain **approved in Meta**, but as of this change nothing calls them: it is orphaned, not deleted, so a future reader should not mistake its continued Meta approval for it being a live sender.
- **Related:** [[Features]], [[Database]], [[APIs]], [[Business-Rules]], [[Decisions#ADR-032|ADR-032]] (the `/owner-invite/:token` pattern this mirrors)

## ADR-051: Declining a lead is its own endpoint, not a status write — and refuses once an activation link is out

- **Date:** 2026-08-06
- **Status:** accepted
- **Context:** `PATCH /api/platform-admin/leads/[id]` already allowed setting `status: "LOST"` (see [[Decisions#ADR-032|ADR-032]]), and the design's default assumption was that adding a notification would mean hooking a WhatsApp send onto that PATCH. Design doc §3 (D5) rejected that: `LOST` is used for two different real outcomes — "we reviewed the enquiry and declined it" and "the applicant went cold and stopped replying" — and a PATCH endpoint has no way to distinguish them. Auto-sending "we are unable to proceed with your application" on every `LOST` write would tell a cold lead something that was never decided.
- **Decision:** `POST /api/platform-admin/leads/[id]/reject` (see [[APIs]]) is a new, explicit action, symmetric with the existing `POST .../approve`. It **requires a non-empty `reason`** (400 `VALIDATION_ERROR` otherwise — the reason is sent to the applicant, not just logged), is guarded by the pure `canRejectLead()` (`src/services/platform-leads/lead-transition-guards.ts`), and is refused (400 `INVALID_TRANSITION`) for any lead already `APPROVED` or beyond, and for a lead already `LOST`. Only this endpoint sets `rejection_reason` and fires ⑤ `stayo_owner_lead_rejected`. The plain PATCH-to-`LOST` path is unchanged and stays silent — see [[Business-Rules]] for the full rule.
- **Alternatives considered:** hooking the notification onto the existing PATCH with a `notify: boolean` flag — rejected, since it makes "did this notify the applicant" a caller-supplied fact about a financially/reputationally sensitive send rather than a property of the action itself, and it would have let a careless PATCH silently trigger a rejection message. A single unified `POST .../decide` with `{outcome: "approve"|"reject"}` — rejected in favor of keeping `.../approve` and `.../reject` as separate, independently-guarded actions, matching the asymmetry already established by `.../approve`.
- **Consequences:** once an activation link has gone out (`APPROVED` and beyond), there is currently **no way to decline a lead through this endpoint at all** — `lead-invitation-service.ts` checks for and rejects an invitation whose status is already `CANCELLED`, but no route in this codebase was found that actually writes that status; cancelling a live invitation is a different, deliberately out-of-scope operation this change does not build, not a path an admin can currently reach. **Unknown / needs clarification:** whether an invitation-cancellation capability exists anywhere else (e.g. a script) or is simply unbuilt.
- **Related:** [[Features]], [[Business-Rules]], [[APIs]], [[Decisions#ADR-032|ADR-032]] (the `.../approve` action this is symmetric with)

## ADR-052: A tenant gets their room on joining — the onboarding payment gate is deleted, not relaxed

- **Date:** 2026-08-07
- **Status:** accepted
- **Context:** Security deposit plus maintenance were treated as a single "onboarding charge" that had to clear before a room was assigned. The rule lived in one derived read model, `reservation-status-service.ts` (`PAYMENT_PENDING` → `RESERVED` → `MOVE_IN_READY`), and was enforced in four places: room allocation at activation, a retroactive `allocateOnboardingTenantIfFinanciallyReady` that ran on every payment event, occupancy counting in `room-capacity-service.ts` (twice — the per-room path called the read model in a loop, the per-hostel path reimplemented the arithmetic inline), and a move-out block. Stayo is becoming a universal platform where many independent owners collect deposits on their own terms, usually **after** the tenant has moved in. Gating the bed on payment is wrong for that market.
- **Decision:** the gate is removed entirely rather than made configurable. `completeActivation` allocates the room unconditionally; the room-capacity check stays, because that is overbooking protection, not a payment gate. Occupancy is now "an active allocation of an `ACTIVE` tenant" with no financial input at all. `reservation-status-service.ts` and `activation-financial-enforcement-service.ts` are **deleted**, along with the `PAYMENT_PENDING`/`RESERVED`/`MOVE_IN_READY` vocabulary everywhere it surfaced — the tenant lifecycle is `INVITED` → `ACTIVE` ("Joined") → vacating → `FORMER_TENANT`. Deposit and maintenance obligations are unchanged: they were already created at invite time and already `PENDING`, so they simply stop being a gate and become ordinary dues alongside rent.
- **What deliberately survives:** `activation-financial-status-service.ts`. It is not only the gate's calculator — it is also the "how much deposit is still owed" figure behind deposit payment intents (`payment-service.ts`) and the tenant CSV export. Only its threshold fields (`depositActivationThreshold`, `depositThresholdOutstanding`, `isDepositCleared`) were removed.
- **Alternatives considered:** keeping the status vocabulary as a non-enforcing dues indicator — rejected, because a parallel status vocabulary that gates nothing is exactly the kind of surface this codebase has repeatedly let drift out of sync with the financial read model (see `docs/business-logic/financial-consistency-investigation-report.md`). Making the threshold an owner-configurable policy — rejected as building a control for a behaviour no owner asked for.
- **Consequences:** **partial/token-deposit reservations stop being expressible.** `tenants.reservation_policy`, `tenants.minimum_reservation_deposit`, the hostel-level `minimum_reservation_deposit` policy and the invite API's `minimum_deposit_threshold` are all dropped (migration 062). Reinstating that would be a new feature, not a revert. The WhatsApp `account_activated_payment_pending_v1` template is now sent by nothing — it remains approved in Meta but is orphaned, like `stayo_owner_welcome` before it. The admissions funnel loses its `reserved` and `payment_pending` stages; `activated`, `joined` and `moved_in` are now the same number by construction.
- **Related:** [[Features]], [[Business-Rules]], [[Database]], [[Decisions#ADR-053|ADR-053]] (shipped together), `docs/superpowers/specs/2026-08-07-tenant-join-without-payment-gate-design.md`

## ADR-053: A `tenants` row is one tenancy, not one person — one live tenancy per profile, enforced by a partial unique index

- **Date:** 2026-08-07
- **Status:** accepted
- **Context:** `tenants.profile_id` was `@unique`, so a person could have at most one `tenants` row **ever**. Invitation creates a fresh row with `profile_id: null` and activation links the profile to it, which meant a `FORMER_TENANT` who had moved out and settled could not be invited to a second hostel: the invite path rejected them with `ALREADY_EXISTS: User with this email already exists`, and past that check the unique constraint would have failed at activation anyway. "One hostel at a time" was implemented as "one hostel, forever". Separately, two owners could each invite the same person, and whoever's link was clicked second got a raw `ALREADY_ACTIVE` error or a Prisma constraint violation.
- **Decision:** drop the global unique and enforce the actual rule in Postgres instead — `tenants_one_live_tenancy_per_profile`, a partial unique index over `status IN ('INVITED','ACTIVE')` (migration 062). Each stay becomes its own row with its own payments, obligations, agreements and allocations. Because activation is what sets `profile_id`, the same index also closes the rival-invite race at the database level. `profile.tenants` becomes a list; every read goes through `lib/tenancy/active-tenancy.ts` (`liveTenancyWhere`, `liveTenancyInclude`, `selectLiveTenancy`, `selectCurrentTenancy`) rather than taking `[0]`.
- **Two selectors, deliberately:** `selectLiveTenancy` **throws** if two rows are live — that state means the index is missing or was bypassed, and picking either would silently attach money to the wrong hostel. `selectCurrentTenancy` (live, else most recent) exists only for activation-link paths, which must still be able to say "this invitation was cancelled/expired" — statuses a live-only filter would hide behind a generic "link invalid". Anything making an authorisation or money decision uses the former.
- **Alternatives considered:** mutating `hostel_id`/`owner_id` on the existing row when someone re-joins — rejected: Hostel A's payments, agreements and move-out records would follow the tenant into Hostel B and become visible to the new owner. A separate `tenancies` table alongside `tenants` — rejected as a second source of truth for the same fact.
- **Consequences:** ~20 call sites that did `findUnique({ where: { profile_id } })` and relied on the old constraint now use `liveTenancyWhere`; without that, a returning tenant would resolve to the hostel they left. One deliberate exception is documented in `tenant-service.requestReactivation`, which targets a *non*-live tenancy by design and would become permanently unreachable under a live-only filter. The eligibility rule ("no live tenancy, and every stay you actually moved into has a `COMPLETED` move-out") lives in `tenancy-eligibility-rules.ts` as pure functions; it treats an invitation that expired or was cancelled **before activation** as owing no settlement, so a never-arrived tenant is not trapped on the platform forever.
- **Disclosure rule:** the invite refusal names the hostel **only when it belongs to the asking owner**. For any other owner's property it says only "currently a tenant at another property on Stayo" — no name, no room, no tenant id. Otherwise any owner could enumerate a competitor's roster, and a person's address, by typing the right email. Enforced on both sides: the backend blanks the fields, and `parseTenancyConflict` on the frontend ignores a hostel name that arrives without an `OWN` scope.
- **Related:** [[Features]], [[Business-Rules]], [[Database]], [[APIs]], [[Decisions#ADR-052|ADR-052]] (shipped together)

## ADR-058: The billing policy splits into focused per-section screens, with section-scoped writes

- **Date:** 2026-08-08
- **Status:** accepted (refines [[Decisions#ADR-043|ADR-043]], does not reverse it)
- **Context:** ADR-043 consolidated three overlapping billing screens into one because each owned a slice of `billing` and they overwrote one another — the old `MoreBillingPage` silently rewrote a PERCENTAGE/PER_DAY late fee to FLAT and dropped its cap by writing a **partial** late-fee shape. That fixed the data hazard but produced a single 352-line form holding five sections, and every Finance row deep-linked to it. Tapping "Security deposit" landed the owner in a six-section wall with no indication which block was theirs — the module screen promised focus the destination did not deliver.
- **Decision:** one form implementation, rendered with only the sections it is asked for, plus a thin screen per section (`rent-schedule`, `part-payments`, `deposit`, `late-fees`, and `agreement-duration` under Hostel). Each Finance row opens the screen that owns *its* fields.
- **What keeps ADR-043's guarantee:** `buildBillingPatch(values, sections)` emits **only** the visible sections' fields, and `PATCH /hostels/:id/preferences` deep-merges — so a hidden section is left exactly as stored and a focused screen cannot clobber what it does not display. The late fee is always written **whole** (type + amount + cap together), which is the specific partial write ADR-043 existed to prevent. Both properties are unit-tested in `billingSections.test.ts`, including one test asserting a schedule patch never mentions `late_fee`, `deposit`, `partial_payments` or `invite_defaults`.
- **One field, one owner:** the deposit lives under Finance and agreement duration under Hostel; neither screen shows the other's field. The old combined `tenant-defaults` row (which showed both) is gone, and its route redirects to `agreement-duration`. A test asserts the Hostel screen has no `security-deposit` row.
- **Also gained:** "Part payments" becomes a real Finance row. `billing.partial_payments` was always stored and editable, but only reachable by scrolling the combined form, so it was effectively hidden. The all-sections screen survives as "All billing settings" for reviewing everything at once, but is no longer any row's deep-link target.
- **Alternatives considered:** duplicating the form per screen — rejected, that is precisely how the three original screens diverged. Keeping the monolith and scrolling to an anchor — rejected as a cosmetic fix that still shows five sections' worth of controls when the owner asked about one.

## ADR-054: Google sign-in is available to tenants, gated by activation rather than by role

- **Date:** 2026-08-08
- **Status:** accepted (supersedes the Owner/Admin-only restriction in [[Decisions#ADR-031|ADR-031]])
- **Context:** `resolveSupabaseSession` rejected any TENANT reaching a session through Google with `TENANT_GOOGLE_NOT_ALLOWED`. The original reasoning was that tenants are provisioned by invitation and must not be able to self-provision. But the invariant that actually protects that is "never auto-provision an account", which is enforced separately — an unknown email is rejected whatever the provider. Blocking by role only guaranteed that a tenant whose account email *is* their Google address had to remember a password Stayo had assigned them.
- **Decision:** remove the role check; keep the auto-provisioning ban. A Google identity resolves to an existing `profiles` row by `auth_user_id`, else by verified email, else it is rejected. In exchange, the gate `authService.login()` applies to an `INVITED` tenancy is **mirrored** here as `TENANCY_NOT_ACTIVATED` — an invited-but-not-activated tenant reaching a dashboard through Google would otherwise skip activation entirely, which is the one thing role-blocking was incidentally preventing.
- **Alternatives considered:** leaving tenants on password-only — rejected, the user asked for parity across roles and the security argument did not survive inspection. Allowing Google to *create* a tenant profile — rejected outright: tenancy is an owner-initiated relationship, and self-provisioning would let anyone with a Google account appear in a hostel's roster.
- **Consequences:** `tests/auth-hardening-security.test.ts` now asserts the *absence* of `TENANT_GOOGLE_NOT_ALLOWED` and the presence of the activation gate, so re-adding a blanket role block fails the suite. Tenants who sign in with Google land on `/tenant/home` via `AuthCallbackPage`'s existing routing. Owners and admins are unaffected.

## ADR-055: Password reset offers a second channel (WhatsApp OTP) that converges on the existing reset endpoint

- **Date:** 2026-08-08
- **Status:** accepted
- **Context:** reset was email-only, and email is the weakest link in this product's identity story: tenants are frequently onboarded with an owner-supplied address they cannot read, and the Resend account has no verified sending domain, so mail falls back to a sandbox sender that only reaches the Resend account owner. Meanwhile a hardened phone-OTP pipeline already existed for signup (hashed codes, 5-minute TTL, attempt caps, per-phone and per-IP limits, replay lock).
- **Decision:** add `POST /api/auth/forgot-password/phone` (send a code) and `POST /api/auth/verify-reset-otp` (exchange a verified code for a **5-minute, channel-tagged** reset token). The token is then submitted to the **existing** `POST /api/auth/reset-password`. Setting the password — the one-time-use Redis lock, session revocation, Supabase identity sync — keeps exactly one implementation rather than gaining a phone-shaped copy.
- **Fails closed, deliberately:** the OTP purpose `PASSWORD_RESET` is **not** in `SKIPPABLE_OTP_PURPOSES`. Those purposes degrade to "no code required" when WhatsApp is unconfigured, which is a reasonable trade for signup phone verification and a full account-takeover vector for password reset. `tests/password-reset-otp-purpose.test.ts` guards this and was verified to fail when the purpose is added to that list.
- **~~No enumeration:~~ AMENDED 2026-08-08 — the phone leg now discloses whether the number is registered.** As originally shipped, both phone endpoints answered identically for a registered number, an unregistered one, and one whose send was rate-limited. That was reversed the same day, deliberately, for two reasons. First, **the product already discloses the same fact**: `selfSignUpOwner` and `selfSignUpTenant` reject a duplicate with `ALREADY_EXISTS: Phone number already registered` on public unauthenticated routes, so anyone could learn whether a number was registered from a signup form — the reset endpoint was guarding a secret already given away. Second, the cost was real and immediate: someone who mistyped a digit sat on a code-entry screen for five minutes waiting for a code that had never been sent. `POST /api/auth/forgot-password/phone` now returns **404 `NO_ACCOUNT_FOR_PHONE`**, and a send failure returns its own code instead of a fake success, so the UI can keep the caller on the number step with the field still editable.
- **What still holds after that amendment:** a **deactivated** account reports as absent, so account *status* is still never disclosed. And the **email** leg remains fully generic: `delivery_degraded` is derived from provider configuration only, never from whether the address has an account, because no equivalent signup-side leak exists for email addresses that would justify changing it.
- **CORRECTED 2026-08-08 — the rate-limit claim in the first version of this ADR was wrong.** It said the per-phone (5/15min) and per-IP (20/hr) limits mean this "cannot sweep a number range." Two errors: (1) **the per-phone limit does nothing against enumeration** — probing means trying *different* numbers, and each new number gets its own fresh budget, so only the per-IP limit constrains it at 20/hour, and IPs are cheap; (2) **the limits were entirely inert at the time**, because `checkFixedWindowLimit` is Redis-backed with no DB fallback and Upstash was not configured — verified empirically: a 6th request to a 5-per-15-min endpoint returned `200`. Redis was provisioned later the same day and the limiter now enforces (the same probe returns `429` on the 6th). **The honest statement is: enumeration is rate-limited to roughly 20 probes/hour/IP when Redis is configured, and unlimited when it is not.** Treat the per-IP limit as the only enumeration control, and note it fails open by design (`failOpen: true`).
  - *If the enumeration property is ever wanted back, it has to be restored in the signup routes first — fixing it here alone would be theatre.*
- **Alternatives considered:** setting the password directly in the verify call — rejected, it would duplicate the reset logic including the one-time-use lock. A long-lived phone token — rejected: unlike an emailed link, this token is handed straight to the browser, so it gets minutes. SMS as a third channel — out of scope, WhatsApp is the only transport implemented.
- **Consequences:** `generateResetToken` gains `{ expiresIn, channel }` and `verifyResetToken` returns the channel; a token with no channel claim reads as `email`, because links minted before this change are still in real inboxes. `profilePhoneCandidates` is exported from `auth-otp-service` so reset lookups match phone-number variants the same way OTP verification does — two notions of "same number" would mean sending a code and then failing to find the account.
- **Related:** [[APIs]], [[Features]], [[Business-Rules]], [[Bugs]], `docs/superpowers/specs/2026-08-08-auth-recovery-design.md`

## ADR-059: A hostel can waive the tenant agreement ceremony, but never the `Agreement` record

- **Date:** 2026-08-09
- **Status:** accepted
- **Context:** owners asked to run hostels without a signed tenant agreement — common for small PGs operating on trust. No flag existed: `activation-workflow-service.assertTransition` unconditionally required `rules_accepted` and `agreement_signed` before `PROFILE` and `ACTIVATE`, and a second, independent gate in the finalise path required `rules_accepted` again.
- **The trap:** "turn off agreements" reads like "stop creating agreements", and that would break billing. The `Agreement` row is the **financial contract** — `contract_rent` is what `payments/rent-change-service.ts` mutates, what obligations are generated against, and what renewals and move-out settlement key to. Suppressing it would not skip paperwork, it would detach rent from its contract.
- **Decision:** `tenant_rules.agreement_required` (default **true**) governs the **signing ceremony only** — the `RULES` and `AGREEMENT` onboarding steps and the guards enforcing them. `Agreement` rows are still created exactly as before. The distinction is stated in the owner-facing screen too ("Rent, dues, deposits and move-out settlement are unaffected"), because an owner reading "not required" could otherwise reasonably assume the opposite.
- **Defaults to required, and an absent flag reads as required.** Every hostel predating this field keeps demanding a signature; a missing flag must never silently relax a legal step. `isAgreementRequired` treats `undefined` and `null` as `true`, and this is tested directly.
- **Skipped steps are reported as skipped, not as complete.** `rules_accepted` / `agreement_signed` keep reporting what genuinely happened; progression and `progress_percent` are computed over `requiredActivationSteps()` instead. Marking them `true` would have been a one-line fix that falsified the audit trail and made a tenant who signed nothing indistinguishable from one who did. Progress becomes 2-of-3 rather than 2-of-5.
- **`agreementRequired` is passed into `computeState`, not read from `tenant.hostels`.** Only one of the four call sites includes the hostel relation (`liveTenancyInclude` does not), so an implicit read would have fallen back to "required" on three paths — the setting would appear broken on some flows and work on others. A narrow `resolveAgreementRequired(hostelId)` select gives every call site the same answer.
- **Both gates were updated.** The finalise path at the end of `activation-workflow-service` re-checks `rules_accepted` independently of `assertTransition`; changing only the state machine would have left agreement-free hostels unable to activate at all.
- **Consequences:** the tenant activation UI needed no flow change — it is driven by `current_step`, which now skips the ceremony — but `ActivationProgress` had a hardcoded four-stage bar, so the "Agreement" pip is dropped when the requirement is off (defaulting to shown, so un-updated callers are unaffected). Attempting `RULES`/`AGREEMENT` on a hostel that does not require them is now itself an invalid transition rather than silently allowed.

## ADR-061: Waiting is a brand moment — the Stayo mark's windows light up, and the app has no circular spinners

- **Date:** 2026-08-09
- **Status:** accepted
- **Context:** loading state was whatever each screen's author reached for: 67 `animate-spin` rings across 42 files (four different colour treatments — `border-accent`, `border-white`, `text-[#F07B1D]`, `text-[#FF7A00]`), four different route-`Suspense` fallbacks, one bare `bg-slate-50` rectangle on the public route tree (off-palette entirely), and — worst — **nothing at all before the JS bundle arrived**, so a cold load was a white page for the length of the download. The one thing every user sees on every visit had no design.
- **Decision:** one loading system, `shared/ui/brand/`, built on a single gesture — the mark's four windows lighting clockwise, like a hostel filling with people. Three scales (`StayoLoader` for buttons/rows, `StayoLoadingBlock` for section bodies, `StayoLoadingScreen` for whole surfaces) plus `StayoErrorScreen`, which is the same stage with the windows unlit and one guttering. **Circular spinners are removed from the app and are not to be reintroduced**; `Loader2` was dropped from every import that had it.
- **The palette is hard-coded, not tokenized.** These surfaces render before a `ThemeProvider` `data-app-theme` scope exists, so `--primary`/`--accent` resolve to the legacy theme or to nothing. Hard-coding is what makes a route fallback, an auth gate and the boot splash actually look identical. Accepted cost: a future rebrand touches this file rather than falling out of the tokens.
- **`index.html` gets a pre-React boot splash (`#stayo-boot`) that duplicates ~40 lines of that CSS and the mark's outline path (~6.7 kB, ~2 kB gzipped).** Duplication is the point: it cannot import anything and still has to paint on the HTML parser's first pass. `main.tsx` fades it out after React's first commit, into a `StayoLoadingScreen` drawing the same screen, so the hand-off reads as one continuous surface rather than a restart. **Both copies must be edited together** — noted in the file headers and in [[Frontend]].
- **Pane sequencing is CSS `animation-delay`, not `requestAnimationFrame`.** The design source drove it from a rAF loop; expressed declaratively it is visually identical, costs no main-thread work, and keeps running while the bundle parses — which is exactly when it matters.
- **Layout skeletons were kept where they beat a splash.** Cold boundaries (platform entry, auth gates, public/auth/journey routes) show the brand screen; transitions inside an already-mounted shell keep their skeletons, because a full-screen takeover on a tab change reads as *slower*, not more branded. "Brand consistency" is not "the same screen everywhere".
- **Error screens were redesigned onto the same stage** rather than left as red-alert cards. Tailwind `red-*` on a cream/terracotta product reads as a browser warning pasted on top of it, and made a flaky-Wi-Fi moment look like data loss. Severity now comes from the badge icon and the copy; stack traces are dev-only and collapsed. `PageError`/`ErrorCard` kept their exact prop signatures, so no caller changed.

## ADR-060: The security deposit stores a calculation *mode*, and the owner sees the resulting rupees before saving

- **Date:** 2026-08-09
- **Status:** accepted
- **Context:** `billing_defaults.deposit_calculation_mode` (`FLAT` | `MONTHS_OF_RENT`) has existed in the backend all along — `resolveTenantInviteDefaults` resolves `MONTHS_OF_RENT` as `deposit_months × rent`. No UI ever wrote it. The Deposit screen wrote `deposit_months` **alone**, so an owner setting "2 months" changed nothing: the stored mode stayed `FLAT` and invites kept using `default_amount`. A silently inert setting.
- **Decision:** the Deposit screen owns the mode explicitly. `buildBillingPatch` writes `calculation_mode` together with whichever amount that mode uses, and only that one — so flipping modes preserves the other value via the backend's deep merge.
- **"Off" is stored as a flat ₹0, because `resolveTenantInviteDefaults` never reads `deposit.enabled`.** It resolves the amount from the mode regardless. Leaving `MONTHS_OF_RENT` stored while switching the deposit off would keep collecting months × rent from every new tenant. Flat ₹0 is the one shape that resolves to nothing. This costs a saved flat amount when switching off from months mode — accepted, because "off" collecting money is not a trade worth making.
- **The consequence is shown, not just the setting.** "2 months" means a different number per room, and the arithmetic only happens later at invite time. The screen states it up front from the hostel's real rents: an exact figure when every room charges the same, a range when they differ, and nothing invented when no room has a rent. The rents come from the grouped-rooms payload the Configuration hub already fetches, so the preview costs no extra request.
- **It also surfaces a trap rather than hiding it:** `rent = auto_fill_room_rent ? room.base_rent : 0`, so `MONTHS_OF_RENT` with auto-fill off resolves to **₹0**. The preview says so explicitly instead of showing a confident ₹16,000 that will not be collected.
- **Consequences:** the Finance row now describes the deposit by mode (`describeDeposit`), and a flat ₹0 deposit that is switched on reads as `attention` rather than the `configured` it previously claimed. `refundable` also becomes editable — it was stored, read by move-out settlement, and unreachable in the UI.

## ADR-057: Food Polls is rebuilt as a real, independent feature — a deliberate third poll/vote system, not a revival of the deleted mock

- **Date:** 2026-08-08
- **Status:** accepted
- **Context:** the owner shared screenshots of a "Food Polls" list + "Create Poll" builder and asked for it to be built for real. Investigation ([[Food]] §16) found this closely matches a mock "Food Polls" surface deleted in [[Decisions#ADR-048|ADR-048]] for being pure `useState` with no backend and no tenant-side voting counterpart — plus a "Workflow: Special selection / Research poll" picker that never existed in this repo's history at all. This is the **second** Food voting/poll concept already in the codebase: [[Decisions#ADR-056|ADR-056]] (earlier the same day) left the real monthly `food_voting_periods`/`food_votes` window in place but dormant. Building this as asked creates a **third**. [[Decisions#ADR-048|ADR-048]] explicitly flagged "two voting systems under two names" as a top-three audit finding — this decision revisits that territory on purpose, not by accident.
- **Decision:** build `food_polls`/`food_poll_options`/`food_poll_votes` as a genuinely new, independent feature — ad-hoc, single-instance polls (own title/options/date/closing-time), not a recurring monthly window, and not reusing `food_voting_periods` in any way. Confirmed directly with the user before building (asked explicitly: new/separate vs. replace the old system; user chose new/separate, fully aware the old system stays dormant). `RATING`/`YES_NO` poll types reuse the same options+votes tables via frontend-resolved fixed labels ("Yes"/"No", "5 stars".."1 star") rather than a nullable rating-value column — one model, four poll types, no branching. The "Workflow" picker (never real) is dropped; every other field from the screenshots is kept, including two the user was asked about and chose to keep as-is: `RATING`/`YES_NO` poll types, and the `Anonymous voting`/`Notify tenants now` toggles.
- **Why this isn't the same mistake ADR-048 fixed:** that finding was about two systems doing the *same job* under different names, discovered by accident, with one of them entirely fake. Here: (1) the two systems do genuinely different jobs — a recurring monthly window that once fed schedule generation, vs. ad-hoc single-meal polls — (2) the relationship is deliberate and documented in three places ([[Food]] §16, this ADR, [[Business-Rules]]) rather than discovered by an audit, and (3) this one is real end-to-end (backend, owner UI, and — unlike either prior system at launch — a genuinely new tenant-vote UI built in the same pass), not a second mock.
- **Alternatives considered:** *reactivating `food_voting_periods`/`food_votes` for this instead* — rejected, because the owner's ask is functionally different (a poll about one specific thing, opened and closed at will) from that system's shape (one window per hostel per month, covering all four meal types at once, previously tied to schedule generation only). Forcing the new UX onto the old monthly-window schema would have meant fighting its `@@unique([hostel_id, month])` constraint and its schedule-generation-shaped fields for no benefit. *Reviving the deleted mock's code* — rejected: it was never wired to anything real, so "reviving" it would mean writing the entire backend and tenant-vote path from scratch regardless; only the visual design was reused, confirmed via `git show ee51a83^:...`.
- **Consequences:** three related-but-distinct poll/vote concepts now live in this module — documented explicitly in [[Food]] §16's opening paragraph specifically so this doesn't quietly become a fourth "which voting system is this" audit finding later. `is_anonymous` is stored but has no current behavioral effect (no results view, old or new, ever exposed a per-voter breakdown) — flagged as an honest scope note rather than asserted as working. The "Allow multiple selections" toggle and the Poll Type selector remain unreconciled (inherited from the screenshot design, not introduced), so an owner can technically pick "Single Choice" with multi-select enabled — a known minor inconsistency, not fixed since nobody asked for it and it wasn't part of what was flagged for removal.
- **Related:** [[Food]] §16, [[Decisions#ADR-056|ADR-056]] (same-day, the system this one is deliberately independent of), [[Decisions#ADR-048|ADR-048]] (the deletion and the "two systems" finding this revisits), [[Business-Rules]], [[APIs]], [[Database]], [[Changelog]].

## ADR-062: Rooms tab floors collapse to an accordion, and room reorder is per-floor drag persisted to `rooms.sort_order`

- **Date:** 2026-08-10
- **Status:** accepted
- **Context:** the owner asked for two changes to the Hostel Drill-down → Rooms tab: (1) floors should collapse like the Food Library's meal-section accordion — tapping a floor reveals its rooms, rather than every floor's rooms always being shown flat — and (2) drag-to-reorder rooms within a floor (e.g. swap 101/102), which they'd tried and found not to work. Investigation found the second complaint had a real cause: the "layout" mode's floor-to-floor room drag used native HTML5 `draggable`, not `motion/react`'s `Reorder` — the exact class of bug [[Decisions#ADR-042|ADR-042]] fixed for the Home Property list (HTML5 DnD doesn't fire on touch) — and `DragHandle`'s own doc comment already flagged this exact call site ("room layout... reorder behaviour genuinely does not exist yet"). There was also no `rooms` ordering column at all — `getFloorsWithRooms` ordered by `room_no ASC`, so no persisted custom order was possible regardless of the drag mechanism.
- **Decision:**
  1. **Floors accordion, collapsed by default.** `FloorGroup` gains `expanded`/`onToggle`, mirroring `FoodLibraryCard`'s pattern exactly. A search match force-expands matching floors regardless of manual state.
  2. **Room order persists server-side** in a new nullable `rooms.sort_order` column — same shape as `hostels.display_order` ([[Decisions#ADR-042|ADR-042]]): NULL means never reordered, read path is `sort_order ASC NULLS LAST, room_no ASC` (`PropertyService.getFloorsWithRooms`), so existing hostels see no reshuffle until an owner actually drags. Written only by `PATCH /api/rooms/reorder`, which rewrites every room's position **within one floor** inside one `prisma.$transaction` — same all-or-nothing reasoning as `HostelOrderService` (`RoomOrderService`, `room-order-service.ts`).
  3. **`motion`'s `Reorder`, third adopter of ADR-042's handle-only rule.** `RoomRow` takes an optional `onDragStart`, wired the same way the Property cards are (`dragListener={false}` + `useDragControls`) — this resolves the gap `DragHandle`'s comment had flagged for this exact call site.
  4. **The old "layout" mode (floor-to-floor room moves) is removed, not fixed.** It was never asked for by the owner and, per the `DragHandle` comment, was already known to not really work. Two floors can't both be usefully drop targets in an accordion where only one section is expanded at a time. Moving a room to a different floor is now done explicitly: `RoomSheetModal`'s edit form gained a "Floor" select (only shown when the hostel has more than one floor), which calls the pre-existing `updateRoom` (`PATCH /rooms/:id`, `floor_id` was already an accepted field server-side).
  5. **Reordering is disabled while a search filter is active.** A filtered room list is a subset of the floor, and the reorder endpoint validates the submitted order is *exactly* the floor's full room set — a partial list would be rejected as `STALE_ORDER`, so drag is simply turned off rather than let it fail confusingly.
- **Consequences:** `useHostelRooms`'s `mode`/`dragRoomId`/`dragOverFloorId`/`startDrag`/`dropOnFloor`/`endDrag` and the `RoomsViewMode` type are gone, replaced by `reorderRooms(floorId, order)` (optimistic, same pattern as `useHostelOrder`). `RoomLayoutCard.tsx` is deleted — `RoomRow` now covers both the plain and draggable row. Fixed a latent, unrelated bug while rewriting `HostelRoomsPage`: the room-deep-link effect called `Object.values()` on `roomsByFloor`, which is a `Map` — `Object.values()` on a `Map` always returns `[]`, so `?room=<id>` deep links into Rooms silently did nothing before this change.
- **Related:** [[Features]], [[Database]], [[APIs]], [[Frontend]], [[Decisions#ADR-042|ADR-042]] (the pattern this reuses for both the order column and the drag mechanism), `docs/obsidian/Food.md` (the accordion pattern this borrows from).

- **Date:** 2026-08-11
- **Status:** accepted
- **Context:** the owner reported two Rooms-tab problems. (1) A vacant room's card did nothing when tapped — only its "Assign" button was interactive — so there was no way to open a vacant room's sheet at all; an occupied/reserved room opened fine. (2) Floors could not be reordered — only per-floor room drag existed ([[Decisions#ADR-062|ADR-062]]), and that reorder auto-saved on every drag release with no review step. The owner asked for a top-level "Reorder" entry point that lets floors and rooms both be dragged into place, with changes only persisted when explicitly saved — not the moment a drag ends. This directly supersedes ADR-062's point 4 ("floor-to-floor moves removed, not asked for") now that floor reordering *has* been asked for, and changes ADR-062's per-floor auto-save room-drag to a staged/explicit-save model.
- **Decision:**
  1. **Vacant rooms are tappable.** `RoomRow` no longer branches into a non-interactive vacant layout — the whole row is always a `role="button"` that calls `onOpen`, occupied or not; "Assign" is a separate button inside it that calls `e.stopPropagation()` so it still works as a one-tap shortcut into the invite flow without also opening the sheet underneath it.
  2. **`RoomSheetModal` shows "No active tenants"** as an explicit empty-state row in the residents list when `room.occupants.length === 0`, instead of silently rendering an empty list above the "+ Assign N vacant beds" button.
  3. **A dedicated "Reorder" mode, entered via a button at the top of the Rooms tab**, next to Search/+ Add (hidden while reordering; replaced by Cancel/Save). Entering it stages a local copy of `floors` and `roomsByFloor` (`HostelRoomsPage`'s `pendingFloors`/`pendingRoomsByFloor`); nothing is written to the server until Save.
  4. **`RoomsReorderPanel`** (new) renders floors as a `motion/react` `Reorder.Group`, each floor a `Reorder.Item` with its own handle, and — nested inside — a second `Reorder.Group` of that floor's rooms with per-room handles. Same handle-only-drag rule as [[Decisions#ADR-042|ADR-042]]/[[Decisions#ADR-062|ADR-062]] (`dragListener={false}` + `useDragControls`, so the two drag scopes — floor and room — don't interfere with each other). All floors are shown expanded in this mode (search is hidden here too), since the point is to rearrange everything, not browse.
  5. **Save diffs staged order against the live data and only writes what moved** — `layout.reorderFloors(newFloorIds)` if the floor order changed, `layout.reorderRooms(floorId, newIds)` per floor whose room order changed — run in parallel, then exits reorder mode. Cancel just discards the staged copy.
  6. **New `reorderFloors` on `useHostelRooms`.** There's no bulk floor-reorder endpoint — it writes each floor's `sort_order` via the existing `PATCH /floors/:id` (already accepted `sort_order`, previously only used by "Add floor"'s initial position), optimistic + invalidate, same shape as the existing room-reorder mutation.
  7. **The old per-floor "expand → drag a room → auto-saves on release" behavior is removed from browsing mode**, not kept alongside the new mode — two ways to reorder the same rooms would be redundant and confusing about which one is "current." `FloorGroup` goes back to a plain accordion (expand/collapse only); all dragging now lives in `RoomsReorderPanel`.
- **Consequences:** `FloorGroup`'s `onReorder`/`reorderDisabled` props and its `motion/react` import are gone; `RoomRow` drops its `onDragStart` prop (no longer draggable outside Reorder mode) and its `handle` rendering. `useHostelRooms.reorderRooms` now returns the mutation's promise (`mutateAsync`) instead of firing-and-forgetting, so `HostelRoomsPage.saveReorder` can `Promise.all` it alongside `reorderFloors` and know when both are done. Also removed two leftover `console.log('DEBUG …')` lines in `reorderMutation` noticed while touching this code — debug output from building ADR-062, not meant to ship.
- **Not verified in a live browser** — this session had no working `tsc`/dev toolchain (`node_modules` present but `typescript` itself missing, `npm run typecheck`/`npm run dev` not runnable) beyond a successful `vite build` (esbuild-only, doesn't type-check) and `check:architecture`, both clean for every file this touched. Whoever picks this up next should smoke-test: opening a vacant room's card, the empty-residents state, dragging a floor's position, dragging rooms both within and (implicitly, since drag is handle-scoped) not across floors, and that Save round-trips through `PATCH /floors/:id` and `PATCH /rooms/reorder` and survives a reload.
- **Related:** [[Features]], [[Decisions#ADR-042|ADR-042]] (handle-only drag pattern), [[Decisions#ADR-062|ADR-062]] (the per-floor auto-save drag and floor-move removal this supersedes), [[Changelog]].
## ADR-065: The pre-activation workspace edits a local draft and sends once; activation is tenant-side only

- **Date:** 2026-08-11
- **Status:** accepted
- **Context:** the owner-facing screen for an invited-but-not-yet-activated tenant (`InvitedTenantProfileView`) exists so an owner can fix mistakes — wrong name, wrong phone, a room or rent renegotiated after the invite went out — without waiting for activation. In practice it could not do that. An audit against live code found the screen's central action broken and most of its content fabricated: the "Configure" form opened blank (see [[Bugs]]), a room was always reported unassigned, "Expires in 3 days" was a literal, Private Notes were two invented strings in component state, and "Copy link" produced `/activate?token=<tenant uuid>` — not a token, and not the route (`/activate/<token>`). Seven cards restated rent three times and room four times, and every row, plus all three items of the "Manage invitation" sheet, opened the same 12-field modal. Meanwhile the invitation table already tracked `opened_at` / `activation_started_at` / a real `expires_at`, and none of it was shown.
- **Decision:**
  1. **No owner-side activation.** The "Activate tenant" button (`tenantService.reactivate(id, {status:'ACTIVE'})`) is removed. It flipped a tenant to ACTIVE without them ever registering, directly contradicting the card above it ("waiting for tenant to create account") and bypassing the activation state machine that creates the room allocation and releases the reservation. A tenant becomes ACTIVE only by completing their own registration. *Per explicit owner direction.*
  2. **Edits collect locally, then send once.** State is `edits: Partial<DraftTerms>` layered over the server's values, so a refetch flows through without clobbering in-progress edits and a successful send clears with `setEdits({})`. A pending-changes bar appears only when something has changed, and `ReviewChangesSheet` names every difference before anything leaves the device. This is not only ergonomics: `invitationService.updateInvitation` delegates to `resendInvitationByEmail`, so **every save rotates the token and re-issues the tenant's link**. Batching means one new link per intent instead of one per field, and the confirmation states that consequence instead of burying it in a modal subtitle.
  3. **One field per sheet.** `TermEditSheet` edits exactly one value; `RoomPickerSheet` is its own surface because picking a bed needs live availability. The monolithic `EditInviteModal` is no longer used here (it remains in use by the legacy `TenantProfilePage`). `InvitedTenantActionsSheet` and `EditTenantModal` are deleted — the sheet duplicated buttons already on the page and two of its three items called the same handler, and `EditTenantModal` sent `{name, phone}` to an endpoint whose schema requires `room_id`, so it had never once succeeded.
  4. **A room change offers the room's pricing as an explicit, pre-ticked choice** rather than silently rewriting rent (the old modal's auto-fill) or silently keeping stale rent. It is asked at the only moment it makes sense — inside the room picker, at the moment of the move.
  5. **Cut rather than fix:** the Agreement card (its "Preview agreement" was a `toast.info` stub and its "Send link" was a second resend button) and the Account Status card (four items only the tenant can supply). Screen goes from seven cards to four sections.
- **Consequences:** `invitationWorkspace.ts` holds the derivations as pure functions (timeline, expiry, diff, move-in total, missing items) with 25 colocated tests, per this repo's node-environment-only frontend test setup. `computeMoveInTotal` is now the single move-in formula — the profile view previously summed rent + deposit while the edit modal summed rent + deposit + one-time maintenance, so one labelled figure disagreed with itself across two screens of one flow. The `invitation` block added to the overview endpoint ([[APIs]]) is the shape owner screens should read; deriving invitation state from the raw `tenant_invitations` array is discouraged, since that array carries the activation token.
- **Related:** [[Features]], [[Bugs]], [[APIs]], [[Frontend]], [[Changelog]], [[Business-Rules]].

## ADR-066: Hostel creation leaves onboarding for an incremental, per-floor Add Hostel builder

- **Date:** 2026-08-12
- **Status:** accepted
- **Context:** hostel setup was steps 4–11 of the 12-step onboarding wizard, before the owner had seen any value. The friction was not the question count — it was that **the answers could not be right**. `OwnerOnboardingData` modelled an entire property as four scalars (`floors`, `roomsPerFloor`, `bedsPerRoom`, one `monthlyRent`), which `hostel-provisioning-service.ts` multiplied into a uniform grid numbered `${floor}${nn}`. That cannot express the ordinary case the owner described: a ground floor of three 4-sharing rooms and one 2-sharing room, each at its own rent. So the building was wrong on arrival and had to be corrected room-by-room in the Rooms tab anyway. Two related symptoms: `capacity` was both asked directly in `DetailsStep` and derived as `floors × rooms × beds`, and `FloorsStep` rendered an "Edit" affordance per floor that did nothing.
- **Decision:**
  1. **Onboarding keeps only what onboarding can do** — welcome → account (+OTP) → KYC → done. Eight screens deleted (`create`, `location`, `details`, `floors`, `rooms`, `beds`, `review`, `publish`), along with the structure/pricing fields, `generationGate`, and the wizard's `submitPublish`. A new owner lands on their **real dashboard** with one invitation to build; no sample data is fabricated and nothing is blocked.
  2. **Rooms are configured per room, from a per-floor default.** A floor takes a room count plus a default sharing size and rent, generates that list, and any room can be tapped to differ. Per-room edits are marked `customised` so later changes to the floor default do not silently clobber them. Rent is remembered **per sharing size** across the session, which is how owners actually price.
  3. **Writes are incremental.** The `hostels` row is created when the hostel is named; floors are created empty; each floor's rooms are saved on leaving it via the new `POST /api/floors/[id]/rooms`. "Finish later" therefore needs no local draft — resuming is a read, and build progress is **derived** (a floor with no rooms is a floor still to do; a hostel with `total_capacity: 0` is one still being built) rather than stored in a setup-step column that could disagree with the data.
  4. **Room rent is presented as a default, never a price.** Verified in code: `rooms.base_rent` → `auto_fill_room_rent` prefills the invite wizard, `allow_override` lets the owner change it per tenant, and the binding figure is `tenants.monthly_rent`. Tenants in one room routinely pay different rents. The builder says so on screen and **shows no revenue projection** — rooms and beds are facts, a monthly total built on `base_rent` would not be.
  5. **The first hostel skips password step-up.** `POST /api/owner/hostels` gated every creation behind `confirmIdentity(…, 'CREATE_HOSTEL')`. The gate now applies only when the owner already has a hostel: it protects an account with data, and the first hostel is created minutes after signup on the emptiest possible account.
  6. **The scene is driven by hostel facts, not step indices.** `OnboardingScene` read `step >= 7` to draw windows and `step >= 8` to light them, welding the artwork to one screen's numbering. It moves to `shared/ui/brand/HostelScene` with a semantic `HostelSceneState`, so the builder reuses the same animation: storeys rise as floors are added, windows appear as rooms do, and light up once those rooms are configured.
- **Consequences:** `POST /api/owner/hostels/provision` loses its only caller — marked deprecated in [[APIs]], removed in a follow-up rather than here. **A lead-funnel regression was found and fixed in the same change:** `markLive` was invoked by the wizard's trailing `completeInvitation(token)`, so removing publish would have stalled lead-originated owners at `HOSTEL_CREATED` forever. A new owner-scoped `markLiveForOwner(ownerId)` fires from the bulk-rooms route instead — the trigger is deliberately the **first rooms landing**, not the hostel row, because under an incremental builder a named hostel with no rooms is not a live property. `HOSTEL_CREATED` itself still fires from `POST /owner/hostels` (ADR-032), unchanged.
- **Related:** [[Features]], [[APIs]], [[Frontend]], [[Changelog]], [[Decisions#ADR-062|ADR-062]] (`rooms.sort_order`, which the builder writes), [[Decisions#ADR-060|ADR-060]] (deposit stays in the Configuration Hub, deliberately not asked during the build), [[Decisions#ADR-032|ADR-032]].
## ADR-067: The new-owner walkthrough is derived from account state, not a stored tour position

- **Date:** 2026-08-12
- **Status:** accepted
- **Context:** a freshly signed-up owner lands on a dashboard that is entirely zeros — no rooms, no tenants, ₹0 collected, empty property list. A conventional spotlight tour over that screen points at cards that do nothing and teaches nothing; what the owner needs is the short sequence that turns an empty account into a working one. No tour library, coach-mark infrastructure, or owner-level onboarding-progress column existed (`profile.onboarding_expires_at` belongs to *tenant* activation).
- **Decision:**
  1. **A three-step checklist, each step derived from real data** — hostel (`total_capacity > 0`), first tenant (`active_tenants + invited > 0`), first payment (`rent_collected_this_month > 0`). Nothing is a stored step, so the card cannot disagree with the account it describes, and work done elsewhere ticks it off automatically.
  2. **Owner KYC is a status line, not a step.** `owner_documents.status` is set by a Stayo admin and "can only be changed by an admin", so a checklist item for it could never be ticked by the person reading it. It is reported, with copy stating explicitly that nothing is blocked on it.
  3. **One-way graduation latch in browser storage.** The payment signal is *this month's* collection and resets on the 1st; without a latch the card would return every month to tell an established hostel it had never taken rent. Completion is permanent even though its signal is not.
  4. **A 3-stop spotlight, gated on real emptiness as well as its dismissal flag.** Because an account with any rooms or tenants is excluded outright, a cleared browser store can only re-show the introduction to someone who still has nothing — which is when showing it is correct. That removes the usual reason to add a column for a "seen" flag.
  5. **Stops are anchored by ref, never CSS selector.** A selector-based tour breaks silently on a rename — dimming the screen while highlighting nothing — and no check in this repo would catch it. A stop whose ref is empty is dropped rather than rendered blank.
  6. **No tour dependency.** Shepherd/Joyride/driver.js would be a new runtime dependency for ~150 lines of overlay, none of which theme cleanly against this app's token setup.
- **Consequences:** `FirstHostelCard` is deleted — step one's incomplete state *is* what it said, and two "start here" prompts on one screen is one too many. `useOwnerDashboard` now exposes `gettingStartedSignals` as raw numbers, because the formatted strings beside them ("₹1,32,600") cannot be compared to zero. The KYC request is `enabled` only while the card can still appear, so a graduated owner never pays for it. A ref-timing defect was found and fixed during implementation: anchor refs populate after the overlay's first render and assigning a ref does not re-render, so the tour filtered every stop out and silently never appeared until it was armed a frame later.
- **Related:** [[Features]], [[Frontend]], [[Changelog]], [[Decisions#ADR-066|ADR-066]] (the builder this checklist's first step leads into).

## ADR-069: Tenant-proposes/owner-approves profile edits — new parallel routes, not a `ChangeManagementFacade` extension

- **Date:** 2026-08-14
- **Status:** accepted
- **Context:** user wanted tenant self-edits to their phone/email/address/DOB gated on owner approval, with everything else saving directly. Initial plan (told to the user, then corrected) was to reuse the existing `change_requests` table's infrastructure — it looked purpose-built (`change_type: 'profile_update'` already existed, `ChangeApprovalLevel.L1 = "Owner only"` reads like an exact fit). On inspection, `ChangeManagementFacade.propose()`/`approve()`/`reject()` are hardwired the *opposite* direction: they power a real, live owner-side feature ("Request Change" on the owner's Tenant Profile page → tenant must approve), with `actor_role` hardcoded per method and `approve()`/`reject()` throwing `FORBIDDEN` unless the caller is the tenant on that specific `tenant_id`. There is no existing tenant-proposes/owner-approves path anywhere in the codebase.
- **Decision:**
  1. **Reuse the `change_requests`/`change_request_events` tables** (schema/audit consistency, and `entity_type`/`change_category`/`approval_level` already have room for this shape) **but do not touch `ChangeManagementFacade`.** New rows are tagged `change_type: 'tenant_self_service_update'`, distinguishing them from the facade's `'profile_update'`/`'contract_amendment'`/`'administrative_correction'` rows in the same table.
  2. **New, separate route set** (`app/api/tenants/me/profile-requests`, `app/api/owner/profile-requests[/[id]/approve|reject]`) with its own authorization and apply-logic, rather than adding a role parameter to the facade's methods. Extending the facade risked subtly changing behavior for the live owner-initiated flow (its `approve()`/`reject()` hardcode `actor_role: "tenant"` in the audit log, assume `tenant_id` on the row is who must approve — none of that is true for this direction).
  3. **Enforcement lives in the service layer, not just routing.** `updateTenantSelfProfile()` rejects governed fields outright (400) even though the new frontend never sends them — defense in depth, since this method has two callers (`/api/tenants/me/profile` and the older `/api/tenants/profile`) and nothing stops a third from appearing later.
  4. **Governed field list is exactly what the user specified**: primary phone, personal email, permanent address, date of birth. Not extended to PAN/blood group/nationality (new fields added the same day) or emergency/guardian contact info, since the user didn't name them and there's no other signal they need the same protection.
- **Consequences:** two directions of "change request" now coexist in one table, disambiguated only by `change_type` — anything reading `change_requests` broadly (e.g. a future admin dashboard) needs to filter or label by direction, not assume one meaning. The primary-phone OTP-verification block inside `updateTenantSelfProfile` is now unreachable dead code for this call path (see [[Business-Rules]]) — left in place rather than removed, flagged for a future cleanup pass. No owner-side review UI existed before this change; a new one was built (`features/owner-profile-requests`, routed at `/owner/profile-requests`, linked from the Alerts → Requests tab) rather than deferring it, per explicit user direction after being told the fuller scope.
- **Related:** [[Database]], [[Business-Rules#Tenant self-service profile edits — governed vs. direct fields (2026-08-14, narrowed same day)|Business-Rules]], [[APIs]], [[Features]], [[Changelog]].

**Amendment, same day (2026-08-14):** point 4's governed field list turned out to be one step ahead of the user's actual intent — after comparing the resulting UI against the design source, the user gave a final, explicit, narrower list: *only* phone and email require approval; date of birth and address (both in the original list) go back to direct-editable, same as everything else. `permanent_address`/`date_of_birth` removed from `GOVERNED_FIELDS`/the profile-requests routes/`GOVERNED_PROFILE_FIELDS`. This also prompted restoring the read-only card visual design (view/edit toggle in `ProfileEditScreen.tsx`, see [[Bugs]] for the field-mapping and validator-wiring bugs found while implementing it) — the interim always-open-form version was a deviation from `Stayo Tenant.dc.html` the user explicitly rejected, not a separate decision.

## ADR-070: Tenant activation — Identity now precedes Agreement, a real backend step-order swap

- **Date:** 2026-08-14
- **Status:** accepted
- **Context:** the tenant activation wizard's design source turned out to have two versions in this repo: `Stayo SaaS redesign/Stayo Onboarding.dc.html` (used for the wizard's original 2026-08-12/13 build) and a second, different folder, `stayo onbaording/Stayo Onboarding.dc.html`, which the user identified as the one that should have been used. Diffing the two showed a real flow change, not a styling revision: the newer source shows Identity (gender/DOB/guardian/emergency/photo, plus mobile-OTP/Gmail moved down from the old Welcome screen) *before* Agreement, whereas the shipped wizard — and the backend's `activation-workflow-service.ts` — required Agreement first. Confirmed via full read of the backend service: `AGREEMENT`-before-`PROFILE` was a hard-enforced server-side gate (`assertTransition()`, HTTP 409 `INVALID_TRANSITION`), not a UI convention, and confirmed there is no data dependency either direction (Agreement's `content_snapshot` never reads Profile-collected fields, and `saveProfile()` never reads the signed agreement) — the old order was a pure policy choice, safe to reverse.
- **Decision:**
  1. **Swap `PROFILE` and `AGREEMENT` in the backend's required step sequence.** `agreement-requirement.ts`'s `ALL_ACTIVATION_STEPS` reordered to `ACCOUNT → RULES → PROFILE → AGREEMENT → ACTIVATE`; `activation-workflow-service.ts`'s `assertTransition()` and `blockedSteps()` updated symmetrically — `PROFILE` no longer requires `agreement_signed`, `AGREEMENT` now requires `profile_completed` instead. The `RULES` auto-accept side effect (runs before every `assertTransition()` call) and `ACTIVATE`'s final re-check are unaffected — both already independent of ordering.
  2. **Merge the Welcome and Identity screens' React components** (`AccountStep.tsx` + `ProfileStep.tsx` → `WelcomeIdentityStep.tsx`) rather than just reordering two separate screens, matching the design source exactly: Welcome trims to Room Allocation + Billing Cycle only (no backend call — a local-only UI phase), and Identity gains the mobile-OTP/Gmail fields alongside photo/gender/DOB/guardian/emergency, submitting the `ACCOUNT` and `PROFILE` backend steps chained behind one tap — the same one-component-two-backend-steps pattern `AgreementStep.tsx` already used for `RULES`+`AGREEMENT`. Chosen over a frontend-only relabel (which would have desynced the progress track from the actual screen shown, since Profile and Agreement remain genuinely distinct backend steps) after being put to the user directly as a scope question.
  3. **`ActivationProgress.tsx`'s node order reordered to match** (`Welcome → Identity → Agreement → Account → Move In`) — a single array reorder, since the track's draw order, done/active state, and click-gating all key off the same `ALL_NODES` array index.
  4. **Dual-brand header, real hostel name, and decorative "Checking in…/Checking out…" speech bubbles** ported from the same newer design source, per explicit user approval — the Stayo icon × hostel-logo/initials badge replaces the old Stayo-only header on both the intro screen and the wizard chrome.
- **Consequences:** a tenant now completes their identity profile before reviewing and signing the residency agreement — the opposite of the original design intent this wizard first shipped with. No functional regression: OTP flows, guardian verification, signature capture, and activation submission are all carried over unchanged, only their step order and screen grouping changed. Any future code reading `ALL_ACTIVATION_STEPS`/`assertTransition`/`blockedSteps` order assumptions (e.g. a report or admin view hardcoding the old sequence) needs updating — grepped for other consumers of step order at the time of this change; none found beyond the files listed above.
- **Related:** [[Business-Rules#Whether a tenant must sign an agreement|Business-Rules]], [[Features]], [[Changelog]].

**Amendment, same day (2026-08-14):** a follow-up comparison against a real screenshot of the design source surfaced three more fields the newer design's Identity screen doesn't show at all — a Profile Type selector, a Guardian Relation dropdown, and a 4th "Prefer not to say" gender option — all carried over from the pre-ADR-070 `ProfileStep.tsx`. Put to the user directly (this contradicted the "keep extra backend fields, restyle" policy confirmed twice earlier the same day); the user chose exact fidelity over the standing policy for these three specifically. Profile Type was safe to drop outright: `tenants.profile_type` already defaults to `STUDENT` at the schema level, is never set during the owner's invite flow, and is directly editable later from the tenant's own portal profile (`tenant-service.ts`'s direct-editable field list) — so removing the selector here loses no capability, it just moves the moment a working-professional tenant corrects it to after activation. Guardian Relation could not simply be deleted, though: `saveProfile()` hard-required it for student profiles, and — since Profile Type dropping means every tenant now defaults to `STUDENT` — every activation would have needed it, with nothing earlier in the (now-reordered) flow left to collect it (the only other place relation is asked, the Agreement step's guardian-signature modal, runs *after* Profile and is optional). Resolved by relaxing `saveProfile()`'s requirement — guardian name and verified phone stay required for students, relation is no longer required at this step and is filled in later only if a guardian actually co-signs the agreement (both `tenants.guardian_relation` and `agreements.guardian_relation` are already nullable columns, so this is schema-safe). Gender trimmed to the design's 3 options (Male/Female/Other); `"Prefer not to say"` is no longer selectable through this flow (still a valid backend value, just not offered here).

**Second amendment, same day (2026-08-14):** Emergency Contact removed from the Identity screen outright, by explicit direct instruction (no design-fidelity ambiguity this time — the field simply isn't wanted here). Unlike Profile Type/Guardian Relation, this one had no other capture point anywhere in the activation flow, so it's a straightforward removal, not a relocation. `saveProfile()`'s unconditional `emergencyPhone` requirement was relaxed the same way Guardian Relation's was: an emergency number is still validated for format *if* one is ever supplied (defense in depth for other callers of this method), but no longer required to complete the `PROFILE` step. `tenants.phone_3`/`emergency_contact` stay nullable columns — schema-safe. Emergency contact info, where still needed operationally, is collected later from the tenant portal profile (already a direct-editable field per `tenant-service.ts`), not during activation.

## ADR-071: `/` becomes an audience chooser; the owner marketing page moves to `/owners`

- **Date:** 2026-08-14
- **Status:** accepted
- **Context:** Stayo serves two audiences with almost nothing in common — students looking for a bed, and owners looking for software — but `/` was the owner marketing page (`LandingPage`, ADR-035's login surface). A student arriving at the root from a search or a shared link landed in a pitch about occupancy dashboards and late-fee automation. `Stayo Welcome.dc.html` (Claude Design project `3f2fbde6`) designed the fork: a full-viewport diagonal seam, tenant above / owner below, that yields to whichever side you hover or tap.
- **Decision:**
  1. **`/` renders `WelcomePage`; `LandingPage` moves to `/owners`.** "Start free" commits to `/owners`. `/login` still renders `LandingPage` with the popup open, unchanged — ADR-035 is untouched.
  2. **Picking a side is reversible — the choice is a mode, not an identity.** The Stayo logo on `LandingPage` (previously an in-page `#top` anchor, since this page *was* `/`) is now a real `<Link to="/">`, and the marketing-chrome logos on `MarketingLayout`/`CompanyPage` point at `/` too. **Rule: logos mean "front door" and go to `/`; content CTAs and route guards go to `/owners`.** The tenant side gets its own way back when that side is designed — there is no tenant page to return *from* yet.
  3. **Auth failures go to `/login`, not `/`.** `ProtectedRoute` (no session) and `ProtectedTenantRoute` previously bounced to `/`; asking someone whose session just expired whether they're a student or an owner — instead of letting them sign back in — loses the thread. The *authorization* failure (signed in, wrong role) still goes to `/`, because there we genuinely don't know which surface they belong on and the chooser is exactly that question.
  4. **`/` renders for everyone, including signed-in owners.** An earlier revision of this ADR had `WelcomePage` hard-`<Navigate>` a signed-in owner to `/owners`. That was **reverted the same day**: it made the tenant side permanently unreachable for the exact person who most needs it — an owner cannot browse hostel listings if the front door ejects them — and it also defeated point 2, since a signed-in owner clicking the logo would have bounced straight back. The session now changes the owner CTA's *wording and destination* ("Go to dashboard" → `/owner/home` for an owner with a hostel; "Start free" → `/owners` otherwise) instead of removing the choice. Persisting the pick in `localStorage` was considered and rejected for the same reason: it makes `/` unpredictable and needs an escape hatch.
  5. **Choosing "owner" is treated as an answer, not just a navigation.** `/owners` carries an `OwnerEnquiryPrompt` asking "Are you a hostel owner?" — which is the exact question the visitor just answered by tapping the owner panel. `WelcomePage` therefore hands `{ declaredOwnerIntent: true }` to `/owners` via router state (matching how `OwnerLeadInvitePage` already passes prefill to `/onboarding`), and `LandingPage` opens `HostelLeadModal` on the first paint while suppressing the prompt. `declaredOwnerIntent` is a new **optional** field on `EnquiryPromptInput`, checked before every other rule and ahead of scroll depth — the question is answered, not merely badly timed. Optional so the callers with no such signal are unchanged, with a test pinning absent ≡ `false`. The state is consumed with a `replace` navigation so history back/forward can't re-open the conversation.
  6. **The tenant panel is deliberately inert.** It expands and reads its pitch, but "Browse hostels" is a non-navigating `aria-disabled` pill labelled "Coming soon" — the hostel-browsing page it would open (cluster listings) is designed later, and routing into a dead end is worse than saying so. Deliberately **not** a separate tenant landing page: per explicit product direction there will be one browsing page, not a marketing page plus a browse page.
  7. **Two deviations from the design source, both deliberate.** The 2.65s intro splash was cut to 1.6s, shown once per browser session (`sessionStorage: stayo.welcome.splashSeen`) and skipped entirely under `prefers-reduced-motion` — fine on a canvas, far too long as a front door on every visit. The commit overlay's rotating ring was replaced with `StayoLoader`: rotating spinners are deliberately absent app-wide (see `shared/ui/brand/index.ts`), every wait is the mark's four windows lighting clockwise.
- **Consequences:** **`/` is no longer the crawlable owner-acquisition page, and this has a real SEO cost** — the root's accumulated ranking for owner keywords does not transfer to `/owners` cleanly. `sitemap.xml` now gives `/owners` the 1.0 priority and demotes `/` to 0.7; a 301 or a canonical from `/` to `/owners` was *not* added, because `/` is a genuine distinct page now, not a duplicate. Worth revisiting once the tenant marketplace ships and `/` has its own reason to rank. The brand palette in `WelcomePage` is hard-coded rather than themed, same as `StayoLoadingScreen` — it renders before any `[data-app-theme]` shell exists, so there is no token scope to inherit.
