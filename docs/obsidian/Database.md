# Database

Related: [[Backend]] · [[Business-Rules]] · [[APIs]] · [[Architecture]]

Postgres (Supabase provider), accessed via Prisma from `apps/backend/`. Source: `apps/backend/prisma/schema.prisma` (2426 lines, PostgreSQL provider, `DATABASE_URL` pooled + `DIRECT_URL` direct connection). This page was generated by reading the schema file in full — every model/enum/relation below is transcribed from the code, not inferred. Several tables carry Prisma advisory comments (`RLS`, `check constraints`, `DB-level comments`) indicating the live database has constraints not fully expressed in `schema.prisma` — treat this file as accurate-but-not-exhaustive for DB-level constraint logic.

**Model count:** ~100 models. **Enum count:** 25. Full field-level detail for every model is not reproduced here (that would just be a copy of `schema.prisma`) — this page covers the domains, the core financial models in detail, all enums, all relations, and — per the "do not invent" instruction — an explicit list of things that could not be determined from the schema alone.

## Core financial models (the heart of the system)

### `rent_obligations`
The central billable line-item — "the core financial entity of the system." Key fields: `tenant_id`, `hostel_id`, `allocation_id`, `agreement_id`, `rent_month`, `amount`, `late_fee`, `total_amount`, `due_date`, `obligation_type` (string: RENT/SECURITY_DEPOSIT/ADMISSION/MAINTENANCE/LATE_FEE/FINE/EXTRA_CHARGE/DAMAGE/UTILITY/ADDITIONAL_CHARGE/OTHER — not a DB enum, validated only in code), billing period/installment fields, `is_superseded`, cancellation fields (`cancelled_at/reason/by`), waiver fields (`waived_at/reason/by/amount`).

Carries **three parallel status representations** on the same row:
- `status: PaymentStatus` (legacy, 8 values, still dual-written for compatibility)
- `lifecycle_status: obligation_lifecycle` (`ACTIVE|WAIVED|CANCELLED`, terminal once non-ACTIVE — "Financial Architecture v2", migration 061)
- `settlement_status: settlement_state` (`UNPAID|PARTIAL|PAID`, independent of lifecycle)

A fourth, **never-persisted** presentation status (`OVERDUE|UPCOMING|PENDING|PARTIAL|PAID|WAIVED|CANCELLED`) is derived at read time from the two v2 columns + due date — see [[Business-Rules]].

Unique constraints: `[allocation_id, rent_month, obligation_type]`, `[agreement_id, rent_month, obligation_type]`.

### `payments`
An actual recorded payment against one obligation (`obligation_id`, `tenant_id`, `hostel_id`, `amount_paid`, `payment_method`, `payment_date`, optional `payment_attempt_id`/`payment_group_id`, `idempotency_key` unique). Produces one `receipts` row (1:1). **Immutable by policy**: `apps/backend/scripts/architectural-invariants-check.ts` statically forbids any `update`/`updateMany`/`upsert`/`delete`/`deleteMany` call against this model anywhere in `lib/services`/`app/api` — settled payment rows are never mutated or deleted by application code.

### `payment_groups`
Doc-commented in the schema itself: *"every payment recording creates a group... Future: Group → Allocations → Payments (three-level)."* One row per payment-recording transaction, wrapping potentially multiple `payments` rows (e.g. one lump payment allocated across several obligations). Carries `total_amount`, `method`, `settlement_breakdown` (JSON), `future_credit_amount`. `reference_number` was added by the most recent migration in the repo (`20260717000000_payment_groups_reference_number`).

### `tenant_financial_ledger`
Double-entry-style credit/debit ledger against a tenant's balance (security deposit, future-rent credit, waivers, corrections). `type: FinancialLedgerType` (CREDIT/DEBIT), `reason: FinancialLedgerReason` (10 values, see enums below), `amount`, `balance_after` (audit display only — the actual balance is recomputed as `SUM(CREDIT) − SUM(DEBIT)` by `tenantFinancialLedgerService`, not read from this snapshot column). **Note:** `docs/data-models/schema.md` still documents this table under the old name `tenant_advance_ledger` with old enum names `AdvanceLedgerReason`/`AdvanceLedgerType` — that doc page is stale; the live model/enum names are `tenant_financial_ledger` / `FinancialLedgerReason` / `FinancialLedgerType`.

### `paymentAttempt` (`@@map("payment_attempts")`)
A payment-gateway transaction attempt (UPI/QR, PhonePe/Razorpay), `status: AttemptStatus` (9 values). Links to one or more obligations via the `payment_attempt_obligations` join table (many-to-many with per-obligation amount). Carries two generations of provider-reference fields side by side (`merchant_txn_id`/`gateway_txn_id` vs. newer `merchant_transaction_id`/`provider_transaction_id`/`provider_order_id`/`provider_reference_id`) — which is canonical at the code level is **Unknown / needs clarification** from the schema alone.

### `move_out_requests` + satellite tables
The central exit-workflow record. Status (`MoveOutStatus` enum) drives a documented transition graph `REQUESTED → SETTLEMENT_PENDING → SETTLEMENT_APPROVED → PHYSICALLY_VACATED → SETTLEMENT_PENDING_PAYMENT → COMPLETED` (branch: `REJECTED`); two legacy enum values `APPROVED`/`VACATED` remain for reading old rows. Satellite 1:1/1:N tables: `move_out_inspections` (room condition + fee breakdown), `move_out_inspection_items` (structured per-item checklist, replacing free-text), `exit_settlement_transactions` (the actual net-settlement computation: deposit + credit − dues − deductions = `net_settlement_amount`, with `settlement_direction`), `exit_disputes` (1:N, disagreements over the settlement), `exit_feedbacks` (1:1 exit survey, 8 rating dimensions).

### `Agreement` / `AgreementTemplate` / `RenewalOffer` / `BulkRenewalBatch` / `RenewalDecision` / `RenewalTimelineEvent`
The tenant-contract subsystem — **entirely undocumented in `docs/data-models/schema.md`** (see gap list below). `AgreementTemplate` is a versioned, publishable contract template per hostel (`TemplateStatus`: DRAFT/PUBLISHED/ARCHIVED). `Agreement` is the signed instance (tenant/guardian/owner signature capture with IP/UA, `AgreementStatus`: DRAFT/SIGNED/EXPIRING_SOON/AGREEMENT_EXPIRED/RENEWED/TERMINATED/VOID), self-referentially linked forward/backward through renewals (`renewed_from_agreement_id`/`renewed_to_agreement_id`). `RenewalOffer` carries the proposed renewal terms and its own status lifecycle (`RenewalOfferStatus`). `RenewalTimelineEvent` (added 2026-07-20, migration `20260720000000_renewal_timeline_events`) is a new append-only audit trail — `RenewalTimelineEventType` (OFFER_CREATED/SENT/DISCUSSED/REVISED/ACCEPTED/DECLINED/EXPIRED, DRAFT_CREATED, RENEWAL_ACTIVATED/ACTIVATION_BLOCKED) × `RenewalTimelineActorType` (OWNER/TENANT/SYSTEM) — written by `renewal-timeline-service.ts`, called from inside the same transaction as the mutation it describes wherever the caller already has one open. Closes the gap where owner-side offer actions previously had no queryable DB record at all (only `logger.info()` lines) and tenant-side actions were only partially captured in `RenewalDecision` (no actor-role, no distinct event vocabulary). See [[Decisions]] ADR-016.

### `change_requests` / `change_request_events`
The newest subsystem in the schema (migration `20260707170000_change_management_system`), also undocumented in `docs/data-models/schema.md`. A generic, governed wrapper for approval-gated modifications to `tenant`/`profile`/`agreement`/`obligation`/`room_allocation` data — captures `before` (full prior state, JSON) and `diff` (changed fields only, JSON), a mandatory `reason`, and a multi-level approval model (`ChangeCategory` A–D, `ChangeApprovalLevel` L0–L3). See [[Business-Rules]] and [[Features]] for the tenant-approval workflow this powers.

### `correction_cases` / `correction_case_events`
The foundation of the Business Recovery Platform (migration `20260720120000_business_recovery_platform`), a new Correction Case lifecycle engine for owner-facing undo/correction workflows — currently schema-only (Task 1 of a 17-task phased build, services/API/UI follow in later tasks). See `docs/business-logic/business-recovery-platform-architecture.md` for full design rationale.

**Enums:**
- `RecoveryTier`: OPERATIONAL_UNDO, FINANCIAL_CORRECTION, ADMINISTRATIVE_REVERSAL (classifies the severity/type of correction)
- `CorrectionDomain`: PAYMENTS, ROOMS, AGREEMENTS, EXPENSES, ADMISSIONS, RENEWALS, SETTINGS, DOCUMENTS, KYC, RESERVATIONS (scope of what's being corrected)
- `CaseStatus`: DRAFT, PREVIEW, VALIDATED, EXECUTING, COMPLETED, FAILED, EXPIRED, CANCELLED (lifecycle state)

**`correction_cases` table:**
One row per correction case — a request to undo or correct an owner action. Key fields: `hostel_id` (non-nullable, scoped per-hostel per the repo's invariant), `domain` + `case_type` (what's being corrected), `tier` + `status` (severity and lifecycle), `entity_refs` (JSON array of entity IDs affected), `reason` (mandatory), `actor_id` + `actor_role` (who initiated), `before_snapshot` (full state of affected entity before correction), `preview_impact` (simulated outcome, populated in PREVIEW status), `execution_result` (actual outcome after execution), `case_detail` (domain-specific correction parameters, JSON), `idempotency_key` (unique, enables safe replay), `depends_on` (array of case IDs that must complete first), `undo_expires_at` (optional deadline for undo-window cutoff), `correlation_id` (tracing across related cases), `created_at`/`updated_at` (audit timestamps). Four indexes: (hostel_id), (hostel_id, status), (status, undo_expires_at), (case_type).

**`correction_case_events` table:**
Append-only audit trail for each correction case. One row per state change/event — `correction_case_id` (FK to correction_cases), `event_type` (e.g. CREATED, PREVIEW_GENERATED, VALIDATED, EXECUTION_STARTED, COMPLETED/FAILED), `actor_id` + `actor_role` (who triggered the event), `reason` (optional rationale), `snapshot` (optional JSON snapshot at event time), `ip_address` + `user_agent` (request metadata), `created_at` (event timestamp). One index: (correction_case_id) for efficient event history retrieval.

### `payment_link_tokens`

A token maps to a `tenant_id` (required) and an optional `obligation_id` hint (nullable — `String? @db.Uuid`, as of 2026-07-21, see [[Decisions]] ADR-017). The hint, when present, only seeds a default pre-filled amount on the payer-facing page (`/pay/[token]`); it does not restrict what the payer can actually pay. There is no `amount` column on this table — the amount charged is always decided at payment time and FIFO-allocated across whatever the tenant currently owes (`OVERDUE`/`PENDING`/`PARTIAL`/`UPCOMING` obligations) via `buildSettlementPlan` (`src/services/payments/settlement-planner.ts`, called from `paymentService.createAmountPaymentIntent` — see [[Backend]]), with any excess credited as future rent. `PaymentLinkService.getOrCreateToken` reuses an existing non-expired token for the same `(tenant_id, obligation_id-hint)` pair rather than always minting a new one; tokens expire after 7 days (`expires_at`). See [[APIs]] (`/api/payments/pay-link`, `/api/payments/pay/[token]`) for the two routes that create and consume a token, and [[Business-Rules#Flexible payment links]] for the allocation rule.

### `food_menu_items` / `food_voting_periods` / `food_votes` / `food_schedules` / `food_schedule_meals`
Added 2026-07-26 for the Monthly Food Planning & Voting rebuild (was 100% mock before this, no backend at all). `food_menu_items` is a persistent, hostel-scoped library of food items grouped by `FoodMealType` (BREAKFAST/LUNCH/SNACKS/DINNER) — the owner maintains it over time; items are soft-deleted (`is_active=false`), never hard-deleted, since past `food_schedule_meals` rows may still reference them. `food_voting_periods` is one row per `(hostel_id, month)` (`@@unique`) with a `FoodVotingStatus` (DRAFT/OPEN/CLOSED) and a start/end window. `food_votes` is one row per `(voting_period_id, tenant_id, meal_type, menu_item_id)` (`@@unique`) — **multi-select per meal type** (changed 2026-07-26 from an earlier single-choice-per-meal-type design, see [[Decisions]] ADR-029): a tenant may vote for as many items as they like within one meal type, one row per item; `POST /api/food/tenant/vote` toggles a single `(meal_type, menuItemId)` pair on/off rather than upserting one row per meal type. `food_schedules` is the key design decision: **one mutable row per `(hostel_id, month)`**, not an immutable/versioned history — the schedule is a *repeating weekly pattern* (Mon–Sun × 4 meal types = 28 `food_schedule_meals` rows), not calendar-dated, so a month's schedule is always exactly 28 cells and carrying it forward to a new month is a straight copy regardless of weekday alignment. `FoodScheduleStatus` (DRAFT/PUBLISHED) + `FoodScheduleSource` (GENERATED/CARRIED_FORWARD/MANUAL) track how the current state came to be. There is no separate "publish new version" concept — once `PUBLISHED`, tenants always read this same row, so an owner edit after publishing takes effect immediately with no additional action. `food_schedule_meals.item_name` denormalizes the item's name at assignment time (`menu_item_id` is nullable, `onDelete: SetNull`) so a later library edit/deactivation can't corrupt what a schedule cell displayed. See [[APIs]] (`/api/food/*`), [[Features]], and [[Changelog]].

### `hostel_announcements` / `hostel_events`
Added 2026-07-26 for the tenant Home tab's Announcements and Upcoming Events cards. Both are deliberately minimal (title/body or title/date/description, hostel-scoped, owner-authored) — no read-tracking, no scheduling/recurrence, no rich content. Owner writes via a new "Notices" panel (`/owner/more/notices`); tenants read their own hostel's rows via `/api/tenants/me/{announcements,events}`.

### `tenant_service_requests` / `tenant_service_request_events`
Added 2026-07-26 for the tenant Room tab's 6 request types — maintenance, room change, cleaning, lost key, visitor pass, extra mattress — modeled as **one unified table** (`ServiceRequestType` enum) rather than 6 separate tables, since the tenant-facing UI itself is one generic form/detail engine driving all 6. `status` (`ServiceRequestStatus`: RAISED/ASSIGNED/IN_PROGRESS/RESOLVED/REJECTED) transitions are owner-driven (`PATCH /api/service-requests/:id/status`) and each transition appends a `tenant_service_request_events` row (append-only timeline + optional note), the same pattern as `RenewalTimelineEvent` (ADR-016) — not a bespoke audit mechanism. `category` is a free-text string, not an enum (matches the "many status-like columns are plain strings" house style) since it's only meaningful for `MAINTENANCE` (Electrical/Water/Furniture/Cleaning/Internet/Other) and would otherwise need a nullable-per-type enum. `fee_amount` uses the same `Decimal @db.Decimal(10,2)` shape as every other money column in the schema (not integer paise, despite CLAUDE.md's general note — verified against `rent_obligations.amount` and siblings before choosing the type).

### `hostel_utility_status`
Added 2026-07-26 for the tenant Room tab's "Living status" grid (water/wifi/electricity/cleaning). One row per `(hostel_id, utility)` (`@@unique`), owner-editable (`PATCH /api/utility-status`), tenant-read via `/api/tenants/me/room`. ### `hostels.hostel_type` / `hostels.food_included` / `hostels.publish_requested`
Added 2026-08-01 ([[Decisions#ADR-040|ADR-040]], migration `20260801100000_hostel_provisioning_fields`, idempotent `ADD COLUMN IF NOT EXISTS`) so `POST /api/owner/hostels/provision` has somewhere to put three fields the onboarding wizard had been collecting and discarding. `hostel_type` is a plain `String?` (`BOYS | GIRLS | CO_LIVING | WORKING_PROS`), not a Prisma enum — matching this schema's existing convention for descriptive statuses; the allowed set is enforced by `HostelProvisionSchema` at the API boundary. `food_included` is `Boolean @default(false)`.

**`publish_requested` is deliberately not `listing_status`.** `listing_status = LIVE` is written only by the Platform Admin console and always paired with `verification_status = VERIFIED` (`POST /api/platform-admin/hostels/:id/approve-listing`); if onboarding wrote it, any owner could self-approve their own public listing past platform verification. `publish_requested` records the owner's *intent* from the wizard's Publish step and leaves that gate alone. **It has no consumer yet** — the admin console neither surfaces nor acts on it; wiring it into the approval queue is open work.

The fourth onboarding field, the security deposit, needed no column — it goes into the existing `hostels.preferences_config` JSON under `billing_defaults`, via the same `sanitizeBillingDefaultsPayload` the preferences API uses. `rooms.base_rent` (pre-existing, `Int?`) is now always populated for newly provisioned rooms; rooms created before this change keep `null` and nothing backfills them.

### `hostels.display_order`
Added 2026-08-04 ([[Decisions#ADR-042|ADR-042]], migration `20260804120000_hostel_display_order`, idempotent `ADD COLUMN IF NOT EXISTS` + `hostels_owner_id_display_order_idx` on `(owner_id, display_order)`). `Int?` — the owner's manual position for their hostel in the Home "Property" list.

**Nullable and deliberately never backfilled.** `NULL` means "the owner has never reordered this hostel". The read path (`PortfolioService.getPortfolioSummary`) orders by `display_order ASC NULLS LAST, name ASC` — which is exactly the `name ASC` order the list had before the column existed. So existing owners see no reshuffle until they actually drag something, and a newly created hostel appends to the end rather than jumping to the top.

Written **only** by `PATCH /api/owner/hostels/reorder`, which rewrites every position for that owner inside one `prisma.$transaction`. There is no single-row "set position" write: patching one row can't express "move to position 2" without renumbering neighbours anyway, and two concurrent single-row patches can interleave into an order the owner never asked for. A partial list is rejected (`409 STALE_ORDER`) rather than best-effort applied.

See [[APIs]] for the endpoint and [[Features]] for the UI.

### `hostels.house_rules`
Added 2026-07-26 (`Json?` column on the existing `hostels` table, not a new table) for the tenant Room tab's House Rules accordion — an array of `{title, items: string[]}` sections. Deliberately kept out of the deep-merged hostel preferences policy blob (`hostelPolicyService`) — house rules are static reference content, not a policy setting, and folding it into that already-complex deep-merge schema risked corrupting real owner config for no benefit. ### `platform_admins` / `hostels.verification_status` / `hostels.listing_status` / `platform_leads` / `subscription_plans` / `hostel_subscriptions` / `platform_invoices` / `notification_templates` / `platform_settings`
Added 2026-07-26 for the Platform Admin Console — deliberately reintroduces the multi-hostel SaaS billing/subscription model ADR-006 removed, per an explicit user product decision (see [[Decisions]] ADR-030 for the full reasoning and reversal record). `platform_admins` is a 1:1 sidecar on `profile` (role `ADMIN`) carrying a `PlatformAdminTitle` (OWNER/SALES/VERIFICATION) — no public self-serve signup, first admin created via `scripts/bootstrap-platform-admin.ts`, later ones invited through the Admin Users panel. `hostels` gained `verification_status` (PENDING/VERIFIED) and `listing_status` (DRAFT/LIVE/SUSPENDED) columns directly — no new table, 1:1 with the hostel. `platform_leads` is prospective **hostel owners** signing up to the platform — a deliberately distinct table/namespace from the pre-existing `leads` table (prospective *tenants* for the admissions/CRM feature); naming collision was a real risk flagged during design. `subscription_plans` is the marketplace plan catalog (Starter/Growth/Premium seeded via a one-off script) — reshaped around "marketplace tier," not the old metered-usage `plans` table ADR-006 dropped. `hostel_subscriptions` is one row per hostel (`hostel_id` unique — changing plan updates the row, not a new one) tracking `HostelSubscriptionStatus` (TRIAL/ACTIVE/RENEWAL_DUE/PAYMENT_FAILED/CANCELLED), created in `TRIAL` status with a 14-day window when an admin first assigns a plan. `platform_invoices` records each collection from an owner (no real payment-gateway integration on this side for V1 — an admin manually records collection via `POST /api/platform-admin/hostels/:id/invoices`, which flips the subscription to `ACTIVE` and advances `next_renewal_at` by one billing cycle); GST (18%) is computed at export time from `platform_invoices.amount`, not stored as a column. `notification_templates` holds admin-configured owner-facing message content (Welcome/Verification Approved/Changes Requested) — content only, sending reuses the existing `notificationService`, no duplicate delivery mechanism. `platform_settings` is a generic `(key, value: Json)` singleton-per-key store — used today only for a `"general"` key (support email/phone/business address) since there's no other platform-wide config store to plug into. See [[APIs]] (`/api/platform-admin/*`), [[Features]], [[Decisions]] ADR-030.

### `platform_leads.google_email` / `platform_lead_invitations` / `PlatformLeadStatus` lifecycle replacement
Owner-acquisition funnel, phases 1–2. **`platform_leads.google_email`** (added 2026-07-28, phase 1) captures the email read from the real Google sign-in the landing page's lead-capture flow uses — never used for authentication, just contact info for the lead. **`platform_lead_invitations`** (added 2026-07-29, phase 2, [[Decisions]] ADR-032) is a single-use activation-token table for an approved lead — deliberately a new table rather than reusing `tenant_invitations` (which is FK'd to `tenant_id`/`hostel_id`/`room_id`, none of which exist for a lead yet), copying its proven shape instead: `id UUID` (PK, never exposed), `lead_id UUID` (FK to `platform_leads`, no formal `@relation`), `token TEXT UNIQUE` (`crypto.randomBytes(32).toString("hex")` — the actual public identifier, separate from `id`, matching `tenant_invitations.token`'s "don't put a DB PK in a URL" discipline), `status TEXT` (free-text state machine — `PENDING → OPENED → ACTIVATED`, or `EXPIRED` — following `tenant_invitations.status`'s convention of a string, not an enum, for workflow sub-state), `expires_at TIMESTAMPTZ` (+7 days from creation). No prefill data is duplicated into this table — the activation-context endpoint joins back to `platform_leads` for name/hostel_name/phone/google_email/city.

**`PlatformLeadStatus` replaced outright** (real `ALTER TYPE`, not `ADD VALUE` — old values were retired, not extended): `NEW, UNDER_REVIEW, APPROVED, INVITE_SENT, OWNER_ACTIVATED, HOSTEL_CREATED, LIVE, LOST`, mapped from the old 6-value set (`CONTACTED→APPROVED`, `DEMO_SCHEDULED→UNDER_REVIEW`, `ONBOARDING→INVITE_SENT`, `ACTIVE→LIVE`, `NEW`/`LOST` unchanged) in the migration's data-cast clause. `APPROVED` and beyond are system-managed — `PATCH /api/platform-admin/leads/[id]` only accepts `NEW`/`UNDER_REVIEW`/`LOST`.

**`platform_leads.converted_owner_id`** (existed since the original `platform_leads` design, phase-1-era, but was schema-only dead code until now — confirmed zero application-code references before this change, see [[Bugs]]) is populated for the first time by `POST /api/auth/owner-signup`'s optional `lead_token` handling, and is what `POST /api/owner/hostels` later looks up to advance a lead to `HOSTEL_CREATED` without any new FK on `hostels`.

See [[APIs]] (`/api/leads/*`, `/api/platform-admin/leads/[id]/approve`), [[Backend]], [[Decisions]] ADR-032.

### `platform_leads.tracking_token` / `applicant_message` / `rejection_reason` (added 2026-08-06, [[Decisions#ADR-050|ADR-050]])
Owner-acquisition funnel notifications work — three new nullable-then-constrained columns, no new table. **`tracking_token TEXT UNIQUE NOT NULL`** — a 32-byte hex string (`crypto.randomBytes(32).toString("hex")`), minted at row creation by `POST /api/leads/self-serve` and never expiring (distinct lifetime from `platform_lead_invitations.token`, which expires in 7 days — the two are deliberately not merged, see [[Decisions#ADR-050|ADR-050]]). It is the public identifier for `GET /api/leads/track/[token]` (see [[APIs]]) and is itself a bearer secret: anyone holding the link can read that enquiry's stage and `applicant_message`. **`applicant_message TEXT?`** — admin-authored, **owner-visible**, returned by the tracking endpoint. **`rejection_reason TEXT?`** — set only by `POST /api/platform-admin/leads/[id]/reject`, fed into the `stayo_owner_lead_rejected` template body. **Critically, `notes` (the pre-existing admin scratchpad column) is unchanged and stays admin-private** — it is never selected by the tracking endpoint's allowlist; `applicant_message` exists specifically so the two audiences (internal assessment vs. what the applicant sees) are kept apart by a distinct column rather than by discipline over one shared field. See [[Business-Rules]] for the full notification-trigger rules this supports.

Migration: `prisma/migrations/20260806120000_platform_lead_tracking/migration.sql` — adds all three nullable, backfills `tracking_token` for existing rows via `encode(gen_random_bytes(32), 'hex')`, then applies `NOT NULL` + a unique index. **Since 2026-08-06 (fix wave):** the migration now opens with `CREATE EXTENSION IF NOT EXISTS pgcrypto;` (matching the pattern in `prisma/migrations/20260514134500_whatsapp_logs_id_default/migration.sql`) — `gen_random_bytes()` is pgcrypto-only, and without the extension the backfill `UPDATE` would throw after the three `ADD COLUMN`s had already committed, leaving a half-applied migration and a failed `_prisma_migrations` row blocking every later migration. See [[Bugs]]. **Not applied to any database in this environment** — no reachable, migrated database was available when this shipped; the migration file is committed but unexecuted. Confirm zero-null backfill before relying on `tracking_token`'s `NOT NULL` in a fresh environment.

**No schema change was needed for the new OTP-row states** — `phone_verification_otps.status` and `.provider_status` are plain string columns, not Prisma enums (see the note above about workflow sub-states as strings). A skipped verification writes `status = 'SKIPPED'`, `provider_status = 'UNAVAILABLE'`, `verified_at = now()` (the freshness windows downstream are measured from `verified_at`), and `failure_reason = 'whatsapp_unavailable:<reason>'`. Such a row **can never be verified**: `otp_hash` holds a hash of a value that was never sent, and `verifyPhoneOtp()` only ever reads `PENDING` rows. It is written rather than omitted so both signup gates still require the caller to have gone through `/api/auth/send-phone-otp` for that exact number.

See [[APIs]] (`/api/auth/send-phone-otp`, `/api/leads/self-serve`, `/api/auth/owner-signup`), [[Business-Rules#Signup phone verification|Business-Rules]], [[Features]].

### `notifications.id` now has a default
Fixed 2026-07-26 — see [[Bugs]]. `id` previously had no `@default(...)`, so every call to `NotificationService.createNotification()` across the entire codebase (not just the new Platform Admin broadcast feature that surfaced it) had always failed at the Prisma layer; call sites using `Promise.allSettled` fan-outs (e.g. Food's publish notification fan-out) silently swallowed the failure. Now `@default(dbgenerated("gen_random_uuid()"))`, matching every other id column in the schema.

### `profile.auth_user_id` / `profile.auth_linked_at` (added 2026-07-28, [[Decisions#ADR-031|ADR-031]])
Supabase Auth migration. `auth_user_id String? @unique @db.Uuid` links a `profiles` row to its `auth.users.id` counterpart in the same Postgres instance (`DATABASE_URL`/`SUPABASE_URL` are the same database); `auth_linked_at DateTime? @db.Timestamptz(6)` records when. **Never assume `auth_user_id === profiles.id`** — they're different UUID spaces linked only by this column (in practice they often coincide for accounts created after this migration, since `registerOwner`/`selfSignUpOwner` now create the Supabase user first and are "born linked," but nothing enforces equality). Both nullable — linking is **just-in-time (JIT)**, not a backfill: a profile gets linked the first time it successfully logs in with a password (`ensureSupabaseIdentity()`, called from the one chokepoint `authService.createSessionAndTokens()`), not via a forced mass migration. A profile that never logs in again simply stays unlinked indefinitely — an accepted, deliberate consequence (see ADR-031), made measurable via `apps/backend/scripts/reconcile-supabase-identities.ts` (dry-run by default, reports linked/unlinked/ambiguous counts by role, never auto-links an ambiguous match). Migration applied via `prisma/migrations/20260728000000_profile_auth_user_id/migration.sql` (idempotent SQL, also mirrored into `SUPABASE_APPLY_ALL_PENDING.sql` per this repo's convention).

### `token_blacklist` dropped (2026-07-28, ADR-031)
Confirmed orphaned before removal — its only reference was `authService.logout()`, itself uncalled from any live route. Dropped in the same migration as the `auth_user_id` addition above.

### `refresh_tokens` — legacy-transition-only, scheduled for removal
Since ADR-031, new sessions are minted by Supabase (`signInWithSupabasePassword()`) and never write a `refresh_tokens` row — the table now exists only to let already-issued legacy HS256 tokens keep working during the dual-accept transition window (`middleware.ts` tags requests `x-auth-mode: legacy|supabase`; legacy access tokens expire on their own ~12h lifetime once `/api/auth/login` stops issuing new ones, so no forced logout is needed). `sessionLifecycleService`'s creation/rotation methods (`createSession`, `rotateRefreshToken`, `revokeTokenFamily`, `revokeAllUserSessions`) were removed as dead code in the same change; only `touchSession()`/`revokeSession()` remain, and `touchSession()` is now only called for `x-auth-mode: legacy` requests (see [[APIs]] `/auth/me`). Plan is to drop `refresh_tokens` and its Prisma relation in a later, separate release (ADR-031 §Phase 6) once no legacy tokens remain in circulation.

## Key relations

`hostels` is the root almost everything scopes to (`owner_id → profile`). `tenants` belongs to one `hostel_id` and is 1:1 with a `profile` (auth identity). `rent_obligations` belongs to a `tenant` + `hostel`, optionally an `allocation`, `agreement`, and `billing_plan`. `payments` belongs to one `obligation` and optionally a `payment_group`/`payment_attempt`, producing exactly one `receipts` row. `move_out_requests` fans out 1:1/1:N into `move_out_inspections`, `move_out_inspection_items`, `exit_settlement_transactions`, `exit_disputes`, `exit_feedbacks`. `Agreement` self-references forward/backward for renewal chains and links to `AgreementTemplate` and `RenewalOffer`. Full per-model relation table (100+ rows) lives in the research artifact this page was built from — not reproduced verbatim here to keep this page navigable; **ask for the full relation dump if you need it.**

A large class of **operational/audit tables intentionally have no formal Prisma `@relation`** — only bare UUID columns (e.g. `payment_operational_anomalies`, `payment_webhook_events`, `financial_reconciliation_issues`, `tenant_transfer_logs`, all the WhatsApp/audit-log tables). This looks deliberate (avoiding FK overhead on high-volume append-only logs) but means an ER diagram built purely from `@relation` annotations will miss these implied links.

## Known schema quirks / inconsistencies (flagged in-code, not assumed)

- **`rent_obligations`** has three parallel status columns (legacy `status`, `lifecycle_status`, `settlement_status`) — intentional migration-in-progress per schema comments, but the old column's deprecation status isn't stated in the schema itself. **Needs clarification.**
- **`paymentAttempt`** has two generations of provider-reference fields coexisting; which is canonical is **Unknown**.
- Several tables look like duplicate/legacy pairs by naming alone: `rent_generation_logs` vs `rent_generation_ledgers`; `financial_invariant_failures` vs `payment_operational_anomalies` vs `payment_reconciliation_items` vs `financial_reconciliation_issues` (four overlapping "something is financially wrong" tables); `hostel_invariant_checks` vs `migration_audit_runs`; `message_logs`/`message_packs` (looks like a legacy SMS-credit system, likely superseded by the WhatsApp-specific tables, with no FK link between the two tables). **Which of each pair is still live could not be determined from the schema alone — needs clarification.**
- `usage_tracking` (per-owner tenant/hostel counts) looks like a vestige of a removed SaaS billing/plan-limits system — a migration named `20260517000000_decommission_saas_tables` exists, and archived SQL (`046_saas_billing.sql`, `050_subscription_billing.sql`) is present in the repo-root `migrations/` folder, but no active plan/subscription model exists in the current schema. Consistent with the many `410 Gone` billing/subscription/addon API routes — see [[APIs]].
- `rooms.floor` (Int?) and `rooms.floor_id` (FK) coexist — `floor` looks deprecated in favor of the normalized `floors` relation.
- Minor redundancies noted directly in the schema: `receipts` declares the same `[hostel_id, receipt_number]` unique constraint twice; `whatsapp_logs` declares the same 3-column index three times under different names.
