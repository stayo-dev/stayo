### Added
- **2026-08-05**: **Every Action Center card now leads to a work queue — Phase 3** ([[Decisions#ADR-046|ADR-046]]). After Phase 2 only Collect Rent went anywhere; Review Agreements, Activate Tenants and Fill Vacant Beds were **structurally incapable** of being tapped, because `StatCard` had no `onClick` prop at all. Dead affordances six, seven and eight, sitting beside a hero card that did navigate. Per explicit direction — *"do not invent different interaction models for different cards"* — the model is now enforced by **one component** rather than by discipline: `WorkQueue` owns the header, the four view states, sections, numbered rows, the reason line and the action bar, and a queue supplies only data and actions. **The Collect Rent screen was refactored onto it too** rather than left as the odd one out, shrinking 9.08 kB → 4.94 kB. **No new backend for any of the three**: agreements reuse `renewalDecisionService.getOwnerRenewalQueue` (which already ranks by decision state and days overdue), activations reuse `usePendingActivations` and the backend activation state machine, and vacancy composes the existing hostel-scoped `GET /api/rooms` fanned out across hostels. `PendingActivationsPage` was rebuilt on the shared component — it previously had no prioritisation and no inline actions, so it could show who was stuck but not let the owner act without opening each profile; it now sorts longest-waiting-first with Call/WhatsApp. **No progress bar or daily target**, per explicit product direction — completion is the row leaving the list. Two bugs caught during implementation: the renewal payload exposes `hostel_id` but no hostel name (the subtitle would have rendered empty), and agreements needed first-match-wins section assignment because the backend tags one agreement with several states at once. **Cross-checked live**: the vacancy queue independently computes 2 rooms / 2 free beds, matching the Home card exactly, so a card and the queue it opens cannot disagree. 178 frontend tests pass; build clean; `tsc` at baseline. **Phase 4 (one merged daily task list) not built.** See [[Features]], [[Bugs]].
- **2026-08-05**: **Intelligent Collection Queue — Phase 2 of the owner navigation model** ([[Decisions#ADR-045|ADR-045]]). The Action Center's "Collect Rent" card showed ₹1,08,600 owed and a `›` chevron — with **no `onClick`**. Fifth dead affordance of that class. It now opens a real work queue at `/owner/money/collect`. **Audit first:** `/api/owner/finance/collections` turned out to be a 410 tombstone, `getDuesReport` is per-obligation and hostel-scoped where a queue is per-tenant and portfolio-wide, and `getTenantDues` is per-tenant async (N+1). The right primitive already existed — `financialService.getTenantPaymentSummary`, sync and documented as taking pre-fetched rows for exactly this batch case — so **no financial figure is computed twice**: outstanding and last payment come from it, overdue-ness from the settlement planner's `isOverdue()`, last reminder from `reminder_logs`. Fixed **4-query budget** regardless of tenant count. Tenants are grouped into **Needs immediate attention → Due today → Waiting after reminder → Due soon** and ordered within each by a score where **every point is attributed** (`factors[]` in owner language: "12 days overdue (+24)", "₹8,800 outstanding (+8)", "Has never paid (+15)"); the card shows the top two, a bottom sheet shows all, and a test asserts `score === sum(factors)`. **Live data caught a real design flaw before ship:** the reminder-cooldown rule put 7 of 10 tenants into "waiting" and ranked an 11-day-overdue tenant below a 12-day one, reporting almost no work while ₹59,000 sat uncollected — a severity cap now stops deferring once reminders have visibly failed. The architectural invariant also caught an optional hostel-id contract and was right to; the service now takes an explicit `hostelFilter: string | null`. `recommendation: null` ships on the contract so the future engine is a value change, not a redesign. Cards not tables, thumb-sized Collect/Call/WhatsApp on every row, lucide icons rather than emoji. 62 new tests (178 frontend, 115 pure backend); all 9 invariants pass; build clean; `tsc` at baseline both apps. **Verified against live data before and after the fix**: 3/7 across "needs attention"/"waiting" before, **4/6** after, with the 11-day-overdue tenant correctly promoted and the ₹84,500 total unchanged. **Phases 3–4 not built.** See [[Business-Rules]], [[Features]], [[APIs]], [[Bugs]].
- **2026-08-05**: **Universal Search — Phase 1 of the new navigation model** ([[Decisions#ADR-044|ADR-044]]). The Home search bar was a `<div>` wrapping a `<span>`: it looked like a field and did nothing. Behind it sat **two overlapping tenant-search endpoints** — `/api/owner/search` (labelled "for the global navbar", tenants only, no ranking, bare array outside the envelope, and **orphaned**: its wrapper `ownerService.searchTenants` existed but nothing called it) and `/api/payments/quick-collect/search` (good ranking, but ACTIVE-only and issuing a per-tenant obligations *and* ledger query per hit — 40 round-trips for 20 results). The orphaned path was rebuilt as the real thing; the payment one was deliberately left alone, since its cost profile suits a considered payment flow and not a typeahead. Search now covers **tenants** (name, four phone fields, room, hostel, roll number, email, and the word "invited"), **hostels** (name, city) and **rooms** (number), grouped and ranked on one shared scale — exact name → phone → room → hostel → prefix → contains → fuzzy. **The route and the client never name a result type**: sources are `SearchProvider`s in a single registry and every result carries its own `href`, so payments/complaints/expenses/staff can be added by writing a provider alone. Providers run under `Promise.allSettled`, so one failing source degrades its own group instead of blanking the search mid-keystroke. **A result is a workspace, not a link** — tenant rows carry inline Call · WhatsApp · Copy number · Collect · Profile, with Collect deep-linking into the existing QuickCollect flow with the tenant preselected, and each action shown only when it can actually work. Reuse over reimplementation: the hostel provider composes `portfolioService.getPortfolioSummary` so search occupancy matches the Home cards exactly, and the tenant provider composes `financialService.getTenantPaymentSummary` over one batched query so outstanding is never independently derived. A unit test caught a real bug pre-ship: a bare 10-digit query against a `+91`-stored number scored only as a weak *contains*; phone matching now compares the national 10-digit tail, verified live (`9845013001` → exact match on `+919845013001`). 45 new tests (151 frontend, 78 pure backend); build clean; invariants pass; frontend `tsc` at **499**, two *below* its baseline. **Phases 2–4 (Collect Rent queue, agreement/activation/vacancy queues, unified daily task list) are not built** — the Action Center still shows counts only. See [[Features]], [[APIs]], [[Bugs]].

### Changed
- **2026-08-05**: **Billing behaviour now has exactly one home, and collecting a payment no longer ambushes the owner.** Reported as "marking a payment says partial payments aren't allowed and I can't find any setting for it" — which turned out to be four problems. (1) `partial_payments.enabled` was fully enforced in `settlement-planner.ts` and defaulted to `false`, but appeared in **no UI at all** — the enforcement shipped years before any control did. (2) The review sheet showed the refusal *and* a complete success preview simultaneously ("1 installment left part-paid… a receipt is generated"), describing an outcome that couldn't happen. (3) **Three screens** each owned part of billing, and `MoreBillingPage` wrote `type: 'FLAT'` unconditionally while omitting `max_amount` — so opening it after setting a PERCENTAGE late fee with a cap **silently destroyed both**. (4) Three Configure screens pinned their save bar at `bottom-0`, putting the button **under the bottom nav**. Per explicit user direction the fix is structural, not a patch: a single canonical **Billing policy** screen now owns rent collection, security deposit, agreement duration, rent schedule and late fees; `MoreBillingPage`, `MoreConfigLateFeesPage` and `MoreConfigTenantDefaultsPage` are **deleted** with their routes redirected. A new **`minimum_percentage`** floor (0-100 of total outstanding) joins `minimum_amount` — both are floors so the larger wins, clamped to the outstanding balance so a big absolute floor can't strand a small final payment. The collect flow now states the policy **before** the amount is typed and, at review, **either** explains the block with a route to fix it **or** shows the outcome — never both. No screen or message names a backend flag; tests assert that. Also added **`npm run test:pure`** — the main vitest config imports `lib/db` and TRUNCATEs the `test` schema, so with no `DATABASE_URL_TEST` the whole suite is unrunnable *including pure functions*; `test:pure` runs 56 settlement tests with no database reachable, which is how the new percentage logic was actually verified. 17 new backend tests + 21 new frontend tests (128 frontend pass); invariants pass; `tsc` at its 501-error baseline. Three old assertions pinning the previous rejection wording were updated — deliberate, not a regression. See [[Decisions#ADR-043|ADR-043]], [[Business-Rules]], [[Features]], [[Bugs]].

### Changed
- **2026-08-04**: **Backend latency — serverless functions pinned to `bom1`, and Prisma `relationJoins` enabled.** The owner Tenants screen was taking ~10.9s. The waterfall looked like slow queries, but measurement said otherwise: `GET /api/tenants` unauthenticated (401, no DB) took **117ms** while `GET /api/health` (same path + one `SELECT 1`) took **1388ms** — so a single trivial query cost **~1271ms**, and function invocation was never the problem. `x-vercel-id: bom1::iad1::…` gave the cause: `apps/backend/vercel.json` declared no `regions`, so functions ran in `iad1` (Washington DC) against a database in `ap-south-1` (Mumbai). Two changes shipped separately, each deployed and re-measured before the next: (1) `"regions": ["bom1"]` — config only, DB round-trip **~1271ms → ~28ms**; (2) `previewFeatures = ["relationJoins"]` — schema flag only, no service code touched, since `join` becomes the default relation load strategy on PostgreSQL once enabled (confirmed by measuring that an unspecified strategy emits the same query count as an explicit `join`), taking the `getAllTenants` `findMany` from **14 SQL queries to 4**. `query` vs `join` result equivalence was verified across every hostel before deploying. **Service-code optimisation was deliberately not done** — `tenant-service.ts` is unchanged, and whether it is still justified will be decided from measurements rather than assumed. Full measured baselines, plus an explicit list of what remains *unmeasured* (notably `GET /api/tenants` end-to-end HTTP latency, which needs an authenticated session), are in the new [[Performance]] page. One measurement round was nearly reported as an 80× regression before `curl`'s `time_namelookup` showed the ~15.1s was a local DNS resolver timing out, identically on unrelated hosts — the page documents the DNS-bypass method so this is not re-encountered. See [[Decisions#ADR-041|ADR-041]], [[Performance]].
