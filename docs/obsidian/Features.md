### Owner Action Registry
- **Status:** shipped (catalog-only slice)
- **Owner-facing?** yes · **Tenant-facing?** no
- **Key files:** `apps/backend/src/services/owner-actions/owner-action-registry.ts` (in-memory registry, `listForEntity(entity, ctx)`), `apps/backend/src/services/owner-actions/definitions/*.ts` (`tenant-actions.ts` → `TENANT_EDIT_PERSONAL_INFO`; `payment-actions.ts` → `PAYMENT_RECEIVE`; `room-actions.ts` → `ROOM_MOVE`), `apps/backend/src/services/owner-actions/bootstrap.ts` (single import point for all definitions), `apps/backend/app/api/owner-actions/route.ts`, `apps/frontend/src/features/owner-actions/api/index.ts`
- **Depends on:** [[APIs]] (`GET /api/owner-actions`)
- **Notes:** A read-only catalog of which owner-facing actions are available for a given entity (currently only `tenant` is queried by the frontend). Each registered action declares `entity`, `category` (`EDIT`/`WORKFLOW`/`CORRECTION`/`VIEW`), a `label`, `allowedRoles`, and a synchronous `isAvailable(ctx)` predicate (evaluated server-side against `tenantStatus`/`actorRole`). `TenantProfilePage.tsx` fetches the tenant's action list and uses it to source the labels on the "Request Change" (`TENANT_EDIT_PERSONAL_INFO`, available only when tenant status is `ACTIVE`) and "Receive Payment" (`PAYMENT_RECEIVE`, always available) buttons on `PrimaryActionsBar`, falling back to hardcoded defaults if the catalog lookup misses. **This is catalog-only in this first slice — no action's actual execution routes through the registry yet** (clicking the buttons still triggers the pre-existing change-request/payment flows directly); the registry exists so future `CORRECTION`-category actions (payment reversal/transfer, expense void, etc. — see the Business Recovery Platform / correction-cases proposal work under `docs/business-logic/`, not yet reflected elsewhere in this vault) have a place to register into without inventing a new mechanism. `ROOM_MOVE` (`entity: "room"`) is registered but has no frontend consumer yet — deliberately out of scope for this slice.

### Correct Payment (Reverse / Transfer)
- **Status:** shipped (Reverse + Transfer — first real UI consumer of the Business Recovery Platform's `/api/recovery/cases/*` routes)
- **Owner-facing?** yes · **Tenant-facing?** no
- **Key files:** `apps/frontend/src/features/recovery/api/index.ts` (`recoveryService.createCase/validate/execute/getById`), `apps/frontend/src/app/components/modals/CorrectPaymentModal.tsx` (self-contained correction-type toggle → reason (+ tenant picker for Transfer) → preview → confirm modal), `apps/frontend/src/features/payments/api/index.js` (`paymentService.quickCollectSearch`, reused for the Transfer "correct tenant" search, same pattern as `RecordPaymentModal.tsx`), `apps/frontend/src/features/tenants/components/financial/FinancialActivityCard.tsx` (`onCorrectPayment` prop, "Correct Payment" button next to "View Receipt"), `UnifiedActivityTimeline.tsx` (threads the prop), `apps/frontend/src/features/tenants/components/profile/TenantProfilePage.tsx` (`correctingPaymentId` state, renders the modal, invalidates `queryKeys.tenants.{obligations,financialTimeline,advance,full,overview}` on close)
- **Depends on:** [[APIs]] (Recovery / Corrections), [[Business-Rules]] (Correction Cases — Payment corrections)
- **Notes:** Wired directly into the Tenant Details page's Activity tab's unified timeline per an explicit product decision to **not** build a separate Recovery Center dashboard in this phase (that list/detail view is deferred to Phase 3). This bypasses the Owner Action Registry entirely — it does not register as a `CORRECTION`-category owner action; the "Correct Payment" button is a conditional render (`receiptPaymentId && onCorrectPayment && canCorrectPayment`) alongside the existing "View Receipt" button, not sourced from `ownerActionsService`. The third condition (`canCorrectPayment = payments.length <= 1`) hides the button for grouped/multi-payment settlement entries — see [[Bugs]] — because reversing/transferring one payment in a group would only be a partial correction of the card's total. The modal now opens with a two-button correction-type toggle ("Wrong / Reverse" vs "Wrong Tenant / Transfer", pre-preview only — hidden once a case exists). Reverse mode is unchanged: `createCase({caseType: 'PAYMENT_REVERSAL', input: {paymentId}})`. Transfer mode additionally requires picking a destination tenant via a debounced (250ms) `paymentService.quickCollectSearch` lookup (fires only when the query is ≥2 chars and no tenant is yet selected) before "Preview Impact" is enabled, then calls `createCase({caseType: 'PAYMENT_TRANSFER', input: {paymentId, toTenantId}})`. Both modes share the same preview → "Confirm Reversal"/"Confirm Transfer" → `validate` + `execute` flow (treated as one logical confirm step; a 422 `VALIDATION_REJECTED` from `validate` stops `execute` from running and shows the rejection reason inline). Edit Reference/Notes (`PAYMENT_REFERENCE_EDIT`) UI is still explicitly out of scope for this slice — the backend handler exists and is reviewed, but has no frontend entry point yet. Reverse mode also supports a guided immediate re-record for the "wrong amount" case: `CorrectPaymentModal` accepts an optional `onSuccessReverse?: (tenantId: string) => void` callback, invoked only when `correctionType === 'REVERSE'` (never Transfer, since a Transfer's money has already moved to the correct tenant, leaving nothing to re-record). `TenantProfilePage.tsx` wires this to reopen the existing Receive Payment flow (`RecordPaymentModal`, reusing the page's existing payment-modal state — no second mount point was introduced) about 1.3s after the reversal's own success state finishes displaying, scoped to the same tenant whose payment was just reversed.

### Change Rent
- **Status:** shipped
- **Owner-facing?** yes · **Tenant-facing?** no
- **Key files:** `apps/frontend/src/features/tenants/api/index.js` (`tenantService.changeRent`), `apps/frontend/src/app/components/modals/ChangeRentModal.tsx` (self-contained FORM → CONFIRM flow, mirroring `WaiveObligationModal.tsx`'s identity-confirmation pattern), `apps/frontend/src/features/tenants/components/profile/TenantProfilePage.tsx` (`showChangeRent` state, "Change Rent" surfaced as one of `PrimaryActionsBar`'s own overflow ("More") menu actions — not a separate adjacent button — gated on `canChangeRent` (tenant status `ACTIVE`), `upcomingRentObligations` derived from the page's already-loaded `dues.items` — no second obligations fetch)
- **Depends on:** [[APIs]] (`POST /api/tenants/:id/change-rent`), [[Business-Rules]] (rent changes are immediate and owner-only, see the Category C exception note)
- **Notes:** Owner picks a new rent amount, the month it should take effect from (dropdown sourced from `upcomingRentObligations` — RENT obligations from the page's existing dues data with zero recorded *net* payments, `Number(o.paid ?? 0) === 0`), and a reason → password re-entry (`identityService.confirmIdentity(password, 'CHANGE_RENT')`) → submit. Applies immediately with no tenant approval step (identity-token gated the same as obligation cancel/waive). On success, invalidates `queryKeys.tenants.{obligations,financialTimeline,advance,full,overview}` and calls the page's `refetch()`. `currentRent` is read from `tenant?.monthly_rent ?? overview?.rent`. `applyRentChangeInTx` now also writes `tenants.monthly_rent` (in the same transaction as `agreement.contract_rent`, mirroring the `tenantContractSync` pattern used by renewal activation in `renewal-activation-engine.ts`) — resolves the previously-flagged "Unknown / needs clarification": `tenant.monthly_rent` **is** kept in sync, so this displayed value no longer goes stale after a successful change. See [[Bugs]] for this fix and a second, related gap: the modal's pre-submit "N installments will change" preview is a client-side count filtered by *net* zero-paid, which is a looser guard than the backend's real safety rule (zero payment *records* on the obligation, `payments.length === 0`) — after a Payment Reversal correction (see Correct Payment above), an obligation can have net paid `0` via two payment rows (original + offsetting reversal) and still be correctly skipped by the backend while still appearing in the frontend's preview count. The modal does not attempt to prevent this (would require exposing raw payment-row counts through `getTenantDues()`, out of scope); instead its success screen now shows the server-reported `obligationsUpdated` count from the response, so any such discrepancy is visible after the fact instead of silent.

(1) `RiskComplianceCard` merges what used to be two independently-derived agreement/KYC/score cards (`TenantHealthCard`'s composite score + checklist, `OwnerInsights`'s prose warnings restating the same checklist items) into one checklist-first card. Separately, the page's action layout (previously 3 groups totaling 8 buttons, including a standalone "Change Rent" button rendered next to the action bar) is now one `PrimaryActionsBar`: 1 primary + 3 secondary always-visible buttons, plus a "More" dropdown/bottom-sheet holding the remaining 4 actions (Share Payment Link, Request Change, Change Rent, Check-out/Exit) — `canChangeRent`/`onChangeRent` props gate the Change Rent item to `ACTIVE` tenants only, same rule as before. A 4th "Stay" tab (room allocation history via `AllocationHistoryTimeline` + the move-out settlement workflow via `ExitWorkflowSection`) was added, replacing what was previously a collapsible card lower on the page. **Purely a frontend recomposition — no backend routes, services, or business rules changed.** See [[Frontend]] for the resulting always-visible-zone + 4-tab structure, and [[Changelog]] for the dated entry.

### Stayo Discover — the public hostel marketplace (2026-08-15; nav restructured 2026-08-16)

- **Routes:** `/discover` (Explore), `/discover/search`, `/discover/h/:slug` (listing detail), `/discover/h/:slug/enquire`. **Saved/Enquiries/Profile moved to `/profile/*`** (`/profile/saved`, `/profile/enquiries`, `/profile/enquiries/:id`, `/profile`, `/profile/details`, `/profile/history`, `/profile/documents`) as of ADR-078 — they're account-level, not Explore-level, and are no longer primary bottom-nav tabs. Explore no longer has its own 4-tab shell (`DiscoverShell` retired as a nav owner, its non-nav helpers `DiscoverEmpty`/`HostelCardSkeleton`/`PrimaryButton` still used); the shared `AppShell`/`AppBottomNav` (`app/layouts/AppShell.tsx`, `app/nav/appNavConfig.ts`) now owns the outer bottom nav everywhere: **Explore | Profile** with no tenancy, **Explore | Dashboard | Profile** with a live tenancy (`tenant_status` `INVITED`/`ACTIVE`).
- **Why its own route tree and not a tab in `/tenant/*`:** almost everyone using Discover has no tenancy. Behind the tenant portal's guard, browsing would require a sign-in (killing SEO and the top of the funnel) and every seeker would be bounced to onboarding. There is **no route guard** on `/discover`; the authenticated Profile page renders an in-place sign-in prompt rather than redirecting. The server is the real boundary.
- **What appears:** hostels that are `listing_status = LIVE` **and** `verification_status = VERIFIED` **and** `ACTIVE` **and** accepting admissions. Owners cannot self-promote into it — that pairing is admin-controlled ([[Decisions#ADR-040|ADR-040]]), and nothing in discovery writes those columns.
- **What it shows, and what it deliberately doesn't.** Real: name, city, address, photos, starting price (`min(rooms.base_rent)`), live vacancy, sharing types from `rooms.capacity`, audience from `hostel_type`, meals from `food_included`, the verified badge. **Omitted rather than faked:** star ratings, review counts, the amenity grid, and distance-to-campus — none of that is modelled, and there is no lat/lng anywhere. An unpriced room reads "Price on request", never "₹0". Listings therefore look thinner than the prototype on purpose; the layouts reserve the space.
- **Filters** are all column-backed: city, price range, sharing type, audience, meals-included, has-vacancy, plus free-text over name/address/city. No geo search and no college proximity in this phase.
- **Enquiries are `visitor_leads` rows** (`source: 'DISCOVER'`), landing in the owner's existing inbox, scoring and funnel — no parallel entity. Owner approval routes into `POST /api/leads/[id]/convert-to-invitation` — **as of 2026-08-20 ([[Decisions#ADR-085|ADR-085]]), this is now an actually-wired live path** (the owner Leads tab's Accept action → the pre-filled Add Tenant wizard → this endpoint on submit; previously the endpoint existed with no frontend caller at all), so an accepted enquiry becomes a real tenant invitation feeding the existing onboarding flow. The seeker sees a projected 3-step stage (`SENT`/`REVIEWING`/`ACCEPTED`/`CLOSED`), never the owner's raw funnel status — `REJECTED` (new alongside `ACCEPTED`/`ON_HOLD`, see below) projects as `CLOSED`, same as `LOST`.
- **~~The account is the existing one (phone-OTP signup)~~ — superseded 2026-08-16.** `authService.selfSignUpTenant()`/`POST /api/auth/tenant-signup` still exist (untouched, in case anything else depends on them) but are no longer wired to `LoginModal`'s primary UI. New Discover accounts are now created via Google — see [[#Google auto-provisioning + phone verification at enquiry (2026-08-16)]] below. Same account shape either way: `role = TENANT`, no `tenants` row, Supabase-linked at creation; later becomes the person's tenancy via owner invite.
- **Scope — phases C and D remain.** C: owner listing content (amenities, distances, bed tiers). D: reviews and ratings. E (owner listing marketing page) explicitly deferred by the owner. Aadhaar KYC is out — it needs a licensed AUA/KUA integration, a commercial and regulatory dependency rather than a coding task. **Phase B shipped 2026-08-15 — see below.**

### The portable Stayo profile (2026-08-15, phase B)

- **Routes:** `/discover/profile/details` — the editor, reachable with **no hostel involved**. That is the requirement it exists for: a tenant fills their details in before enquiring anywhere, and every later onboarding opens pre-filled.
- **What moved:** identity left `tenants` (one row per tenancy per hostel) for `profile_identity` (one row per person). Harmless while identity was frozen per tenancy; with an editable profile it meant regenerating an old agreement could print an address the signatory never agreed to. Now snapshotted at signing. ### Google auto-provisioning + phone verification at enquiry (2026-08-16)

- **What changed:** tenant signup is Google-only now — `LoginModal`'s Sign Up tab no longer has a name/email/phone/password form, just "Continue with Google". The Log In tab keeps email+password (for existing password-based accounts) alongside Google. `AuthContext.signUpTenant()`/`POST /api/auth/tenant-signup` (phone-OTP signup) are **untouched, just unwired** from this UI, in case anything else still depends on them.
- **The auto-provisioning invariant is not weakened.** `resolveSupabaseSession()` (`lib/auth/supabase-session.ts`) is completely unmodified and still rejects an unknown Google email with `NO_STAYO_ACCOUNT` on the plain login path — `tests/auth-hardening-security.test.ts`'s "No Auto-Provisioning" suite passes unchanged. A new, separate, narrowly-scoped function, `provisionMarketplaceTenantFromSupabase()` (`lib/auth/supabase-provision.ts`), handles the new-account case — reachable only from the new `POST /api/auth/google/provision` endpoint, which itself requires an already-valid Supabase session (i.e., Google has already authenticated the person; this endpoint only decides whether to create a `profiles` row for them). It creates the profile only when no `profiles` row exists for that email at all (any role — never re-links or takes over an existing account), then delegates back to the untouched `resolveSupabaseSession()` to build the session payload, so there is exactly one payload-building implementation. Rate-limited via the existing `checkFixedWindowLimit` primitive (email + IP), reusing infra rather than adding a new one. See [[Decisions#ADR-078|ADR-078]] for the full reasoning and [[APIs]] for the endpoint.
- **No database schema changes were needed.** `profile.phone`, `profile.phone_verified`, and the `phoneVerificationOtp` table all already existed (built for the original phone-OTP signup flow) — this work reuses them entirely.
- **Frontend flow:** `AuthContext.loginWithGoogleAllowProvision()` (new; delegates to the untouched `loginWithGoogle()`) sets a `sessionStorage` intent flag + a return-to path before the OAuth redirect — necessary because a full-page redirect to Google and back cannot carry in-memory callback state. `AuthCallbackPage` reads the flag on return: on `NO_STAYO_ACCOUNT` with the flag set, it calls the provision endpoint, retries `/auth/me`, and — new — honours the stored return-to path instead of always landing on `/tenant/home`/`/discover`, so a visitor mid-enquiry lands back on the exact enquiry they were filling in. Owner mode never calls the provisioning variant — untouched invariant.
- **Phone verification moved from signup-time to enquiry-time, and only asks once.** `EnquiryPage` now gates "Send enquiry to owner" on `user.phone_verified` (new field, surfaced on `/auth/me` and `AuthUser`) rather than just `isSeeker`. A Google-provisioned account has no phone on file at all; the enquiry page shows an inline "confirm your phone" step (also collects name, if missing) → `PATCH /api/profile` saves it (which re-arms `phone_verified: false` if the number is genuinely changing — see below) → the existing `authApi.sendPhoneOtp`/`verifyPhoneOtp` (same calls `LoginModal`'s old signup flow used) → on verify success, submits the enquiry immediately. If `phone_verified` is already `true`, none of this shows — straight to submit, no repeat OTP. If WhatsApp OTP delivery is unavailable, the existing skip/degrade behavior (ADR-034) applies the same way it always did for signup.
- **`PATCH /api/profile` (pre-existing route, `app/api/profile/route.ts`) gained one correctness fix**, load-bearing for the above: changing `phone` now resets `phone_verified`/`mobile_verified` to `false` when the new value actually differs from what's on file (previously it left the old verified flag in place, which would have made a *new, never-verified* number read as verified). Also returns a friendly `409 PHONE_TAKEN` instead of a raw 500 when the phone is already registered to another account (a real, previously-unhandled case now that this route is actually called from the UI for the first time).
- **What the owner sees is unaffected — no enquiry-creation route changes.** `discoveryService.createEnquiry()` already reads `seeker.phone` from the session-resolved profile with no separate phone parameter; since submission is now gated on `phone_verified`, whatever's in `seeker.phone` at that point already is the verified number, by construction.
- **`middleware.ts`/`SupabaseClaims` gained one small extension:** Google's `user_metadata.full_name`/`.name` is now surfaced as an `x-auth-name` header (added to the identity-header strip list, like every other `x-auth-*` header) — the only consumer is the new provisioning path, which needs *some* value for `profile.name` (`NOT NULL`) when creating a brand-new profile with no other source for it.
- **See also:** [[Decisions#ADR-078|ADR-078]], [[APIs]], [[Business-Rules]].

The resend's error body carries no `activation_link`, so the original is carried forward rather than lost.

  **Verification limits, stated plainly:** the 30 tests cover the pure decision logic (all three delivery cases, `needs_email`, the 202 error-body reading, link preservation, clipboard success/denial/absence, share-URL building). ## Password recovery by email or WhatsApp, and Google sign-in for every role (2026-08-08)

- **What it does:** `/forgot-password` asks how you want to prove it's you, then follows through. **Email** sends the one-hour reset link it always did. **WhatsApp** sends a 6-digit code, and the same screen that accepts the code also takes the new password. Login, logout and password reset now work the same way for owners, tenants and admins, and "Continue with Google" is available to all three ([[Decisions#ADR-054|ADR-054]]).
- **Why the second channel:** email is the weakest link in this product's identity story — tenants are often onboarded with an owner-supplied address they cannot read, and the Resend account still has no verified sending domain, so mail falls back to a sandbox sender that only reaches the Resend account owner. The phone-OTP pipeline built for signup was already hardened, so reset reuses it ([[Decisions#ADR-055|ADR-055]]).
- **Fails closed:** the `PASSWORD_RESET` OTP purpose is deliberately excluded from `SKIPPABLE_OTP_PURPOSES`. Those purposes degrade to "no code needed" when WhatsApp is unconfigured — fine for signup verification, an account-takeover vector for reset. Guarded by `tests/password-reset-otp-purpose.test.ts`, which was confirmed to fail when the purpose is added to that list.
- **Checks the number before sending** (amended 2026-08-08): an unregistered number gets 404 `NO_ACCOUNT_FOR_PHONE` and the UI keeps you on the number step, rather than advancing to a code screen for a code that was never sent. This deliberately discloses whether a number is registered, because the signup routes already do; see [[Decisions#ADR-055|ADR-055]] for the full reasoning and what still holds (per-probe rate limits, status never disclosed, email channel still fully generic).
- **Where:** Backend — `app/api/auth/forgot-password/phone/route.ts`, `app/api/auth/verify-reset-otp/route.ts`, `lib/services/auth-service.ts` (`requestPasswordResetByPhone`, `verifyPasswordResetOtp`), `lib/services/email-delivery.ts`, `lib/services/auth/password-reset-purpose.ts`, `lib/config/supabase-auth-config.ts`. ### Platform Admin — owner document review queue

- **Status:** shipped 2026-08-07 (branch `feat/owner-onboarding-ux`)
- **Owner-facing?** indirectly (the outcome is shown on the onboarding KYC step) · **Admin-facing?** yes
- **Key files:** Frontend — `platforms/admin/pages/AdminDocumentsPage.tsx`, `platforms/admin/documents/{documentQueue.ts,documentQueue.test.ts,DocumentViewer.tsx}`, `features/platform-admin/api/index.ts`. Backend — `app/api/platform-admin/owner-documents/route.ts`, `.../[id]/review/route.ts`, `src/services/owner-documents/document-review-guards.ts`.
- **Route:** `/admin/documents` (sixth tab in `AdminAppShell`'s `ADMIN_TABS`).
- **Why it exists:** owner KYC uploads had been landing in `owner_documents` since ADR-038 with **no admin endpoint and no admin UI**. The uploader deliberately cannot set `status`, so `VERIFIED` was unreachable in practice and every owner's documents sat in `PENDING` forever.
- **Shape:** a two-pane queue, not a card grid — reviewing is a loop (oldest → look → decide → next), and an "open in new tab" link breaks that loop on every item. The document renders inline with zoom and rotate, because what arrives is phone photos of Aadhaar cards, frequently sideways. Documents are grouped **by owner** so Aadhaar and PAN can be name-checked against each other.
- **Ordering:** oldest waiting first, with an Overdue flag past 24h. Newest-first would push whoever has waited longest further down each time someone new uploads — and an owner cannot go live until this is done.
- **Business rule:** rejection requires a reason (stored in `owner_documents.review_note`, shown to the owner). Re-reviewing a decided document is refused; reversing means the owner re-uploads. A profile photo never gates verification — it is not an identity document. See [[Business-Rules]], [[APIs]], [[Database]].
- **Not verified:** the rendered screen has not been checked in a browser — doing so needs a real ADMIN session. Verified by type-check, build and 16 pure tests over the queue logic only.

### Configuration: deposit calculation mode, edit-aware Save, and an optional tenant agreement (2026-08-09)

Three changes to the owner Configuration surface, each fixing something that was stored-but-inert or misleading.

**Security deposit: fixed amount or months of rent, with the rupees shown before saving** ([[Decisions#ADR-060|ADR-060]]). The Deposit screen now writes `calculation_mode`, which it never did — previously setting "2 months" left the stored mode at `FLAT`, so invites kept charging the flat `default_amount` and the setting did nothing at all. The screen states the consequence live: `2 months × ₹8,000 rent = ₹16,000` when every room charges the same, a range (`₹12,000 – ₹18,000`) when they differ, and no figure at all when no room has a rent yet. It also warns when `auto_fill_room_rent` is off, because months-of-rent then resolves to ₹0. Switching the deposit off is stored as a flat ₹0, since the invite resolver ignores `deposit.enabled`. `refundable` became editable — it was already read by move-out settlement but unreachable in the UI.

**Save appears only when something has changed.** Every configuration screen with a Save button (five billing screens, receipt footer, hostel identity, profile) previously showed a permanent Save bar: an untouched screen looked identical to an edited one, and saving a screen you had only read still issued a PATCH, bumping the policy version and writing a Recent Changes entry for a change that never happened. Dirtiness is judged against a baseline captured from the loaded policy (`config/dirtyState.ts`), so retyping the same value or double-toggling leaves the screen clean. **Discard** sits beside Save. Screens that apply instantly on toggle (Notifications, Automation, clause library) keep that behaviour and have no Save bar.

**The tenant agreement is now optional per hostel** ([[Decisions#ADR-059|ADR-059]]). New `Configuration › Agreements › Tenant agreement` screen writes `tenant_rules.agreement_required` (default true). When off, onboarding runs `ACCOUNT → PROFILE → ACTIVATE`, the tenant's progress bar drops the Agreement stage, and both activation gates stop demanding a signature. It governs the signing ceremony **only** — `Agreement` rows are still created, because that record is the financial contract rent changes, obligations, renewals and settlement key to. The screen says so explicitly, so "not required" cannot be misread as "no contract". Existing signed agreements are unaffected.

**Not verified in a browser.** No tenant has been onboarded end-to-end through an agreement-free hostel, and no deposit has been resolved through a real invite since the mode became writable.

- **Three deliberate departures from the design**, all of the same kind — it draws data Stayo does not have, or an action that would bypass review:
  1. Its status toggle **publishes**; here it submits for review / withdraws, and the caps label carries the real revision state (Draft / In review / Live / Changes requested). Nothing reaches Discovery without an admin ([[Decisions#ADR-076|ADR-076]]).
  2. `1,240 views · 30d` renders as an **em dash** — Stayo tracks listing views nowhere.
  3. `★ 4.8 · 126 resident reviews` renders as **"No reviews yet"** — none are collected yet, and the card stays locked either way because owners may never write one.

- **Template reuse is still deferred** ([[Decisions#ADR-076|ADR-076]]). The design's "Switch / reuse" and "Save as new" now open a sheet that says so plainly, instead of rendering as two disabled buttons — one page serving several hostels means one edit re-opens review for all of them, which is an approval-model decision rather than a missing button.
- **Photos are uploaded from the device** — file picker or drag-and-drop, multi-select, straight to ImageKit `/hostel_listings` via `POST /owner/hostels/:id/marketing/photos`. JPG/PNG/WebP, 8MB each, 10 per request, 24 per listing. ### Owner Leads tab — returning-tenant awareness + Accept / Hold / Reject (2026-08-20, [[Decisions#ADR-085|ADR-085]])

- **Status:** shipped
- **Owner-facing?** yes · **Tenant-facing?** indirectly (WhatsApp notice on Reject only — see amendment below)
- **Route:** `/owner/alerts` (Alerts screen, "Leads" tab — reached via Home's bell icon, not the bottom nav). **This is a different, confirmed-live surface from the `/admissions` route flagged elsewhere on this page** (`AdmissionsView`/redirect status still unconfirmed — not touched or resolved by this entry).
- **What it does now:** each lead row shows tenant name, hostel, status pill, and Call/WhatsApp icon actions (WhatsApp was previously a "Coming soon" stub — now a real `wa.me` deep link via the shared `openWhatsAppShare()`). Tapping the card (previously required a separate "Follow up" button, now removed) opens `LeadDetailSheet`, whose footer offers exactly three actions — **Accept / Hold / Reject** — instead of nothing. Accept sets `status: ACCEPTED` and routes to the Add Tenant wizard, pre-filled with the lead's name/phone/email/hostel (`?fromLead=<id>`, survives a refresh). Hold opens an inline reason textarea; the message is required and stored as a `lead_notes` row — **and, per same-day amendment, sends no tenant notification at all**. Reject opens an inline confirm, then fires a friendly WhatsApp notice pointing the tenant back to Stayo. All three are disabled/hidden once a lead is no longer in an actionable status (already accepted/rejected/converted), and use `useMutation`'s `isPending` to block double-submit.
