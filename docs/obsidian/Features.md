### Owner Action Registry
- **Status:** shipped (catalog-only slice)
- **Owner-facing?** yes · **Tenant-facing?** no
- **Key files:** `apps/backend/src/services/owner-actions/owner-action-registry.ts` (in-memory registry, `listForEntity(entity, ctx)`), `apps/backend/src/services/owner-actions/definitions/*.ts` (`tenant-actions.ts` → `TENANT_EDIT_PERSONAL_INFO`; `payment-actions.ts` → `PAYMENT_RECEIVE`; `room-actions.ts` → `ROOM_MOVE`), `apps/backend/src/services/owner-actions/bootstrap.ts` (single import point for all definitions), `apps/backend/app/api/owner-actions/route.ts`, `apps/frontend/src/features/owner-actions/api/index.ts`
- **Depends on:** [[APIs]] (`GET /api/owner-actions`)
- **Notes:** A read-only catalog of which owner-facing actions are available for a given entity (currently only `tenant` is queried by the frontend). Each registered action declares `entity`, `category` (`EDIT`/`WORKFLOW`/`CORRECTION`/`VIEW`), a `label`, `allowedRoles`, and a synchronous `isAvailable(ctx)` predicate (evaluated server-side against `tenantStatus`/`actorRole`). `TenantProfilePage.tsx` fetches the tenant's action list and uses it to source the labels on the "Request Change" (`TENANT_EDIT_PERSONAL_INFO`, available only when tenant status is `ACTIVE`) and "Receive Payment" (`PAYMENT_RECEIVE`, always available) buttons on `PrimaryActionsBar`, falling back to hardcoded defaults if the catalog lookup misses. **This is catalog-only in this first slice — no action's actual execution routes through the registry yet** (clicking the buttons still triggers the pre-existing change-request/payment flows directly); the registry exists so future `CORRECTION`-category actions (payment reversal/transfer, expense void, etc. — see the Business Recovery Platform / correction-cases proposal work under `docs/business-logic/`, not yet reflected elsewhere in this vault) have a place to register into without inventing a new mechanism. `ROOM_MOVE` (`entity: "room"`) is registered but has no frontend consumer yet — deliberately out of scope for this slice.

### Correct Payment (Reverse / Transfer)
- **Status:** shipped (Reverse + Transfer — first real UI consumer of the Business Recovery Platform's `/api/recovery/cases/*` routes)
- **Owner-facing?** yes · **Tenant-facing?** no
- **Key files:** `apps/frontend/src/features/recovery/api/index.ts` (`recoveryService.createCase/validate/execute/getById`), `apps/frontend/src/app/components/modals/CorrectPaymentModal.tsx` (self-contained correction-type toggle → reason (+ tenant picker for Transfer) → preview → confirm modal), `apps/frontend/src/features/payments/api/index.js` (`paymentService.quickCollectSearch`, reused for the Transfer "correct tenant" search, same pattern as `RecordPaymentModal.tsx`), `apps/frontend/src/features/tenants/components/financial/FinancialActivityCard.tsx` (`onCorrectPayment` prop, "Correct Payment" button next to "View Receipt"), `UnifiedActivityTimeline.tsx` (threads the prop), `apps/frontend/src/features/tenants/components/profile/TenantProfilePage.tsx` (`correctingPaymentId` state, renders the modal, invalidates `queryKeys.tenants.{obligations,financialTimeline,advance,full,overview}` on close)
- **Depends on:** [[APIs]] (Recovery / Corrections), [[Business-Rules]] (Correction Cases — Payment corrections)
- **Notes:** Wired directly into the Tenant Details page's Activity tab's unified timeline per an explicit product decision to **not** build a separate Recovery Center dashboard in this phase (that list/detail view is deferred to Phase 3). This bypasses the Owner Action Registry entirely — it does not register as a `CORRECTION`-category owner action; the "Correct Payment" button is a conditional render (`receiptPaymentId && onCorrectPayment && canCorrectPayment`) alongside the existing "View Receipt" button, not sourced from `ownerActionsService`. The third condition (`canCorrectPayment = payments.length <= 1`) hides the button for grouped/multi-payment settlement entries — see [[Bugs]] — because reversing/transferring one payment in a group would only be a partial correction of the card's total. The modal now opens with a two-button correction-type toggle ("Wrong / Reverse" vs "Wrong Tenant / Transfer", pre-preview only — hidden once a case exists). Reverse mode is unchanged: `createCase({caseType: 'PAYMENT_REVERSAL', input: {paymentId}})`. Transfer mode additionally requires picking a destination tenant via a debounced (250ms) `paymentService.quickCollectSearch` lookup (fires only when the query is ≥2 chars and no tenant is yet selected) before "Preview Impact" is enabled, then calls `createCase({caseType: 'PAYMENT_TRANSFER', input: {paymentId, toTenantId}})`. Both modes share the same preview → "Confirm Reversal"/"Confirm Transfer" → `validate` + `execute` flow (treated as one logical confirm step; a 422 `VALIDATION_REJECTED` from `validate` stops `execute` from running and shows the rejection reason inline). Edit Reference/Notes (`PAYMENT_REFERENCE_EDIT`) UI is still explicitly out of scope for this slice — the backend handler exists and is reviewed, but has no frontend entry point yet. Reverse mode also supports a guided immediate re-record for the "wrong amount" case: `CorrectPaymentModal` accepts an optional `onSuccessReverse?: (tenantId: string) => void` callback, invoked only when `correctionType === 'REVERSE'` (never Transfer, since a Transfer's money has already moved to the correct tenant, leaving nothing to re-record). `TenantProfilePage.tsx` wires this to reopen the existing Receive Payment flow (`RecordPaymentModal`, reusing the page's existing payment-modal state — no second mount point was introduced) about 1.3s after the reversal's own success state finishes displaying, scoped to the same tenant whose payment was just reversed.

### Change Rent
- **Status:** shipped
- **Owner-facing?** yes · **Tenant-facing?** no
- **Key files:** `apps/frontend/src/features/tenants/api/index.js` (`tenantService.changeRent`), `apps/frontend/src/app/components/modals/ChangeRentModal.tsx` (self-contained FORM → CONFIRM flow, mirroring `WaiveObligationModal.tsx`'s identity-confirmation pattern), `apps/frontend/src/features/tenants/components/profile/TenantProfilePage.tsx` (`showChangeRent` state, "Change Rent" surfaced as one of `PrimaryActionsBar`'s own overflow ("More") menu actions — not a separate adjacent button — gated on `canChangeRent` (tenant status `ACTIVE`), `upcomingRentObligations` derived from the page's already-loaded `dues.items` — no second obligations fetch)
- **Depends on:** [[APIs]] (`POST /api/tenants/:id/change-rent`), [[Business-Rules]] (rent changes are immediate and owner-only, see the Category C exception note)
- **Notes:** Owner picks a new rent amount, the month it should take effect from (dropdown sourced from `upcomingRentObligations` — RENT obligations from the page's existing dues data with zero recorded *net* payments, `Number(o.paid ?? 0) === 0`), and a reason → password re-entry (`identityService.confirmIdentity(password, 'CHANGE_RENT')`) → submit. Applies immediately with no tenant approval step (identity-token gated the same as obligation cancel/waive). On success, invalidates `queryKeys.tenants.{obligations,financialTimeline,advance,full,overview}` and calls the page's `refetch()`. `currentRent` is read from `tenant?.monthly_rent ?? overview?.rent`. `applyRentChangeInTx` now also writes `tenants.monthly_rent` (in the same transaction as `agreement.contract_rent`, mirroring the `tenantContractSync` pattern used by renewal activation in `renewal-activation-engine.ts`) — resolves the previously-flagged "Unknown / needs clarification": `tenant.monthly_rent` **is** kept in sync, so this displayed value no longer goes stale after a successful change. See [[Bugs]] for this fix and a second, related gap: the modal's pre-submit "N installments will change" preview is a client-side count filtered by *net* zero-paid, which is a looser guard than the backend's real safety rule (zero payment *records* on the obligation, `payments.length === 0`) — after a Payment Reversal correction (see Correct Payment above), an obligation can have net paid `0` via two payment rows (original + offsetting reversal) and still be correctly skipped by the backend while still appearing in the frontend's preview count. The modal does not attempt to prevent this (would require exposing raw payment-row counts through `getTenantDues()`, out of scope); instead its success screen now shows the server-reported `obligationsUpdated` count from the response, so any such discrepancy is visible after the fact instead of silent.

## Resident & guardian WhatsApp command center (2026-08-27)

The rebuilt conversational surface for the two people who pay rent. Owner-facing WhatsApp (`owner-whatsapp-assistant.ts`) is untouched and out of scope. See [[Decisions#ADR-127|ADR-127]], [[Decisions#ADR-128|ADR-128]], [[Business-Rules#Resident & guardian command center|Business-Rules]].

**Files:** `lib/services/notifications/command-center/*`, `routing/{types,identity-resolver,intent-resolvers}.ts`, `providers/whatsapp/rent-reminder-template-contract.ts`.

### The five commands

| Command | Answers | Notes |
|---|---|---|
| `RENT` | What is payable, what it is made of, how late it is, where they are in the plan | Replaces `BAL`, `BALANCE`, `DUES`, `STATUS` |
| `PAY` | A secure link for the **whole** payable amount | Tenant-scoped token via `PaymentLinkService` |
| `PLAN` | Instalment progress — paid / due / overdue / upcoming, with totals | **New.** `installment_sequence` was in the schema and unread |
| `RECEIPT` | Asks **which payment**, then sends that receipt as a PDF attachment | **New.** Picker skipped when there is only one payment |
| `HELP` | The menu, and which residents this number is recognised for | |

Retired words (`BAL`, `BALANCE`, `DUES`, `STATUS`, `SWITCH`) still resolve and are advertised nowhere.

### Guardians as first-class users

- Recognised from `tenants.guardian_phone` as role `GUARDIAN` — **no account, no login** ([[Decisions#ADR-127|ADR-127]] upholds the existing "no second account" boundary).
- **Verified by OTP on first financial request**, re-verified every 90 days. Never waived, even when WhatsApp OTP delivery is degraded.
- Addressed in the third person — "Aarav's rent", never "your rent".
- **Contacted before the due date**, not only after ([[Business-Rules#Guardian reminder escalation|the escalation table]]). Previously a guardian's first-ever message arrived at 3 days overdue, so every guardian touchpoint was a complaint.
- A guardian of several residents gets a **priced picker** — each row states the room and the amount due — rather than being placed in an invisible 30-minute mode.

### Guardian onboarding handshake (`stayo_guardian_whatsapp_activated`)

When a tenant enters their guardian's number during activation and verifies it, the guardian now receives **Guardian Access Activated** — the channel's first word to them, sent from `activationWorkflowService.completeProfile` after the row commits. It names the tenant and hostel, says what the number can now do, and carries a **[Help] quick-reply button**.

- **Approved in Meta as Utility, English, 12-hour validity.** Body variables in order: `{{1}}` guardian name, `{{2}}` **tenant name — never a possessive**, `{{3}}` hostel name. Footer: *Stayo Property Management*.
- **The tap works.** Template quick-reply taps arrive as webhook type `button`, which the extractor used to drop outright — the button would have done nothing. It now resolves through the ordinary command vocabulary, so a guardian's first interaction is a tap rather than remembering a keyword.
- **No second OTP.** `isGuardianVerified` accepts the onboarding `ParentVerify` proof as well as `GUARDIAN_ACCESS`, so tapping [Help] opens the menu instead of challenging a handset that verified minutes earlier.
- Idempotent per `(tenant, guardian number)`; a **changed** guardian number sends afresh. Never blocks onboarding.

### Trust and voice

- Every money message names the **hostel** and signs `— <Hostel>, via Stayo`. Nothing signs `- HMS`.
- Payment confirmations are pushed unprompted the moment a payment is recorded (`payment_recorded` event → `sendPaymentConfirmation`), to the resident and to verified guardians, **with the receipt PDF attached**. The channel used to go silent at exactly the moment it had earned trust.
- No apologies, no `━━ section rules ━━`, no `███░░░` progress bar, no "Lifetime Summary", and never the string "N/A".
- Buttons carry the amount (`Pay ₹8,000`, not `Pay now`) and are never offered when they would be useless — no pay button on a settled account, no receipt button for someone who has never paid.

### The portable Stayo profile (2026-08-15, phase B)

### Email + password signup returns, without the phone step (2026-08-24)

- **What changed:** `LoginModal`'s Sign Up tab (tenant mode — Discover and `/login`) takes **name, email, password and confirm password** and submits to the existing `POST /api/auth/tenant-signup`. "Continue with Google" stays beneath an OR divider. Google-only signup, from 2026-08-16, meant someone without a Google account had **no way** to create a Stayo account at all — `signUpTenant()` and its endpoint existed but were unreachable.

### Add Hostel, made completable — and hostels can be removed (2026-08-24)

Creating the hostel and creating the floors are both idempotent too — stepping back and continuing used to leave duplicate hostels and duplicate floors behind. See [[Bugs]].
- **The floor form is three cards, one per question** ([[Decisions#ADR-109|ADR-109]]): *how many rooms*, *what these rooms are like*, *the rooms*. Only the middle block used to be carded, so nothing indicated which controls belonged together. The tally moved beside the counter it describes (it used to sit at the foot of the list, reading as a fourth room row), numbering moved into the rooms card labelled "Numbered across the whole building", and "Copy these N rooms to the next floor" moved out of an unsectioned float above the footer. Teaching copy now shows only on an empty floor. Five separate things told the owner which floor they were on, pushing the first control to 42% down a phone screen — the eyebrow is gone and the journey label no longer repeats the floor name.
- **The numbering picker actually renumbers.** It was wired to a bare `setPattern`, so changing the scheme highlighted a chip and left every existing room on its old number — and, because the scheme is one value for the whole builder, changing it on a later floor left earlier floors on the old one. See [[Bugs]].
- **Floors are switchable, not a one-way walk** ([[Decisions#ADR-108|ADR-108]]). A strip of floor chips at the top of the Rooms step — tap any floor to work on it, instead of reversing through every floor in between to fix one room. Each chip shows its own state: ✓ written, ● entered but not written yet, plain = still needs rooms. **Finishing sweeps up every floor still holding unsaved rooms**, because free navigation removed the guarantee the linear walk gave for free — you could not previously reach floor 3 without floor 1 being written on the way past. The sweep validates every floor before writing any of them, and is only cheap because saving a floor is idempotent ([[Decisions#ADR-114|ADR-114]]). The primary button follows the same rule: it continues to the next floor still *needing rooms*, wrapping to the start, not simply to the next index.
- **One form around every step**, so Enter submits from any field on any screen — on a two-field first screen that was the obvious gesture and it did nothing.
- **The progress bar tracks the real work.** `builderJourney` advances floor by floor through the Rooms phase and names the floor the owner is standing on ("Ground floor · 1 of 3"), instead of "Step 3 of 4" for what may be five screens.
- **A blocked button says why.** `continueBlocker` puts the reason beside the button; the message written for the empty-name case previously lived inside a click handler a disabled button never reaches.
- **Smaller repairs:** floor names renameable after creation; a room removable from the middle rather than only off the end; rent fields accept "6,000" and can't be changed by a stray scroll; the Rooms step no longer opens with a warning; the Floors step stopped describing an illustration deleted nine months earlier; content centred rather than pinned to the left of an empty page.
- **Floors and rooms can be deleted** ([[Decisions#ADR-099|ADR-099]]). `DELETE /api/floors/:id` and `DELETE /api/rooms/:id` existed with no frontend caller anywhere, so an owner could add either and never remove it. **Hostels were never part of this gap** — archiving one has long been wired to the dashboard's hostel card menu (`HostelOptionsSheet` → `ArchiveHostelModal`); the hostel Overview screen now opens that same modal as a second door rather than a second confirmation UI.
  - **Room** — room sheet → edit mode, two taps. A **real** delete, and the confirmation says so. Refuses on an occupied bed ("move them out") or a reserved one ("cancel the invite") — different problems, different fixes, named separately.
  - **Floor** — on an expanded floor, and **only when it is empty**: emptying it first is the point, so deleting a floor is never a way to delete rooms nobody looked at. This also required rendering empty floors at all — the Rooms tab returned `null` for a floor with no rooms, which made a deletable floor invisible.
  - Eligibility lives in one pure `propertyRemoval.ts`; the server stays the authority, and its own reason is surfaced when it refuses.
- **An archived hostel with no history can finally be deleted for good** ([[Decisions#ADR-100|ADR-100]]). The Archived tab offered **Reactivate and nothing else**, so a hostel created by mistake was stuck in the account permanently. A new `DELETE /api/hostels/:id/permanent` accepts only an already-archived hostel with zero tenants, payments, obligations, allocations, agreements, receipts, expenses and enquiries; anything with history stays archived and the refusal says so plainly. Deletes rooms → floors → hostel in one transaction. The one irreversible action in the owner app, so it asks for the hostel's name to be typed.

### Home shows what you kept, not just what you collected (2026-08-24)

### Google auto-provisioning + phone verification at enquiry (2026-08-16)

- **What changed:** tenant signup became Google-only — `LoginModal`'s Sign Up tab no longer had a name/email/phone/password form, just "Continue with Google". **The password form returned on 2026-08-24 ([[Decisions#ADR-113|ADR-113]]); everything else on this page still holds, including phone-verification-at-enquiry, which that change deliberately kept.** The Log In tab keeps email+password (for existing password-based accounts) alongside Google. `AuthContext.signUpTenant()`/`POST /api/auth/tenant-signup` (phone-OTP signup) are **untouched, just unwired** from this UI, in case anything else still depends on them.
- **The auto-provisioning invariant is not weakened.** `resolveSupabaseSession()` (`lib/auth/supabase-session.ts`) is completely unmodified and still rejects an unknown Google email with `NO_STAYO_ACCOUNT` on the plain login path — `tests/auth-hardening-security.test.ts`'s "No Auto-Provisioning" suite passes unchanged. A new, separate, narrowly-scoped function, `provisionMarketplaceTenantFromSupabase()` (`lib/auth/supabase-provision.ts`), handles the new-account case — reachable only from the new `POST /api/auth/google/provision` endpoint, which itself requires an already-valid Supabase session (i.e., Google has already authenticated the person; this endpoint only decides whether to create a `profiles` row for them). It creates the profile only when no `profiles` row exists for that email at all (any role — never re-links or takes over an existing account), then delegates back to the untouched `resolveSupabaseSession()` to build the session payload, so there is exactly one payload-building implementation. Rate-limited via the existing `checkFixedWindowLimit` primitive (email + IP), reusing infra rather than adding a new one. See [[Decisions#ADR-078|ADR-078]] for the full reasoning and [[APIs]] for the endpoint.
- **No database schema changes were needed.** `profile.phone`, `profile.phone_verified`, and the `phoneVerificationOtp` table all already existed (built for the original phone-OTP signup flow) — this work reuses them entirely.
- **Frontend flow:** `AuthContext.loginWithGoogleAllowProvision()` (new; delegates to the untouched `loginWithGoogle()`) sets a `sessionStorage` intent flag + a return-to path before the OAuth redirect — necessary because a full-page redirect to Google and back cannot carry in-memory callback state. `AuthCallbackPage` reads the flag on return: on `NO_STAYO_ACCOUNT` with the flag set, it calls the provision endpoint, retries `/auth/me`, and — new — honours the stored return-to path instead of always landing on `/tenant/home`/`/discover`, so a visitor mid-enquiry lands back on the exact enquiry they were filling in. Owner mode never calls the provisioning variant — untouched invariant.
- **Phone verification moved from signup-time to enquiry-time, and only asks once.** `EnquiryPage` now gates "Send enquiry to owner" on `user.phone_verified` (new field, surfaced on `/auth/me` and `AuthUser`) rather than just `isSeeker`. A Google-provisioned account has no phone on file at all; the enquiry page shows an inline "confirm your phone" step (also collects name, if missing) → `PATCH /api/profile` saves it (which re-arms `phone_verified: false` if the number is genuinely changing — see below) → the existing `authApi.sendPhoneOtp`/`verifyPhoneOtp` (same calls `LoginModal`'s old signup flow used) → on verify success, submits the enquiry immediately. If `phone_verified` is already `true`, none of this shows — straight to submit, no repeat OTP. If WhatsApp OTP delivery is unavailable, the existing skip/degrade behavior (ADR-034) applies the same way it always did for signup.
- **`PATCH /api/profile` (pre-existing route, `app/api/profile/route.ts`) gained one correctness fix**, load-bearing for the above: changing `phone` now resets `phone_verified`/`mobile_verified` to `false` when the new value actually differs from what's on file (previously it left the old verified flag in place, which would have made a *new, never-verified* number read as verified). Also returns a friendly `409 PHONE_TAKEN` instead of a raw 500 when the phone is already registered to another account (a real, previously-unhandled case now that this route is actually called from the UI for the first time).
- **What the owner sees is unaffected — no enquiry-creation route changes.** `discoveryService.createEnquiry()` already reads `seeker.phone` from the session-resolved profile with no separate phone parameter; since submission is now gated on `phone_verified`, whatever's in `seeker.phone` at that point already is the verified number, by construction.
- **`middleware.ts`/`SupabaseClaims` gained one small extension:** Google's `user_metadata.full_name`/`.name` is now surfaced as an `x-auth-name` header (added to the identity-header strip list, like every other `x-auth-*` header) — the only consumer is the new provisioning path, which needs *some* value for `profile.name` (`NOT NULL`) when creating a brand-new profile with no other source for it.

  **The trap that made this easy to get wrong twice:** both endpoints report delivery *failure* with a **2xx** status. `POST /api/owners/invitations` answers `202` when neither channel sent (`apiResponse(result, (whatsapp_sent || email_sent) ? 201 : 202)`), and `POST /api/tenants/resend-invitation` answers `202` with an *error-shaped* body (`{error:{code:'EMAIL_FALLBACK_REQUIRED'}}`). Axios resolves on 2xx, so neither ever rejects — a `try`/`catch` reads both as success. All delivery state is therefore read from the body, and anything unrecognised resolves to **undelivered**, never delivered (`whatsapp_sent: "false"` as a string does not count as sent).

  Three result states: WhatsApp delivered → "Invitation sent successfully"; WhatsApp failed but email delivered → "Invitation sent by email", naming the address; neither → "Invitation could not be delivered" with the reason, the activation link on screen, and **Copy link / Share link** (a `wa.me` deep link) so the owner is never stranded. When `needs_email` is true the result screen prompts for an address inline and re-dispatches via the existing resend route — no restart, no new backend surface. The resend's error body carries no `activation_link`, so the original is carried forward rather than lost.

  **Verification limits, stated plainly:** the 30 tests cover the pure decision logic (all three delivery cases, `needs_email`, the 202 error-body reading, link preservation, clipboard success/denial/absence, share-URL building). There is **no DOM test harness** — `apps/frontend` had no test suite at all, and adding jsdom + testing-library was judged a larger footprint than the fix; components are thin renderers over tested state. ### Configuration: deposit calculation mode, edit-aware Save, and an optional tenant agreement (2026-08-09)

Three changes to the owner Configuration surface, each fixing something that was stored-but-inert or misleading.

**Security deposit: fixed amount or months of rent, with the rupees shown before saving** ([[Decisions#ADR-060|ADR-060]]). The Deposit screen now writes `calculation_mode`, which it never did — previously setting "2 months" left the stored mode at `FLAT`, so invites kept charging the flat `default_amount` and the setting did nothing at all. The screen states the consequence live: `2 months × ₹8,000 rent = ₹16,000` when every room charges the same, a range (`₹12,000 – ₹18,000`) when they differ, and no figure at all when no room has a rent yet. It also warns when `auto_fill_room_rent` is off, because months-of-rent then resolves to ₹0. Switching the deposit off is stored as a flat ₹0, since the invite resolver ignores `deposit.enabled`. `refundable` became editable — it was already read by move-out settlement but unreachable in the UI.

**Save appears only when something has changed.** Every configuration screen with a Save button (five billing screens, receipt footer, hostel identity, profile) previously showed a permanent Save bar: an untouched screen looked identical to an edited one, and saving a screen you had only read still issued a PATCH, bumping the policy version and writing a Recent Changes entry for a change that never happened. Dirtiness is judged against a baseline captured from the loaded policy (`config/dirtyState.ts`), so retyping the same value or double-toggling leaves the screen clean. **Discard** sits beside Save. Screens that apply instantly on toggle (Notifications, Automation, clause library) keep that behaviour and have no Save bar.

**The tenant agreement is now optional per hostel** ([[Decisions#ADR-059|ADR-059]]). New `Configuration › Agreements › Tenant agreement` screen writes `tenant_rules.agreement_required` (default true). When off, onboarding runs `ACCOUNT → PROFILE → ACTIVATE`, the tenant's progress bar drops the Agreement stage, and both activation gates stop demanding a signature. It governs the signing ceremony **only** — `Agreement` rows are still created, because that record is the financial contract rent changes, obligations, renewals and settlement key to. The screen says so explicitly, so "not required" cannot be misread as "no contract". Existing signed agreements are unaffected.

**Not verified in a browser.** No tenant has been onboarded end-to-end through an agreement-free hostel, and no deposit has been resolved through a real invite since the mode became writable.

## Owner "Money in" — payout visibility (2026-08-23)

The owner's half of the settlement system, added inside **Money → Collections** rather than as a fourth tab: a separate tab would leave the owner reconciling two screens himself. See [[Decisions#ADR-090|ADR-090]].

**The payout strip** sits above the existing dues queue and is an *event* line, not a status line — `3 tenants paid today · ₹18,500 / in your bank by Wed 27 Aug`, then the payers by name and time, then `Stayo takes ₹0 · Last 8 payouts — all on time`. It exists because online rent lands in *Stayo's* account, not the owner's, so being paid stops being an event he witnesses; without it, online rent feels like less control than cash, and he is the one who has to push tenants to use it. It also stitches the tab together — a tenant he is chasing in the list below moves up into the strip the moment they pay.

On a failed transfer the strip leads with it and carries a **one-tap route into the payout-account form**, since only the owner can correct his own bank details.

**`/owner/money/payouts`** ("Money in") holds the month reconciliation block — five nested lines that add up, plus "still to collect" linking back to the dues queue — the kept-promise counter, and the payout history. Search matches **UTR, amount, or tenant name**, because an owner reconciling reads his bank statement first and the app second.

**Each payout expands into the tenants who paid it**, with `Collected / Stayo fee ₹0 / You received`, room and hostel per tenant, and a tap through to that tenant's profile. This expansion is the point of the feature: a payout he cannot open into names is a number Stayo asserts, while an opened one is a claim he can check by phoning someone.

**Notifications** ([[Backend]] `payout-notifications.ts`) fire on three moments — a tenant paid, the payout is on its way (carrying the committed date), it reached the bank (carrying the UTR) — plus a failure message that states the cause and that the money is still safe. In-app only; the WhatsApp equivalents need Meta template approval and must not gate this.

**Deferred:** statement export (PDF/CSV) for a CA or a working-capital loan application.

## Money export — four documents, chosen by purpose (2026-08-23)

One **Export** action in the Money tab header, available from all three tabs. It asks *what do you need it for*, not what format you want ([[Decisions#ADR-093|ADR-093]]):

| He picks | He gets |
|---|---|
| **For my accountant** | Excel — *Report* / *Rent received* / *Expenses* / *Summary* sheets, month by month |
| **Proof of income** | PDF — for a bank, landlord or partner |
| **Bank reconciliation** | Excel — one row per payout with its reference, tenants indented underneath |
| **Who owes me** | PDF — printable chase list, ordered by the collection queue's existing priority |

Choosing the purpose **dissolves the collections-versus-payouts split** — the owner never picks a data domain. It also pulled expenses in, since a CA cannot file from income alone; the old scope-and-format `ExportExpensesModal` is deleted rather than left as a second way to export from the same tab.

**Proof of income keeps verified and self-reported money in separate sections** with their own subtotals, always both present ([[Decisions#ADR-094|ADR-094]]).

**Period presets are financial-year aware** — This month / Last month / This FY / Last FY / Custom, resolved server-side ([[Decisions#ADR-095|ADR-095]]).

**Every document carries its own provenance**: period, hostels, row count, total, generated-at, and *"Figures as recorded in Stayo."* Nobody should have to trust that nothing got truncated.

**A preflight line says what is in the file before it is built** — "1,247 payments · ₹14,80,000" — so an owner can tell it is the right thing without opening it. An empty period says so in words rather than showing "0 payments · ₹0", which reads like a fault.

**Share uses the Web Share API** (`navigator.share({ files })`), which reaches WhatsApp through the OS sheet — a `wa.me` link cannot carry a file. Where unsupported, the button is not shown and Download stands alone rather than promising something it cannot deliver.

**Two PDF constraints worth knowing:** pdf-lib's standard fonts are WinAnsi, so money is written `Rs.` and never `₹`, and tenant names are sanitised — a Telugu or Devanagari name would otherwise throw and fail the chase list for exactly the owners most likely to have one.
