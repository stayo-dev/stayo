# Frontend — `apps/frontend/`

Related: [[Architecture]] · [[APIs]] · [[Features]]

Canonical UI: Vite + React 19 SPA. This page reflects a direct read of `apps/frontend/src/` — routing, folder purposes, and the current migration-in-progress from `features/` to `domains/`.

> **Correction, 2026-07-26 — most of this page describes dead code, not the live app.** A full read-only readiness audit (and the routing-migration note dated the same day, further down this page) confirmed `app/components/views/*` — everything the sections below call "owner-facing screens" (`PortfolioView`, `TenantsPortfolioView`, `SettingsView`, `BillingView`, `FinancialControlCenter`, `MoveOutsView`, `AlertsView`, `AdmissionsView`, the `hostel-detail/`/`modals/`/`settings/` sub-trees, etc.) and the routes listed under "Owner routes" below (`/dashboard`, `/hostels/:hostelId(/:tab)`, `/billing`, `/settings`, `/move-outs`, …) — is **orphaned**: reachable only from `app/App.tsx`, which nothing in the live router imports. The real, live owner app is `platforms/owner/router/OwnerRoutes.tsx`'s `/owner/*` tree (`/owner/home`, `/owner/tenants(/:tenantId)`, `/owner/money`, `/owner/food`, `/owner/alerts`, `/owner/more(/settings|/billing|/profile|/hostel|/help|/about)`, `/owner/hostels/:hostelId/(overview|rooms|tenants)`), whose real screens live under `features/owner-*` (see the `features/` list further down). The orphaned tree is real, working code — not mock — so it's being used as a salvage source (port real logic into `/owner/*`, then delete) rather than deleted outright; as of 2026-07-26 that salvage covers Dashboard/Hostel/Tenants(list+detail+invite)/Money/Quick-Collect/Change-Rent/Move-out/core-Settings (see [[Changelog]]). Treat every description below that references `app/components/*` or the pre-`/owner/*` route list as **historical**, describing what to salvage from, not what ships.

## Top-level `src/` structure

| `lib/` | `api-client.ts` (axios instance), `supabaseClient.ts` (Supabase JS client singleton, new in ADR-031), `queryKeys.ts` (centralized React Query key factory), `queryClient.ts`, `errors.ts`, `toast.ts`, `sanity/` (CMS client). |

## `src/lib/queryKeys.ts` and `src/lib/api-client.ts`

- **`queryKeys.ts`**: single `queryKeys` object, namespaced (`me`, `owner.*`, `notifications`, `portfolio.*`, `dashboard.*`, `tenants.*`, `moveOut.*`, `rooms.*`, `payments.*`, `expenses.*`, `activity.*`, `admissions.*`). Guards against a missing `hostelId` by returning a `['__noop__', ...]` key rather than a real cache key.
- **`api-client.ts`**: `baseURL` comes unconditionally from `VITE_API_URL` — no local-dev shortcut, no hardcoded production fallback. Throws at module load if the var is missing or blank, in every environment alike (fixed during the StayO frontend-foundation pass; this line was stale until 2026-07-24 — see `docs/migration/frontend-foundation-tracker.md`). The dev-server proxy target works the same way, via `HMS_API_PROXY_TARGET` in `vite.config.ts`. Default export `api` (credentials included, CSRF header attached from an `hms_csrf` cookie, bootstrapped via `/auth/csrf`); `publicApi` (no credentials, for public endpoints like receipt verification). **Since [[Decisions#ADR-031\|ADR-031]] (2026-07-28)**: request interceptor attaches `Authorization: Bearer <token>` from `(await supabase.auth.getSession()).data.session?.access_token` instead of an in-memory variable. The old manual 401-refresh-retry block (`POST /auth/refresh`) is gone entirely — Supabase's SDK refreshes proactively and serializes concurrent refreshes. The response interceptor now only handles the still-relevant server-driven cases (`SESSION_INACTIVE`/`SESSION_REVOKED` error codes), calling `supabase.auth.signOut()` and dispatching the same `window` `CustomEvent('hms:session-expired')` as before.

## Auth (`context/AuthContext.tsx`, `lib/supabaseClient.ts`)

Rewritten under [[Decisions#ADR-031\|ADR-031]] (2026-07-28) to make Supabase Auth the single authentication provider. See [[Backend#Auth/session model|Backend's Auth/session model section]] for the backend half (dual-accept JWT verification, JIT identity linking, `resolveSupabaseSession`).

- **`lib/supabaseClient.ts`** — a module-level singleton: `createClient(VITE_SUPABASE_URL, VITE_SUPABASE_ANON_KEY, { auth: { persistSession: true, autoRefreshToken: true, detectSessionInUrl: true, flowType: 'pkce' } })`. Must stay a true singleton — `AuthContext` mounts at 3+ separate route-tree roots, and multiple `GoTrueClient` instances in one tab would fight over storage/refresh timers. Throws at module load if either env var is missing, matching `api-client.ts`'s existing hard-fail convention.
- **`AuthContext.tsx`** — public interface (`{ user, loading, login, loginWithGoogle, updateUser, logout }`) is unchanged except `loginWithGoogle`'s signature: was `(code, redirectUri) => Promise<AuthUser>` (popup-based `@react-oauth/google`), now a zero-arg `() => Promise<void>` that calls `supabase.auth.signInWithOAuth({ provider: 'google', options: { redirectTo: \`${origin}/auth/callback\` } })` — a full-page redirect. `LoginPage.tsx` is the only caller.
  - The old `initAuth` bootstrap effect (read `localStorage['ownerUser'|'tenantUser']`, then silent-refresh) is gone. Replaced by `supabase.auth.onAuthStateChange()` plus a `hydrate()` function that calls `GET /auth/me` to build the `AuthUser` object (role/owner_id/tenant_id/name) whenever a Supabase session appears.
  - `login(email, password)` still does `POST /auth/login` first (rate-limiting, tenant-status checks, and `PASSWORD_RESET_REQUIRED` all stay backend-mediated — the SPA never calls `supabase.auth.signInWithPassword()` directly), then calls `supabase.auth.setSession({ access_token, refresh_token })` from the response and builds the `AuthUser` directly, without waiting on the auth-state listener.
  - `logout()` calls `POST /auth/logout` (Redis revocation + server-side `supabase.auth.admin.signOut()`) then `supabase.auth.signOut()` locally.
  - `persistUser`/`readStoredUser` and the `ownerUser`/`tenantUser` `localStorage` keys are gone — Supabase persists its own session (in `localStorage`, under its own keys), and the profile is re-hydrated from `/auth/me` on every auth-state change rather than cached locally.
  - The idle-timeout system (`useIdleSessionTimeout`, the 25-min warning modal, the `hms:session-expired` window event) is unchanged — Supabase has no concept of this app's 30-minute idle business rule, so it stays a layer on top; see [[Backend#Auth/session model|Backend]] for the Redis-based server side of the same rule.
- **`app/pages/AuthCallbackPage.tsx`** (new) — the `/auth/callback` route landed after `signInWithOAuth`'s redirect. Waits for `supabase.auth.getSession()` to resolve (relies on `detectSessionInUrl: true` processing the redirect during client init), makes its own `GET /auth/me` call to get the specific rejection reason if any (`NO_STAYO_ACCOUNT`/`TENANT_GOOGLE_NOT_ALLOWED`/`ACCOUNT_DISABLED` — Google never auto-provisions an account), then either routes by role or calls `supabase.auth.signOut()` and shows the error with a "Back to sign in" link.
- Three pages that used to bypass `AuthContext` and hand-write `localStorage` now go through Supabase directly: `portal/pages/ActivateAccountPage.tsx` (tenant-activation auto-login calls `supabase.auth.setSession()`), `portal/pages/CompleteProfilePage.tsx` (calls `updateUser({ is_profile_completed: true })` instead of writing `localStorage['tenantUser']`), `app/pages/ResetPasswordPage.tsx` (calls `supabase.auth.signOut()` instead of removing the old localStorage keys).
- `@react-oauth/google`, `GoogleOAuthProvider` (`app/providers/AuthShellProviders.tsx`), `useGoogleLogin`, and `VITE_GOOGLE_CLIENT_ID` are all removed. `shared/ui-patterns/GoogleSignInModal.tsx` — the "Continue with Google" button on the marketing landing page's lead-capture funnel — was out of scope for ADR-031 itself (a different product flow from real login) but has since been made real too, in a later pass — see the Owner-Acquisition Funnel section below.

## Owner-Acquisition Funnel (landing page → real lead → activation → onboarding)

Two passes, both against real backend endpoints (no mocks) — see [[Decisions]] ADR-032 for the second pass's design, [[APIs]] for the endpoints:

- **Landing → lead capture** (`app/pages/public/LandingPage.tsx`'s "Manage My Hostel" CTA): `shared/ui-patterns/GoogleSignInModal.tsx` calls real `supabase.auth.signInWithOAuth({provider:'google', options:{redirectTo: '/lead-signup/callback'}})` — a full-page redirect, deliberately a *different* redirect target from the real `/login` flow's `/auth/callback`, since this identity is never resolved into a StayO session (`resolveSupabaseSession()` would reject a brand-new visitor by design — see ADR-031). `app/pages/public/LeadSignupCallbackPage.tsx` reads the Google identity client-side via `supabase.auth.getUser()` (never calls `/api/auth/me`), then renders `features/owner-onboarding/components/HostelLeadModal.tsx` (details + phone OTP, both real — `POST /auth/send-phone-otp`/`verify-phone-otp` with `purpose: "LEAD_CAPTURE"`, then `POST /leads/self-serve`), and signs the Supabase session back out afterward regardless of outcome — it never becomes a real account. `features/hostel-leads/api/index.ts` is this funnel's dedicated API wrapper.
- **Admin approval → activation link → prefilled onboarding** (added 2026-07-29, ADR-032): `platforms/admin/pages/AdminLeadsPage.tsx`'s "Approve Lead" now calls `POST /api/platform-admin/leads/[id]/approve` (was a bare status PATCH) and shows the real WhatsApp/email delivery result as a toast; its status dropdown is trimmed to the 3 manually-settable values, with a new Timeline section reading that lead's logged events. `app/pages/public/OwnerLeadInvitePage.tsx` (new, `/owner-invite/:token`) fetches `GET /api/leads/invitation/[token]`, shows distinct invalid/expired/already-used states, and on success hands `{prefill, token}` to `/onboarding` via router `state` (not a query param). `features/owner-onboarding/hooks/useOwnerOnboardingState.ts` gained an optional `initialData` param (merged into its previously-hardcoded `INITIAL_DATA`) and a new `city` field (didn't exist before, even though the backend always supported it); `OwnerOnboardingWizard.tsx` reads `location.state` once at mount. The `token` threads through `useOnboardingSubmission.ts` into `POST /auth/owner-signup`'s optional `lead_token` and a trailing `POST /api/leads/invitation/[token]/complete` call after the publish step's floor/room loop finishes — both no-ops for a normal, non-lead-originated `/onboarding` visit.

## Enforced architectural boundaries

`scripts/check-architecture.mjs` fails the build if: raw `fetch()`/`axios` is used outside `@lib/api-client` in `app/`, `platforms/`, `shared/ui`, `features/`, `portal/`, or `context/`; `src/portal` gains a file outside its allowlist (above); `src/shared` imports from `app|platforms|portal|features|domains|services`.

## StayO rebuild additions (new structure, layered on top of the above)

The StayO redesign is being built in place inside this same tree, per the design source in `Stayo Homepage Design (5)/` and `Stayo SaaS redesign/` at the repo root. Full engineering-decision narrative lives in `docs/migration/frontend-foundation-tracker.md`; summary here:

- **`app/providers/ThemeProvider.tsx`** — `useAppTheme()`/`<ThemeProvider theme="marketing"|"product">`. Sets `data-app-theme` on both a wrapper element and `document.documentElement` (the latter so portaled content — Radix `Dialog`, `vaul` drawers, `sonner` toasts — still resolves the right token scope, since portals render outside the wrapper's DOM subtree).
- **`styles/tokens/{marketing,product,fonts}.css` + `styles/stayo-theme.css`** — new StayO design tokens, scoped under `[data-app-theme]`, coexisting with the untouched legacy `styles/theme.css`/`fonts.css`. Google Fonts (Manrope/Inter) are loaded via a `<link>` in `index.html`, not a CSS `@import` — see the tracker doc for why a nested `@import` there gets silently dropped by the browser.
- **`shared/ui-patterns/`** — StayO's shared design-system components (`StatCard`, `DarkHeroCard`, `ListRow`, `StatusPill`, `BottomSheet`, `StepProgress`, `SegmentedControl`, `EmptyState`, `Toast` (`stayoToast`), `DragHandle`, `LoginModal`). Built directly on raw npm packages (`vaul`, `@radix-ui/react-dialog`) rather than `app/components/ui/*` wrappers, because `shared/` is architecturally forbidden from importing `app/` (`check-architecture.mjs`). `StatCard` takes a `variant?: 'snapshot' | 'action'` prop (default `snapshot`) for two visually distinct mockup card styles rather than a duplicate component; `BottomSheet` takes a `hideHeader?: boolean` prop for sheets (e.g. `PaySheet`) whose own content renders a custom header the standard title+close row would duplicate — see the 2026-07-27 UI fidelity migration entry in [[Changelog]].
- **`app/layouts/{PublicLayout,OwnerAppShell,TenantAppShell,ConfigShell}.tsx`** — new StayO layout shells. `OwnerAppShell`'s bottom nav is exactly the 5 tabs in `BottomNav.dc.html` (Home/Tenants/Money/Food/Configure — no "Alerts" tab; alerts is reached via the bell icon on Home). `OwnerAppShell` takes a `basePath` prop (default `/owner`) so the mock `/get-started/*` preview tree can reuse it without its bottom nav linking into the real `ProtectedRoute`-gated routes. `Stayo App.dc.html` has **zero `@media`/desktop rules** (verified by grep — a fixed 402×874 mobile device-frame mockup end to end, no desktop design exists to extract), so on `sm:`+ viewports `OwnerAppShell`/`TenantDetailPage`/`HostelDrilldownLayout` simply center the same mobile layout in a bordered `max-w-[480px]` frame rather than inventing new breakpoints.
- **`shared/mocks/`** — centralized mock data (`dashboard.ts`, `tenants.ts`, `payments.ts`, `rooms.ts`, `expenses.ts`, `food.ts`, `alerts.ts`, `more.ts`), deliberately not per-feature, so multiple owner-app modules can read the same tenant/property/room/expense/food/alert data instead of each inventing their own. Pure data/type modules, no `app/` imports, so `shared/`'s architecture boundary (can't import `app/platforms/portal/features/domains/services`) is unaffected. Several export `get*Insights()`/`get*Stats()`/`get*Winner()` helpers (`getExpenseInsights`, `getHostelRoomStats`, `getPollWinner`) that *derive* stat-tile numbers from the underlying records instead of hardcoding them separately, so they can't drift out of sync.
- **`features/owner-onboarding/`**, **`features/owner-dashboard/`**, **`features/owner-tenants/`**, **`features/hostel-drilldown/`**, **`features/owner-money/`**, **`features/owner-food/`**, **`features/owner-alerts/`**, **`features/owner-more/`** — the owner acquisition journey (Landing → real Google sign-in → real lead popup → admin approval → activation link → prefilled 12-step Onboarding — see the Owner-Acquisition Funnel section above), the Tenants tab (list + Invite wizard + Tenant Detail + Quick Collect), the Hostel Drill-down (Overview + Rooms grid/layout + hostel-scoped Tenants, reached from a Home property card), the Money tab (Overview/Collections/Expenses + Add Expense wizard + Filters/Export/Detail), the Food tab (Monthly Schedule meal planner + Food Polls), the Alerts tab (Leads/Admin/Renewals/Requests, reached via Home's bell icon), and the More tab (profile/Settings/Billing/Help & Support/About/Sign out — the central configuration hub). `features/owner-dashboard/quick-actions/` wires Home's FAB and "View all" sheet, reusing `QuickCollectModal`/`InviteTenantWizard` directly and routing to Money/Food with router state for Add Expense/Create Food Poll rather than duplicating those flows. See [[Features]] for the full file list and notes.

  **Update, 2026-07-26 — `/get-started/*` retired, migrated into `/owner/*`.** The architecture audit found that the real, `ProtectedRoute`-gated `/owner/*` tree (`platforms/owner/router/OwnerRoutes.tsx`) was 100% blank `RouteScaffold` placeholders, while all the actual built UI lived at `/get-started/*` behind the separate mock `MockOwnerJourneyContext` gate that a real logged-in session never reached — two disjoint owner frontends, neither of which a real owner actually saw. Per explicit product direction ("stop adding features, pick one canonical app"), the tab pages (Home/Tenants/Money/Food/Alerts/More + sub-screens), Tenant Detail, and the Hostel Drill-down were moved to render under `/owner/*` instead (same component files, no duplication) and now sit behind the real `ProtectedRoute`/`AuthProvider` stack via `OwnerProviderShell`. `/get-started/*` now only hosts what it always should have: the still-mock lead-capture funnel (`/get-started/submitted`, `/get-started/activate/:token`), still gated by `MockOwnerJourneyContext`/`RequireMockOwnerJourney`, explicitly deferred to a later "Admin" phase. `/onboarding` (real sign-up/OTP/hostel-creation, added 2026-07-25) is ungated on entry and now lands the owner on `/owner/home` on success, not `/get-started/dashboard`. `RequireOwnerSession.tsx` (a stopgap real-session route guard added briefly during the 2026-07-25 backend-integration pass) was deleted — the real `ProtectedRoute` already covers this, more correctly (it doesn't require a hostel to exist, so a freshly-signed-up owner with zero hostels can still reach the dashboard instead of being bounced out). All owner-app screens were still mock-data at the time of this note — that was purely a routing consolidation, not a data-wiring change. **Since then (2026-07-26, same day, later pass)**: Dashboard, Hostel (Overview+Rooms), Tenants (List/Detail/Invite), Money (Pulse/Collections/Expenses incl. create/edit/delete/export), Quick Collect, Change Rent, Move-out/Checkout, and core Settings (Billing policy/My Profile/Hostel Identity) are all real, verified against the live backend — see [[Changelog]]'s "Phase 1 continuation" entry. Still mock/placeholder: Food (no backend exists), Alerts, Settings' Tenant Defaults/Automation/Notifications/Access/Agreement-editor sub-sections, and Reports (no page exists at all).

  Tenant Detail and the Hostel Drill-down remain real routes (`/owner/tenants/:tenantId`, `/owner/hostels/:hostelId/*`), not modals, mounted outside `OwnerAppShell` as full-screen takeovers with their own back button; Money, Food, and Alerts stay a single route each with internal tab/modal state, matching how the design treats them (no full-screen sub-pages) — Food's Poll Results is a tall `BottomSheet` rather than a route for the same reason. More's sub-screens (Settings/Billing/Help/About) are real nested routes, since the design keeps the bottom nav visible across all of them.
- **`app/pages/public/LandingPage.tsx`** — new StayO marketing homepage, now mounted at `/` (replacing the legacy `HomePage.tsx`, which is `@deprecated` but not deleted). Owns its own nav/footer directly rather than using `PublicLayout.tsx` (built in the foundation pass but still unused) — the design's nav has scroll-linked chrome and page-specific anchor links that don't generalize as a shared layout.
