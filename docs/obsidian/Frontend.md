# Frontend — `apps/frontend/`

Related: [[Architecture]] · [[APIs]] · [[Features]]

Canonical UI: Vite + React 19 SPA. This page reflects a direct read of `apps/frontend/src/` — routing, folder purposes, and the current migration-in-progress from `features/` to `domains/`.

> **Correction, 2026-07-26 — most of this page describes dead code, not the live app.** A full read-only readiness audit (and the routing-migration note dated the same day, further down this page) confirmed `app/components/views/*` — everything the sections below call "owner-facing screens" (`PortfolioView`, `TenantsPortfolioView`, `SettingsView`, `BillingView`, `FinancialControlCenter`, `MoveOutsView`, `AlertsView`, `AdmissionsView`, the `hostel-detail/`/`modals/`/`settings/` sub-trees, etc.) and the routes listed under "Owner routes" below (`/dashboard`, `/hostels/:hostelId(/:tab)`, `/billing`, `/settings`, `/move-outs`, …) — is **orphaned**: reachable only from `app/App.tsx`, which nothing in the live router imports. The real, live owner app is `platforms/owner/router/OwnerRoutes.tsx`'s `/owner/*` tree (`/owner/home`, `/owner/tenants(/:tenantId)`, `/owner/money`, `/owner/food`, `/owner/alerts`, `/owner/more(/settings|/billing|/profile|/hostel|/help|/about)`, `/owner/hostels/:hostelId/(overview|rooms|tenants)`), whose real screens live under `features/owner-*` (see the `features/` list further down). The orphaned tree is real, working code — not mock — so it's being used as a salvage source (port real logic into `/owner/*`, then delete) rather than deleted outright; as of 2026-07-26 that salvage covers Dashboard/Hostel/Tenants(list+detail+invite)/Money/Quick-Collect/Change-Rent/Move-out/core-Settings (see [[Changelog]]). Treat every description below that references `app/components/*` or the pre-`/owner/*` route list as **historical**, describing what to salvage from, not what ships.

## Router / route tree

Entry: `app/Router.tsx` → `app/router/AppRouter.tsx`, composing four route-group functions:

> **v1 (2026-09-03, [[Decisions#ADR-170|ADR-170]]):** `DiscoverRoutes()` is **unmounted** from `AppRouter.tsx` — the Stayo Discover marketplace is shelved for v2. `ProfileRoutes()` (the `/profile/*` hub it used to nest) is mounted directly under `SeekerAppShell`, so the Tenant Dashboard still shares one provider tree. `/` renders `LandingPage` (owner marketing/login) instead of the `WelcomePage` audience fork; a signed-in owner with a hostel is auto-forwarded to `/owner/home`. `DiscoverRoutes.tsx` + `app/pages/discover/*` stay on disk.

**Public routes** (two lazy shells): `PublicShell` — `/` (`LandingPage` in v1), `/owners`, `/about`, `/company`, `/contact`, `/legal/*`, `/visit/:hostelSlug`, `/verify/r/:token`. `AuthShell` — `/login`, `/forgot-password`, `/reset-password`, `/activate(/:token)`, `/invite/:token`, `/complete-profile`.

**Legal content (2026-09-10, [[Decisions#ADR-180|ADR-180]]).** `src/content/legal/` is the single registry of published legal documents: one typed module per document, plus `index.ts` exporting `legalDocuments`. Blocks are a discriminated union (`LegalBlock`: paragraph, subheading, clause, notice, list, definitions, table, contact_list). `LegalPage`'s renderer switch over it is exhaustive, so a new block type is a compile error rather than a silently dropped section. Route resolution (`documentIdForPath`), hub links (`documentHref`) and date display (`formatEffectiveDate`, parsed by hand so an ISO date never shows as the previous day west of UTC) are pure functions tested directly. `routes.test.ts` reads `PublicRoutes.tsx` via Vite's `?raw` and fails if the registry declares a URL the router does not serve. The old flat `src/content/legal.ts` and the divergent backend copy are deleted. Entity facts and the payment-partner descriptor live in `src/content/company.ts`.

**Tenant onboarding — the Identity screen's field policy and theming (2026-08-25, [[Decisions#ADR-111|ADR-111]]).** Three things worth knowing before editing `platforms/tenant/onboarding/`:

- **The sky is the header band only; the step body sits on `FLOW_GROUND` (cream) at every hour** ([[Decisions#ADR-184|ADR-184]], superseding ADR-111's `useSky()`/`onSky*` tokens — `skyContext.tsx` no longer exists). Text you add to a step body takes its colour from `FLOW_INK` (`skyTheme.ts`); text in the header takes the phase-aware `lockup*` tokens; text in the progress panel takes `PANEL_INK`; text on the splash card takes `INTRO_CARD_INK`. **`skyTheme.test.ts` proves every one of those clears WCAG AA against the actual gradient rows under it in all three phases** — change a colour or a stop and run it rather than judging by eye in whichever phase the clock is showing. Palette is Stayo's warm brand (Warm Clay/Terra Cotta/Dusty Orange/Latte/Charcoal/Cream); the same test fails on any saturated cool colour in `platforms/tenant/onboarding/`, because the whole flow was once re-skinned blue without anyone noticing ([[Bugs]]).
- **Which fields to render is decided by the server**, not the component: `GET /api/tenants/activate/context` returns `identity_fields`, and `phone_trust` decides the OTP. Adding a client-side rule for either would let the form and the validation that accepts it drift apart.
- **Date of birth is `DateOfBirthField.tsx` over the pure `dateOfBirth.ts`**, not an `<input type="date">`. The logic (parsing without `new Date()`, leap years, day clamping, age, validation) lives in the `.ts` and is tested; the component is a renderer, per this app's node-only test setup.

**`ActivateAccountPage.tsx` is on this allowlist but is `@deprecated` and no longer routed** (2026-08-12) — `PublicRoutes.tsx`'s `/activate`, `/activate/:token`, `/invite/:token` now mount `platforms/tenant/onboarding/ActivationPage.tsx` instead. This was the second and final slice of the `portal → platforms/tenant` extraction: `ActivationLayout.tsx`/`ActivationProgress.tsx` (the chrome) moved first; the step bodies moved in this change, redesigned to match `Stayo Onboarding.dc.html`. See [[Features]] and [[Changelog]]. Kept on disk/allowlist per the deprecate-don't-delete policy until confirmed safe to remove.

## `src/lib/queryKeys.ts` and `src/lib/api-client.ts`

- **`queryKeys.ts`**: single `queryKeys` object, namespaced (`me`, `owner.*`, `notifications`, `portfolio.*`, `dashboard.*`, `tenants.*`, `moveOut.*`, `rooms.*`, `payments.*`, `expenses.*`, `activity.*`, `admissions.*`). Guards against a missing `hostelId` by returning a `['__noop__', ...]` key rather than a real cache key.
- **`api-client.ts`**: `baseURL` comes unconditionally from `VITE_API_URL` — no local-dev shortcut, no hardcoded production fallback. Throws at module load if the var is missing or blank, in every environment alike (fixed during the StayO frontend-foundation pass; this line was stale until 2026-07-24 — see `docs/migration/frontend-foundation-tracker.md`). The dev-server proxy target works the same way, via `HMS_API_PROXY_TARGET` in `vite.config.ts`. Default export `api` (credentials included, CSRF header attached from an `hms_csrf` cookie, bootstrapped via `/auth/csrf`); `publicApi` (no credentials, for public endpoints like receipt verification). **Since [[Decisions#ADR-031\|ADR-031]] (2026-07-28)**: request interceptor attaches `Authorization: Bearer <token>` from `(await supabase.auth.getSession()).data.session?.access_token` instead of an in-memory variable. The old manual 401-refresh-retry block (`POST /auth/refresh`) is gone entirely — Supabase's SDK refreshes proactively and serializes concurrent refreshes. The response interceptor now only handles the still-relevant server-driven cases (`SESSION_INACTIVE`/`SESSION_REVOKED` error codes), calling `supabase.auth.signOut()` and dispatching the same `window` `CustomEvent('hms:session-expired')` as before.

## Auth (`context/AuthContext.tsx`, `lib/supabaseClient.ts`)

Rewritten under [[Decisions#ADR-031\|ADR-031]] (2026-07-28) to make Supabase Auth the single authentication provider. See [[Backend#Auth/session model|Backend's Auth/session model section]] for the backend half (dual-accept JWT verification, JIT identity linking, `resolveSupabaseSession`).

- **`lib/supabaseClient.ts`** — a module-level singleton: `createClient(VITE_SUPABASE_URL, VITE_SUPABASE_ANON_KEY, { auth: { persistSession: true, autoRefreshToken: true, detectSessionInUrl: true, flowType: 'pkce' } })`. Must stay a true singleton — `AuthContext` mounts at 3+ separate route-tree roots, and multiple `GoTrueClient` instances in one tab would fight over storage/refresh timers. Throws at module load if either env var is missing, matching `api-client.ts`'s existing hard-fail convention.
- **`AuthContext.tsx`** — public interface (`{ user, loading, login, loginWithGoogle, updateUser, logout }`) is unchanged except `loginWithGoogle`'s signature: was `(code, redirectUri) => Promise<AuthUser>` (popup-based `@react-oauth/google`), now a zero-arg `() => Promise<void>` that calls `supabase.auth.signInWithOAuth({ provider: 'google', options: { redirectTo: \`${origin}/auth/callback\` } })` — a full-page redirect. `LoginPage.tsx` is the only caller.
  - The old `initAuth` bootstrap effect (read `localStorage['ownerUser'|'tenantUser']`, then silent-refresh) is gone. Replaced by `supabase.auth.onAuthStateChange()` plus a `hydrate()` function that calls `GET /auth/me` to build the `AuthUser` object (role/owner_id/tenant_id/name) whenever a Supabase session appears.
  - `login(email, password)` still does `POST /auth/login` first (rate-limiting, tenant-status checks, and `PASSWORD_RESET_REQUIRED` all stay backend-mediated — the SPA never calls `supabase.auth.signInWithPassword()` directly), then calls `supabase.auth.setSession({ access_token, refresh_token })` from the response and builds the `AuthUser` directly, without waiting on the auth-state listener.
  - `logout()` calls `POST /auth/logout` (Redis revocation + server-side `supabase.auth.admin.signOut()`) then `supabase.auth.signOut()` locally.
  - `persistUser`/`readStoredUser` and the `ownerUser`/`tenantUser` `localStorage` keys are gone — Supabase persists its own session (in `localStorage`, under its own keys), and the profile is re-hydrated from `/auth/me` on every auth-state change rather than cached locally.
  - The idle-timeout system (`useIdleSessionTimeout`, the 25-min warning modal, the `hms:session-expired` window event) is unchanged — Supabase has no concept of this app's 30-minute idle business rule, so it stays a layer on top; see [[Backend#Auth/session model|Backend]] for the Redis-based server side of the same rule.
- **`app/pages/AuthCallbackPage.tsx`** (new) — the `/auth/callback` route landed after `signInWithOAuth`'s redirect. Waits for `supabase.auth.getSession()` to resolve (relies on `detectSessionInUrl: true` processing the redirect during client init), makes its own `GET /auth/me` call to get the specific rejection reason if any (`NO_STAYO_ACCOUNT`/`TENANT_GOOGLE_NOT_ALLOWED`/`ACCOUNT_DISABLED` — Google never auto-provisions an account), then either routes by role or calls `supabase.auth.signOut()` and shows the error with a "Back to sign in" link.
- Three pages that used to bypass `AuthContext` and hand-write `localStorage` now go through Supabase directly: `portal/pages/ActivateAccountPage.tsx` (tenant-activation auto-login calls `supabase.auth.setSession()`), `portal/pages/CompleteProfilePage.tsx` (calls `updateUser({ is_profile_completed: true })` instead of writing `localStorage['tenantUser']`), `app/pages/ResetPasswordPage.tsx` (calls `supabase.auth.signOut()` instead of removing the old localStorage keys).
- `@react-oauth/google`, `GoogleOAuthProvider` (`app/providers/AuthShellProviders.tsx`), `useGoogleLogin`, and `VITE_GOOGLE_CLIENT_ID` are all removed. `shared/ui-patterns/GoogleSignInModal.tsx` — the "Continue with Google" button on the marketing landing page's lead-capture funnel — was out of scope for ADR-031 itself (a different product flow from real login) but has since been made real too, in a later pass — see the Owner-Acquisition Funnel section below.

## Owner-Acquisition Funnel (landing page → real lead → activation → onboarding)

Two passes, both against real backend endpoints (no mocks) — see [[Decisions]] ADR-032 for the second pass's design, [[APIs]] for the endpoints:

- **Landing → lead capture** (`app/pages/public/LandingPage.tsx`'s "Manage My Hostel" CTA): `shared/ui-patterns/GoogleSignInModal.tsx` calls real `supabase.auth.signInWithOAuth({provider:'google', options:{redirectTo: '/lead-signup/callback'}})` — a full-page redirect, deliberately a *different* redirect target from the real `/login` flow's `/auth/callback`, since this identity is never resolved into a StayO session (`resolveSupabaseSession()` would reject a brand-new visitor by design — see ADR-031). `app/pages/public/LeadSignupCallbackPage.tsx` reads the Google identity client-side via `supabase.auth.getUser()` (never calls `/api/auth/me`), then renders `features/owner-onboarding/components/HostelLeadModal.tsx` (details + phone OTP, both real — `POST /auth/send-phone-otp`/`verify-phone-otp` with `purpose: "LEAD_CAPTURE"`, then `POST /leads/self-serve`), and signs the Supabase session back out afterward regardless of outcome — it never becomes a real account. `features/hostel-leads/api/index.ts` is this funnel's dedicated API wrapper.
- **Admin approval → activation link → prefilled onboarding** (added 2026-07-29, ADR-032): `platforms/admin/pages/AdminLeadsPage.tsx`'s "Approve Lead" now calls `POST /api/platform-admin/leads/[id]/approve` (was a bare status PATCH) and shows the real WhatsApp/email delivery result as a toast; its status dropdown is trimmed to the 3 manually-settable values, with a new Timeline section reading that lead's logged events.
  **Superseded 2026-08-31 ([[Decisions#ADR-159|ADR-159]]):** the "prefilled onboarding" hand-off described above is gone — it was also the security gap the ADR closes (`/onboarding`'s account step worked with no token at all). The activation link is now `/activation/:token` → `app/pages/public/OwnerActivationPage.tsx` (replaces `OwnerLeadInvitePage.tsx`), which fetches `GET /api/leads/invitation/[token]` and **is** the activation form itself — read-only name/hostel/phone, email only if the lead has none, then password/confirm — rather than redirecting into `/onboarding` via router `state`. On success it hands off the returned Supabase session and navigates straight to `/owner/home`. `POST /api/auth/owner-signup`'s `lead_token` is no longer optional, and the endpoint no longer accepts `name`/`phone` in the body at all (both are read from the lead). `useOwnerOnboardingState.ts`'s `initialData` param and `useOnboardingSubmission.ts` were removed — `/onboarding` (now `welcome → kyc → success`) is `ProtectedRoute`-gated and reachable only by an already-authenticated owner.

## Loading & error surfaces — `shared/ui/brand/`

**One gesture for every wait in the app: the Stayo mark's four windows lighting clockwise. There are no circular spinners anywhere in `apps/frontend` — `animate-spin` and lucide's `<Loader2 />` were removed from all 42 files that used them (2026-08-09, see [[Changelog]] and [[Decisions#ADR-061|ADR-061]]). Do not reintroduce either.**

| Component | Use for |
|---|---|
| `<StayoLoader size="xs\|sm\|md\|lg" />` | inside a button, beside a label, in a table row. Inherits `currentColor`. |
| `<StayoLoadingBlock message?=… />` | a card or section body waiting on its own data. |
| `<StayoLoadingScreen />` | a whole surface: route fallback, auth gate, payment polling, a modal body that owns the dialog. |
| `<StayoErrorScreen />` | the same surface when it failed — identical stage, windows unlit, one guttering. |
| `<StayoMark panes="solid\|loading\|dark" />` / `<StayoWordmark />` | the brand vector itself; these files are the source of truth for its geometry. |

Notes that matter when touching this:

- **The palette in `stayo-loading.css` is hard-coded, not tokenized, on purpose.** These surfaces render *before* a `ThemeProvider` `data-app-theme` scope exists (route `Suspense` fallbacks, auth gates, the boot splash), so `--primary`/`--accent` would resolve to the legacy theme or to nothing.
- **`index.html` carries a duplicate copy of that CSS and of the mark path**, as `#stayo-boot`. It is the only thing that can paint before the JS bundle arrives; `main.tsx` fades it out after React's first commit. Both draw the same screen, so the hand-off is invisible. **Edits to the loading screen's palette or timing must be made in both places.**
- **Full brand screen vs. layout skeleton**: cold boundaries where nothing is mounted yet (platform entry, auth gates, public/auth/journey routes) get `StayoLoadingScreen`; page-to-page transitions *inside* an already-mounted shell (`OwnerProviderShell`, `TenantProviderShell`) keep their layout skeletons, which preserve perceived speed better.
- `PageError` and `ErrorCard` (`shared/ui/error/`) kept their exact prop signatures through the redesign — only their surface changed, so every existing caller still works. `ErrorCard` is theme-tokenized (it always renders inside a themed shell); `PageError` is not, for the reason above.

- **`app/providers/ThemeProvider.tsx`** — `useAppTheme()`/`<ThemeProvider theme="marketing"|"product">`. Since `headerFor()`'s longest-prefix match would show the generic "Settings" title for every subpage regardless, `MoreScreenHeader`'s own per-page title (e.g. "Late fees", "Billing policy", "Agreement") is the *only* place that specific identity renders — hiding it would be a net loss of information, not a de-duplication. This is the one place this phase's own evidence contradicted the "hide the duplicate header" pattern used everywhere else, so it was correctly not applied here.
- **Two `BottomSheet`s found (`MoreNoticesPage`'s "Post an announcement", `MoreHelpPage`'s "Licenses") — left as-is.** Neither was part of the audited P1 finding (which was about width/chrome, not overlays); converting them would be scope creep beyond "eliminate the single identified gap." Flagged as a design decision, not fixed.
- **Not touched:** every data hook and mutation (`useUpdateOwnerProfile`, the billing-policy save mutations, etc.), all backend contracts, `hubSections.ts`'s grouping, `MoreScreenHeader.tsx`'s own markup, the two `BottomSheet`s' content, Owner Tenants/Money/Hostels/Food, `WorkQueue`, the existing Owner shell architecture, Tenant/Profile work from Phases 3.1–3.6.

**Do not `import` the desktop primitives** unless executing a plan phase. `MasterDetail`/`AppConsoleShell`/`adaptive-surface` are in `app/` (not `shared/ui/`) because `check-architecture.mjs` forbids `shared/` → `app/` imports.

## Clerk in the SPA (2026-09-09, ADR-176 Phase 2)

`apps/frontend` is Vite + React 19, so the Clerk integration uses **`@clerk/clerk-react`** — `@clerk/nextjs` cannot run here. (The Next.js app is `apps/backend`, which is the API; its `app/(dashboard)` and root landing page are stale pre-Stayo leftovers, not the product UI.)

| File | Role |
|---|---|
| `lib/auth/clerkConfig.ts` | Resolves `VITE_CLERK_PUBLISHABLE_KEY` — the **only** Clerk variable this app reads. `readClerkConfig()` is the single point of contact with `import.meta.env` (a static property access, so Vite inlines the literal); `resolveClerkConfig(value)` is pure and holds the rules, including rejecting an `sk_` secret key outright. |
| `lib/auth/sessionAuthority.ts` | Pure. `decideRouteAccess()` — **accepts the Clerk state and ignores it**, see below. Plus `clerkPresence()` and `shouldExplainUnlinkedClerkSession()` for display. |
| `app/providers/clerkSessionContext.ts` | The session context, in a module that imports **nothing** from Clerk. |
| `app/providers/ClerkRuntime.tsx` | Everything touching `@clerk/clerk-react` at module scope — reached only by dynamic `import()`. |
| `app/providers/ClerkAuthProvider.tsx` | Mounts Clerk when configured; renders children untouched when not. Mounted **per-route** — in `ClerkAuthScreen` and `ProtectedAppProviders` — never in `RootProviders`. |
| `app/pages/auth/*` | `/sign-in` and `/sign-up`, sharing `ClerkAuthScreen` (which carries the unconfigured branch). |
| `app/components/ClerkUserButton.tsx` | `ClerkUserButton` (admin header) and `ClerkAccountSlot` (fixed, for the mobile owner/tenant shells). Both render `null` without a Clerk session. |

**A Clerk session authorises nothing.** Roles come from `profiles` through `AuthContext`, which is still Supabase-backed. `ProtectedRoute` delegates to `decideRouteAccess`, and `sessionAuthority.test.ts` asserts across a 4×4 matrix that varying the Clerk state changes no decision — the mechanical proof that this phase changed nobody's access. Phase 3 rewrites that test deliberately.

**Three rules keep Clerk off the public landing page**, and each exists because a violation of it was measured, not imagined:

1. **Mount per-route, never globally.** `ClerkAuthScreen` mounts it for `/sign-in` and `/sign-up`; `ProtectedAppProviders` mounts it for every authenticated tree (owner, admin, and tenant via `SeekerAppShell`). Mounted in `RootProviders`, it suspended `/` on the Clerk chunk *before* the router could fetch its own route chunk — two serialised fetches on the page that must be fastest.
2. **The SDK sits behind dynamic `import()`.** `ClerkRuntime` and `<UserButton>` each do, leaving Clerk in its own ~113 KB chunk.
3. **Nothing on the public path may statically import a Clerk-owning module.** The session hook lives in `clerkSessionContext.ts`, which imports nothing from Clerk, and is imported *from there* — never re-exported through `ClerkAuthProvider`. That re-export is a static edge into the module owning the `lazy()`, and `ProtectedRoute` importing it that way put `clerkConfig` and the ClerkRuntime import straight back into the entry chunk. It happened twice.

`clerkBundleIsolation.test.ts` walks the static import graph from `main.tsx` and fails if any of the three is broken. Entry-chunk cost is +1.3 KB over a no-Clerk build (`sessionAuthority` and the context module, which route guards need on every render).

**Routes are `/sign-in/*` and `/sign-up/*`.** The splat is required: `<SignIn routing="path">` renders its own sub-steps (email-code entry, SSO callback, session tasks) as child paths, which 404 without it.

**Env vars: `VITE_` prefix, and this app's own `.env`.** Vite exposes only `VITE_`-prefixed variables to browser code — a production build inlines `import.meta.env` as literally `{BASE_URL, DEV, MODE, PROD, SSR, VITE_*}` and nothing else. It also reads `apps/frontend/.env`, not the repo-root one (`loadEnv` runs from `process.cwd()`). So the Clerk keys in the root `.env` are backend-only: `CLERK_SECRET_KEY` must never reach this app, and the root's Next-style publishable key is invisible here. `clerkConfig.ts` briefly read that Next-style name to explain the mistake — **that check could never fire**, since the name is absent from `import.meta.env` by construction, and it has been removed.

**Which sign-in strategies appear is Clerk Dashboard configuration**, not code. `<SignIn>` renders whatever the instance allows, so passwordless email OTP is a dashboard setting this repo cannot enforce or verify.

## Google sign-in is Clerk's (2026-09-09, ADR-176 Phase 3)

Every `supabase.auth.signInWithOAuth({ provider: 'google' })` is gone — `AuthContext`, `HostelLeadModal`, and the unused `GoogleSignInModal` (deleted). `<ClerkGoogleSignIn>` (`shared/ui-patterns/`) replaces them and calls `signIn.authenticateWithRedirect({ strategy: 'oauth_google' })`.

**The SDK stays off the landing page.** `LoginModal` is in the entry chunk (`AppRouter → SeekerAppShell → DiscoverAuthContext`), so `ClerkGoogleSignIn` statically imports only `clerkConfig` (env parsing, no SDK) and reaches everything else through a dynamic `import()` of `ClerkGoogleButton`. That module mounts `ClerkProvider` **directly** rather than reusing `app/providers/ClerkAuthProvider` — `src/shared` must stay a leaf, and `check-architecture.mjs` fails the build otherwise.

**Sessions are read from `window.Clerk`, not React context** (`lib/auth/clerkBrowser.ts`). `api-client` is a plain module and `AuthProvider` sits above `ClerkAuthProvider` on every shell; inverting that nesting would have dragged Clerk onto `/`. `pickSessionSource()` holds the rule — **Supabase wins whenever it has a session, even if Clerk also does** — so a half-finished Clerk sign-in can never displace a live session.

`AuthCallbackPage` now lands both: it mounts Clerk (so the global exists on a cold load) and proceeds when *either* provider has a session.

**Known gap:** Google *signup* for a brand-new person does not work yet — see the ADR. Existing users are unaffected.
